# Внешняя обработка 1С для обмена с админкой синхронизации (FTP)

Эта папка — 1С-сторона FTP-канала. Приложение (`app/workers/ftp_channel.py`)
кладёт на FTP файлы-задания и забирает результаты и выгрузку остатков.
Обработка `ОбменССайтом` должна крутиться в 1С по расписанию (или по кнопке)
и отрабатывать этот протокол.

Файл `ОбменССайтом_МодульОбъекта.txt` — исходник модуля объекта обработки на
встроенном языке 1С. Собрать `.epf` из него — в Конфигураторе (см. «Сборка»).

## Протокол файлов (контракт с приложением — менять только вместе с кодом)

Кодировка всех файлов — **UTF-8**. Разделитель полей — `|`. Публикация файла
атомарная: сначала пишем `имя.part`, потом переименовываем в `имя` (чтобы
другая сторона не прочитала полуфайл).

### Задания: приложение → 1С

Приложение кладёт файлы `task_ГГГГММДДЧЧММСС.txt` в каталог **tasks**. В файле
одна или несколько строк-команд:

| Команда (строка файла) | Что делает 1С |
|---|---|
| `EXPORT_STOCK_ON_HAND` | Выгрузить остатки склада `ЦС` в файл `stock_*.txt` (каталог results). |
| `EXPORT_BARCODES` | Выгрузить полный справочник баркодов в файл `barcodes_*.txt` (каталог results). |
| `EXPORT_STOCK_ON_DATE`&#124;`ГГГГММДД` | Выгрузить остатки склада `ЦС` **на конец указанного числа** в файл `ondate_ГГГГММДД_*.txt` (каталог results). |
| `CREATE_MOVEMENT`&#124;`баркод`&#124;`склад_откуда`&#124;`склад_куда`&#124;`кол-во`&#124;`order_id`&#124;`площадка`&#124;`дата` | Создать и провести перемещение (резерв под заказ: `ЦС` → `<Площадка>.Ожидает`). |
| `CONFIRM_MOVEMENT`&#124;`баркод`&#124;`склад_откуда`&#124;`склад_куда`&#124;`кол-во`&#124;`order_id`&#124;`площадка`&#124;`дата` | Перемещение при подтверждении: `<Площадка>.Ожидает` → `Склад <Площадка>`. |
| `CANCEL_MOVEMENT`&#124;`order_id`&#124;`площадка` | Возврат неподтверждённого заказа: `<Площадка>.Ожидает` → `ЦС`. |

**Восьмое поле `дата`** (`ГГГГММДД`, необязательное) — дата документа перемещения.
Пустое значение означает текущую дату. Нужно для старта задним числом: приложение
проводит уже состоявшиеся отгрузки реальными датами заказов, иначе движения в 1С
встали бы сегодняшним днём и отчёты по периодам разошлись бы с площадками.

Поток по требованию: заказ либо **подтверждается** (`Ожидает` → `Склад
<Площадка>`, терминально), либо **не подтверждается** и возвращается (`Ожидает`
→ `ЦС`). `CANCEL_MOVEMENT` приходит только для ещё не подтверждённых заказов —
продажу и возврат ПОСЛЕ подтверждения приложение не отправляет.

Обработав файл задания, 1С **переносит его в каталог archive** и пишет
результаты (ниже). `order_id` нужно сохранять в созданных документах
(реквизит/комментарий), чтобы по нему находить движения для `CONFIRM`/`CANCEL`.

### Результаты по заданиям: 1С → приложение

По каждой команде с `order_id` (create/confirm/cancel) 1С пишет строку в файл
`result_ГГГГММДДЧЧММСС.txt` в каталог **results**:

```
order_id|OK|номер_документа|ИМЯ_КОМАНДЫ
order_id|ERROR|текст_ошибки|ИМЯ_КОМАНДЫ
```

Четвёртое поле — имя команды (`CREATE_MOVEMENT`, `CONFIRM_MOVEMENT`,
`CANCEL_MOVEMENT`) — обязательно. По одному номеру заказа у приложения бывает и
создание перемещения, и его отмена; без имени команды ответ по ОТМЕНЕ закрывал
задание СОЗДАНИЯ (берётся самое старое незакрытое), отмена уходила в `timeout` и
навсегда считалась «в пути» со знаком минус — остаток завышался ровно на
количество заказа, и это уезжало на площадки. Формат обратно совместим: строку
из трёх полей приложение примет, но сопоставит приблизительно.

Приложение забирает `result_*.txt`, закрывает по нему задания и архивирует файл
у себя — **после** успешного разбора, а не до: иначе сбой записи в базу унёс бы
ответы 1С безвозвратно. `EXPORT_STOCK_ON_HAND` результат-строки не требует (его ответ — файл
остатков ниже).

### Выгрузка остатков: 1С → приложение

На команду `EXPORT_STOCK_ON_HAND` 1С пишет файл `stock_ГГГГММДДЧЧММСС.txt` в
каталог **results**, по строке на позицию склада `ЦС`:

```
uid_1c|артикул|наименование|количество|баркод1,баркод2|размер|цвет
```

Размер и цвет — характеристика номенклатуры и реквизит цвета; приложение хранит их
у товара и показывает в списках. Количество может быть отрицательным (пересортица) —
приложение сохраняет минус как есть, на площадки при этом уходит 0.

### Выгрузка остатков на заданное число: 1С → приложение

На команду `EXPORT_STOCK_ON_DATE|ГГГГММДД` 1С пишет файл
`ondate_ГГГГММДД_ГГГГММДДЧЧММСС.txt` в каталог **results** (первая дата — число
среза, вторая — метка времени обработки). Формат строки тот же, что у обычной
выгрузки остатков:

```
uid_1c|артикул|наименование|количество|баркод1,баркод2|размер|цвет
```

Остаток берётся на **конец** указанного дня (`Новый Граница(КонецДня(Дата),
ВидГраницы.Включая)`) — то есть движения самого этого числа в срез входят.

**Префикс `ondate_`, а не `stock_`, — часть контракта, а не украшение.** Файлы
`stock_*.txt` приложение применяет как ТЕКУЩИЙ остаток: они идут в сверку, в
`Product.stock_on_hand` и оттуда на площадки. Срез за прошлое число под именем
`stock_*.txt` означал бы рассылку в WB/Ozon/Kit цифр той давности, которую
оператор запросил всего лишь для справки, — то есть оверселл. Файлы `ondate_*`
живут в отдельной таблице и в остаток товара не попадают никогда.

Ответ-строки в `result_*.txt` команда не требует. Если 1С не смогла построить
срез (например, дата раньше начала учёта), она пишет ошибку в журнал регистрации,
а приложение через три часа помечает заявку как «1С не ответила».

Запрашивает выгрузку оператор со страницы «Остатки на дату» в админке; сама по
себе она не запрашивается никогда.

### Выгрузка справочника баркодов: 1С → приложение

На команду `EXPORT_BARCODES` 1С пишет файл `barcodes_ГГГГММДДЧЧММСС.txt` в каталог
**results**, по строке на КАЖДЫЙ баркод (в отличие от выгрузки остатков, где баркоды
одного товара перечислены через запятую):

```
uid_1c|артикул|наименование|баркод|размер|цвет
```

Эта выгрузка не зависит от остатков: в ней есть и позиции с нулём на складе. Нужна
для сопоставления товаров площадок с 1С — по полному справочнику оно работает даже
там, где каталог площадки ещё не догружен.

- `uid_1c` — `УникальныйИдентификатор()` номенклатуры (тот же ключ, что в
  приложении: `Product.uid_1c`).
- `количество` — целое; **может быть отрицательным** (пересортица — приложение
  корректно отправит 0 на площадки, это не ошибка выгрузки).
- Последнее поле — все баркоды позиции через запятую (минимум один).

## Каталоги обмена

Три подкаталога на FTP (пути задаются и в 1С, и в `.env` приложения — должны
совпадать):

- **tasks** — задания от приложения (1С читает и архивирует).
- **results** — результаты и выгрузка остатков от 1С (приложение читает и
  архивирует).
- **archive** — обработанные файлы.

## Что нужно НАСТРОИТЬ под вашу конфигурацию

В модуле помечено комментариями `// НАСТРОИТЬ:`. Это места, зависящие от
конкретной базы «Магазин одежды и обуви»:

1. **Поиск номенклатуры по штрихкоду** — регистр сведений штрихкодов (в модуле
   заглушка `НайтиНоменклатуруПоШтрихкоду`).
2. **Документ перемещения** — тип документа и его реквизиты (склады, товар,
   количество, где хранить `order_id`).
3. **Регистр остатков** для выгрузки `ЦС` (`ТоварыНаСкладах`/`ОстаткиТоваров` —
   имя зависит от конфигурации).
4. **Справочник складов** — поиск склада по имени (`ЦС`, `WB.Ожидает`,
   `Склад WB` и т.д.).

## Параметры обработки

В начале модуля (константы `ПараметрыОбмена`): адрес FTP, логин, пароль, порт,
пути к трём каталогам. Пароль в 1С храните в защищённом реквизите/константе, не
в открытом коде на боевой базе.

## Сборка .epf

1. Конфигуратор → Файл → Новый → **Внешняя обработка**. Имя: `ОбменССайтом`.
2. Открыть **Модуль объекта**, вставить содержимое `ОбменССайтом_МодульОбъекта.txt`.
3. (Опционально) добавить форму с кнопкой, вызывающей `ВыполнитьОбмен()`, и/или
   регламентное задание, вызывающее его же по расписанию (например, раз в минуту).
4. Настроить места `// НАСТРОИТЬ:` под свою конфигурацию.
5. Файл → Сохранить как → `ОбменССайтом.epf`.
6. Проверить на копии базы: положить тестовый `task_*.txt` в tasks вручную,
   запустить `ВыполнитьОбмен()`, убедиться, что появился `result_*.txt` и
   документ создан.

## Готовые к сборке исходники (`1c/src/`)

В `1c/src/` лежат XML-исходники обработки, собранные через навык `epf-init` и
проверенные `epf-validate` (0 ошибок). Модуль объекта (`ObjectModule.bsl`) —
это код из `ОбменССайтом_МодульОбъекта.txt`, а он, в свою очередь, снят с ЖИВОЙ
`.epf` сервера (16.09.2026) и совпадает с ней байт в байт. Правки, сделанные в
конфигураторе, обязательно переносить сюда: до 16.09 исходник в `1c/src/` отставал
на FTP-версию с заглушками `// НАСТРОИТЬ:`, и сборка из него дала бы неработающую
обработку. Осталось собрать бинарный `.epf`
на машине с установленной платформой 1С.

**Вариант 1 — навык `epf-build`** (нужны `1cv8.exe` и любая файловая база):

```powershell
python <skills>\epf-build\scripts\epf-build.py `
  -V8Path "C:\Program Files\1cv8\8.3.27.1859\bin" `
  -InfoBasePath D:\bases\scratch `
  -SourceFile <repo>\1c\src\ОбменССайтом.xml `
  -OutputFile <out>\ОбменССайтом.epf
```

Файловую базу для сборки можно создать навыком `db-create`, если её нет.

**Вариант 2 — Конфигуратор вручную**: Файл → Открыть → выбрать
`1c\src\ОбменССайтом.xml` (загрузка обработки из XML-исходников), затем
Файл → Сохранить как → `ОбменССайтом.epf`.

> ВНИМАНИЕ: `epf-validate` проверяет только XML-структуру, НЕ синтаксис
> встроенного языка в `ObjectModule.bsl`. Первая сборка/открытие в
> Конфигураторе проверит код 1С и подсветит места `// НАСТРОИТЬ:`, которые
> нужно адаптировать под вашу конфигурацию (документ перемещения, регистры

## Выгрузка остатков на дату — что менялось в модуле (17.09.2026)

Правка **обязательная**, если нужна страница «Остатки на дату»: без неё
приложение будет слать команду, на которую живая обработка не отвечает, и
заявки будут висеть до таймаута. Тестовой базы 1С нет, поэтому переносить
аккуратно и сразу проверить приёмкой из последнего пункта.

В `ОбменССайтом_МодульОбъекта.txt` (и в `1c/src/.../ObjectModule.bsl`) изменилось
ровно четыре места:

1. В `ОбработатьФайлЗадания` добавлена переменная `ДатыОстатков = Новый Массив;`.
2. Туда же — ветка разбора команды `EXPORT_STOCK_ON_DATE` (складывает дату в массив).
3. После публикации `barcodes_*.txt` — цикл по `ДатыОстатков`, публикующий
   `ondate_<дата>_<метка>.txt`. Каждая дата в своей `Попытке`: сбой одного среза
   не должен рушить остальной обмен.
4. Появились функции `ВыгрузитьОстаткиЦСНаДату` (свой запрос с параметром
   `&Момент`) и `СтрокиВыгрузкиОстатков` (общая сборка строк, вынесена из
   `ВыгрузитьОстаткиЦС` без изменений).

Запрос текущих остатков (`ВыгрузитьОстаткиЦС`) намеренно **не трогали**: это
источник остатка, который уходит на площадки, проверить его правку негде.
Поэтому у выгрузки на дату свой запрос, а общей сделана только сборка строк —
так форматы двух файлов не могут разойтись.

Приёмка после переноса: положить в `C:\sync\tasks` файл `task_test.txt` с
единственной строкой `EXPORT_STOCK_ON_DATE|20260901`, запустить `ВыполнитьОбмен()`
и убедиться, что в `results` появился `ondate_20260901_*.txt`, а файлов
`stock_*.txt` он при этом НЕ создал.

## Два необязательных исправления в модуле (17.09.2026)

Оба — на стороне 1С, приложение к ним уже готово и без них работает, просто
менее точно. Правки маленькие, но модуль трогает боевую базу, поэтому решение
за вами.

### 1. Уникальное имя файлов результата (важнее)

Сейчас метка формируется в момент обработки задания:

```1c
Метка = Формат(ТекущаяДата(), "ДФ=ггггММддЧЧммсс");
```

Точность — секунда. Если 1С обработает два файла задания в одну и ту же секунду,
второй `result_*.txt` затрёт первый (`ОпубликоватьФайл` сначала удаляет
существующий файл), и ответы по целому батчу пропадут: задания уйдут в
«просрочено» и разбирать их придётся вручную.

Имена файлов заданий со стороны приложения теперь содержат микросекунды и
гарантированно уникальны, поэтому метку проще взять прямо из имени задания:

```1c
Метка = СтрЗаменить(ФайлЗадания.ИмяБезРасширения, "task_", "");
```

Побочный плюс: по имени `result_*.txt` сразу видно, на какое задание он отвечает.

### 2. Имя команды в строке ответа (точное сопоставление) — СДЕЛАНО

Было `ИдЗаказа|OK|НомерДок`. По одному номеру заказа у приложения бывает и
создание перемещения, и его отмена, а различить их в ответе было нечем —
сопоставление шло по порядку, и ответ по отмене закрывал создание. Имя команды
последним полем делает сопоставление однозначным:

```1c
СтрокиРезультата.Добавить(ИдЗаказа + "|OK|" + НомерДок + "|" + Команда);
...
СтрокиРезультата.Добавить(ИдЗаказа + "|ERROR|" + ОписаниеОшибки() + "|" + Команда);
```

Так в обеих ветках — и в `CREATE_MOVEMENT`/`CONFIRM_MOVEMENT`, и в
`CANCEL_MOVEMENT`. Формат обратно совместим: приложение принимает и строки без
этого поля, и последнее поле засчитывается за команду, только если оно в
точности `CREATE_MOVEMENT`, `CONFIRM_MOVEMENT` или `CANCEL_MOVEMENT` — обычная
подробность с символом `|` за команду не сойдёт.

### 3. Экранирование разделителя в артикуле и наименовании

В выгрузке остатков размер, цвет и баркоды уже прогоняются через
`СтрЗаменить(…, "|", " ")`, а артикул и наименование — нет. Товар с именем вида
`Джинсы|36` сдвигает поля в строке.

Приложение с 17.09.2026 разбирает такие строки устойчиво (режет хвост справа,
критичные поля не сдвигаются), но чинить лучше в источнике:

```1c
Артикул = СтрЗаменить("" + Выборка.Номенклатура.Артикул, "|", " ");
Наименование = СтрЗаменить("" + Выборка.Номенклатура.Наименование, "|", " ");
```

То же самое — в выгрузке справочника баркодов.
