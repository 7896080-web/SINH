## 1. ДЕФЕКТ: результат одного файла затирает результат другого

### Что происходит

`ОбработатьФайлЗадания` формирует имя файла ответа из текущего времени **с
точностью до секунды** (строка 51):

```bsl
Метка = Формат(ТекущаяДата(), "ДФ=ггггММддЧЧммсс");
...
ОпубликоватьФайл(Пар.КаталогResults, "result_" + Метка + ".txt", ...);   // строка 102
```

`ВыполнитьОбмен` обрабатывает **все** накопившиеся `task_*.txt` в одном цикле,
один за другим. Файлы разбираются быстро, поэтому два соседних легко попадают в
одну и ту же секунду — и тогда оба получают **одинаковое имя ответа**.

А `ОпубликоватьФайл` (строка 375) существующий файл не бережёт:

```bsl
УдалитьЕслиЕсть(ПутьИтог);
ПереместитьФайл(ПутьВрем, ПутьИтог);
```

Второй ответ молча затирает первый. Задания из первого файла остаются без
ответа навсегда, при этом сам файл задания благополучно уезжает в архив —
снаружи это выглядит как «1С забрала файл и промолчала».

### Подтверждение на данных

19.09 в 01:04–01:06 приложение выложило четыре файла заданий:

| Файл | Строк | Результат |
|---|---|---|
| `task_...220331` | 1 | ответ получен |
| `task_...220431` | **7** | **ответа нет** |
| `task_...220531` | 7 | ответ получен |
| `task_...220631` | 2 | ответ получен |

В каталоге ответов за этот цикл лежат **три** файла: `result_...010934` (1 строка),
`result_...010935` (7 строк), `result_...010936` (2 строки). Четыре задания — три
ответа. Ровно один потерян, и потерян целиком.

Второй случай в тот же день, `task_...151814` (5 строк), — та же картина.

### Правка

Имя ответа должно быть уникальным для каждого файла задания. Проще и надёжнее
всего — взять метку из имени самого задания: приложение гарантирует уникальность
имён `task_*.txt` (проверяет и каталог заданий, и архив перед публикацией).

В `ОбработатьФайлЗадания`, вместо строки 51:

```bsl
	// Метка ответа — из ИМЕНИ ЗАДАНИЯ, а не из текущего времени.
	// ТекущаяДата() имеет точность до секунды, а файлы разбираются быстрее:
	// два задания в одной секунде получали одинаковое имя ответа, и второй
	// ответ затирал первый (ОпубликоватьФайл удаляет существующий файл).
	// Задания из затёртого ответа оставались непроведёнными навсегда.
	Метка = СтрЗаменить(СтрЗаменить(ФайлЗадания.Имя, "task_", ""), ".txt", "");
```

Имена `stock_`, `barcodes_`, `ondate_` тоже используют `Метка`, но у них другие
префиксы, поэтому между собой они не конфликтуют. Отдельного внимания это не
требует: правка делает уникальными все четыре.

**Приложение менять не нужно.** Оно ищет ответы по маске `result_*.txt` и
сопоставляет строки с заданиями по номеру заказа, а не по имени файла.

## 1б. Тот же дефект с другой стороны: файл архивируется ПОСЛЕ выгрузок

В `ОбработатьФайлЗадания` порядок такой:

```
… разбор строк, создание документов …
ОпубликоватьФайл("result_" …)      // ответ
ОпубликоватьФайл("stock_" …)       // выгрузка остатков, 152 тыс. позиций
ОпубликоватьФайл("barcodes_" …)
… ondate_ …
ПереместитьФайл(ФайлЗадания …)     // ← архив ТОЛЬКО ЗДЕСЬ
```

Документы уже созданы и проведены, а файл задания всё ещё лежит в `tasks`.
Если на любом шаге между ними вылетит исключение — а `ВыгрузитьОстаткиЦС` это
запрос по всему складу, самый тяжёлый в обработке, — файл останется в каталоге
и на следующем запуске будет разобран **заново**. Все его `CREATE_MOVEMENT`
выполнятся второй раз, то есть появятся **дубли документов перемещения**.

Часовой файл от приложения содержит и `EXPORT_STOCK_ON_HAND`, и строки
перемещений одновременно — так что это не гипотетическое сочетание.

Внешняя `Попытка` в `ВыполнитьОбмен` исключение поймает и запишет в журнал
регистрации, но файл не заархивирует — именно в этом и беда.

### Правка

Архивировать задание **сразу после публикации ответа**, до тяжёлых выгрузок:

```bsl
	Если СтрокиРезультата.Количество() > 0 Тогда
		ОпубликоватьФайл(Пар.КаталогResults, "result_" + Метка + ".txt", СтрСоединить(СтрокиРезультата, Символы.ПС));
	КонецЕсли;

	// Архивируем ЗДЕСЬ, а не в конце процедуры: документы уже проведены, и если
	// на выгрузке остатков ниже вылетит исключение, файл останется в tasks и
	// будет разобран заново — с дублями документов перемещения.
	ПутьВАрхиве = СоединитьПуть(Пар.КаталогArchive, ФайлЗадания.Имя);
	УдалитьЕслиЕсть(ПутьВАрхиве);
	ПереместитьФайл(ФайлЗадания.ПолноеИмя, ПутьВАрхиве);
```

и убрать этот же блок из конца процедуры. Выгрузки остатков идут после и на
архивирование больше не влияют: не получилась выгрузка — приложение попросит её
следующим часом, это не стоит ни одного документа.

Идемпотентность из пункта 2 закрывает и этот случай — но лечить причину дешевле,
чем полагаться на защиту.

## 2. Идемпотентность `CREATE_MOVEMENT` по номеру заказа

### Зачем

Задание, на которое не пришёл ответ, означает «неизвестно, создан документ или
нет». Приложение не может повторить его вслепую — рискует завести **второй**
документ перемещения на тот же заказ. Если же повтор безопасен, он одновременно
служит проверкой: ответ `OK` значит «документ есть», независимо от того, был он
раньше или создан сейчас.

После этой правки в приложении включается автоматическое перепроведение зависших
(до пяти попыток), и разбирать их руками больше не придётся.

### Правка

Документ уже помечается номером заказа в комментарии (строка 160):

```bsl
Документ.Комментарий = "sync order_id=" + ИдЗаказа + " " + Площадка;
```

И поиск по этому комментарию уже написан — в `ОтменитьПеремещенияЗаказа`
(строки 174–180). Остаётся вызвать такой же поиск перед созданием.

В начало `ВыполнитьПеремещение` (после строки 139), **до** поиска номенклатуры:

```bsl
	// Идемпотентность по номеру заказа: если документ по этому заказу уже
	// проведён, второй раз не создаём и возвращаем его номер. Повтор задания —
	// это не ошибка приложения, а способ узнать, дошёл ли документ, когда ответ
	// на первую попытку потерялся.
	Запрос = Новый Запрос;
	Запрос.Текст =
		"ВЫБРАТЬ ПЕРВЫЕ 1 Ссылка, Номер ИЗ Документ.ПеремещениеТоваров
		|ГДЕ Комментарий ПОДОБНО &Шаблон И Проведен = ИСТИНА
		|УПОРЯДОЧИТЬ ПО Дата";
	Запрос.УстановитьПараметр("Шаблон", "%order_id=" + ИдЗаказа + " %");
	ВыборкаСущ = Запрос.Выполнить().Выбрать();
	Если ВыборкаСущ.Следующий() Тогда
		Возврат Строка(ВыборкаСущ.Номер);
	КонецЕсли;
```

Важно: проверка нужна **только** для `CREATE_MOVEMENT`. Для `CONFIRM_MOVEMENT`
(перемещение со склада «в пути» на склад площадки) комментарий содержит тот же
номер заказа, и общая проверка запретила бы законное второе перемещение.
Поэтому либо выносить проверку в ветку `Команда = "CREATE_MOVEMENT"`, либо
добавить в шаблон поиска склад-получатель.

### Как приложение это использует

Переключатель `MOVEMENT_REPOST_ENABLED` в `.env` на боевом сервере. Пока правки
нет — он выключен, и повторов не происходит вовсе (закрыто тестом). Включаем
только после подтверждения, что идемпотентность работает.

## 3. Оперативная отдача остатка ЦС (`delta_*.txt`)

### Зачем

Сейчас приложение просит полную выгрузку раз в час: это 152 тыс. товаров, чаще
нельзя. Поэтому правка остатка в 1С доезжает до страницы **до часа с четвертью**.
Файл дельты сокращает это до минуты — приложение читает каталог ответов ежеминутно.

### Формат

Файл `delta_ГГГГММДДЧЧММСС.txt` в каталоге `results`. Префикс намеренно **не**
начинается на `stock_`: файлы `stock_*` приложение применяет как ПОЛНЫЙ снимок и
обнуляет всё, чего в них нет. Дельта под таким именем обнулила бы весь каталог.

Строка:

```
баркод|новый остаток ЦС|источник|идентификатор
```

- **новый остаток** — АБСОЛЮТНОЕ значение по этой позиции на ЦС, не приращение.
  Приращения копят ошибку навсегда, если файл потерялся или задвоился;
  абсолютное число самолечится следующим же сообщением.
- **источник** — `sync` для документов, созданных по нашим заданиям (у них
  комментарий начинается на `sync`), и любое другое значение для всего
  остального. Приложение строки с `sync` **отбрасывает**: наше перемещение уже
  списало остаток в момент приёма заказа, применить его второй раз значит списать
  единицу дважды.
- **идентификатор** — уникальный ключ изменения. Приложение запоминает
  применённые и второй раз тот же не применяет: файл приезжает повторно при
  переотправке, повторном проведении, ручном перезапуске обработки.
  Рекомендуемый вид — `<UUID документа>:<ВерсияДанных>`. UUID сам по себе не
  годится: перепроведение того же документа меняет остаток по-настоящему, а ключ
  остался бы прежним, и изменение было бы пропущено. `ВерсияДанных` меняется при
  каждой записи документа и эту разницу как раз ловит.

Строка без идентификатора приложением **пропускается** — без него повтор не
отличить от новости. Ничего страшного не произойдёт: часовая выгрузка принесёт
этот остаток не позже чем через час, но смысл дельты потеряется.

Пример:

```
2000932307169|7|Реализация|8f3c1e2a-...-9b:AAAAAAAAB1s=
2000932307176|0|Списание|1b7d4f90-...-2c:AAAAAAAAB1w=
```

### Как получать изменения

Не сравнением полного остатка (это те же 152 тыс. позиций), а по движениям
регистра с момента прошлой проверки. Запускать по расписанию раз в минуту — там
же, где сейчас запускается `ВыполнитьОбмен`.

Набросок:

```bsl
Процедура ВыгрузитьИзменениеОстатковЦС(Пар, МоментПрошлойПроверки) Экспорт
	Запрос = Новый Запрос;
	Запрос.Текст =
		"ВЫБРАТЬ РАЗЛИЧНЫЕ
		|	Дв.Номенклатура КАК Номенклатура,
		|	Дв.ХарактеристикаНоменклатуры КАК Характеристика,
		|	Дв.Регистратор КАК Регистратор
		|ИЗ РегистрНакопления.ТоварыНаСкладах КАК Дв
		|ГДЕ Дв.Период > &Момент И Дв.Склад = &СкладЦС";
	Запрос.УстановитьПараметр("Момент", МоментПрошлойПроверки);
	Запрос.УстановитьПараметр("СкладЦС", НайтиСклад("ЦС Склад"));

	Строки = Новый Массив;
	Выборка = Запрос.Выполнить().Выбрать();
	Пока Выборка.Следующий() Цикл
		// Источник: наши же документы помечены комментарием "sync ..."
		Источник = "Прочее";
		Если ТипЗнч(Выборка.Регистратор) = Тип("ДокументСсылка.ПеремещениеТоваров")
			И СтрНачинаетсяС(СокрЛП(Выборка.Регистратор.Комментарий), "sync") Тогда
			Источник = "sync";
		Иначе
			Источник = Строка(ТипЗнч(Выборка.Регистратор));
		КонецЕсли;

		Ключ = Строка(Выборка.Регистратор.УникальныйИдентификатор())
			+ ":" + Строка(Выборка.Регистратор.ВерсияДанных);

		// Текущий ОСТАТОК по позиции на ЦС — абсолютное число, не движение.
		Остаток = ОстатокНаЦС(Выборка.Номенклатура, Выборка.Характеристика);

		Для Каждого Баркод Из БаркодыПозиции(Выборка.Номенклатура, Выборка.Характеристика) Цикл
			Строки.Добавить(Баркод + "|" + Формат(Остаток, "ЧГ=0") + "|" + Источник + "|" + Ключ);
		КонецЦикла;
	КонецЦикла;

	Если Строки.Количество() > 0 Тогда
		ОпубликоватьФайл(Пар.КаталогResults,
			"delta_" + Формат(ТекущаяДата(), "ДФ=ггггММддЧЧммсс") + ".txt",
			СтрСоединить(Строки, Символы.ПС));
	КонецЕсли;
КонецПроцедуры
```

`МоментПрошлойПроверки` хранить в константе или регистре сведений и двигать
**только после успешной публикации файла**: иначе сбой записи потеряет изменения
безвозвратно.

Строки с источником `sync` можно и не выгружать вовсе — приложение их всё равно
отбросит. Но присылать их полезно: по ним видно, что канал живой, и они ничего не
стоят.

## 4. Отмена находит собственные обратные документы

`ОтменитьПеремещенияЗаказа` ищет документы так:

```bsl
"ВЫБРАТЬ Ссылка ИЗ Документ.ПеремещениеТоваров
|ГДЕ Комментарий ПОДОБНО &Шаблон И Проведен = ИСТИНА"
Запрос.УстановитьПараметр("Шаблон", "%order_id=" + ИдЗаказа + " %");
```

а сам обратный документ получает комментарий:

```bsl
Обратный.Комментарий = "sync REVERSE " + Исходный.Комментарий;
```

то есть внутри него тот же `order_id=<номер> <площадка>` — и он **подходит под
тот же шаблон**. Вторая отмена по тому же заказу отменит и исходное перемещение,
и его реверс: товар уедет на склад площадки вместо того, чтобы вернуться на ЦС.

Сейчас это не выстрелило: приложение шлёт `CANCEL_MOVEMENT` один раз. Но защиты
нет никакой, а цена — неверный остаток на ЦС.

### Правка

Исключить реверсы из выборки:

```bsl
	Запрос.Текст =
		"ВЫБРАТЬ Ссылка ИЗ Документ.ПеремещениеТоваров
		|ГДЕ Комментарий ПОДОБНО &Шаблон
		|	И НЕ Комментарий ПОДОБНО &ШаблонРеверса
		|	И Проведен = ИСТИНА";
	Запрос.УстановитьПараметр("Шаблон", "%order_id=" + ИдЗаказа + " %");
	Запрос.УстановитьПараметр("ШаблонРеверса", "sync REVERSE%");
```

Та же оговорка, что и в пункте 2: если понадобится различать создание и
подтверждение, к шаблону добавляется склад-получатель.

## Порядок

**№1 и №1б — вперёд и вместе.** Обе про один файл заданий, обе в одной процедуре,
и обе про потерю или задвоение уже проведённых документов. Без них задания будут
теряться и дальше, сколько бы механизмов мы ни строили вокруг.

**№2** позволяет приложению чинить последствия самостоятельно и заодно страхует
от дублей при повторном разборе файла.

**№4** — маленькая, независимая, но лучше в тот же заход: правка в один запрос.

**№3** (дельта остатков) ни с чем не связана и делается отдельно, когда дойдут
руки: часовая выгрузка работает и никуда не денется.

## Как накатить (без разработчика 1С)

Модуль уже поправлен в репозитории. Нужно перенести его в `.epf` на боевой
машине — это делается в Конфигураторе, программированием тут ничего не требуется.

### Порядок

1. **Сделать копию текущей обработки.** Найти файл `ОбменССайтом.epf` на сервере
   и скопировать рядом как `ОбменССайтом_до_19.09.epf`. Это единственный способ
   откатиться, если что-то пойдёт не так.
2. Конфигуратор → Файл → Открыть → выбрать боевой `ОбменССайтом.epf`.
3. Правая панель → **Модуль объекта** (двойной клик).
4. Выделить **всё** содержимое модуля (Ctrl+A) и удалить.
5. Вставить целиком содержимое `1c/ОбменССайтом_МодульОбъекта.txt` из репозитория.
6. **Синтаксический контроль**: меню Конфигурация → Синтаксический контроль
   (или Ctrl+F7). Должно быть «Ошибок не обнаружено». Если ошибки есть —
   не сохранять, прислать текст ошибки.
7. Файл → Сохранить (Ctrl+S), закрыть Конфигуратор.
8. Дождаться ближайшего запуска обмена (или запустить кнопкой) и проверить, как
   описано ниже.

### Что проверить сразу после

**Ответы больше не затираются.** В `C:\sync\archive` имена файлов ответов
теперь совпадают с именами заданий: на задание `task_20260919...` приходит
`result_20260919...` с той же меткой. Раньше метка бралась от часов и могла
совпасть у двух заданий.

```powershell
Get-ChildItem C:\sync\archive\task_*.txt | Select-Object -Last 5 Name
Get-ChildItem C:\sync\archive\result_*.txt | Select-Object -Last 5 Name
```

Число ответов должно сравняться с числом заданий.

**Зависшие задания начали закрываться.** На `/diagnostics` карточка «Зависшие
задания 1С» должна пустеть после включения автоповтора (см. ниже).

**Дельта поехала.** В `C:\sync\results` или `archive` появляются файлы
`delta_*.txt`. В логе воркера — строка `stock_delta: {...}`:

```powershell
Get-Content C:\sync_admin\logs\worker.err.log -Encoding UTF8 -Tail 200 |
    Select-String "stock_delta"
```

### Когда включать автоповтор

Только после того, как убедились, что идемпотентность работает: повторное
задание по уже проведённому заказу возвращает номер существующего документа и
**не создаёт второй**. Проверяется по числу документов перемещения с одним
`order_id` в комментарии — их должно остаться по одному на склад-получатель.

Включение — переменная `MOVEMENT_REPOST_ENABLED=1` в `.env` на боевом сервере и
перезапуск воркера. Это правка `.env`, поэтому попросите меня подготовить её
отдельно: там же лежат боевые токены площадок.

### Если что-то пошло не так

Вернуть сохранённую копию `.epf` на место. Обмен продолжит работать как раньше —
с потерей части ответов, но без новых рисков. Данные от этого не пострадают:
все правки касаются только того, КАК обработка отвечает и проверяет, а не того,
какие документы она создаёт.
