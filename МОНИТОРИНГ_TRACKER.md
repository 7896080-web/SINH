# Tracker.ru и Sync Admin: что из функций полезно

Разбор страницы https://tracker.ru/docs/features (сохранённая HTML-копия,
23.09.2026). Tracker.ru — внешний сервис мониторинга доступности сайтов
(uptime-монитор). Прямого отношения к WB/Ozon/Kit/1С он не имеет, но может
снаружи следить за самим Sync Admin: жив ли веб, работает ли планировщик,
не истёк ли сертификат.

> Разобрана только страница-оглавление. Подстраницы каждой функции (форматы
> запросов, точные лимиты тарифов, цены) не открывались: из среды разработки
> `tracker.ru` недоступен. Прежде чем настраивать, сверьте детали на самих
> подстраницах.

## Что из этого уже есть в Sync Admin

`GET /health` (`app/routers/health.py`) сделан как раз для внешнего
мониторинга:

- открыт без авторизации, текст ошибок наружу не отдаёт;
- возвращает **503**, если хоть один воркер «протух» (не запускался дольше
  тройного интервала), упал с ошибкой, обязательный воркер так и не появился
  после старта планировщика или вообще нет ни одного heartbeat
  (то есть планировщик не запущен);
- при 200 тело начинается с `{"ok":true,` (JSONResponse пишет JSON без
  пробелов).

Поэтому один HTTP-монитор Tracker.ru на `/health` покрывает сразу и веб
(uvicorn + nginx), и планировщик, и базу (`/health` читает из неё).
Встроенный механизм heartbeat в Tracker.ru для этого не нужен.

## Рекомендуемая настройка (без изменений в коде)

1. **HTTP-монитор `https://<домен>/health`**
   - ожидаемый код 200 (503 и так считается падением);
   - keyword: `"ok":true`. Это страховка на случай, если прокси или
     заглушка хостинга ответит 200 со своей страницей. Keyword заставляет
     Tracker.ru делать GET вместо HEAD. Это нормально: `/health`
     объявлен как `@router.get`, и на HEAD FastAPI ответил бы 405.
   - интервал: не чаще раза в минуту. Реальная реакция `/health` — от
     ~2 минут (dispatch, 45 с × 3) до ~6 минут (опрос заказов, 2 мин × 3).
2. **SSL expiration alert** для того же домена. Сейчас
   `deploy/nginx-sync-admin.conf` слушает только `listen 80`. Если HTTPS
   прикручен отдельно (certbot и т.п.), алерт полезен. Если нет, сначала
   нужен HTTPS: `/health` открыт без авторизации, а вот логин в админку по
   голому HTTP — отдельная проблема.
3. **Окно обслуживания** (разовое) на время `sudo bash deploy/safe_deploy.sh`.
   Иначе рестарт сервисов при деплое даст ложный алерт. На Free окна
   недоступны (лимит 0), значит алерт при деплое придётся просто
   игнорировать.
4. **Heartbeat для бэкапа.** Если `deploy/backup.sh` стоит в cron, добавьте
   в конец crontab-строки `&& curl -fsS -m 10 https://hb.tracker.ru/ping/<token>`.
   Точный формат запроса смотрите на подстранице heartbeat-мониторинга.
   Код для этого не меняется.
5. **Каналы алертов:** Telegram или MAX. Email — запасной канал.

## Что потребовало бы правки кода (не сделано, только предложение)

Heartbeat-пинг из самого планировщика (например, из `_heartbeat` в
`app/workers/scheduler.py` после успешного `job_poll_orders`) дал бы
«пассивный» сигнал: Tracker.ru поднимет тревогу, даже если сервер целиком
недоступен снаружи или nginx лежит. Но:

- это исходящий HTTP-вызов из воркера. Его нужно делать с коротким
  таймаутом и глотать ошибки, чтобы сбой Tracker.ru не ронял приём заказов;
- токен пинга — секрет, его место в `.env`, а менять `.env` на проде
  можно только с подтверждения (см. `CLAUDE.md`);
- для большинства случаев хватает HTTP-монитора на `/health`.

Делать это стоит, только если внешний HTTP-чек `/health` окажется
недостаточным.
