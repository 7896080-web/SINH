## 5. Расчётные сущности

⚠️ **Прогноз спроса — многоканальный, не только Lamoda.** Разделы 5.2-5.3 (классификация, прогноз) ведутся раздельно по каждой паре (`product_size`, `channel`) — тот же аппарат (SBC-классификация, TSB/CrostonSBA/сглаживание/бустинг/DeepAR, бэктест-турнир), просто прогоняется отдельно для Lamoda, WB, Ozon, собственного сайта: один и тот же товар может быть Smooth на WB (стабильные продажи, большая аудитория) и Lumpy на Lamoda (маленький объём, скачками) — разная аудитория, разное поведение, нет смысла считать одним прогнозом на все каналы сразу. `demand_forecast` получает поле `channel` (раздел 10), аналогично `margin_calc`.

**Раздел 5.1 (цензурирование по stockout) — механика специфична для Lamoda/FBO.** У WB/Ozon (FBS) и собственного сайта (раздел 4) нет отдельного склада площадки и, соответственно, нет инерции ранжирования конкретно на этой площадке при дефиците, как у Lamoda — дефицит для этих каналов означает "на ЦС закончилось", что сразу отражается на **всех** этих каналах одновременно (они делят один физический остаток), не на каждом отдельно. Право-цензурирование возвратами и общая логика "дни без остатка не считаются нулевым спросом" всё равно применимы — просто корректирующее событие общее сразу для всех, не по одному.

**Раздел 5.5 (точка заказа) — закупка у поставщика по агрегированному спросу со всех каналов.** ЦС питает не только Lamoda (через FBO-поставки), но и WB/Ozon напрямую (FBS — отгрузка с ЦС по каждому заказу), плюс собственный сайт (awer-russia.ru) и розницу. Точка заказа и страховой запас на ЦС (раздел 5.5 ниже) считаются от **суммарного** спроса по всем каналам, тянущим с одного физического остатка — не только от прогноза для Lamoda. Раздел 6, страница «Закупка у поставщика» — использует этот агрегированный спрос; страница «Поставка на FBO» — только Lamoda-специфичная часть (см. выше).

### 5.1 Временной ряд спроса (censored demand correction)

Дни с нулевым остатком на FBO не считаются нулевым спросом — исключаются из обучения или заменяются оценкой по соседним периодам.

```
net_спрос(t) = Delivered(t) − возвраты_с_лагом(t)
```

**Право-цензурирование возвратами:** последние `N` дней истории (`N = медиана lead_возврат по категории`, раздел 5.4) исключаются из обучающей выборки — за эти дни ещё не все возвраты успели прийти, значит `net_спрос` завышен. Решение: последний "рабочий" день истории для обучения = сегодня − N, а не сегодня.

**Хвост восстановления после OOS:** после возврата товара в наличие продажи не сразу выходят на норму — несколько дней действует инерция алгоритма ранжирования Lamoda (карточка была понижена в выдаче на время stockout) и поведенческая инерция покупателей. Дни в окне `recovery_tail_days` (3–14, задаётся по категории) сразу после восстановления остатка помечаются `is_recovery_tail_corrected = true`, наблюдаемый спрос делится на `recovery_tail_coefficient` (0.3–0.7) перед использованием в обучении — иначе первые дни после пополнения занизят прогноз, система примет вялые продажи за новую норму.

**Риск на будущее (не реализуем сейчас, держим в уме):** наивное исключение дней stockout без реконструкции значения может создать spiral-down эффект — заниженный прогноз → недостаточный запас → снова заниженный прогноз, по кругу. Если после запуска увидим систематическое занижение у часто дефицитных SKU (сверяем через `forecast_accuracy_log`, раздел 5.8) — путь апгрейда: Tobit Exponential Smoothing (TETS), встраивающий цензурирование прямо в модель сглаживания вместо постфактум-коррекции.

### 5.2 Классификация SKU

- **новинка** (< 60 дней истории) → прогноз по аналогам (см. 5.6)
- **активный** (есть история) → модель прогноза зависит от прерывистости спроса (см. ниже)
- **затухающий** (устойчиво падающие продажи, подтверждается `/v2/stocks/illiquid`) → консервативный прогноз, пополнение не считаем

**Минимальная история для доверия сезонной компоненте.** Порог "новинка" (< 60 дней) — про наличие истории вообще. Отдельно: сезонная составляющая прогноза (раздел 5.3) при истории короче одного полного сезонного цикла ненадёжна — модель ещё не видела, как категория ведёт себя в разные сезоны. До накопления 1-2 полных сезонных циклов истории по категории сезонная компонента берётся с сезонной группы (см. ниже), а не с собственного, ещё не показательного ряда SKU.

**Сезонные группы — не по категории, а по паттерну сезонности.** Разные товарные категории могут иметь одинаковую форму сезонной кривой (например, у лёгких летних вещей пик в одни и те же месяцы независимо от того, футболка это или шорты) — объединяем в группы по паттерну, а не считаем сезонность отдельно на каждую категорию:
```
seasonal_group: назначается вручную при заведении товара, либо кластеризацией
                исторических помесячных профилей продаж (похожая форма кривой → одна группа)
```
Сезонные коэффициенты (раздел 5.3) считаются на уровне `seasonal_group`, а не `category`. Категория остаётся отдельным измерением — используется для ABC×XYZ, воронки, маржи (разделы 5.2, 5.7) — но не диктует сезонность напрямую.

**Сезонный индекс из долгой истории (WB/Ozon/розница, раздел 4) — приоритетнее короткой истории Lamoda, пока своя не накопилась.** Форма сезонной кривой обычно похожа между каналами (пик в одни и те же месяцы), даже если абсолютный объём разный:
```
для каждой seasonal_group:
  сезонный_индекс(месяц) = среднее(продажи в этом месяце за все годы истории WB/Ozon/розница)
                            / среднегодовое(продажи по всем месяцам)
                            # нормализовано так, что среднее по индексу за год = 1.0 —
                            # это форма кривой, не абсолютный объём
```
Используется вместо/поверх сезонной компоненты из собственной истории Lamoda, пока не накоплено 1-2 полных сезонных цикла (см. порог выше) — форма кривой известна из длинной истории задолго до того, как это можно увидеть по самой Lamoda.

**Классификация типа спроса (SBC-метод, Syntetos-Boylan-Croston) — две оси, не одна.** Раньше критерий был бинарным (только регулярность во времени). SBC добавляет вторую ось — изменчивость объёма — и даёт 4 категории, каждая со своим методом прогноза и своим буфером:
```
ADI (Average inter-Demand Interval) = дни в периоде / дни с ненулевым спросом
CV² (Squared Coefficient of Variation) = (σ/среднее)² по ненулевым продажам

Плавный (Smooth):          ADI < 1.32, CV² < 0.49  → обычная модель (сглаживание + сезонность), обычный буфер
Неустойчивый (Irregular):  ADI < 1.32, CV² >= 0.49 → обычная модель прогноза; буфер шире автоматически
                                                        (через σ_ошибки_прогноза, раздел 5.5 — не отдельный множитель)
Прерывистый (Intermittent): ADI >= 1.32, CV² < 0.49 → TSB/CrostonSBA, обычный буфер для этого класса
Неравномерный (Lumpy):     ADI >= 1.32, CV² >= 0.49 → TSB (не CrostonSBA — точнее на этой категории
                                                        по эмпирическому сравнению); буфер шире автоматически —
                                                        самый сложный случай: непредсказуемы и время,
                                                        и объём одновременно
```
Многие размеры внутри модели (особенно крайние — например, самый большой размер куртки) попадают в Intermittent или Lumpy — обычное сглаживание здесь даёт смещённую оценку. Реализуется через `statsforecast.models.TSB` / `CrostonSBA` (раздел 7 — не пишем с нуля):

⚠️ **Не путать с XYZ-классификацией выше.** XYZ считается на уровне модели, обычным CV (не в квадрате), пороги 10%/25%, и определяет z/частоту пересмотра. SBC CV² считается на уровне размера, в квадрате, порог 0.49, и определяет **метод прогноза** (не буфер напрямую — буфер по-прежнему считает раздел 5.5 через σ_ошибки_прогноза, которая естественно окажется шире у Irregular/Lumpy сама по себе, без дополнительного ручного множителя поверх).
```
При каждом ненулевом спросе d(t):
  ẑ(t) = ẑ(t-1) + α × (d(t) − ẑ(t-1))       # сглаженный размер спроса
  p̂(t) = p̂(t-1) + β × (интервал − p̂(t-1))   # сглаженный интервал между продажами
прогноз = (1 − β/2) × ẑ(t) / p̂(t)            # поправка Syntetos-Boylan (SBA) на смещение;
                                              # TSB дополнительно обновляет вероятность спроса
                                              # даже в дни без продаж — точнее на Lumpy-категории
```
Перед расчётом ADI/CV² — фильтр выбросов (3σ, уже заложен в разделе 5.5) — большие разовые продажи иначе завышают CV² и искажают классификацию.

Для Smooth (обычные "активные" SKU) — обычная модель, как раньше.

**Выбор метода через бэктест — не жёсткое правило, а проверка на истории.** SBC-классификация выше — только начальный кандидат, не финальное решение. При каждом плановом пересмотре (частота — по сегменту ABC×XYZ, таблица выше) для каждого `product_size` прогоняются кандидаты (сглаживание, `TSB`/`CrostonSBA`, наивный сезонный — как базовая линия для сравнения, и для SKU с достаточной историей и признаками цены/промо — градиентный бустинг, `XGBoost`/`LightGBM`/`CatBoost`, с `monotone_constraints` по признаку цены — гарантирует, что рост цены в прогнозе не увеличивает спрос, экономически осмысленный результат вместо возможного шума модели без ограничений) на holdout-окне последних периодов, и выбирается метод с наименьшим WAPE на этом окне:
```
для каждого кандидата (кроме DeepAR): обучить на истории до T, прогноз на holdout [T, T+период]
WAPE_кандидата = Σ|факт − прогноз| / Σ факт за holdout
model_type = argmin(WAPE_кандидата)
```
**DeepAR (`GluonTS`, open source, Apache 2.0, бесплатно) — отдельный, шестой кандидат, архитектурно не такой, как остальные.** Не обучается заново на каждый `product_size` отдельно — одна общая модель обучается сразу на всём каталоге (все ряды вместе), затем выдаёт прогноз для каждого ряда. Включается в тот же бэктест-турнир по тому же критерию WAPE на holdout, но обучается **один раз за цикл пересмотра**, не по разу на кандидата на SKU — вычислительно легче, чем кажется: реалистично обучается на CPU (без GPU) при масштабе AWER (сотни-тысяча рядов) за время порядка часа, укладывается в тот же еженедельный цикл. Дополнительный плюс — совместное обучение на всех рядах даёт естественный перенос знаний на новинки без истории (раздел 5.6) — можно использовать как альтернативный/сверочный источник прогноза новинки наравне с аналог-based newsvendor-подходом, не только для активных SKU.

Смена метода логируется в `model_recalibration_log` с `triggered_by = 'backtest'` — та же таблица, что уже используется для override по MAPE-тревоге (раздел 5.8, `triggered_by = 'auto'`/`'manual'`), просто третья причина записи.

**ABC-классификация** — комбинированный скор по выручке и по количеству (не одна метрика):

| Класс | Критерий |
|---|---|
| A — ходовые | топ по комбинированному скору (выручка + кол-во) |
| B — средние | основная масса |
| C — хвост | низкие продажи |
| затухающие | устойчиво падающие |

**XYZ-классификация** — по стабильности спроса, независимо от ABC (важность ≠ предсказуемость). Считается на уровне модели — `net_спрос` суммируется по всем размерам за день, затем CV берётся от полученного ряда; это отдельный сигнал от `demand_pattern` (SBC-классификация выше — та считается на уровне размера и решает, какой метод прогноза использовать для конкретного размера, а не какой буфер держать для модели в целом):
```
CV = σ(net_спрос) / среднее(net_спрос) × 100%
X: CV < 10%   — стабильный спрос
Y: CV 10–25%  — умеренные колебания
Z: CV > 25%   — нерегулярный, трудно прогнозируемый спрос
```

**Комбинированная матрица ABC×XYZ** — определяет и z (сервис-уровень), и частоту пересмотра плана:

| Сегмент | z (сервис-уровень) | Частота пересмотра |
|---|---|---|
| AX | 1.88 (97%) | ежедневно/еженедельно |
| AY | 1.75 (~96%) | еженедельно |
| AZ | 1.65 (95%) | еженедельно + ручная проверка перед закупкой |
| BX | 1.65 (95%) | раз в 2 недели |
| BY | 1.5 (~93%) | раз в 2 недели |
| BZ | 1.28 (90%) | раз в 2 недели + ручная проверка |
| CX | 1.28 (90%) | раз в месяц |
| CY | 1.28 (90%) | раз в месяц |
| CZ | автопополнение не считаем — закупка только вручную по триггеру | по триггеру отклонения |
| затухающие | пополнение не считаем | — |

### 5.3 Прогноз спроса

```
прогноз_спроса = f(net_спрос, сезонность, флаг_акции, температура,
                    сигнал_каннибализации, коэф_интерес)
```

**Разделение на базовый спрос и промо-аплифт.** `флаг_акции` сейчас просто один из входов общей функции — смешанный прогноз не показывает, что было бы без акции. Разделяем на два явных числа:
```
базовый_спрос = прогноз при флаг_акции = 0 (контрфактический — "если бы акции не было")
промо_аплифт  = факт_за_период_акции − базовый_спрос
```
Используется как честная база для `margin_calc` (какой объём продался бы по обычной цене) и для решения "продлевать ли акцию" — сравниваем аплифт с потерей маржи от скидки напрямую, а не гадаем по смешанному числу.

**Каннибализация цветов/размеров — формализована через кросс-эластичность.** При обнулении остатка одного цвета/размера — проверяем прирост продаж по соседним цветам/размерам того же артикула за тот же период. Вместо разовой эвристики — та же регрессия, что для собственной эластичности (раздел 5.10), только между парой связанных SKU:
```
кросс_эластичность(A, B) = ∂ln(спрос_B) / ∂ln(доступность_A)   # доступность = 1 при наличии, 0 при stockout
                                                                # оценивается по историческим эпизодам stockout A
```
Даёт количественную оценку перетёкшего спроса (`demand_shift_qty`), а не только флаг "событие было" — можно сразу использовать в прогнозе соседнего SKU, а не только логировать факт.

**Промо-каннибализация между разными артикулами — второй, отдельный механизм.** В отличие от предыдущего (замена цвета/размера при дефиците внутри одного артикула) — здесь речь о том, что акция на **один** артикул уводит покупателей от **другого**, конкурирующего артикула (например, две похожие рубашки в одной категории), продающегося по обычной цене. Обнаруживается статистически, не эвристикой:
```
D = Snp − Sp
Snp — средние непромо-продажи артикула A, когда артикул B НЕ в акции
Sp  — средние непромо-продажи артикула A, когда артикул B в акции

t_stat, p = двухвыборочный_t_test(продажи_A_при_B_без_акции, продажи_A_при_B_с_акцией)
если p < 0.05 и D > 0 → пара статистически значимо каннибализирует друг друга
```
Прогоняется по всем парам моделей внутри категории (не обязательно одного артикула). Требует точной разметки акций — источник `GET /v2/promotions` (раздел 4); неразмеченные скидки (акции вне этого API, если такие есть) дают ложноположительные и ложноотрицательные срабатывания.

**Blending интереса (Вордстат + Google Trends + клики Директа).** Вордстат и Google Trends — не взаимозаменяемы, а два независимых замера поискового интереса (разные поисковики, разная база пользователей), усредняются в единый источник:
```
коэф_поискового_интереса = среднее(коэф_вордстат, коэф_google_trends) — если доступны оба;
                            иначе — тот, что доступен (сейчас обычно только Google Trends, т.к.
                            Вордстат ждёт доступа к API Директа)
```
Клики по объявлениям на карточку своего сайта — сигнал точнее общего поискового интереса: это интерес к конкретной модели, а не к фасону/категории в целом, и часто доступен раньше, чем карточка вообще появляется на Lamoda (если рекламная кампания на сайте стартует до листинга на маркетплейсе).
```
коэф_direct = темп_роста(клики на product_model_id) / темп_роста(клики у аналога в его запуск)

качество_аудитории(t) = среднее по 4 измерениям (пол, возраст, устройство, гео) от:
                         [1 − (Σ_value |доля_кликнувших − доля_покупателей| внутри измерения) / 2]
                         # считается отдельно на каждом измерении, потом усредняется — иначе гео
                         # с десятками городов задавит бинарный пол просто числом слагаемых
                         # без эталона по измерению — оно выпадает, среднее берётся по оставшимся
                         # без эталона вообще (нет данных CRM) — качество_аудитории = 1 (не корректируем)

коэф_direct_скорректированный = коэф_direct × качество_аудитории(t)
                         # клики от аудитории, не похожей на реальных покупателей, взвешиваются ниже —
                         # сигнал по кликам сам по себе зашумлён, если кликает не та аудитория, что покупает

коэф_интерес = 0.6×коэф_direct_скорректированный + 0.4×коэф_поискового_интереса
```
⚠️ **Без компонента "воронка Lamoda"** — отчёт «Воронка продаж» без API-доступа исключён из автопайплайна (раздел 4). Раньше вес воронки рос по мере набора статистики после публикации карточки (до 85% в стабильном режиме) — теперь коэф_интерес держится на внешних сигналах (клики + поиск) весь жизненный цикл SKU, без снижения точности со временем за счёт внутреннего сигнала Lamoda. Веса стартовые, калибруются регрессией по накоплению истории. Если для конкретной модели рекламы в Директе не было — компонент выпадает, весь вес уходит на `коэф_поискового_интереса`.

**Anomaly-детекция без данных воронки.** Правило "падение конверсии в корзину = проблема карточки" (требовало просмотров/добавлений в корзину) неприменимо без API-доступа к воронке. Замена, доступная через `/v2/orders`: рост доли отменённых/недоставленных заказов (`Not delivered`/`Canceled` среди `items[].status`) — более грубый, но автоматизируемый индикатор проблемы с карточкой/логистикой, не спросом.

### 5.4 Состояния товара и lead time

```
поставщик → остаток_1С → в пути на FBO → остаток_FBO → в пути к клиенту
                                                             │         │
                                                         Delivered  возврат
                                                         (продано)     │
                                                                  остаток_FBO (снова)
```

```
lead_поставка_FBO = медиана(дата_приёмки_FBO − дата_создания_поставки)
lead_возврат       = медиана(дата_возврата_в_остаток − дата_статуса_возврата), по категории
lead_поставщик     = срок_производства + срок_доставки (из справочника поставщика)
```
`fbo_shipments.status` (раздел 10) обновляется вебхуком `fulfilmentShipmentValidationRest` (раздел 4) сразу по результату валидации поставки Lamoda — не только по факту появления товара в `stock_fbo`, что раньше было единственным сигналом.

### 5.5 Точка заказа и рекомендация пополнения

```
прогноз_остатка(T) = остаток_FBO
                    + в_пути_на_FBO (ожидаемые к приёмке ≤ T)
                    + в_пути_от_клиента × доля_с_lead_возврат_≤_T
                    − прогноз_продаж(до T)

точка_заказа = прогноз_спроса(на L) + страховой_запас
```

**Незащищённое окно L — не только срок доставки.** Между плановыми пересчётами вмешаться в остаток нельзя, значит окно шире, чем время доставки:
```
L = lead_поставка_FBO (или + lead_поставщик, если нужна закупка с нуля) + интервал_пересмотра
```
`интервал_пересмотра` — из частоты пересмотра сегмента ABC×XYZ (раздел 5.2, таблица review_frequency, в днях). У товаров с редким пересмотром (классы C/Z — раз в месяц) это увеличивает L существенно, а расчёт без этого слагаемого систематически занижает буфер именно там.

**Базовая формула страхового запаса:**
```
страховой_запас = z × σ_ошибки_прогноза × √L
```
`σ_ошибки_прогноза` — стандартное отклонение **разницы факт − прогноз** (из `forecast_accuracy_log`, раздел 5.8), а не сырого `net_спрос`. Сезонность, тренд и промо-эффект уже учтены в прогнозе (раздел 5.3) — если взять σ от сырых продаж, эти эффекты задвоятся в буфере. Дни stockout (`is_stockout_corrected`) и выбросы за пределами 3σ (разовая оптовая продажа/тендер) исключаются из расчёта σ — иначе буфер раздувается на месяцы вперёд из-за одного нетипичного дня.

**Расширенная формула — при нестабильном сроке поставки:**
```
страховой_запас = z × √(L × σ_ошибки² + d² × σL²)
```
`σL` — стандартное отклонение фактического lead time (`lead_time_stats.std_days`, `lead_type = 'supplier'`, раздел 5.9), `d` — средний дневной спрос. Применяется вместо базовой формулы, когда `on_time_delivery_rate` поставщика (раздел 5.9) заметно ниже 100% — до сих пор мы просто увеличивали L "на глаз", теперь нестабильность входит в формулу явно. Если сроки скошены (обычно вовремя, изредка сильно опаздывает) — вместо симметричной σL берётся эмпирическая надбавка: 95-й перцентиль фактических сроков минус средний срок (это честнее, не занижает).

**Для прерывистого спроса (раздел 5.2, Croston-ветка)** — не масштабировать через `√L`: множитель корня и вносит основную ошибку на рваных позициях, потому что нулевые дни ломают предпосылку о независимости. Вместо этого — σ считается сразу по скользящим суммам спроса за окна длины L (не по дневному ряду), без последующего умножения на `√L`.

Полный lead time (компонент `L`, без интервала пересмотра) = `lead_поставка_FBO`, если товар есть на 1С, либо `lead_поставщик + lead_поставка_FBO`, если нужна закупка с нуля.

Если `доступен_к_заказу_у_поставщика = false` — рекомендация закупки не формируется, вместо неё — предупреждение "SKU без пополнения, идёт на исчерпание остатка".

### 5.6 Новинки — первая поставка

**Новый цвет существующего артикула — отдельный случай, точнее совсем новой модели.** Если запускается новый цвет артикула, который уже продаётся в других цветах — есть собственная история по артикулу в целом, просто не по этому конкретному цвету. Вместо подбора аналогов среди чужих моделей (как для полностью новой модели) — распределяем свою же историю:
```
прогноз_по_артикулу = агрегат по всем product_model (цветам) этого артикула, раздел 5.3-5.5

прогноз_нового_цвета = прогноз_по_артикулу × доля_цвета
доля_цвета — из норматива распределения по цвету в категории (color_profile), перемножается
             с размерным профилем так же, как раздел размерной раскладки ниже
```
Точнее чужих аналогов, потому что это ваш собственный спрос на артикул — просто ещё не разложенный по конкретному новому цвету.

**Новинка на Lamoda с историей на другом канале (WB/Ozon/розница, раздел 4) — третий, приоритетный случай.** "Новинка" по Lamoda-данным не значит "новый товар вообще" — если артикул уже продаётся годами на WB/Ozon/рознице, это не задача холодного старта, а задача пересчёта известного спроса на новый канал:
```
если есть история товара на другом канале ≥ 1 год:
  канал_коэффициент = среднее(Lamoda_продажи / продажи_канала) по товарам, которые продаются
                       на обоих каналах одновременно, за перекрывающийся период
                       # калибруется по факту на паре товаров с обоими каналами, не константа
                       # с потолка — у разных категорий соотношение может быть разным

  прогноз_новинки_по_истории_канала = продажи_канала_за_аналогичный_период_года × канал_коэффициент
```
Приоритетнее аналог-based метода ниже, когда доступен — это буквальная история продаж того же товара, не оценка по похожести на другие товары. Аналог-based метод (ниже) — резерв на случай, когда ни у одного канала нет истории вообще (действительно новая модель).

**Недооценённый потенциал — товар уже на Lamoda, но продаётся заметно хуже, чем предсказывает канал-коэффициент.** Отдельный от прогноза новинок случай: не "сколько закупить впервые", а "это правда нет спроса на Lamoda, или проблема с листингом (карточка/цена/категория/видимость), которую стоит проверить, прежде чем списывать товар как непопулярный на этой площадке":
```
ожидаемые_продажи_Lamoda = продажи_на_канале_за_период × канал_коэффициент(категория)

если факт_продажи_Lamoda << ожидаемые_продажи_Lamoda (напр. факт < 20% от ожидаемых)
   и товар в наличии на FBO весь период (не сам дефицит — причина низких продаж):
   флаг "недооценённый потенциал" — приоритет для проверки менеджером карточки/цены/категории,
   не автоматическое решение прекратить закупку
```
Не заменяет суждение менеджера — это фильтр, какие товары стоит посмотреть в первую очередь, среди всех, что продаются на Lamoda слабее ожидаемого. Флаг снимается, если после проверки причина объективная (например, категория и правда хуже заходит на аудитории Lamoda, не проблема листинга).

**Диагностический чек-лист при срабатывании флага — часть автоматически, часть только вручную:**

*Проверяется автоматически (данные уже в системе):*
```
1. Полнота атрибутов карточки — GET /v2/nomenclatures/{sku}/attributes (раздел 8.1),
   сравнить с полной карточкой той же категории; пустые атрибуты бьют по видимости в фильтрах
2. Наличие именно по ходовым размерам, не "хоть что-то есть" — сверить размеры, дающие
   основные продажи на канале-источнике (size_profile/external_channel_sales_history),
   реально ли они в наличии на FBO, а не только нестандартный неходовой размер
3. Цена относительно категории (category_market_trends.avg_category_price) и относительно
   цены на канале-источнике за тот же период — заметно дороже без видимой причины = кандидат
4. Статус карточки — не на модерации ли, нет ли проблем с маркировкой/сертификацией
5. Акции у конкурентов в категории (GET /v2/promotions, раздел 4) — конкуренты в акции,
   мы нет — может объяснять разницу без проблемы с самой карточкой
```
*Требует ручной проверки — честная граница возможностей без API:*
```
6. Фактическая видимость в поиске / позиция в ранжировании Lamoda — то, что закрыла бы
   «Воронка продаж» (просмотры/показы), но она без API, исключена из автопайплайна (раздел 4).
   Проверяется только вручную — зайти на сайт Lamoda и посмотреть позицию по релевантным
   запросам, как обычный покупатель
7. Отзывы/рейтинг товара — отдельного API-метода в изученной документации не встретили,
   тоже вручную через ЛК
```
Пункты 1-5 система может подсветить сама рядом с флагом (что именно похоже на проблему); пункты 6-7 — только напоминание менеджеру проверить, не автоматизируемая часть.

**Прогноз (для полностью новой модели без истории ни по артикулу, ни на других каналах):**
```
коэф_тренда_категории = f(собственная_динамика_категории, индекс_роста_категории_рынок)
                         # собственная — по вашей истории продаж в категории (было и раньше)
                         # рыночная — по конкурентной аналитике (раздел 4), вес выше, когда своей
                         # истории в категории мало или нет вообще (совсем новая для вас категория)

прогноз_по_аналогам = Σ(продажи_аналога_за_первые_N_недель × вес_сходства) / Σ(весов)
                      × коэф_тренда_категории

прогноз_новинки_финальный = прогноз_по_аналогам
                            × медиана_поправки_категории   (историческая точность прогноза
                                                              новинок именно в этой категории)
                            × коэф_поискового_интереса^вес   (вес < 1, модерирующий сигнал; Вордстат+Google
                                                                Trends вместе, раздел 5.3)
```

**Объём первой поставки** (тестовая партия, модель newsvendor — одноразовый заказ перед стартом продаж без права допоставки в короткий срок):
```
период_охвата = lead_поставщик + lead_поставка_FBO + 3-4 недели буфера

Cu (underage) = маржа_ед_по_плановой_цене        # раздел 5.7, формула маржи, но price_realized заменена на
                                                    product_models.planned_launch_price — margin_calc для новинки
                                                    ещё не существует (нет фактических продаж)
Co (overage)  = себестоимость_ед × (1 − liquidation_recovery_rate)  # потеря на единицу непроданного остатка;
                                                                       -- liquidation_recovery_rate — доля себестоимости,
                                                                       -- которую в среднем удаётся вернуть уценкой
                                                                       -- (параметр настроек, раздел 3, по умолчанию 0.5)

критическая_доля = Cu / (Cu + Co)
z_новинки = Φ⁻¹(критическая_доля)                 # квантиль нормального распределения

σ_объёма = прогноз_новинки_финальный(период_охвата) × σ_поправки_категории  # мультипликативно, не по дням —
                                                                              -- σ_поправки_категории это разброс
                                                                              -- коэффициента факт/прогноз по прошлым
                                                                              -- новинкам категории, не суточная
                                                                              -- волатильность, поэтому без √T

объём_первой_поставки = прогноз_новинки_финальный(период_охвата) + z_новинки × σ_объёма
```
`z_новинки` больше не фиксированное число — считается индивидуально по экономике каждого SKU: товар с высокой маржой и дешёвой ликвидацией при неудаче получает более высокий z (выгоднее перезаказать), товар с тонкой маржой и дорогой уценкой — низкий (выгоднее недозаказать).

Округление вверх до MOQ поставщика. Если расчётный объём заметно ниже MOQ — явный сигнал риска ("MOQ вынуждает завезти в X раз больше расчётной потребности").

**Погода** сдвигает не объём, а дату начала периода_охвата — аномально тёплая осень сдвигает старт вправо, холодная — влево.

**Размерная раскладка:** по собственному размерному профилю (раздел 4 — расчёт из истории заказов через API, не отчёт Lamoda — у него нет API).

**Контрольная точка пересчёта** — через 2-4 недели после старта продаж:
```
факт/прогноз = реальный_темп_продаж / прогноз_на_этот_период
```
- В коридоре (напр. 0.7–1.3) → SKU переходит в обычный сегмент ABC×XYZ (раздел 5.2)
- Сильно ниже → переоценка вниз, возможен переход в "затухающие"
- Сильно выше → досрочная закупка вне обычного цикла

### 5.7 Маржинальность и ценообразование

**Себестоимость:**
```
курс_фактический(t) = курс_ЦБ_текущий(t) + корректировка_курса   # напр. 85.3 + 4 = 89.3

себестоимость_ед(t) = закупка_USD × курс_фактический(t)
                     + доля_логистики_от_поставщика
                     + доля_пошлины/растаможки
                     + упаковка + маркировка (КИЗ)
```
`корректировка_курса` — редактируемый параметр (справочник настроек маржи), может быть и отрицательным. Отражает реальный курс покупки валюты, а не биржевой курс ЦБ напрямую.

⚠️ Курс берётся **текущий на дату расчёта, а не на дату закупки** — весь товар в ЦС учитывается в долларах, и переоценка идёт по всему остатку (1С + в пути + FBO), включая уже давно поставленные позиции, а не только по будущим закупкам. Это значит маржа пересчитывается ежедневно вместе с курсом ЦБ, а не только при разовых скачках. **Подтверждено:** 1С сама ведёт учёт товара в долларах по текущему курсу — значит расхождения с бухучётом нет, отдельная «учётная» маржа не нужна, цифра единая.

В выводе рекомендации по цене добавляется `причина_отклонения = курс / спрос / комиссия`, чтобы отличать курсовую переоценку от реальной проблемы со спросом или наличием товара.

**НДС (УСН доходы с НДС 5%):**
```
НДС_к_уплате = цена_реализации_с_НДС × 5 / 105
цена_без_НДС = цена_реализации_с_НДС − НДС_к_уплате
налог_УСН    = цена_без_НДС × 6%
```
⚠️ Уточнить у Lamoda формулу компенсации скидки на комиссию для ставки НДС 5% (для 10% есть множитель ×1.15, для 20%/без НДС — нет; официальные документы с точными формулами есть у Lamoda для ставок 20%, 10% и без НДС — но не для 5% (новая ставка для УСН-плательщиков), её отдельно нет в найденных материалах). **Решение:** закладываем как параметр `commission_vat_multiplier = 1` по умолчанию — после ответа Lamoda меняем одно значение в настройках, формулу переписывать не нужно.

**Маржа:**
```
маржа_ед = цена_реализации_с_НДС
         − себестоимость_ед
         − (цена_реализации_с_НДС × 0.42)   # комиссия Lamoda
         − логистика_FBO_на_ед
         − НДС_к_уплате
         − налог_УСН

маржа_% = маржа_ед / цена_реализации_с_НДС
```
⚠️ Для товаров в акции `цена_реализации` — это **«цена за счёт продавца»**, не цена, которую видит покупатель: скидка на маркетплейсе часто комбинированная (продавец + Lamoda). Источник — `GET /v2/promotions/{promotionId}/products` (API v2, раздел 4). Схема ответа не подтверждена детально — если там есть явная разбивка цены продавца отдельно от общей скидки, используем её напрямую; если нет (отдаёт только итоговую цену покупателя) — тогда fallback на `цена_факт` из `/v2/orders`, с тем же известным риском занижения маржи на долю Lamoda в скидке. Проверить на этапе реализации, какой случай верный.

**Промо-период → дневной расчёт.** `GET /v2/promotions/{promotionId}/products` (раздел 4) опрашивается ежедневно вместе с обычными продажами — `margin_calc` считается по факту каждого дня сразу, без задержки и без backfill (в отличие от прежней схемы с еженедельным Excel-отчётом). Если ответ API даёт только среднюю цену за период акции, а не по дням — тогда та же логика "одна цена на весь период акции", что была заложена для Excel-варианта, просто с ежедневным обновлением самого факта участия в акции, не только цены.

**Правила рекомендаций:**

| Ситуация | Рекомендация |
|---|---|
| маржа_% < 30% | повысить цену до мин. порога, либо приостановить закупку |
| маржа_% в 30–80% + неликвид (`/v2/stocks/illiquid`) | снизить цену / завести в акцию — ускорить оборот |
| маржа_% на нижней границе + неликвид | не трогать цену; списание/уценка как крайний случай |
| маржа_% > 80% + стабильный спрос | тестовое повышение цены — через A/B-подход (раздел 5.10), а не сразу на весь остаток |
| курс USD изменился (пересчёт ежедневный, т.к. себестоимость в ЦС валютная) | маржа всего активного ассортимента пересчитывается; отклонение помечается `причина_отклонения = курс`, чтобы не путать с проблемой спроса |

**Ежемесячная сверка с официальным отчётом.** Lamoda ежемесячно присылает через ЭДО «отчёт комиссионера» с полем «Цена реализации, руб. вкл. НДС» — официальная фискализируемая цифра, которую они называют базой расчёта. Не источник для автопайплайна (документ, не API) — но раз в месяц сверяем собственный расчёт `margin_calc` с этой цифрой, чтобы заметить накопленное расхождение (особенно ожидаемое там, где в дни акций мы использовали `цена_факт` вместо недоступной «цены за счёт продавца», раздел 5.7 выше).

**Маржинальность по WB и Ozon — параллельный расчёт, тот же принцип.** `margin_calc` обобщена на несколько каналов (поле `channel`, раздел 10) — тот же товар, тот же `cost_unit` из 1С (себестоимость канало-независима), но своя цена реализации и своя структура комиссии на каждой площадке:
```
маржа_% (канал) = (price_realized − cost_unit − commission_amount − logistics_fbo_amount − налоги) / price_realized

price_realized:      Lamoda — «цена за счёт продавца» (см. выше) / WB, Ozon — price_actual из
                      постоянного потока продаж (раздел 4), у них нет аналога «цены продавца»
commission_amount:    по channel_commission_rates (раздел 10) — WB: Tariffs API (комиссии по категориям,
                      меняются, отслеживать effective_from/effective_to); Ozon — точный метод не
                      подтверждён документацией, раздел 9 — на старте можно взять комиссию из отчёта
                      о продажах, если она там указана построчно
```
⚠️ Собственный сайт (awer-russia.ru) в эту маржинальность не входит — там нет комиссии маркетплейса, только эквайринг/платёжный шлюз, другая по природе структура затрат. Считается отдельно, если понадобится, не в рамках этого многоканального сравнения.
**Назначение — сравнение прибыльности одного и того же товара между каналами**, не отдельная система для каждой площадки: один и тот же запрос к `margin_calc` с фильтром по `product_size_id` и разными `channel` показывает, где товар выгоднее продавать прямо сейчас — тот же принцип, что уже частично используется в детекторе недооценённого потенциала (раздел 5.6), но здесь про маржу, не про объём продаж.

⚠️ Розница (раздел 4) в эту маржинальность не входит — там нет понятной комиссионной структуры маркетплейса, розничная маржа считается по-другому (или уже считается в 1С отдельно, не дублируем здесь).

### 5.8 Контроль точности прогноза (MAPE/WAPE, fill rate)

Раздел 5.6 даёт контрольную точку только для новинок. Системная метрика нужна для всего ассортимента — чтобы видеть, где модель систематически ошибается, а не только реагировать постфактум на нехватку/избыток.

```
MAPE = среднее(|факт − прогноз| / факт) × 100%
WAPE = Σ|факт − прогноз| / Σ факт × 100%
MAE  = среднее(|факт − прогноз|)              # абсолютная ошибка в штуках, сопоставимо между позициями
RMSE = √(среднее((факт − прогноз)²))          # с большим штрафом за крупные единичные промахи
средний_дефицит = среднее(max(факт − прогноз, 0))   # недопрогноз — упущенная маржа
средний_профицит = среднее(max(прогноз − факт, 0))  # перепрогноз — риск уценки
```
MAPE/WAPE/MAE/RMSE — симметричные метрики, считают недопрогноз и перепрогноз одинаково "плохими". Но экономически они разные: недопрогноз стоит упущенной маржи, перепрогноз — риска уценки (раздел 5.7, `liquidation_recovery_rate`). Дефицит/профицит разделяют это явно — если дефицит систематически выше профицита у конкретного сегмента, это сигнал, что буфер занижен (не проблема метода прогноза), и наоборот.
MAPE/WAPE усредняют ошибку по всему ассортименту — единичный крупный промах (каннибализация, всплеск от акции, хвост восстановления после OOS) тонет среди множества обычных дней. RMSE ловит именно такие случаи за счёт квадратичного штрафа — используется как дополнительный сигнал к порогам эскалации ниже, не вместо MAPE.

Считается регулярно по каждому `product_size_id` и агрегируется по сегменту ABC×XYZ (раздел 5.2) — сравнение точности между сегментами объективнее, чем абсолютные цифры без нормализации.

**Источник `forecast_qty` для новинок vs обычных SKU.** Пока SKU в статусе "новинка" (раздел 5.2, до контрольной точки пересчёта раздела 5.6) — `forecast_qty` берётся из `new_item_size_allocation.allocated_qty`. После контрольной точки, когда SKU переходит в обычный сегмент ABC×XYZ, источник переключается на `demand_forecast.forecast_qty`. Переключение источника — по тому же событию, что и смена статуса SKU (раздел 5.6), не отдельная логика.

**Fill rate — вторая метрика, отдельно от z.** Наш `z` (раздел 5.2/5.5) — это cycle service level (Type 1): вероятность не уйти в дефицит за цикл пополнения, бинарный исход. Он используется для расчёта буфера — это нормально. Но для мониторинга результата важнее **fill rate (Type 2)** — доля фактически закрытого спроса, а не факт "был дефицит хоть раз":
```
fill_rate = Σ выполненный_спрос / Σ весь_спрос_за_период × 100%
```
Fill rate считается по факту (не для расчёта буфера, а для проверки), потому что честнее показывает реальные потери выручки — SKU может быть "в дефиците всего 2 дня" (низкий урон по cycle service level), но потерять там 80% ожидаемого спроса пикового периода (сильный урон по fill rate).

⚠️ Оговорка: знаменатель ("весь спрос") — это тот же реконструированный `demand_timeseries` (раздел 5.1), что участвует в обучении прогноза. Fill rate здесь не полностью независимая проверка, а согласованная с моделью метрика — полезна для сравнения между SKU/периодами, но не как абсолютная истина о "реальном" спросе.

**Пороги отклонения и эскалация — что делать с MAPE после того, как его посчитали.** Сама по себе цифра MAPE бесполезна без реакции на неё:
```
MAPE < warning_threshold (напр. 20%)                     → status = норма
warning_threshold ≤ MAPE < critical_threshold (напр. 40%) → status = предупреждение
MAPE ≥ critical_threshold                                  → status = критично
```
Пороги — параметры настроек (по категории, т.к. у категорий разная естественная волатильность — раздел 5.2, XYZ). Реакция разная по статусу:
- **предупреждение**, удерживается `consecutive_periods_trigger` периодов подряд (напр. 3) → помечается как систематическое отклонение, не разовый шум. Кандидат на смену метода прогноза для этого SKU (например, перевести на Croston/SBA, если модель систематически промахивается на фактически прерывистом спросе — раздел 5.2), с логированием смены
- **критично** → сразу эскалация в агент триажа аномалий (раздел 8.2) — резкое расхождение чаще говорит о внешнем факторе (сорванная поставка, всплеск/провал спроса, ошибка в данных), а не о постепенном дрейфе модели, разбираться нужно быстрее одного цикла

**Приоритет правил выбора модели:** SBC-классификация по ADI×CV² (раздел 5.2, Syntetos-Boylan-Croston) — это дефолтное правило, пересчитывается каждый цикл заново. Запись в `model_recalibration_log` — override поверх дефолта, действует до следующего пересчёта дефолтного правила; если после override классификация снова меняется — дефолтное правило выигрывает автоматически, override не "залипает" навсегда молча.

**Степень достоверности рекомендации — отдельный индикатор для страницы поставок (раздел 6), в процентах.** Не то же самое, что WAPE сам по себе — композитный сигнал из нескольких независимых факторов, каждый из которых может подрывать доверие к цифре по своей причине:

```
достоверность_% = 100
  − штраф_WAPE                    # масштабируется от WAPE последнего периода/бэктеста —
                                   # напр. min(WAPE_%, 40) — на этой шкале WAPE 40%+ уже
                                   # снимает все 40 пунктов, дальше не усугубляет
  − штраф_паттерна                # demand_pattern (раздел 5.2): Smooth=0, Irregular=5,
                                   # Intermittent=10, Lumpy=20 — фиксированные, не от WAPE
  − штраф_короткой_истории        # новинка (<60 дней, раздел 5.2) = 25, короче полного
                                   # сезонного цикла = 10, иначе 0 — низкий WAPE на малой
                                   # выборке ничего не гарантирует, штраф отдельный от WAPE
  − штраф_расхождения_моделей     # |победитель_бэктеста − DeepAR| / среднее(двух) × 30,
                                   # максимум 20 пунктов — две независимые модели разошлись
  − штраф_свежего_отклонения      # status=warning в последних периодах (раздел 5.8) = 10,
                                   # critical = 20, свежая запись в model_recalibration_log
                                   # (младше одного цикла пересмотра) = 10, суммируются
  − штраф_stockout_доли           # доля дней is_stockout_corrected (раздел 5.1) за период × 15 —
                                   # высокая доля означает спрос в основном реконструирован

достоверность_% = max(0, достоверность_%)   # не может уйти в минус, 0 — нижняя граница
```
Округляется до целого для отображения. Цветовая подсветка для быстрого сканирования поверх числа — не вместо него: ≥70% зелёная, 40–69% жёлтая, <40% красная — но на странице всегда виден сам процент, не только цвет.

**Пояснение — отдельное поле рядом с процентом, не скрытый расчёт.** Собирается из тех же компонентов, что и сам процент, но человекочитаемым текстом — перечисляются только штрафы, которые реально сработали (нулевые не показываются, чтобы не шуметь):
```
пояснение = список сработавших штрафов через запятую, например:
  "Новинка (-25), Lumpy-паттерн (-20), WAPE 35% (-14)"
  # или, если ничего не сработало:
  "Все факторы в норме"
```
В интерфейсе — раскрывающееся поле рядом с числом (по клику/наведению разворачивается, свёрнуто не мешает читать таблицу). В Excel-выгрузке (раздел 6) — обычный текстовый столбец, раскрывать там нечего, но содержимое то же самое.
Назначение — не заменить решение менеджера, а подсветить, каким рекомендациям можно доверять с меньшей проверкой, а какие (новинка + Lumpy + свежий пересмотр метода одновременно) требуют взгляда человека перед подтверждением, даже если рекомендованное количество выглядит разумным на глаз.

### 5.9 Надёжность поставщика

Упущенные продажи возникают не только от ошибки прогноза, но и от срыва сроков поставщиком. Фиксируем факт: заявленный `lead_time` из справочника поставщика (раздел 3) против фактической даты готовности каждой поставки. Агрегированный `on_time_delivery_rate` используется как модификатор буфера — поставщику с низкой надёжностью закладывается увеличенный lead time в расчёте точки заказа (раздел 5.5), а не номинальный из договора.

### 5.10 Ценовая эластичность и сценарный анализ

**Проблема, которую закрывает раздел:** правило "тестовое повышение цены" (раздел 5.7, маржа > 80%) сейчас работает вслепую — подняли цену, потом постфактум смотрим по воронке, что случилось. С историческими данными о продажах при разных ценах (обычная цена + акции, раздел 4) можно оценить эффект заранее.

**Оценка эластичности:**
```
ln(спрос) = a + b × ln(цена) + контрольные_переменные (сезон, конкуренция по категории)
эластичность = b
```
Считается по `product_model_id`, если хватает исторических точек с разной ценой (акции дают эту вариацию); при недостатке истории — fallback на уровень категории (менее точно, но лучше отсутствия оценки).

**Продвинутый вариант — бустинг с monotone constraints.** Когда данных по цене/спросу достаточно (после накопления истории), log-log регрессия — грубое приближение реальной, часто нелинейной зависимости. Точнее — `XGBoost`/`LightGBM` с `monotone_constraints = -1` по признаку цены: модель ищет сложную нелинейную зависимость, но гарантированно не выдаст "рост цены увеличивает спрос" — ограничение сохраняет экономический смысл результата, которого чистый ML без constraints не гарантирует.

**Сценарный анализ (what-if):** перед принятием ценового решения — прогон гипотезы, а не только мониторинг по факту:
```
прогноз_спроса_при_новой_цене = прогноз_спроса_текущий × (1 + эластичность × %Δцена)
ожидаемое_изменение_маржи = f(новая_цена, прогноз_спроса_при_новой_цене, себестоимость_ед, комиссия)
```
Правило из раздела 5.7 ("маржа > 80% + стабильный спрос → тестовое повышение цены") теперь сначала прогоняется через сценарий — если ожидаемое падение спроса перекрывает выигрыш в марже, рекомендация не выдаётся вообще, а не проверяется по факту после того, как цена уже изменена.

Сценарии, которые применили (а не только просчитали), логируются — чтобы позже сверить прогноз сценария с фактом и калибровать оценку эластичности.

**A/B-подход к тестовому повышению цены (правило из раздела 5.7).** На маркетплейсе нельзя случайно разделить покупателей на группы — все видят одну цену одновременно, значит классический A/B не применим напрямую. Вместо этого — **разница-в-разницах (difference-in-differences)**: сравниваем изменение спроса у тестируемого SKU с изменением спроса у похожих SKU, цену которых не трогали, за тот же период.

```
Тестовая группа:    SKU, где сработало правило "маржа > 80% + стабильный спрос"
Контрольная группа: похожие SKU (из product_analogs — вес_сходства, либо тот же сегмент ABC×XYZ
                     и категория), цена которых в этот период не менялась

эффект = (Δспрос_тестовая − Δспрос_контрольная)
```
Вычитание контрольной группы убирает общий сезонный/трендовый шум периода — эффект не весь приписывается изменению цены, только та часть, которая отличается от естественного движения спроса у похожих товаров.

**Окно теста:** короткое (1-2 недели) — не сразу на весь остаток и не навсегда. По итогам:
- эффект в пределах ожидания (прогноз из сценария, раздел выше) → цена сохраняется, распространяем на весь остаток/похожие размеры
- эффект хуже прогноза за пределами допуска → откат к прежней цене, `price_ab_test.decision = rollback`

Так сценарный анализ (прогноз до) и A/B-тест (факт после) замыкают цикл — сначала оцениваем ожидаемый эффект, потом измеряем реальный на малом окне, и только затем принимаем решение на весь ассортимент.

### 5.11 Оптимизация цен по всей линейке

**Отличие от раздела 5.10:** там — сценарий/тест для одного SKU по отдельности. Здесь — одна задача оптимизации сразу по всей линейке, учитывающая, что цены товаров одной категории не независимы (кросс-эластичность, раздел 5.3): изменение цены одного SKU задевает спрос на связанные.

```
Переменные:  Δp_i — % изменения цены каждого SKU i относительно текущей

Спрос (линейное приближение вокруг текущей цены — корректно при малых Δp,
других и не допускаем из-за guardrail):
  Δспрос_i = эластичность_i × Δp_i + Σ_j (кросс_эластичность_ij × Δp_j)
             # первое слагаемое — собственная эластичность (5.10)
             # второе — влияние цен связанных SKU (cross_elasticity / promo_cannibalization_pairs, 5.3);
             #          для большинства SKU без известных связей это слагаемое = 0

Целевая функция:  максимизировать  Σ_i  маржа_ед_i(Δp_i) × спрос_i × (1 + Δспрос_i)
                  # суммарная маржа по линейке, не по одному SKU
                  # спрос_i = demand_forecast.forecast_qty на период_охвата планируемого изменения

Ограничения:
  |Δp_i| ≤ max_step_pct                     # guardrail на резкость шага (раздел 5.7)
  мин_маржа ≤ маржа_%_i(Δp_i) ≤ макс_маржа  # пороги раздела 5.7, здесь — жёсткое ограничение, не триггер
```

⚠️ **Оптимизация без остатков сама по себе не гарантирует исполнимость.** Формула выше максимизирует маржу по экономике, но не знает, что снижение цены на товар, который вот-вот уйдёт в дефицит (остаток близко к точке заказа, раздел 5.5), бессмысленно — скидка потеряется на нехватке физического товара, не даст обещанный объём продаж. Перед передачей в `pricing_recommendations` результат фильтруется: снижение цены исключается или помечается предупреждением для SKU, где `остаток_FBO + в_пути < прогноз_спроса на период_охвата акции`.

**Решается численно** — `scipy.optimize.minimize` (SLSQP). Для масштаба AWER (сотни SKU) задача лёгкая, промышленный солвер не нужен. Структура разреженная: SKU без кросс-эффектов с соседями по факту оптимизируются независимо, задача распадается на небольшие связанные группы (артикул + его конкуренты по категории), не решается как единый плотный блок.

**Периодичность:** не ежедневно — раз в неделю, либо по триггеру значимого изменения входных данных (курс валюты, раздел 5.7).

**Результат не применяется автоматически** — пакет рекомендаций уходит в уже существующий механизм ручного подтверждения (раздел 6), менеджер видит весь список сразу и подтверждает пакетом или по одному; применение — тем же API-механизмом.

⚠️ Ограничение "отступ от цены конкурента" (упоминалось в разделе про динамическое ценообразование, раздел 11) сюда не включено — по-SKU данных о ценах конкурентов нет, только грубый `category_market_trends.avg_category_price` (раздел 5.6). Задел на будущее при появлении точного источника.
