## 4. Входные потоки данных

⚠️ **Историческая выгрузка с других каналов (WB, Ozon, 2 розничных магазина) — отдельная категория, не ежедневный поток.** Lamoda и собственный сайт дают всего несколько месяцев истории; WB/Ozon/розница — 5-7 лет. Это разовая (или редкая, при необходимости) загрузка исторических данных — назначение здесь: не текущие остатки/продажи, а сезонный индекс и история для новинок (раздел 5.2/5.6).

⚠️ **Отдельно от исторической загрузки — постоянный поток по WB и Ozon для прогноза спроса и маржинальности на текущий момент (раздел 5.2-5.7-доп).** В отличие от истории выше, это уже ежедневный/еженедельный автопайплайн, не разовая загрузка: текущие продажи (те же API, что и для истории — Statistics API WB / FinanceAPI Ozon) + тарифы/комиссии по категориям (WB Tariffs API; Ozon — точный метод уточнить, раздел 9). Розница в этот постоянный поток не входит — только площадки с понятной комиссионной структурой и API-доступом к продажам.

| Канал | Источник | Формат | Назначение |
|---|---|---|---|
| Wildberries | Statistics API — `GET /api/v5/supplier/reportDetailByPeriod` («Отчёт о продажах по реализации», `statistics-api.wildberries.ru`) — отдельный токен (Statistics API Key, не тот же, что для заказов/контента); лимит 1 запрос/мин (всплеск до 10) — закладывать паузы. Готовый клиент — `wbsdk` (Python) | по баркоду, помесячно за весь период | сезонный индекс, история для новинок |
| Ozon | Seller API — `AnalyticsAPI`/`FinanceAPI`, отчёты о продажах товаров (`docs.ozon.ru/api/seller`). Авторизация — заголовки `Client-Id`+`Api-Key`, не Bearer-токен | по баркоду, помесячно | то же |
| Розница (2 магазина) | 1С (если продажи розницы уже заведены в 1С — уточнить; если нет — отдельная выгрузка кассовой системы) | по баркоду цветоразмера, помесячно | то же |

Новый клиент не писать: переиспользовать/вынести существующий код (авторизация, пагинация, маппинг статусов) | опрос API по расписанию, сопоставление по баркоду из пула | канал `own_site`, тянущий с ЦС напрямую (DBS-подобная модель — свой сайт, своя доставка) |

⚠️ **WB и Ozon — модель FBS, не FBO.** В отличие от Lamoda, у этих площадок нет собственного промежуточного склада — отгрузка идёт прямо с ЦС по каждому заказу. Это значит: страница «Поставка на FBO» (раздел 6) относится только к Lamoda — для FBS-каналов нет решения «сколько отгрузить на склад площадки», это не применимо по определению модели. Собственный сайт (awer-russia.ru) — та же логика, своя доставка напрямую с ЦС, только без маркетплейса вообще. Спрос со всех этих каналов так же тянет остаток с ЦС, просто напрямую — см. ниже про агрегированный спрос для раздела 5.5/6.

⚠️ **Известное расхождение данных WB (подтверждено сообществом продавцов, не наша догадка):** `pricewithdisc` не совпадает между методом "Заказы" и методом/отчётом "Продажи" — для расчётов истории ориентироваться на отчёт о продажах по реализации, не на заказы.

Ключевое условие использования — сопоставление по **баркоду цветоразмерного SKU** (`barcode_pool`, раздел 3/10), не по артикулу целиком и не по внутреннему SKU каждой площадки (они разные) — тот же ключ, что уже используется для начальной загрузки карты сопоставления с Lamoda (раздел 3). Ozon Seller API подтверждает баркод как рабочий ключ и на своей стороне — прямой метод поиска отправления по баркоду (`POST /v2/posting/fbs/get-by-barcode`).

**Примечание по токенам API:** TTL 15 минут / 900 секунд (Lamoda Seller JSON-RPC), 24 часа (B2B Platform REST) — модуль забора данных должен сам обновлять токен.

**Нотификации (вебхуки) — ускоритель доставки событий, не замена опроса.** ⚠️ Исправление к прежней формулировке: источником истины по заказам официально остаётся **поллинг** (`GET /v2/orders` по `updatedAtFrom`) — вебхуки не гарантируют доставку и порядок, пропуски нужно закрывать регулярным опросом за период. Архитектура: вебхук ускоряет реакцию (не ждать до следующего планового опроса), но каждое событие подтверждается запросом `GET /v2/orders/{orderId}` (используется `data.id` из тела вебхука, например `"CZ117391950"` — не `trackingId`, это разные поля) и обрабатывается идемпотентно по ключу "id заказа + статус". Регулярный полный опрос по `updatedAtFrom` продолжает работать параллельно как страховка от пропущенных/недоставленных вебхуков.
```
statusChanged, itemStatusChanged          → ускоряют реакцию на продажи/возвраты,
                                             но не отменяют регулярный опрос /v2/orders
moderationApproved, moderationRejected    → ускоряют получение результата модерации цены
                                             (раздел 6, "ценовой карантин")
fulfilmentShipmentValidationRest          → ускоряет получение результата валидации поставки FBO
                                             (раздел 5.4, fbo_shipments)
```
Требования к эндпоинту (наша сторона): HTTPS, URL ≤1024 символов, доступен 24/7, отвечает <5 секунд, POST-обработчик по `type` события, опционально Basic Auth (`none` по умолчанию). **Подписка настраивается не самостоятельно через API, а через менеджера (KAM) или поддержку** — предоставляем URL эндпоинта (и логин/пароль для Basic Auth, если нужен), Lamoda сама включает нужные события. Без активной подписки на конкретный тип события вебхуки этого типа не приходят вообще, даже если эндпоинт готов принимать все типы.

**Возвраты для FBO — только через статус товара, не через отдельный метод.** `GET /v2/fbs/return-boxes`/`return-items` существуют, но только для модели FBS — для FBO (наш случай) единственный путь отследить возврат — статус `Returned` в `items[].status` (пример из вебхука `itemStatusChanged`, раздел 4) через опрос или вебхук заказов. Это подтверждает уже заложенный в разделе 4 источник возвратов, не меняет его.

**Практические ограничения API (из официального FAQ и документации по авторизации):**
- ⚠️ **Суммы — целые числа в минорных единицах валюты** (копейки для RUB/BYN, тиыны для KZT), не рубли с копейками как десятичная дробь. Модуль забора данных делит на 100 при приёме **каждого** денежного поля из API — цены, скидки, суммы заказов. Касается всех таблиц с `NUMERIC(x,2)` в рублях (margin_calc, order_items, promo_report_*, price_elasticity и т.д.) — конвертация на границе приёма данных, не внутри бизнес-логики.
- Пагинация: у заказов/отгрузок/возвратов — по умолчанию 100, максимум 1000; у номенклатур/минимальных цен — максимум 25 (без отдельного дефолта). Смотреть `meta` (`total`/`page`/`limit`/`totalPages`) в ответе, не считать вручную.
- `GET /v2/nomenclatures` требует обязательный параметр `country` (`RU`/`BY`/`KZ`) — без него `400`.
- Неизвестный query-параметр API молча игнорирует, не возвращает ошибку — источник тихих багов при опечатке в имени параметра.
- Официальных лимитов частоты запросов нет, но при `429`/`503` — экспоненциальный backoff; батчи держать ≤100 элементов, между запросами — пауза.
- `client_id`/`client_secret` + `sellerId` — общие для всех версий API, но нужны все три (не только ключи). `403 FORBIDDEN` чаще всего означает несовпадение `sellerId` с тем, под который выдан токен.
- Единый формат ошибок: `{"error": {code, message, details?}}` — коды `VALIDATION_FAILED`(400) / `UNAUTHORIZED`(401) / `FORBIDDEN`(403) / `NOT_FOUND`(404) / `TOO_MANY_REQUESTS`(429) / `SERVICE_UNAVAILABLE`(503) / `INTERNAL_SERVER_ERROR`(500) — единообразная обработка ошибок в модуле забора данных.
- Обновление токена — два правила одновременно: проактивно за 30-60 секунд до истечения `expires_in` (не хардкодить время жизни константой — брать из ответа `POST /v2/auth-token` каждый раз) **и** реактивно по факту `401` (перевыпустить токен и повторить исходный запрос один раз).
- Тело `POST /v2/auth-token` — единственное исключение в snake_case (`grant_type`/`client_id`/`client_secret`); везде в остальном API — camelCase.
- **Переотправка пропущенных нотификаций** — `POST /api/v1/notifications/resend`, тело `{"trackingIdCollection": [...]}`, максимум 100 номеров заказов за раз, код `201`. Переотправляет **все** сохранённые нотификации заказа в хронологическом порядке без фильтра по типу события — дубли гарантированы, идемпотентность (уже заложена, раздел 10) обязательна. Только для заказов (`statusChanged`/`itemStatusChanged`) — поставки FBO так не переотправляются, у них свой идентификатор. Повторный запрос по тому же заказу, пока предыдущий ещё выполняется, временно блокируется.

⚠️ **Исключено из автоматизированного пайплайна (нет API, только ручная выгрузка из ЛК):** отчёт «Воронка продаж» (просмотры/корзина на уровне модели — без замены, полностью теряем этот сигнал, раздел 5.3). Акции — **больше не в этом списке**: найден `/v2/promotions` в API v2 (см. таблицу выше), возвращены в автопайплайн после того, как считались недоступными по устаревшей v1-документации.

**Открытый вопрос к Lamoda:** уточнить у `api-integration@lamoda.ru`, есть ли API-эквивалент отчёта «Воронка продаж» (сейчас только ручная выгрузка, исключён из автопайплайна — акции больше не в этом списке, найдены в `/v2/promotions`), точную схему ответа `/v2/promotions/{promotionId}/products` (есть ли разбивка цены за счёт продавца), и формулу компенсации скидки на комиссию для ставки НДС 5%.
