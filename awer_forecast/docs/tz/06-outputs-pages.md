## 6. Выходные рекомендации

⚠️ **Приоритет (MVP) — две отдельные страницы вывода, не строки одного общего дашборда.** Отгрузка с ЦС и закупка у поставщика — разные рабочие сценарии для разных решений (первое — просто отгрузить то, что уже есть на складе; второе — заказать то, чего нет), поэтому разводим по разным экранам с самого начала, а не объединяем в одну таблицу с фильтром:

1. **Страница «Рекомендации по поставке с ЦС на FBO»** — только по SKU, где `остаток_1С > 0` (товар уже есть на своём складе, просто нужно решить, сколько и когда отгрузить на Lamoda). Источник — `shipment_recommendations` (ниже). Выгрузка в Excel — отдельный файл/лист.
2. **Страница «Рекомендации по закупке у поставщика»** — SKU, где своего остатка не хватает и нужен заказ у поставщика, по агрегированному спросу со всех каналов сразу (Lamoda+WB+Ozon+собственный сайт+розница, раздел 5). Источник — `purchase_recommendations` (ниже). Выгрузка в Excel — отдельный файл/лист, не общий с первой страницей.

Обе страницы читают из уже описанных ниже таблиц-источников, разделение — только на уровне представления (UI + экспорт), не новая логика расчёта.

**Отгрузка на FBO — точная структура страницы/выгрузки:**
```
артикул | цвет | размер | остаток_на_ЦС | остаток_FBO | рекомендация_к_отгрузке |
степень_достоверности_% (раздел 5.8, число 0-100 с цветовой подсветкой) |
пояснение_достоверности (раскрывающееся поле, текст сработавших факторов) |
подтверждено_к_поставке
```
- `остаток_на_ЦС`, `остаток_FBO` — снимок текущего наличия (см. выше), не расчётные величины
- `рекомендация_к_отгрузке` — то, что считает система (`qty_to_ship`)
- `подтверждено_к_поставке` — **пустое поле по умолчанию**, менеджер вручную вписывает финальную цифру. Не автоматически равно рекомендации — управленческое решение остаётся за человеком, система только предлагает.

**Сборка поставки — по заполненным строкам, отдельным действием.** Поставка собирается не из всей страницы рекомендаций, а только из строк, где менеджер заполнил `подтверждено_к_поставке`. Действие «Собрать поставку» берёт только эти строки и формирует Excel-выгрузку в том же формате и с теми же колонками, что и вся страница — но это уже готовый документ для передачи в пайплайн отгрузки (УПД / Честный Знак / ЭТрН), а не список рекомендаций на рассмотрение. Заполнение поля переводит строку в статус `confirmed` (раздел 10) — так «что подтверждено» отличимо от «что ещё рассматривается» без отдельного флага.

⚠️ "В пути к клиенту" и "в пути от клиента" — **намеренно не колонки этой страницы**. Они участвуют в расчёте `прогноз_остатка(T)` (раздел 5.5) как входные данные формулы, но на самой странице рекомендаций не показываются — страница про решение "сколько отгрузить сейчас", а не про разбор компонентов расчёта.

→ стыкуется с существующим пайплайном УПД / Честный Знак / ЭТрН.

⚠️ **Штраф за позднюю/резкую корректировку уже созданной поставки.** Lamoda штрафует, если корректировка внесена позже допустимого срока и при этом объём отличается от начального плана более чем на 15% (штраф — фиксированная сумма за единицу). Если пересчёт прогноза предлагает изменить объём уже созданной (не отгруженной) поставки более чем на 15% близко к плановой дате — система должна показать это как предупреждение с ожидаемым штрафом, а не просто молча выдать новую рекомендацию поверх старой.

**Закупка у поставщика:**
```
sku_id, размер, кол-во_к_закупке, поставщик_id, срок_готовности
```
Формируется при `точка_заказа > остаток_1С + остаток_FBO + в_пути` и `доступен_к_заказу_у_поставщика = true`.

**Ценообразование:**
```
sku_id, текущая_маржа_%, рекомендация (повысить/снизить/тест/без изменений), обоснование
```

**Дашборд «Прогноз-факт»:**
```
sku_id, размер, категория, сегмент_ABC×XYZ, период,
прогноз, факт, отклонение_%, статус (норма/предупреждение/критично),
причина_отклонения (курс/спрос/комиссия — если применимо, раздел 5.7)
```
Табличное представление построчно по SKU (источник — `forecast_accuracy_log`, раздел 5.8), с фильтрами по категории/сегменту/статусу и сводкой сверху (общий MAPE/WAPE, доля SKU в статусе "критично"). Строки со статусом "предупреждение"/"критично" сортируются наверх — не нужно скроллить весь ассортимент, чтобы найти то, что требует внимания.

**Ручные корректировки прогноза.** Алгоритм не знает того, что знает менеджер — договорённость о крупной оптовой закупке через Lamoda, инфоповод, коллаборацию. Прогноз можно скорректировать вручную поверх расчётного:
```
sku_id, размер, период, прогноз_расчётный, прогноз_скорректированный,
причина (свободный текст), кто_скорректировал, дата
```
Скорректированное значение используется вместо расчётного во всех downstream-расчётах (точка заказа, раздел 5.5) на срок действия корректировки. Расчётное значение никогда не перезаписывается — только добавляется новая запись override поверх, история видна целиком, а не теряется при следующем автопересчёте.

**Применение ценовых рекомендаций через API (ручное подтверждение).** Система только рекомендует (`pricing_recommendations`, раздел 5.7) — цену на Lamoda меняет менеджер, по явному подтверждению, а не автоматически по расписанию.

```
Поток: pricing_recommendations (status=pending) → менеджер видит в дашборде → подтверждает →
       вызов Lamoda API → лог применения (успех/ошибка/на модерации)
```

**Метод API (FBO, v2):** `POST /v2/nomenclature-price` — параметры `lamoda_parent_sku` (не `seller_sku` — тот для FBS), `partner_id`, `country`, `price`/`salePrice` (объекты `{amount, currency}`, amount — целое число в копейках), `saleStart`/`saleEnd` (camelCase, полный ISO-datetime). Для массового подтверждения нескольких SKU разом — `POST /v2/nomenclatures-prices`, а не по одному вызову на SKU. (v1-эквиваленты `v1.nomenclature.update-price`/`v1.nomenclatures.set-prices` — не использовать в новой разработке, отключаются 01.01.27, раздел 7).

⚠️ **Частая ошибка "Партнёр не найден" (50400)** — если перепутать метод под модель: FBS-метод — идентификатор `seller_sku`, FBO-метод (наш случай) — идентификатор `lamoda_parent_sku` + `partner_id`. Использование не того метода для нашей модели (FBO) даёт эту ошибку, а не тихо работает с другим набором параметров.

⚠️ **Ценовой карантин Lamoda:** снижение цены больше чем на 70% не применяется мгновенно даже через API — уходит на модерацию в ЛК (раздел "Цены" → "На модерации"). Система должна предупреждать об этом менеджера **до** подтверждения ("это снижение уйдёт на модерацию, применится не сразу"), а не молча ждать несуществующего немедленного эффекта. Результат модерации приходит вебхуком (`moderationApproved`/`moderationRejected`, раздел 4) для быстрой реакции — статус `quarantined` в `price_change_log` обновляется по событию, но регулярный опрос за период остаётся страховкой на случай недоставленного вебхука (раздел 4 — вебхуки не гарантируют доставку).

⚠️ **Валидация акционной цены по медиане 30 дней и фрод-проверка.** Lamoda рассчитывает медианную цену за последние 30 дней и отклоняет `sale_price`, если скидка не проходит их порог валидации — независимо от нашего собственного guardrail `max_step_pct` (раздел 5.11). Отдельно — автоматическая фрод-проверка цены (`fraudValidationResult` в ответе метода), ещё один самостоятельный фильтр. Обе проверки внешние, не наши — `api_response_status` в `price_change_log` различает `validation_failed` от общего `api_failed` (раздел 10).

⚠️ **HTTP 200 не гарантирует применение цены.** Успешный код ответа не означает, что цена принята — нужно проверять поля `errors[]`, `priceStatuses`, `fraudValidationResult` в теле ответа, а не только HTTP-статус. Модуль применения цен (раздел 6) парсит тело ответа на каждый вызов, не считает успехом факт отсутствия HTTP-ошибки.

**Два разных механизма скидки — оба доступны по API v2, не путать.** (1) Участие в акциях Lamoda (с возможной доплатой от них) — `POST /v2/promotion-variants/{promotionVariantId}/products`/`remove-products` (раздел 4) — добавление/удаление товаров из уже существующей акции Lamoda, не создание своей акции. (2) Собственная временная скидка за счёт продавца, без участия в программе Lamoda — `salePrice`/`saleStart`/`saleEnd` в том же методе `POST /v2/nomenclature-price`, что и обычная цена (раздел 6 выше). Для A/B-теста (раздел 5.10) и применения результата оптимизации по линейке (раздел 5.11) используем именно второй механизм — не пытаемся встроить тест в чужую акцию Lamoda с её собственными сроками и условиями участия.

**Статусы `pricing_recommendations`:** `pending` (ждёт решения) → `approved` (менеджер подтвердил) → `applied` (API вернул успех) / `api_failed` (ошибка вызова) / `quarantined` (ушло на модерацию Lamoda, ждёт их подтверждения) — расширяет уже существующие `active`/`suppressed`/`superseded` (раздел 10).
