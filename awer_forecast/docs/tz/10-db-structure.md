## 10. Структура БД

Полная схема — отдельный файл `lamoda_forecast_schema.sql`. Ключевые решения:
- Иерархия `product_models` (артикул+цвет) → `product_sizes` (+размер); прогноз/остатки/маржа — на уровне `product_sizes`, аналоги — на уровне `product_models`. Таблицы `funnel_model`/`funnel_size` в схеме остаются, но не заполняются автоматически (нет API) — опциональны при ручном разборе, если понадобится точечная проверка
- `fbo_shipments` — факт созданных поставок (источник компонента «в пути на FBO» в разделе 5.4, отдельно от `shipment_recommendations`, которые лишь рекомендация)
- `stock_reconciliation_log` — сверка расчётного состояния (state-machine) с фактическим снимком `stock_fbo`
- `new_item_size_allocation` — явный шаг раскладки агрегатного прогноза новинки (уровень модели) по размерам через `size_profile`
- `cannibalization_events` — хранит сигнал каннибализации между цветами/размерами, используемый в прогнозе (раздел 5.3)
- `size_profile` включает поле `gender` (профиль отличается по полу — раздел 5.6)
- `margin_settings.commission_vat_multiplier` — заглушка под множитель компенсации комиссии по ставке НДС 5% (по умолчанию 1, обновить после ответа Lamoda, открытый вопрос №2)
- `abc_xyz_classification`, `forecast_accuracy_log`, `supplier_deliveries` — классификация по индустриальной практике (ABC×XYZ, MAPE/WAPE, надёжность поставщика), раздел 5.8-5.9
- `demand_forecast.demand_pattern` — SBC-классификация (Smooth/Irregular/Intermittent/Lumpy по ADI×CV²), заменила бинарный флаг прерывистости, раздел 5.2; `model_backtest_results` — турнир методов, включая DeepAR (`GluonTS`) как отдельного, обучаемого один раз на весь каталог кандидата
- `cross_elasticity` (внутри артикула, по доступности) и `promo_cannibalization_pairs` (между разными артикулами, по акции, t-test) — два отдельных механизма каннибализации, не путать, раздел 5.3
- `price_optimization_run`/`price_optimization_result` — оптимизация цен сразу по всей линейке (не по одному SKU), раздел 5.11; результат фильтруется по остаткам (`stock_check_passed`) перед выдачей рекомендации
- `webhook_events_log` — идемпотентная обработка вебхуков Lamoda по ключу «id заказа + статус», вебхуки — ускоритель, не замена регулярного опроса (раздел 4)
- `price_change_log` различает три независимые внешние проверки при применении цены: карантин (>70% снижения), валидация по медиане 30 дней, фрод-проверка (раздел 6)
- Суммы из Lamoda API — минорные единицы (копейки), конвертация на границе приёма данных (раздел 7); методы API в тексте раздела 3-8 частично оставлены как v1 с явной пометкой — таблица соответствия v1→v2 в разделе 7
- `demand_forecast`/`margin_calc` — многоканальные (поле `channel`: lamoda/wb/ozon/own_site, раздел 5/5.7-доп); тот же аппарат прогноза (SBC/TSB/DeepAR/бэктест) прогоняется отдельно по каждой паре SKU+канал
- `central_stock_aggregate_demand` — суммарный спрос по всем каналам сразу, источник для точки заказа/закупки у поставщика (раздел 5.5/6), т.к. WB/Ozon/собственный сайт (не-Lamoda каналы) тянут остаток напрямую с ЦС, без промежуточного склада площадки
- `external_channel_sales_history`/`channel_ratio_calibration`/`seasonal_index_reference` — историческая выгрузка WB/Ozon/розницы (5-7 лет, разовая загрузка) для сезонного индекса и прогноза новинок с историей на другом канале (раздел 4/5.2/5.6)
- `underperformance_flags` — детектор «недооценённого потенциала» (сильные продажи на другом канале, почти нулевые на Lamoda) с пятью автоматическими диагностическими проверками, раздел 5.6
- `recommendation_confidence` — степень достоверности рекомендации в процентах с пояснением сработавших факторов, раздел 5.8/6
- `channel_commission_rates` — комиссия/логистика по каналу и категории (WB: Tariffs API подтверждён; Ozon: метод не подтверждён, открытый вопрос №5, раздел 5.7-доп)
- `barcode_pool` — сопоставление по совпадению любого одного баркода из пула, не единственного канонического значения (раздел 3)
