# AWER Forecast — прогноз спроса и планирование поставок

Система из ТЗ `docs/tz/` (передача «awer-forecast-handoff»): прогноз спроса по цветоразмерному
SKU, рекомендации **поставки с ЦС на FBO Lamoda** и **закупки у поставщика**. Работает рядом с
Sync Admin: остатки ЦС читает из того же FTP-моста 1С, ничего у него не забирая.

**Состояние: Фаза 1 (MVP без ML) — реализована, проверена на тестовых данных.** Против живого
API Lamoda и живой 1С ещё не запускалась — см. «Что не проверено».

## Что умеет Фаза 1

- **БД** — вся `docs/schema.sql` (70 таблиц) миграцией Alembic 0001; на PostgreSQL 16 база после
  миграции совпадает с `psql -f schema.sql` до колонки, умолчания и индекса (тест
  `test_migration_0001_equals_raw_schema_sql_on_postgresql`). Отличия Фазы 1 — миграцией 0002 (ниже).
  Работает и на SQLite (тесты, локальный запуск, сервер без PostgreSQL).
- **Справочник** из Excel-карты мэппинга: модели (артикул+цвет) → размеры → **пул баркодов**.
  Сопоставление везде — по совпадению ЛЮБОГО баркода из пула; для Lamoda ещё по размерному SKU и SKU
  продавца. Недостающие Lamoda SKU проставляет сверка с `GET /v2/nomenclatures`.
- **Lamoda Seller API v2** (только v2): токен с обновлением заранее и по 401, `sellerId`, пагинация по
  `meta.totalPages`, повторы на 429/5xx с `Retry-After`, единый разбор ошибок, копейки → рубли на входе.
  Остатки FBO (с нулями — это признак stockout), поставки FBO «в пути», заказы по `updatedAtFrom` с
  курсором и перекрытием — идемпотентно по «заказ + позиция + статус».
- **1С**: свежайший `stock_*.txt` из каталогов обмена Sync Admin (только чтение); продажи розницы, WB,
  Ozon и сайта — файлы `sales_*.txt` в предложенном формате (чтение выгрузки «бота план продавцов» —
  когда будет образец, см. вопросы).
- **Расчёт** (раздел 5.5): ряд net-спроса (выкуплено − возвращено), дни без остатка исключаются;
  плоское сглаживание с подбором α; σ ошибки прогноза; оптовые всплески срезаются до порога;
  `страховой = z·σ·√L`, `точка заказа = d·L + страховой`, пополнение до уровня точки заказа.
- **Две страницы** с Excel-выгрузкой (раздел 6): поставка на FBO с полем «Подтверждено к поставке»
  (пустое по умолчанию) и действием «Собрать поставку» — только заполненные строки, тот же формат
  файла; закупка у поставщика по сумме всех каналов, с блоком «без пополнения» и отметкой «заказано».
- **Главная**: даты срезов, итог каждого шага цикла, ручной запуск, параметры расчёта.

## Попробовать на тестовых данных

```bash
cd awer_forecast
python -m venv .venv && .venv/bin/pip install -r requirements.txt      # Windows: .venv\Scripts\pip
.venv/bin/python -m forecast demo --serve                                # http://127.0.0.1:8010, demo / demo
```

Демо собирает `demo/demo.db`: выдуманный ассортимент AWER (6 моделей, 28 размеров, часть баркодов на
Lamoda отличается от 1С), 120 дней продаж с дефицитом и возвратами, поставка FBO в пути, файл остатков
1С и файл розничных продаж. Всё проходит через настоящий код: импорт карты, клиент Lamoda (поверх
имитации API без сети), разбор файлов 1С, расчёт, страницы.

## Установка на сервер

1. Python 3.11+; `python -m venv .venv`, `.venv\Scripts\pip install -r requirements.txt`.
2. `.env` из `.env.example`: база, `FORECAST_SESSION_SECRET`, ключи Lamoda, каталоги 1С.
   PostgreSQL по ТЗ — `postgresql+psycopg://…`; если на Windows-сервере PostgreSQL нет, на старте
   хватит SQLite-файла (так работает Sync Admin).
3. `python -m forecast set-password` → строку `FORECAST_PASSWORD_HASH=…` в `.env`.
4. `python -m forecast migrate` — схема.
5. `python -m forecast import-catalog карта.xlsx` — справочник (или на странице «Справочник»).
6. `python -m forecast daily` — первый цикл. Первый опрос заказов тянет историю за
   `LAMODA_ORDERS_BACKFILL_DAYS` (по запросу на заказ — это долго, но один раз).
7. Страницы: `python -m forecast serve --host 0.0.0.0 --port 8010` (служба — через NSSM, как у Sync Admin).
8. Ежедневный цикл — задача Планировщика Windows на `python -m forecast daily`, например в 06:30,
   после утренней выгрузки остатков 1С.

**База на сервере — сразу в `BACKUPS.md`** (правило репозитория): при установке добавить копию в
`selectel:awer-backups/awer_forecast` (снимок SQLite через `Connection.backup()` или `pg_dump`).

## Решения владельца (21.10.2026)

1. **Продажи двух магазинов есть в 1С**, их уже выгружает отдельная обработка для «бота план продавцов».
   Читать будем её выгрузку, а не заводить новую команду в `ОбменССайтом` — нужен образец файла.
2. **Спрос WB, Ozon и сайта — из 1С**, не из API площадок. Это заменяет «постоянные потоки WB/Ozon»
   из Фазы 3 ТЗ. Lamoda — только из API: её продажи в данных 1С не учитываются (канал `lamoda` в
   выгрузке 1С отклоняется), иначе спрос задвоится. Перемещения на склад Lamoda — не продажа.
3. **Отгрузку на FBO в 1С списывают с ЦС после создания поставки в Lamoda.** Значит, пока поставка
   не доехала до склада Lamoda, её товар виден и в поставке, и в остатке ЦС. Расчёт это учитывает
   (ниже, «Как считается»).

## Ежедневный цикл

| Шаг | Откуда | Куда |
|---|---|---|
| `lamoda_catalog` | `GET /v2/nomenclatures` | `product_sizes.lamoda_sku`, `product_models.lamoda_sku`, `barcode_pool.seller_sku` (только пустые) |
| `lamoda_stocks` | `GET /v2/fbo/stocks?withZeroQuantity=true` | `stock_fbo` (снимок на день, по складам) |
| `lamoda_shipments` | `GET /v2/fbo/shipments`, `…/{id}/items` | `fbo_shipments` — «в пути на FBO» = план − принято |
| `lamoda_orders` | `GET /v2/orders?updatedAtFrom=…` + `GET /v2/orders/{id}` | `order_items` (курсор — в `job_runs`) |
| `onec_stock` | свежайший `stock_*.txt` в `ONEC_EXCHANGE_DIRS` | `stock_1c` (размеры, которых нет в файле, — 0) |
| `onec_sales` | `sales_*.txt` в `ONEC_SALES_DIR` | `channel_sales_daily` |
| `recalc` | всё выше | `sales_daily`, `demand_timeseries`, `demand_forecast`, `central_stock_aggregate_demand`, `reorder_points`, `lead_time_stats`, рекомендации |

Сбой шага не останавливает остальные; пересчёт идёт по последним данным, даты срезов видны на страницах.

## Как считается

- **Спрос Lamoda** = позиции `DELIVERED` − возвраты (первая строка позиции в статусе `REFUND_NECESSARY` /
  `READY_TO_REFUND` / `REFUNDED` / `REFUND_BY_PARTNER`, если её выкуп мы видели). Ряд начинается с первого
  дня продажи или ненулевого остатка FBO, кончается вчера.
- **Цензурирование (минимальное)**: день, когда в срезе остаток 0 и продаж нет, из обучения исключается.
- **Прогноз**: SES, α из {0,05…0,5} по минимуму ошибки; меньше 14 дней истории — среднее, σ не ниже √среднего.
- **Выбросы**: день с продажами выше «среднее ненулевых + 3·max(σ, √среднего)» срезается до порога до сглаживания.
- **FBO**: `L = срок поставки на FBO (медиана наших поставок, иначе PLAN_FBO_LEAD_DAYS) + пересмотр`;
  к отгрузке = ⌈точка заказа⌉ − (FBO + в пути), не больше доступного на ЦС. Доступно = остаток ЦС −
  резерв − собранное у нас − товар поставок Lamoda, ещё не списанный в 1С. Затухающие/снятые модели
  и капсулы — 0 с пояснением. Строки — только где остаток ЦС > 0.
- **Ещё не списано в 1С** — поставка Lamoda в статусах до прибытия на склад: `DRAFT`, `NEW`, `SENT`,
  `VALIDATION`, `VALIDATION_ERROR`, `CONFIRMED`, `READY_FOR_SHIPMENT`, `CHANGING_WAREHOUSE`
  (`PLAN_FBO_STATUSES_ON_CS`). С `UNLOADING_NEEDED` и дальше товар считается списанным с ЦС.
- **Закупка**: спрос всех каналов (Lamoda из API + магазины, WB, Ozon, сайт из 1С), σ = √Σσ²;
  `L = производство + доставка поставщика + пересмотр`; есть = ЦС + FBO + в пути (без того, что ещё
  числится на ЦС) + заказано. Недоступные к заказу — блок «без пополнения»; MOQ проверяется по сумме
  модели (предупреждение, количество не раздувается).
- **Подтверждённое не теряется**: пересчёт переносит «подтверждено» в новую партию; собранное в поставку
  считается «в пути» (и вычитается из доступного на ЦС), пока в Lamoda не появится поставка с этим размером.

Достоверность % — пока заглушка «—» (Фаза 4, раздел 5.8).

## Отличия от schema.sql (миграция 0002)

- `order_items.lamoda_item_id` BIGINT → TEXT: в API v2 `items[].id` — строка. Плюс `lamoda_sku`,
  `external_sku` — чтобы позицию, не сопоставленную сразу, привязать после пополнения справочника.
- `fbo_shipments`: `qty_accepted`, `warehouse_code`.
- `shipment_recommendations`: `batch_id`, `confirmed_by`, `confirmed_at`, `assembly_id`; статус `superseded`.
- `purchase_recommendations`: снимок входов расчёта, `explanation`, `ordered_*`; статусы `no_reorder`, `superseded`.
- Новые: `job_runs` (журнал заданий и курсор опроса), `channel_sales_daily` (дневные продажи не-Lamoda
  каналов по баркоду — в schema.sql такой таблицы нет).

Тест `test_schema.py` сверяет модели со schema.sql и падает на любом необъявленном отличии.

## Допущения Фазы 1 (открытые вопросы ТЗ, раздел 9)

- №4 статусы: продажа — `DELIVERED`; возврат — группа REFUND_* (без `REFUND_INVESTIGATION`);
  `NOT_BOUGHT`/`NOT_DELIVERED`/`CANCELED` — не продажа. Незнакомый статус сохраняется и в спрос не идёт.
- Дата события позиции — день последнего обновления заказа (по Москве): точной даты смены статуса
  позиции в ответе нет. Уточнить в Фазе 2 через `/v2/orders/{id}/item-statuses` или вебхуки.
- Единый уровень сервиса z = 1,65 и пересмотр 7 дней для всех — до ABC×XYZ (Фаза 2).
- Граница «списано с ЦС в 1С» — по статусу поставки Lamoda (см. выше): если в 1С списывают раньше
  прибытия (например, в день отгрузки машины), на день-два доступное на ЦС будет занижено, а потребность
  в закупке — завышена на объём поставки. Поправляется списком статусов в `.env`.
- Lamoda-заказ в «в пути к клиенту»/«от клиента» в прогноз остатка не входит (раздел 5.5 — Фаза 2).
- Штраф Lamoda за корректировку поставки > 15% — не реализован (нужен план поставки, Фаза 2).

## Что не проверено

- **Клиент Lamoda против живого API.** Методы и поля сверены с официальной OpenAPI-спецификацией
  (`docs/lamoda/`), пути проверены без ключей (401 на существующие, 404 на несуществующие), формат ошибки
  совпал. С настоящими `client_id/client_secret/sellerId` — ни разу. Первый запуск — по шагам
  (`python -m forecast run lamoda_catalog`, затем `lamoda_stocks`, …) с просмотром сводок на главной.
- **Формат продаж 1С** — предложенный, у обработки такой команды нет.
- **Работа на Windows-сервере** (службы, Планировщик, пути) — не разворачивалась.
- PostgreSQL проверен на 16 в Linux; на Windows не проверялся.

## Вопросы по 1С (нужны образцы)

1. **Выгрузка для «бота план продавцов»**: пришлите образец файла (пару дней продаж хватит) и скажите,
   куда обработка его кладёт и как часто. Есть ли в нём баркод — или только артикул, размер и цвет?
   Магазин указан отдельно в каждой строке?
2. **Попадают ли в эту выгрузку WB, Ozon и сайт?** Если нет — они видны в 1С только перемещениями
   Sync Admin (`ЦС → WB.Ожидает → Склад WB`). Тогда нужна выгрузка этих перемещений
   (дата, баркод, количество, склад площадки) — её можно добавить в ту же обработку или в `ОбменССайтом`.
3. **Когда именно списывают отгрузку на FBO**: в день отгрузки машины, при создании поставки или после
   приёмки Lamoda? Сейчас считаем, что до прибытия на склад Lamoda товар ещё в остатке ЦС.
4. Пришлите Excel-карту мэппинга (хотя бы шапку и пару строк): проверю распознавание колонок.

Пока образца нет, принимается формат `sales_<с>_<по>_<метка>.txt` со строками
`дата(ГГГГММДД)|баркод|количество|сумма_руб|канал`, где количество < 0 — возврат, а канал — `retail_1`,
`retail_2`, `wb`, `ozon`, `own_site` (`lamoda` отклоняется).
