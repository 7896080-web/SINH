# Аудит ТЗ прогнозирования спроса и схемы БД

Дата: 25.09.2026. Предмет: `tz_lamoda_forecast.md` и `lamoda_forecast_schema.sql` (исходная версия — первый
коммит этой папки, исправленная — следующий; `git diff` между ними показывает каждое изменение).

**Как проверялось.** ТЗ прочитано целиком и сверено с самим собой (формулы, ссылки между разделами, имена
таблиц и полей), со схемой БД и с кодом sync-admin в этом репозитории (`app/models.py`,
`app/workers/ftp_channel.py`, `app/workers/platform_clients/`). Схема загружена в PostgreSQL 16 до и после
исправлений; ограничения проверены вставками (`schema_smoke_test.sql`: каждая «ожидаем ОШИБКУ» падает, остальные
проходят). Найденные в исходной схеме дефекты A-02, A-03, A-06, A-07 воспроизведены на реальной базе, не выведены
из чтения.

**Чего аудит не проверял.** Реальные ответы API Lamoda v2, WB, Ozon, KIT (ключей нет) — всё, что сказано о
форматах ответов, взято из ТЗ и документации. Численные значения по умолчанию (пороги XYZ, WAPE, перцентиль
цензурирования, порог прогноза по размеру) — обоснованные стартовые, калибруются на первых данных.

Номер `A-xx` встречается в комментариях схемы и в тексте ТЗ там, где сделано исправление.

## 2. Методические — формально работает, но результат бесполезен при наших объёмах

При ~50-100 заказах в день на 1000-3000 размеров средний размер продаётся примерно раз в месяц.

## Решения, принятые аудитом, — стоит подтвердить

Это не исправления очевидных ошибок, а выбор одного из вариантов. Каждый легко откатить.

1. **Иерархический прогноз** (A-30) — порог 30 продаж за 180 дней.
2. **Недельные корзины** для SBC и XYZ, пороги XYZ 25/50% (A-28, A-31).
3. **WAPE вместо MAPE** для статусов, пороги 30/60% (A-08).
4. **Цены на уровне модели** (A-24) — если на Lamoda у вас есть товары с разной ценой по размерам, решение нужно пересмотреть.
5. **Себестоимость выгружается в USD**, переоценка на нашей стороне (A-01). Что доп. расходы внутри — подтверждено; USD — ещё подтвердить.
6. **Резерв под подтверждённую поставку через `products.reserve`** sync-admin (A-09) — требует небольшой доработки sync-admin (снятие резерва по факту списания).
7. **Защита остатка ЦС** при отгрузке на FBO (A-14) — FBS-каналы получают приоритет над пополнением FBO. Если приоритет должен быть у Lamoda — меняется одно слагаемое.

тестового адреса Lamoda v2 пока нет; KIT API проверен и используется; **в 1С хранится многолетняя история продаж,
