# Схема системы: блоки, потоки данных, цикл изменений

## 1. Общая схема — четыре слоя
1. **Источники данных.**
   - Яндекс: Директ, Метрика (счётчик 110246968), Вебмастер, Яндекс Доставка, AWER CRM (`kitcrm.db`, только чтение).
   - Wildberries: API «Продвижение», «Аналитика» (с «Джемом»), «Статистика», «Финансы».
   - Данные пользователя: `wb_cost.csv` (себестоимость), `wb_watch.csv` (свои запросы), `RULES` в `wb_bids.py`.
2. **Токены.**
   - Яндекс — из `~/AWER CRM/config.json` через `yandex_token.py`.
   - Яндекс Доставка — `yandex_delivery_token.txt`.
   - WB — `wb_tokens.txt` («Название кабинета = токен»).
   - Claude Code эти файлы читать не может: запрет в `.claude/settings.json`. Скрипты читают их сами.
3. **Отчёты** — только чтение, в кабинетах ничего не меняют, запускаются без подтверждения:
   - `direct_check`, `direct_before_after`, `metrika_*`, `webmaster_report`, `yandex_delivery_report`;
   - `wb_positions`, `wb_daily`, `wb_unit`, `wb_queries`, `wb_ads_report`.
4. **Изменения** — пишут в кабинеты, только по циклу из раздела 3:
   - Директ: `direct_stage1`, `direct_age_45_54`, `direct_awer_jackets`;
   - WB: `wb_bids` (автопилот), `wb_create`.

Между отчётами и изменениями решение принимает пользователь вместе с Claude Code. Изменения попадают в кабинеты,
следующий отчёт показывает результат.

## 2. Wildberries — как блоки передают данные друг другу
```
Финансы WB (отчёт реализации) ─┐
wb_cost.csv (себестоимость) ───┴─► wb_unit.py ─► wb_unit_economics.csv («лимит цены заказа»)
                                                     ├─► wb_bids.py (max_cost_per_order: "auto")
                                                     └─► wb_daily.py (прибыль, окупаемость рекламы)
Поиск WB («Джем», запросы) ─► wb_queries.py ─► wb_queries_actions.csv ─► wb_daily.py
«Джем» + воронка + реклама ─► wb_positions.py ─► wb_history.db (история)
                                                 ├─► wb_positions_actions.csv ─► wb_daily.py
                                                 └─► wb_positions.html (графики)
Реклама WB (ставки, рекомендации, кластеры) ─► wb_bids.py ─► кабинеты WB (ставки, минус-фразы, лимиты)
                                                  └─ wb_bids_state.json, wb_bids_backups\, wb_bids_log.txt
```
- **`wb_unit.py`** — главный ограничитель: сколько можно отдать рекламе за заказ, чтобы оставаться в плюсе
  (с учётом выкупа). Пока себестоимость не заполнена, берётся 37% от цены.
- **`wb_positions.py`** — ежедневная история.
  - Что хранит: медианная и средняя позиция товара и кабинета, позиции по каждому запросу, свои запросы,
    воронка по дням, рекламная позиция и расход.
  - Сигналы с причинами (остатки, доставка, цена, рейтинг, реклама).
- **`wb_queries.py`** — раз в неделю.
  - Деление запросов на ВЧ, СЧ и НЧ.
  - Действия по запросам: минус-фраза, поднять ставку, не покупать ВЧ, кандидат «за показы», SEO.
- **`wb_daily.py`** — утренний итог.
  - Вчера против недели, остатки.
  - «Что сделать сегодня»: собственные пункты плюс пункты из `wb_queries` и `wb_positions`.
- **`wb_bids.py`** — новая ставка = минимум из трёх величин, но не ниже минимальной ставки WB:
  - рекомендованная ставка WB;
  - окупаемая ставка: лимит цены заказа × конверсия;
  - абсолютный потолок.
  
  Дополнительные правила:
  - не больше +30% в сутки (от ставки на начало дня);
  - товар без остатка (склады WB + свой склад FBS) → минимальная ставка;
  - в наличии размеры меньше чем на 30% спроса → минимальная; меньше 60% → не повышать, без автоминуса;
  - трогает только кампании из `RULES`.

## 3. Цикл изменений: пробный прогон → «да» → `--apply` → `--rollback`
1. **Пробный прогон** — запуск без флагов. Показывает, что изменится (старое → новое и почему); в кабинете
   ничего не меняется.
2. **Подтверждение.** Пользователь читает план. Claude Code запускает `--apply` только после явного «да»:
   так настроено в `.claude/settings.json`, так же работает навык `/wb-autopilot`.
3. **`--apply`.**
   - Сначала резервная копия: `direct_backups\` — `backup_*`, `age4554_*`, `awer_jackets_*`; `wb_bids_backups\bids_*.json`.
   - Потом изменения.
   - Директ после изменения перечитывает кабинет; `wb_bids` пишет итог в `wb_bids_log.txt`.
   - `wb_bids --apply` **пересчитывает план заново**, поэтому цифры могут немного отличаться от пробного прогона.
4. **`--rollback`** — возвращает прежние значения по последней резервной копии этого скрипта.

**Ограничения отката (проверено по коду 11.10.2026) — предупреждать пользователя:**
- Откатывается **только последний запуск**. Повторный `--rollback` не уходит дальше назад, а повторяет тот же
  откат. При автопилоте 3 раза в день можно вернуться только на один запуск назад.
- Откат применяется **сразу, без пробного прогона**.
- Откат ставит значения «как было до запуска» и **перезаписывает ручные изменения**, сделанные после запуска.
- **`direct_stage1.py --rollback` затронет и возраст 45–54**: вернёт корректировку к состоянию до 06.10,
  и текущие −20% пропадут. Если откатывать оба, порядок обратный: сначала `direct_age_45_54.py --rollback`,
  потом `direct_stage1.py --rollback`.
- **У `wb_create.py` отката нет.** Созданная кампания не тратит деньги, пока её не запустить (`--start ID --apply`),
  остановить — `--pause ID --apply`. Без `--apply` запуск, пауза и пополнение бюджета только показывают, что будет.

**Защиты, добавленные 11.10.2026 (проверены на имитации API):**
- Директ: если менять нечего, `--apply` ничего не делает и **не создаёт резервную копию** — иначе она стала бы
  «последней», и откат к прежнему состоянию был бы потерян. `direct_stage1.py` теперь хранит −20% для 45–54.
- `direct_stage1.py --rollback` **не трогает стратегию**, если её тип с тех пор сменился (после этапа 2) —
  чтобы не сбросить обучение; бюджет в этом случае вернуть вручную.
- `direct_awer_jackets.py` пишет резервную копию до изменений. Папка `direct_backups` — всегда рядом со скриптами.
- `direct_age_45_54.py` не принимает число без знака («20» → ошибка, нужно `-20` или `+20`).
- `wb_bids.py --apply` **ничего не меняет**, если не загрузились статистика кампаний, статистика запросов или остатки.
- `wb_bids.py` не пишет минус-фразы товару, по которому WB не вернул текущий список (иначе запись стёрла бы его).
  Если в пробном прогоне видно «WB не вернул текущие минус-фразы» по всем товарам — разобраться до `--apply`.
- Откаты `wb_bids.py` записываются в `wb_bids_log.txt`.
- `wb_bids.py`: рост ставки — не больше +30% **в сутки** от ставки на начало дня (хранится в `wb_bids_state.json`),
  а не за запуск: три запуска в день больше не дают ×2,2. Пробный прогон состояние не меняет.
- `wb_bids.py`: автоминус по товару — только после 14 дней подряд на складах WB (`MINUS_AFTER_RESTOCK_DAYS`);
  слова «не наша аудитория» — сразу. При `"auto"` предупреждает, если юнит-экономики нет, ей больше 14 дней
  или себестоимость в ней — оценка.
- `wb_unit.py --cabinet` не стирает строки других кабинетов в `wb_unit_economics.csv`; `wb_cost.csv` дописывается,
  введённая себестоимость не теряется. Пустой результат отчёта перезаписывает CSV пустым (только заголовок) —
  старые данные не выдаются за новые; `wb_daily.py` не берёт пункты из `wb_queries_actions.csv` старше 8 дней.
- Возможная доработка (предложена пользователю, не сделана): откат автопилота на несколько запусков назад или
  на дату с предварительным показом.

**Автоматический режим.** Когда `wb_bids --apply` идёт по расписанию, подтверждать каждый запуск некому.
«Подтверждением» становятся правила `RULES`, утверждённые один раз:
- максимальная цена заказа;
- потолки ставок;
- не больше +30% в сутки;
- дневной лимит.

Расписание включать только после нескольких дней ручных пробных прогонов.

## 4. Роли кампаний WB для одних и тех же товаров
- **№1. Поиск, ручная ставка, оплата за клики** — основная кампания (27643, 36446): ставки на позиции 3–10
  не дороже окупаемого, автоминус-фразы, дневной лимит.
- **№2. Рекомендации, ручная ставка, оплата за показы** — те же товары, только рекомендации. Если окупаемая ставка
  ниже минимальной WB две недели подряд — выключить.
- **№3. Поиск, оплата за показы** — этап 2, только при стабильном остатке на WB.
  - Ставки на 10 запросов, которые приносят больше всего заказов в №1; эти запросы уходят в минус-фразы №1
    (`route_from`).
  - Если запрос в №3 окупается хуже, он автоматически возвращается в №1 на 30 дней.
- Правило: на один товар в одной зоне и по одному запросу ставит **одна** кампания.

## 5. Расписание
- **Каждое утро:** `wb_positions.py` (5–15 мин), затем `wb_daily.py`.
- **3 раза в день:** `wb_bids.py --apply` — после нескольких дней ручных проверок.
- **Раз в неделю:** `wb_queries.py`, `wb_ads_report.py 7`.
- **Раз в 1–2 недели:** `wb_unit.py`.
- Команды Планировщика заданий Windows — в `docs/wb-history.md`.
