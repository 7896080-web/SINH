# Статус готовности (актуально, 2026-09-16)

Скорректированный «честный» список — прежний устарел (п.1 и п.3 фактически выполнены).

## 1. HTTP-клиенты площадок на живых ключах — ✅/⚠️ (было: «не проверены»)
- **WB — ✅ проверено на живых ключах.** Реально тянет заказы (520 / 244 / 55 по трём кабинетам),
  историческая выборка `get_orders_since` вернула корректные заказы с датами, `push_stock`
  отрабатывал, бэкфилл создал реальные документы.
- **Kit — ✅ с оговоркой.** Тянет (154 заказа), но ловит `429` (rate limit) → нужен троттлинг.
- **Ozon — ⚠️ не подтверждено.** Эндпоинт отвечает, но вернул 0 заказов → разбор ответа на
  непустых данных не проверен. Нужен кабинет Ozon с FBS-заказами.
- Старый комментарий-предупреждение в `base.py` устарел для WB/Kit.

## 2. Детект «заказ подтверждён» (Впути → Склад) — не требуется при Варианте А
Под текущей моделью (Вариант А) резерв сразу в основном складе площадки
(`warehouse_pending == warehouse_sold`), отдельное перемещение «Ожидает → Склад» намеренно не
создаётся (`process_confirmation` его пропускает). Пункт **не блокирует прод**. Заполнять
`get_confirmed_orders` для WB/Ozon (у Kit уже есть) понадобится только при переходе на
двухшаговую схему.

## 3. Backfill «задним числом» — ✅ реализовано (было: «не реализовано»)
- Через «Дату начала» на /testing → `get_orders_since` тянет реальные FBS-заказы с даты →
  каждый проводится **своей реальной датой** (`FtpTask.movement_date` → 8-е поле → `.epf`).
- `broadcast_active_since` наш бэкфилл **не использует** (оператор задаёт дату вручную). Поле
  осталось неиспользуемым — связать или убрать как устаревшее.
- Проверено: проведено 8 по LACIVERT/RED, фильтр по баркоду точный.

## 4. Автозапуск .epf по расписанию — способ согласован и настроен
Пакетный `1cv8 ENTERPRISE … /CEXCHANGE`, `ПриОткрытии` привязан в палитре, задача в Планировщике
Windows; нужна интерактивная сессия. Осталось — подтвердить стабильность срабатывания.
