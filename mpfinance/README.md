# Финансы площадок

Отдельная программа рядом с Sync Admin и «Репрайсером». Отчёты WB, Lamoda и
Яндекс KIT приводятся к единой форме. По ним считаются юнит-экономика и
дашборды по площадкам и делается сверка. Отчёты о продажах загружаются в 1С.

Своя база, свой вход, свои ключи площадок, своя служба Windows. Sync Admin
программа не трогает: его базу только читает, ради мэппинга баркодов и
принятых заказов.

## Откуда данные

| Площадка | Источник | Что это |
| --- | --- | --- |
| Wildberries | finance-api по токену с категорией «Финансы» | Официальные еженедельные отчёты реализации (тот же отчёт, что в кабинете) и их «Итого к оплате» |
| Wildberries | файл детализации из кабинета | То же, если API нет |
| Яндекс KIT | API заказов | Финансового отчёта у KIT нет. Продажи за период собираются из официальных данных заказов: доставлено минус отказы, стоимость доставки |
| Яндекс KIT | база AWER CRM на этом же сервере (`C:\awer_crm_data\kitcrm.db`, только чтение) | Продажи сайта раз в сутки, по календарным неделям, за 4 полные недели: выполненные заказы, дата — вручение, отказы при получении не считаются, комиссия (3,5%, настройка) вычитается. То же правило, что у выгрузки CRM, но дата у заказа без вручения не «кочует» (см. ниже) |
| Яндекс KIT | файл «Продажи» из AWER CRM (`sales-items-…xlsx`) | То же файлом, если базы CRM не видно. Строка — одна штука. «Сумма» — до комиссии; комиссия вычитается при загрузке. Период берётся из имени файла |
| Яндекс KIT | API заказов, поле `seller_costs` | Доставка для продавца. Когда продажи KIT берутся из AWER CRM (настройка по умолчанию), загрузка по API берёт из заказов только доставку |
| Lamoda | почта (b2b@lamoda.ru) | Еженедельный отчёт: предварительные продажи по неделям |
| Lamoda | файл или письмо | Отчёт комиссионера, итоговый документ. Предварительные данные за его период заменяются им (коррекция) |
| Lamoda | почта или файл | Партнёрский отчёт («Lamoda Sales Report - AWER ….xlsx»): НЕ продажи, а справочник «артикул Lamoda → EAN». По нему строки недельного отчёта (там EAN нет) находят товар 1С |
| Wildberries | API тарифов (`common-api …/tariffs/commission`), раз в сутки | Текущая комиссия WB по предмету (FBS и FBO) — в юнит-экономике рядом с фактически удержанной |
| любая | шаблон единой формы | Отчёт, который программа не умеет читать сама |

Себестоимость берётся из 1С (регистр «Себестоимость номенклатуры», в долларах)
и переводится в рубли по курсу ЦБ на дату продажи. Её можно задать и вручную
через Excel. Ручная цена приоритетнее, выгрузка из 1С её не перебивает.

## Страницы

- **Дашборд площадок**: выручка, к перечислению, прибыль по площадкам, динамика,
  лучшие и убыточные артикулы.
- **Отчёты площадок**: загрузка файлом, загрузка по API, продажи сайта из
  AWER CRM («Забрать из CRM»), журнал загрузок.
  На странице отчёта: сверка денег, сверка с заказами Sync Admin, товары без
  1С, отправка в 1С.
- **Сверка со сводом WB**: список отчётов WB (из API или файлом из кабинета)
  против загруженных. Видно, какие не загружены, у каких сходится и у каких
  расходится итог, по каким статьям. У каждого ИП свой кабинет WB и свой свод:
  отбор по кабинету и юрлицо в строке. Отдельно — загруженные отчёты, которых
  нет ни в одном своде (обычно отчёт другого кабинета, чей свод не загружен).
- **Юнит-экономика**: по артикулу или SKU; комиссия, логистика, хранение,
  себестоимость, налог, прибыль, маржа, ROI.
- **Себестоимость**: Excel туда и обратно, запрос себестоимости из 1С; там же
  настройки расчёта (налог, доп. расходы, склады 1С, ручной курс, откуда
  продажи KIT и комиссия AWER CRM).
- **API-ключи**: кабинеты, токены, кнопка «Проверить доступ», связь с кабинетом
  Sync Admin, почта для отчётов Lamoda.
- **Диагностика**: версия обработки 1С, справочник баркодов, задания 1С, фон,
  журнал действий.

## Шкала прогресса

У каждой кнопки есть шкала. При загрузке файла видны проценты отправки, потом
ход разбора на сервере (строки, запись, сопоставление баркодов). Выгрузки в
Excel скачиваются с процентами. Фоновые дела показываются полосой над каждой
страницей, пока идут, и итогом, когда закончились: загрузка WB по API (по
отчёту в минуту, с оценкой оставшегося времени), загрузка KIT, задания 1С и
отчёты, отправленные в 1С.

## 1С — последним этапом

Обмен с 1С **по умолчанию выключен**. Программу сначала проверяют и отлаживают
без 1С. Пока обмен выключен, программа не пишет в папки обмена `C:\sync` и не
заглядывает в них. Справочник товаров (баркоды из 1С) она берёт из базы Sync
Admin, раз в сутки и кнопкой на «Диагностике». Себестоимость в это время
вносится через Excel.

Подключение 1С, когда программа проверена:

1. Обновить обработку «ОбменССайтом» до **mark-4**: модуль
   `1c/ОбменССайтом_МодульОбъекта.txt` переносится в Конфигураторе, как обычно.
2. «Диагностика» → «Включить обмен с 1С» → «Проверить обработку 1С». Пока
   обработка не ответила версией mark-4, программа не шлёт в 1С ничего, кроме
   этой проверки.

Как устроен обмен: задания `task_fin_*.txt`, ответы в `C:\sync\results\finance`.
Протокол описан в `1c/README.md`, раздел «Финансы площадок».

- По отчёту в 1С уходят **баркод, количество и сумма к перечислению продавцу**
  и только по кнопке «Отправить в 1С» на странице отчёта.
- Баркод для 1С. Товар ищется по «Мэппингу» Sync Admin, затем по справочнику
  баркодов. В 1С уходит баркод, прописанный у этого товара в самой 1С.
- Еженедельные отчёты Lamoda в 1С не уходят: в них нет баркодов и возвратов.
  В 1С уходит отчёт комиссионера.

## Установка на сервер

Всё — PowerShell **от администратора**.

1. Скопировать на сервер пакет `mpfinance_finN.ps1` и запустить:
   `powershell -ExecutionPolicy Bypass -File <путь>\mpfinance_finN.ps1`.
   Он раскладывает файлы в `C:\mpfinance`.
2. Первая установка:
   `powershell -ExecutionPolicy Bypass -File C:\mpfinance\deploy\install_server.ps1`.
   Скрипт создаёт venv, `.env` со своими ключами, миграции, прогоняет тесты,
   заводит первого пользователя, ставит службу `mpfinance` на `127.0.0.1:8003`
   и ярлык «Финансы площадок» со своим значком (круговая диаграмма,
   `deploy\mpfinance.ico`; рисует его `scripts/gen_icon.py`). Обновление
   пересоздаёт ярлык тоже; отдельно — `deploy\create_shortcut.ps1`.
3. Обновление: новый пакет, затем
   `powershell -ExecutionPolicy Bypass -File C:\mpfinance\deploy\update_server.ps1 -Tag finN`.
   По порядку: копия базы, миграции, тесты, перезапуск, проверка фона.

`MPFIN_SECRETS_KEY` из `C:\mpfinance\.env` — ключ шифрования токенов площадок.
Храните его отдельно от копий базы.

## Копии и восстановление

Копия базы снимается раз в сутки в `C:\mpfinance\backups` (и накатом перед
миграциями). Вторая площадка — облако Selectel, тот же бакет, что у других
программ сервера, своя папка. Подключение один раз:

1. Конфиг rclone для программы — копией конфига Sync Admin (ключ тот же):
   `Copy-Item C:\sync_admin\rclone.conf C:\mpfinance\rclone.conf`
2. «Диагностика» → «Вторая площадка копий» → «Путь в облаке»:
   `selectel:awer-backups/mpfinance` → «Сохранить» → «Выгрузить копию сейчас».
   Программа выгружает копию и проверяет, что в облаке лежит файл того же
   размера. Дальше — каждые сутки сама; «давно не было» карточка подсвечивает.

Восстановление (служба остановлена, PowerShell от администратора):

```powershell
nssm stop mpfinance
C:\mpfinance\.venv\Scripts\python.exe C:\mpfinance\scripts\restore_db.py --list
C:\mpfinance\.venv\Scripts\python.exe C:\mpfinance\scripts\restore_db.py C:\mpfinance\backups\mpfinance-ГГГГММДД-ЧЧММСС.db
nssm start mpfinance
```

Из облака — `restore_db.py --from-cloud mpfinance-ГГГГММДД-ЧЧММСС.db`. Скрипт
проверяет копию до того, как что-то тронуть, сохраняет текущую базу рядом
(`.before-restore-…`), убирает `-wal`/`-shm` (иначе SQLite наложил бы их
страницы поверх копии) и проверяет базу после замены. Ключ `MPFIN_SECRETS_KEY`
должен быть тем же, что при снятии копии.

## Первый запуск: что проверить

1. «Диагностика» → «Обновить справочник из Sync Admin». Должны появиться
   баркоды и товары. Обмен с 1С пока не включать.
2. «API-ключи»:
   - завести кабинет WB, вписать токен с категорией «Финансы», нажать
     «Сохранить и проверить доступ»;
   - связать кабинет с кабинетом Sync Admin;
   - то же для KIT;
   - кабинет Lamoda и почта: IMAP-сервер, адрес, пароль приложения.
3. «Себестоимость» → «Настройки»: склады 1С по площадкам. У Lamoda склад по
   умолчанию пустой, в базе он заведён как «Lamaoda_Склад».
4. «Отчёты площадок» → загрузка WB по API за 2–3 недели. Затем «Сверка со
   сводом WB»: итог строк должен сойтись с «Итого к оплате» WB.
5. Lamoda: отчёт комиссионера (файлом) и недельные письма. Предварительные
   данные за месяц должны замениться официальными.
6. Последним этапом — 1С (раздел выше). Первый отчёт в 1С: открыть созданные
   документы, сверить с отчётом и только потом проводить. По умолчанию
   документы создаются непроведёнными.

## Что НЕ проверено на живом

- WB finance-api и заказы KIT на живых токенах. Методы и поля взяты из
  официальных спецификаций; первую загрузку нужно сверить с кабинетом.
- Документы продаж в 1С (`SALES_REPORT`): имена документов и реквизитов в
  модуле помечены `// НАСТРОИТЬ:` и с базой не сверены.
- Почта: проверена на поддельном IMAP-сервере. Нужен настоящий ящик, куда
  приходят письма b2b@lamoda.ru.
- AWER CRM: «Номер заказа» — номер для покупателя, а Sync Admin хранит заказы
  KIT по внутренним id, поэтому сверки отчёта CRM с заказами Sync Admin по
  номеру нет (страница отчёта так и пишет).
- AWER CRM, автозагрузка из базы. Правило отчёта восстановлено по базе CRM
  (копия от 18.10.2026) и сверено с девятью её выгрузками: сентябрь — 49 штук,
  309 950 ₽, совпадает до даты каждой строки; июль–сентябрь целиком — 221 штука,
  917 892 ₽, итог тот же. Одно намеренное отличие: заказу без даты вручения и
  без истории статусов CRM ставит дату СВОЕЙ последней записи, и при каждой
  пересинхронизации он переезжает в другой месяц (сентябрь от 30.09 — 367 714 ₽,
  тот же сентябрь от 18.10 — 309 950 ₽). Программа берёт время изменения заказа
  в самом KIT, и такие 13 летних заказов ложатся в июль и август. Поэтому июль
  и август из базы больше, чем в файлах CRM, — на эти заказы. Схема CRM
  сверяется при каждом чтении: новая версия CRM без нужной колонки даст отказ с
  её именем, а не пустой отчёт.
- Одни и те же продажи вторым отчётом не ложатся: выгрузка CRM файлом поверх
  загрузки из базы (и наоборот), месячный файл поверх недельного, продажи из API
  KIT поверх CRM. Продажа узнаётся по номеру заказа, баркоду и сумме; файл с уже
  загруженными продажами не принимается (в сообщении — номера отчётов), неделя
  автозагрузки пропускается с объяснением в журнале загрузок, а отчёт, чьи
  продажи уже лежат в другом отчёте, в 1С не отправляется. Пары, лёгшие раньше,
  видны на дашборде («повтор») и на странице отчёта.
- Доставка KIT (`seller_costs`) — то, что KIT пишет в заказе; совпадает ли оно
  со счётом службы доставки, не сверено.

Разбор отчётов проверен на настоящих файлах:
- детализация WB №848966494 (читается целиком, статьи раскладываются по формуле WB);
- свод «Финансовые отчёты» WB (271 отчёт; формула «Итого к оплате» сходится
  до копейки);
- отчёт комиссионера Lamoda № CR000179664 за сентябрь 2026 (итог совпадает
  со строкой «Итого»);
- еженедельный отчёт Lamoda от 2026-10-05 (недельные суммы совпадают со
  сводкой отчёта).
- партнёрский отчёт Lamoda от 06.10.2026 (1121 артикул, у 979 есть EAN).
- продажи KIT из AWER CRM за 01–30.09.2026 (49 позиций, итог 309 950 ₽ совпадает
  со строкой «Итого:»).
