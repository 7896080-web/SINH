# Финансы площадок — инструкции для Claude Code

Отдельная программа (каталог `mpfinance/`, пакет `finapp`, на сервере
`C:\mpfinance`, служба `mpfinance`, порт 8003). Корневой `CLAUDE.md` —
про Sync Admin. Здесь его правила про деньги и 1С действуют так же, но код,
база и накат — свои. Обзор — `README.md` рядом.

## Перед любым изменением

- Тесты — дважды, в UTC и по Москве (сервер в Москве):
  ```bash
  cd mpfinance && pytest -q && TZ=Europe/Moscow pytest -q
  ```
- Изменил `finapp/models.py` → новая миграция (`alembic revision
  --autogenerate`, `DATABASE_URL` на временную SQLite и `MPFIN_SECRETS_KEY`,
  `MPFIN_SESSION_SECRET` в окружении). Проверь файл глазами и прогони
  upgrade → downgrade → upgrade и `alembic check`.
- Календарные даты — `today_local()` / `local_date_of()` /
  `local_day_start_utc()`, не `.date()` от UTC.

## Границы

- **База Sync Admin — только чтение** (`syncdb.py`, `mode=ro`). Ни записи, ни
  импорта его моделей. Схему читаем простым SQL: `barcodes`, `products`,
  `platform_accounts`, `processed_orders`.
- **1С** подключается последним этапом: выключатель на «Диагностике»
  (`settings.ONEC_ENABLED`), по умолчанию выключен. Выключен — ни одного файла
  в `C:\sync`; справочник берётся из базы Sync Admin.
- **1С** (когда включена): свои файлы `task_fin_*`, ответы в `results\finance`.
  - Пока обработка не ответила mark-4 на FIN_PING, не шлём ничего, кроме
    FIN_PING (ответ старой обработки ушёл бы в общую папку sync_admin).
  - Отчёт о продажах уходит только по кнопке и своим файлом.
  - В 1С — баркод, количество, сумма к перечислению.
  - Правка модуля 1С (`1c/` в корне репозитория) — в обоих файлах (.txt и .bsl:
    тот же текст с BOM и CRLF). Корневой `scripts/check_1c_module.py` и тесты
    Sync Admin должны оставаться зелёными: модуль общий.
- **Площадкам — только чтение** (finance-api WB, заказы KIT). Почта — только
  чтение (`readonly`, `BODY.PEEK`).
- **Lamoda**: еженедельный отчёт — предварительный, отчёт комиссионера —
  итоговый. При загрузке отчёта комиссионера предварительные строки за его
  период удаляются (`finance/lamoda.py`).
  Строка Lamoda без EAN (или с EAN не из мэппинга) ищется по справочнику
  артикулов из ПАРТНЁРСКОГО отчёта Lamoda («Lamoda Sales Report - AWER ….xlsx»,
  `lamoda.import_catalog` → `LamodaArticle`, `lamoda.ArticleBook`): полный
  артикул или короткий + размер партнёра → EAN → товар 1С. Партнёрский отчёт —
  аналитика без дат и заказов: продажи из него НЕ брать (за «7 дней» они задвоили
  бы недельный отчёт). Полный артикул из короткого и размера не собирать: у
  Lamoda это не всегда «короткий + IN + размер» («2.5XL» → «…IN25XL», джинсы —
  «…JE3234»). Запасной путь — артикул в «Мэппинге» Sync Admin
  (`importer.lamoda_sku_keys`), но 18.10.2026 на бою артикулов Lamoda там не было
  ни одного. Неотправленные отчёты со строками без товара пересопоставляются раз
  в час (`job_daily`) и сразу при приёме партнёрского отчёта.
- **Шкала прогресса** (`static/progress.js`, `finapp/progress.py`). Кнопки
  форм уходят фоном; ответ-переход для них отдаёт JSON (`progress_middleware`
  в `main.py`, стоит ВНУТРИ SessionMiddleware — иначе флеш съедается).
  Формы не отправлять через `form.submit()` (нет события submit) — только
  `requestSubmit()`; ссылки на выгрузки — с `data-download`; долгая операция в
  обработчике сообщает ход через `progress.report`. Новое фоновое дело —
  в `/progress/jobs` (`routers/progress.py`).
- **AWER CRM**: «Сумма» — до комиссии (ставка — настройка). Продажи KIT из CRM
  → загрузка KIT по API берёт только доставку (`fetch._run_kit`).
  - База CRM (`kitcrm.db`, `MPFIN_CRM_DB`) — ТОЛЬКО ЧТЕНИЕ, как база Sync Admin
    (`sources/crm.py`, `mode=ro`). Правило отчёта восстановлено по базе и
    сверено с выгрузками CRM; дату заказа без вручения НЕ брать из
    `orders.updated_at` — это время записи CRM, оно меняется при
    пересинхронизации, и продажа переезжает в другой месяц.
  - Отчёты из базы CRM — `source="crm"`, не «api»: `_drop_superseded_kit`
    удаляет неотправленные отчёты по `source`, и доставка KIT иначе сносила бы
    продажи из CRM. Доставку не трогает загрузка CRM (`keep_delivery`).
  - В архиве CRM лежат ключи (`config.json`, `rclone.conf`): присылать и брать
    в работу только `kitcrm.db`; базу с данными покупателей в репозиторий не
    класть — тесты на поддельной (`FakeCrm` в conftest).

- **Себестоимость из 1С** — строго `uid|цена` (`costs.parse_cost_file`): файл
  не того вида отвергается целиком, поля не угадываются. 18.10 справочник
  баркодов (`uid|артикул|…|цвет`), загруженный как себестоимость, дал «цену»
  из артикула и себестоимость WB 692 млрд ₽. На дашборде себестоимость больше
  цены продажи в 10 раз и больше (`SUSPICIOUS_COST_RATIO`) в прибыль не
  берётся и помечается «под сомнением».

- **Как читается детализация WB** (сверено 19.10.2026 на отчёте №848966494 до
  копейки и на своде «Финансовые отчёты» — 271 отчёт, формула сошлась у всех):
  - В «К перечислению продавцу» УЖЕ вычтено то, что мы зовём комиссией: на
    каждой строке продажи и возврата «Вайлдберриз реализовал Товар (Пр)» −
    «К перечислению» = эквайринг + ВВ без НДС + НДС с ВВ + возмещение ПВЗ.
    ВВ на продажах бывает ОТРИЦАТЕЛЬНЫМ (WB возмещает свою скидку СПП из
    вознаграждения), поэтому комиссия WB выглядит маленькой — это не ошибка.
  - Отдельно от «К перечислению» вычитаются: доставка (вкл. «Коррекцию
    стоимости доставки»), хранение, операции на приёмке, удержания (там же
    реклама WB — вычитать её ещё раз из «доп. расходов» нельзя), штрафы,
    корректировка ВВ, участие и баллы лояльности, разовое изменение срока.
    «Итого к оплате» = «К перечислению за товар» − всё это.
  - НЕ суммировать: строки «Возмещение издержек по перемещению и операционной
    обработке» и «Возмещение за выдачу и возврат товаров на ПВЗ» — у них сумма
    в своей колонке погашена отрицательными ВВ и НДС той же строки, на выплату
    не влияют (`rebill_logistic_cost` не читаем, «К перечислению» у ПВЗ — 0).
  - «Компенсация скидки по программе лояльности» (`cashbackDiscount`) — УЖЕ
    внутри «К перечислению»: в своде она «в том числе» продажи, формула итога
    её отдельно не прибавляет. Разбор до 19.10.2026 прибавлял её к компенсациям,
    и на бою семь отчётов из двадцати четырёх разошлись с «Итого к оплате» WB
    ровно на неё (116,66 / 16 / 79 ₽ — копейка в копейку с колонкой свода).
    Теперь колонка не читается; записанное убрала миграция 0009.
  - «По выкупам» — отдельные отчёты со своими продажами и доставкой, не копия
    основного. Неделя на стыке месяцев приходит двумя отчётами.
  Список отчётов из API отдаёт итоги шапки по ВСЕМ статьям — сверка по статьям
  работает и для отчётов из API (`statements.WB_SUMMARY_ALIASES`).

- **Маржинальность — от суммы К ПЕРЕЧИСЛЕНИЮ продавцу, не от выручки**
  (`Totals.margin` = прибыль / `total_payout`; решение владельца 19.10.2026).
  Выручку площадка забирает себе наполовину (у WB расходы ~52% выручки), и
  процент от выручки показывал 2,4% там, где от перечисленного — 5,1%.
  `total_payout` — то же «К перечислению», что на дашборде, и у WB это «Итого к
  оплате» свода: «К перечислению за товар» − доставка − хранение − обработка −
  прочие удержания − штрафы (и корректировка ВВ, участие и баллы лояльности,
  разовое изменение срока). Компенсация лояльности НЕ прибавляется: в своде она
  «в том числе» и уже внутри «К перечислению за товар» — с ней 48 отчётов из 273
  не сходятся с «Итого к оплате». Перечисление ≤ 0 — маржинальности нет («—»),
  а не процент от копеечной базы. Таблица «Куда уходит выручка» по-прежнему
  в долях выручки — это раскладка выручки, не маржинальность.

- **Загрузка по API — параллельно по кабинетам WB** (`fetch.run_pending`):
  дорожка на кабинет (`lane_of`), своим потоком и СО СВОЕЙ сессией базы (сессия
  не потокобезопасна); KIT и CRM — одна общая дорожка, их отчёты заменяют друг
  друга. Лимит WB — запрос в минуту на профиль продавца, у каждого ИП свой, и
  пауза в 61 с живёт в клиенте кабинета (`WbFinanceApi`), то есть по-прежнему на
  кабинет. Запись отчёта — `_store_locked`: `store_api_report` И коммит под
  общим замком; без коммита внутри замка соседний поток не видит товар 1С,
  только что заведённый `mapping._ensure_products`, и заводит его второй раз
  (UNIQUE). Новый путь записи из заявок — через `_store_locked`. Отметка
  задания из дорожек — своей сессией и не чаще раза в 20 с
  (`jobs._fetch_heartbeat`).

- **Тарифы WB по категориям** (`finance/tariffs.py`) — тем же запросом, что в
  «Репрайсере»: `GET common-api…/api/v1/tariffs/commission`, FBS —
  `kgvpMarketplace`, FBO — `paidStorageKgvp`; токен любой категории (берётся
  «Финансы» активного кабинета WB), раз в сутки из `job_daily` и кнопкой на
  «Диагностике». Итог, и неудачный, — в настройку `TARIFFS_RESULT` (её
  показывает «Диагностика»); неудача срок не сдвигает. Предмет карточки — из
  детализации отчётов WB («Предмет» / `subjectName`, `WbCard`), без токена
  «Контент»; тариф ищется по названию предмета, два предмета с одним названием и
  разными тарифами — не угадываются. В юнит-экономике тариф стоит РЯДОМ с
  «WB удержал» и не обязан с ним совпадать: в удержанное входят эквайринг, ПВЗ,
  лояльность и продажи со склада WB. Ozon не сделан: ключей Ozon в программе нет.
  Проценты хранятся в сотых долях (`*_bp`), не float.

- **Повторы продаж** (`finance/repeats.py`): одни и те же продажи (номер
  заказа + баркод + вид + сумма за штуку; дата НЕ входит — у CRM она
  «кочует») во втором отчёте — отказ: файлом — ошибка загрузки, автозагрузка
  CRM/KIT — неделя пропускается с объяснением, в 1С такой отчёт не уходит.
  Отчёты, у которых ОБОИХ есть номер площадки, между собой не сравниваются
  (у WB одна продажа законно бывает в двух отчётах), предварительные недели
  Lamoda не в счёт. Неотправленные продажи прежнего источника за те же недели
  (`fetch._replaceable`) — не повтор, а замена. Новый путь загрузки продаж —
  через `store_api_report`/`import_report`, мимо них проверки нет.

## Накат на сервер

Пакет: `python scripts/gen_package.py --tag finN --out mpfinance_finN.ps1`.
Его запускают на сервере, затем `deploy\update_server.ps1 -Tag finN`. Первая
установка — `deploy\install_server.ps1`.

Патч — только изменённое после версии на сервере: `python scripts/gen_package.py
--tag finN --since <коммит той версии> --base-tag finM --out finN_deploy.ps1`.
Файл переносят в `C:\mpfinance` и запускают (`powershell -ExecutionPolicy Bypass
-File C:\mpfinance\finN_deploy.ps1`) — так накатывают и на этом сервере, и Sync
Admin. С `--paste` тот же патч выходит блоками для вставки в консоль. Apply сверяет
`INSTALLED_TAG` и SHA256 каждого заменяемого файла ДО первой записи; разошлось
хоть что-то — не трогает ничего. Удалённые файлы патчем не накатить — нужен
полный пакет. После патча — тот же `update_server.ps1 -Tag finN`.

Подтверждение человека нужно перед правкой `.env` на сервере и перед
восстановлением базы из копии.
