# sync_admin — синхронизация остатков 1С ↔ маркетплейсы

Документация к текущей версии. Обновлено 2026-09-16.

Приложение синхронизирует остатки между 1С «Магазин одежды и обуви» и маркетплейсами
(Wildberries, Ozon, Яндекс.Кит), а также проводит в 1С документы перемещения по заказам.
Ключ сопоставления везде — **штрихкод (баркод)**.

---

## 1. Общая схема

```
Маркетплейсы (WB/Ozon/Kit)                1С «Магазин одежды и обуви»
      │  заказы (FBS)                            ▲  документы ПеремещениеТоваров
      ▼                                          │
┌──────────────┐   очередь остатков   ┌────────────────────┐  файлы обмена  ┌───────────┐
│ order_poller │ ──────────────────▶  │  sync_admin worker │ ◀────────────▶ │ C:\sync\* │ ◀─▶ .epf «ОбменССайтом»
│  dispatch    │ ◀── остатки ЦС ───   │  (планировщик)     │  task/result/  └───────────┘
└──────────────┘                      └────────────────────┘  stock/barcodes
        ▲                                       │
        │ web-интерфейс (FastAPI, порт 8000) ───┘
```

- **sync_admin_web** (NSSM-служба, порт 8000) — админка/тестирование.
- **sync_admin_worker** (NSSM-служба) — планировщик фоновых задач (опрос заказов, рассылка,
  сверка, обмен файлами с 1С). Вся боевая логика синхронизации крутится **здесь**.
- **1С .epf «ОбменССайтом»** — обработка на стороне 1С, читает задания из `C:\sync\tasks`,
  создаёт документы перемещения, выкладывает результаты/остатки/справочник баркодов в
  `C:\sync\results`. Запускается по расписанию (см. §9).

Кабинеты (PlatformAccount):

|----|-----------------|----------|
| 1  | ИП Яворская     | wb       |
| 2  | ИП Ребрик       | wb       |
| 3  | ИП Караман      | wb       |
| 4  | Озон            | ozon     |

Склады (справочник 1С «Склады»), **Вариант А** (резерв в основной склад площадки):

- Приёмники: **Wildberries_Склад_FBO**, **OZON_Склад**, **Сайт AWER** (Kit).

## 3. Протокол обмена (локальные папки)

Папки: `C:\sync\tasks` (задания в 1С), `C:\sync\results` (ответы 1С), `C:\sync\archive`.
Кодировка **UTF-8**, разделитель полей `|`, публикация атомарная (`имя.part` → переименование).

Строки заданий (`task_*.txt`):

| Команда              | Поля                                                                                 |
|----------------------|--------------------------------------------------------------------------------------|
| `CREATE_MOVEMENT`    | `команда \| баркод \| склад_откуда \| склад_куда \| кол-во \| order_id \| площадка \| дата(ГГГГММДД, необяз.)` |
| `CONFIRM_MOVEMENT`   | то же (перемещение «Ожидает» → «Склад площадки»; при Варианте А обычно не создаётся)  |
| `CANCEL_MOVEMENT`    | `команда \| order_id \| площадка` (реверс проведённых перемещений заказа)             |
| `EXPORT_STOCK_ON_HAND` | выгрузка остатков ЦС → `stock_*.txt`                                                |
| `EXPORT_BARCODES`    | выгрузка справочника баркодов → `barcodes_*.txt`                                      |

**8-е поле даты** — дата документа перемещения (старт задним числом). Пусто → 1С ставит
текущую дату; 8 цифр ГГГГММДД → `Документ.Дата = Дата(...)`. Проведение неоперативное
(`РежимЗаписиДокумента.Проведение`), задним числом допускается (в пределах даты запрета).

Ответы 1С: `result_*.txt` (`order_id|OK|номер` или `order_id|ERROR|описание`),
`stock_*.txt` (`uid_1c|артикул|наименование|кол-во|баркоды|размер|цвет`),
`barcodes_*.txt` (`uid_1c|артикул|наименование|баркод|размер|цвет`).

## 4. Ключевые механизмы

### 4.1 Опрос заказов (order_poller.py)
Каждые ~2 мин по каждому кабинету: `get_orders_awaiting_confirmation()` → по каждому заказу
`process_new_order()`. Баркод резолвится в товар (`resolve_barcode`), списывается остаток,
создаётся `ProcessedOrder` (идемпотентность по кабинет+order_id), задание `CREATE_MOVEMENT`
в 1С, рассылка нового остатка на остальные кабинеты.

### 4.2 Отбор по включённым товарам (гейт) — важно
`process_new_order` трогает товар **только если синхронизация включена** (`SyncSetting.enabled`
по паре товар+кабинет). Выключенный товар живой поллер **пропускает полностью и тихо**: без
движения в 1С, списания, рассылки, аномалии и без отметки об обработке. После включения на
странице «Товары и остатки» поллер сам начинает вести товар; прошлые заказы добираются
бэкфиллом (§4.6). Явные действия оператора не гейтятся: **бэкфилл** (`respect_enabled=False`)
и **синтетический тест** (`is_test=True`) выполняются независимо от флага.

**Правило:** по умолчанию не включено ничего → синхронизируется только то, что оператор явно
включил; всё остальное отсекается.

### 4.3 Расчёт отправляемого остатка (app/transmit.py)
Одна лестница на рассылку и на интерфейс (`explain` / `quantity_for_account`), приоритет
в момент отправки:
0. `broadcast_enabled = False` → **0** (товар снят с продажи на площадках).
1. Кабинет не отмечен для товара (`SyncSetting.enabled = False`) → **0** в этот кабинет.
2. Рассылка на кабинет на паузе (`PlatformAccount.dispatch_enabled = False`) → **0**.
3. `broadcast_offset` задан → **max(0, остаток ЦС − порог)**. Порог трансляции фиксирован
   и может быть отрицательным; заказы и сверка двигают только остаток, поэтому цифра не
   дрейфует. → см. §7.
4. `transmit_override` задан (устаревший режим) → **ровно это число** (не ниже 0).
5. Иначе: `available = max(0, остаток − reserve)`; если `available ≤ min_threshold` → 0
   (не продать последние штуки во всех каналах одновременно); иначе `available`.

Порог кабинета (шаг 5) применяется только в автоматическом режиме: порог трансляции и
ручной остаток заданы оператором явно, страховой буфер поверх них не навешивается.

Идентификатор для площадки: WB — баркод, Ozon — offer_id/артикул, Kit — variant_id
(берётся из загруженного каталога кабинета, иначе падаем на баркод).

### 4.4 Рассылка (dispatch.py)
Очередь `DispatchQueueItem` схлопывается по товару (последнее значение за окно), уходит батчем
на кабинеты с `dispatch_enabled=True`. Тестовые записи (`is_test`) на площадку не уходят.

### 4.5 Сверка и заведение товаров (reconciliation.py)
Выгрузку остатков **просим у 1С раз в час** (это полный снимок 152 тыс. товаров), а вот
**смотрим, не пришёл ли ответ, раз в 5 минут** — это разные по цене вещи. Разными они стали
после 17.09.2026: сверка была часовой и шла через 5 минут после запроса, то есть молча
закладывалась на то, что 1С ответит быстрее; обработка 1С запускается своим расписанием, раз в
10 минут, и отвечала через семь. Файл приходил всегда после того, как сверка ушла, а фаза
держалась до перезапуска воркера — сверка не срабатывала вообще. Применяется по-прежнему только
снимок новее последнего запроса.

Импорт остатков/ассортимента из выгрузки 1С: создаёт/обновляет `Product` (в т.ч. размер/цвет),
пишет физический остаток ЦС. Справочник баркодов обновляется отдельно (запрос раз в сутки +
импорт каждые 15 мин), создаёт недостающие `Barcode` (source `1c_dict`) и чистит конфликты.

### 4.6 Бэкфилл — «старт задним числом» (страница «Тестирование»)
По выбранному товару тянет с площадки **реальные исторические FBS-заказы с указанной даты**
(`get_orders_since`) и проводит по каждому перемещение в 1С **его реальной датой**. Нужен, когда
в 1С с этой даты не отражены отгрузки на маркетплейсы. Полный боевой путь `process_new_order`
(списание + рассылка + документ), `is_test=False`, `respect_enabled=False`. Идемпотентность не
даёт провести заказ дважды. Фильтрация — строго по баркодам выбранного товара.

## 5. Модель данных (основное)

- **Product**: `uid_1c` (id характеристики/номенклатуры 1С), `article`, `name`, `size`, `color`,
  `stock_on_hand` (физический остаток ЦС), `reserve`, `transmit_override`, `broadcast_enabled`.
- **Barcode**: `barcode`, `uid_1c`, `source_platform` (`1c_export`/`1c_dict`). Ключ сопоставления.
- **PlatformAccount**: кабинет (площадка, warehouse_id, is_active, dispatch_enabled).
- **SyncSetting**: `uid_1c` + `account_id` + `enabled` + `min_threshold` — **отбор** (§4.2).
- **PlatformCatalogItem**: карточка площадки (external_id/article/barcode/name) для мэппинга.
- **ProcessedOrder**: обработанные заказы (идемпотентность), статус processed/confirmed/cancelled.
- **FtpTask**: задание в 1С (command, barcode, склады, qty, order_id, **movement_date**, is_test).
- **MappingConflict**: неопознанный баркод (для страницы «Сопоставление площадок»).
- **DispatchQueueItem**, **SyncAnomaly**, **TestLogEntry** — очередь рассылки, аномалии, журнал теста.

## 6. Страница «Тестирование» (/testing)

- **Товар** — поиск по **сопоставленным** товарам (у которых есть баркод): вводите артикул или
  название, выбираете из выпадающего списка.
- **Кабинет** — конкретный кабинет или **«Все площадки»** (бэкфилл соберёт по всем сразу).
- **Дата начала** — для старта задним числом.
- **Старт задним числом** — «Загрузить заказы с площадки» → таблица реальных FBS-заказов (в
  режиме «Все площадки» с колонкой «Кабинет») → «Провести перемещения задним числом». Проведение
  реальное (не тест). Список показывается до проведения — сверить перед записью в 1С.
- **Сколько сейчас уходит на площадки** — справочно; сам порог задаётся на «Товары и остатки» (§7).
- **Шаг 1** — отправить текущий остаток (реальный, безопасный push).
- **Шаг 2** — синтетический заказ (весь код без реальной покупки; `is_test`).
- **Шаг 3** — очистка тестовых данных; **Живой журнал** (HTMX, каждые 2 с).

## 7. Порог трансляции (broadcast_offset) — страница «Товары и остатки»

Постоянное расхождение между учётом 1С и реальным складом. Считается один раз по пересчёту:
`порог = (остаток ЦС на дату) − (реально найдено на дату)`; может быть отрицательным. Дальше
на площадки уходит `max(0, текущий остаток ЦС − порог)`. Порог фиксирован — любое движение
склада (приход, расход, списание, пересортица, заказ) меняет остаток, а не порог, поэтому
цифра **не дрейфует**.

Задаётся в колонке «Порог трансляции» на /products: числом напрямую либо кнопкой «посчитать»
(два поля — учёт 1С и реальное количество). Пусто = порог не задан, работает автоматический
расчёт «остаток − резерв».

**Устаревшее:** `transmit_override` («ручной передаваемый остаток»). Он «дышал» вместе с
заказами и сверкой, поэтому его приходилось поправлять руками. Порог его заменил и гасит при
установке; из интерфейса задать его больше нельзя, осталась только кнопка «сбросить» в строке
товара, если он проставлен с прошлых версий.

## 8. Развёртывание и эксплуатация

- Python venv: `C:\sync_admin\.venv`. Зависимости — `requirements.txt`.
- Службы NSSM: `sync_admin_web` (порт 8000), `sync_admin_worker`.
  Перезапуск: `nssm restart sync_admin_web` / `nssm restart sync_admin_worker`.
  **Важно:** боевая логика в воркере — после изменения кода в `app/workers/*` обязательно
  перезапускать `sync_admin_worker`, иначе в памяти остаётся старый код.
- Миграции: `python -m alembic upgrade head`. Актуальная голова — `b8d4f2a6c1e9` (movement_date).
- Здоровье: `GET /health` — статусы воркеров (dispatch, ftp_send/receive, poll_orders_account_N,
  reconcile_accounts, reconciliation, import_barcodes).
- Планировщик (scheduler.py): опрос заказов (2 мин/кабинет), рассылка, обмен файлами (ftp_send/
  receive ~10 мин), сверка (ежечасно, сеет товары), запрос справочника баркодов (24 ч) + импорт
  (15 мин).

## 9. 1С .epf «ОбменССайтом» и автозапуск

- Модуль объекта — `1c/ОбменССайтом_МодульОбъекта.txt` (эталон). Точка входа `ВыполнитьОбмен()`.
- `ВыполнитьПеремещение(...)` принимает необязательный `ДатаДок` (ГГГГММДД) — 8 цифр → дата
  документа задним числом, иначе `ТекущаяДата()`. Строки товара: `ХарактеристикаНоменклатуры`,
  `ЕдиницаИзмерения = Номенклатура.ЕдиницаХраненияОстатков`, `Коэффициент = 1`.
- Автозапуск (пакетный режим 1С 8.3.9): `1cv8.exe ENTERPRISE /S "..." /N "..." /P "..."
  /Execute "...ОбменССайтом.epf" /CEXCHANGE /DisableStartupDialogs /DisableStartupMessages`.
  Форма обычная — обработчик `ПриОткрытии` привязывать в палитре свойств; проверяет
  `ВРег(СокрЛП(ПараметрЗапуска)) = "EXCHANGE"` → обмен + завершение работы. Нужна интерактивная
  сессия Windows (толстый клиент).

## 10. Диагностика (готовые скрипты)

Запуск: `& C:\sync_admin\.venv\Scripts\python.exe C:\sync_admin\<скрипт>.py [аргументы]`.

- `diag_bc.py <баркод>` — привязки баркода в 1С (uid/товар) + карточки площадок + конфликты.
- `recent_orders.py` — 30 последних обработанных заказов (время, товар, enabled).
- `trace_orders.py <баркод_товара> <ГГГГ-ММ-ДД>` — что вернула площадка и как отработал фильтр
  бэкфилла по кабинетам.
- `watch.py` (+ `cutoff.txt`) — проверка гейта: заказы после перезапуска воркера, сколько
  выключенных «просочилось» (должно быть 0).
