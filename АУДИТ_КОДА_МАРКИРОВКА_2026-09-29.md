# Аудит кода программы «Маркировка и поставки» — 29.09.2026

Предмет — `marking/` (этапы 2–3) и часть модуля 1С `ОбменССайтом`, которую
программа использует. Смотрели четыре вещи: стабильность, правильность
сопоставления (мэппинга), правильность расчётов и причинно-следственные связи
между модулями. Итог: 7 дефектов исправлены, 5 замечаний оставлены
осознанно, одна строка ТЗ исправлена под фактическое поведение.

## Где загружается исходный документ черновика

«Поставки» → «Новая поставка» → поле «Файл поставки» (`/supplies/new`,
`routers/supplies.py: supply_create` → `supplies.parse_input` →
`supplies.create_supply`). Раньше при поставке сохранялось только ИМЯ файла,
и вернуться к исходнику со страницы поставки было нельзя. **Теперь файл
хранится при поставке** (`Supply.source_file`, миграция 0003), и в шапке
поставки есть ссылка «Исходный файл» на скачивание.

## Цепочка данных и где что сопоставляется

```
входящий файл (Seller SKU, кол-во, B1 дата, B2 номер)
  └─ parse_input ──► SupplyRow(supplier_sku, qty)
        └─ «Одежда полный» (точное совпадение артикула) ──► ean, price
              └─ SUPPLY_CHECK: 1С ищет штрихкод в пуле SKU ──► товар 1С, остаток ЦС
                    └─ SUPPLY_MOVEMENT: один документ ЦС → Lamoda_Склад
                          └─ дельта остатка ЦС ──► sync_admin перестаёт продавать
  «Поставки FBO» (Lamoda) ──► сверка с поставкой (артикул, кол-во, цена, EAN)
        ├─ GTIN из КИЗ ──► справочник GTIN ──► Нацкаталог
        └─ УПД (схема по дате УПД) и стикеры (та же схема)
```

Проверенные звенья сопоставления:

| Звено | Правило | Итог |
|---|---|---|
| артикул → каталог | точное совпадение, подсказка по пробелам | верно |
| штрихкод → SKU 1С | любой штрихкод пула, пул только своего SKU | верно (29.09) |
| два артикула → один SKU 1С | отказ перемещению | верно (29.09) |
| артикул → GTIN | 1:1, конфликт показывается, не перезаписывается | верно |
| FBO → поставка | артикул, количество, цена, EAN | верно |
| итог 12550 | 80 стр., 338 шт., 4 337 500,00 = «Итого» FBO | сходится |

## Исправленные дефекты

### 1. КРИТИЧНО. Поставку можно было править, пока её перемещение уже в 1С

Статус «перемещено» ставит ОТВЕТ 1С. До ответа (файл в пути, 1С молчит,
задание зависло) поставка оставалась «проверенной», то есть правимой.
- Правка количества: 1С проводит документ со старым составом, у нас новый. Когда
  придёт ответ OK, поставка станет «перемещено» с составом, которого в 1С нет.
- Смена номера: ключ идемпотентности `lamoda-<номер>` меняется, и повтор
  зависшего перемещения создаёт ВТОРОЙ документ. Товар уезжает на Lamoda дважды,
  а отмены у поставки нет.

**Исправлено.** `supplies.movement_sent` замораживает поставку с момента
постановки перемещения в очередь. Замороженными остаются состояния
pending, sent, timeout и done. Размораживает только внятный отказ 1С (failed):
документа тогда точно нет. Замораживаются количество, «Перечитать», удаление,
номер, дата и повторная проверка.

### 2. ВЫСОКО. Две проверки в одном файле путали строки двух поставок

Обработка пишет подробности проверки одним файлом `supplycheck_<метка>.txt` на
весь файл задания: строка на штрихкод, без order_id. Воркер складывал в один
файл все ждущие задания. Если две поставки проверяли в пределах 30 секунд, их
строки попадали в общий список. Строки поставки A получали остаток и статус по
«нужно» поставки B, а общий штрихкод у двух поставок — обычное дело.

**Исправлено.** Не больше одной SUPPLY_CHECK на файл, остальные проверки
уходят следующими циклами. Модуль 1С менять не пришлось.

### 3. ВЫСОКО. Дата поставки из B1 молча терялась

Инструмент КИЗ пишет дату в B1 числом Excel без формата ячейки (46297). Такой
тип не разбирался и не давал ошибки: поставка создавалась без даты, хотя дата
в файле была. **Исправлено**: число Excel читается как дата. На образце
`reference_kiz_tool_supply_12550.xlsx` получается 02.10.2026.

### 4. ВЫСОКО. Смена каталога после загрузки не останавливала черновик

ТЗ 5.2 обещал предупреждение, а в коде его не было. Черновик хранит штрихкод и
цену на момент загрузки. Если каталог Lamoda за это время обновили, в 1С уехал
бы старый штрихкод, «Поставки FBO» потом не сошлись бы и УПД не выпустился бы.
Перемещение при этом уже не отменить. **Исправлено**: `supplies.catalog_drift`
закрывает проверку и перемещение до нажатия «Перечитать из «Одежды полной»».

### 5. СРЕДНЕ. Один сломанный файл ответа останавливал весь канал 1С

Исключение при разборе уходило наверх. Каждые 30 секунд воркер спотыкался о
первый по имени плохой файл. Ответы за ним не применялись никогда, и зависшие
задания не отмечались. **Исправлено**: каждый файл разбирается отдельно.
Сломанный остаётся на месте и называется в отметке задания, остальные
разбираются.

### 6. СРЕДНЕ. /health был зелёным при падающем обмене с 1С

/health смотрел только на время последнего прогона. Задание, которое падает
каждые 30 секунд, отмечается каждые 30 секунд, поэтому выглядело свежим.
**Исправлено**: у обязательного задания со свежей отметкой, но с ошибкой
/health возвращает 503 и текст ошибки.

### 7. СРЕДНЕ. «_» в номере поставки ломал идемпотентность в 1С

`НайтиПроведённоеПеремещение` ищет документ через `ПОДОБНО "%order_id=lamoda-<номер> %"`,
а в ПОДОБНО «_» означает любой символ. Поставка «A_1» нашла бы документ
поставки «AB1» и объявила бы себя перемещённой, не переместив ничего.
**Исправлено**: «_» в номере поставки запрещён. В номере документа он
по-прежнему разрешён, потому что в ключ не входит.
