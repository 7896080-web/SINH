# Sync Admin — инструкции для Claude Code

**Если это первое открытие проекта после передачи — сначала прочитай
`HANDOFF.md`.** Там снимок состояния на момент передачи и конкретный
чеклист того, что нужно проверить, когда появились реальные ключи
площадок. Этот файл (`CLAUDE.md`) — общие правила работы над кодом,
актуальны всегда, не только при первом открытии.

Синхронизация остатков между 1С «Магазин одежды и обуви» и Wildberries,
Ozon, Яндекс KIT. FastAPI + PostgreSQL + фоновый планировщик (APScheduler).
Работает с реальными деньгами и реальными остатками товаров — ошибка может
привести к оверселлу или к неверным документам в 1С. Читай этот файл перед
тем, как что-либо менять, тестировать или разворачивать.

## Прежде чем менять что угодно

1. **Всегда читай, что уже сломано/не проверено** — раздел «Что не
   проверено» в README.md и `deploy/README.md` честно перечисляют это.
   Не предполагай, что всё работает, если это не покрыто тестом.
2. **Всегда запускай тесты перед тем, как предлагать или применять
   изменение:**
   ```bash
   pytest tests/ -q
   ```
   609 тестов, все должны быть зелёными. Если изменение ломает тест — это
   сигнал остановиться и разобраться, а не подогнать тест под новое
   поведение, пока не понятно, что поведение действительно должно было
   измениться.
3. **Любое изменение `app/models.py` требует новой миграции**:
   ```bash
   export DATABASE_URL="sqlite:///./alembic_test.db" SESSION_SECRET=x \
       SECRETS_ENCRYPTION_KEY=$(python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())")
   alembic revision --autogenerate -m "краткое описание"
   rm -f alembic_test.db
   ```
   Проверь получившийся файл в `alembic/versions/` глазами — autogenerate
   не всегда угадывает правильно (например, переименования колонок видит
   как drop+add, теряя данные при реальном апгрейде).

## Локальный запуск для тестирования

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

export DATABASE_URL="sqlite:///./dev.db"
export SESSION_SECRET="dev-secret-32-characters-long-xx"
export SECRETS_ENCRYPTION_KEY=$(python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())")

alembic upgrade head
python create_admin_user.py admin devpass
uvicorn app.main:app --reload
```

SQLite годится для разработки и для запуска тестов (`tests/conftest.py`
сам поднимает файловую SQLite), но **не для прода** — там PostgreSQL
(см. `deploy/README.md`, причины перечислены там же).

## Как устроен код — коротко

- `app/models.py` — вся схема. Единица подключения к площадке —
  `PlatformAccount` («кабинет»), не сама площадка: у WB может быть
  несколько кабинетов (разных ИП/ООО) с разными токенами и складами.
- `app/workers/order_poller.py` — сердце системы: `process_new_order` и
  `process_cancellation` содержат ВСЮ логику приёма/отмены заказа. И живой
  опрос (`poll_new_orders`), и страница тестирования (`app/routers/testing.py`)
  вызывают эти же функции — не создавай отдельную копию логики для теста.
- **`is_test` флаг** (`DispatchQueueItem`, `FtpTask`, `SyncAnomaly`) —
  критичная граница безопасности. Если добавляешь новый тип побочной
  записи с внешним эффектом (звонок в API площадки, файл для 1С) —
  добавь туда `is_test` и исключи `is_test=True` из реальной отправки.
  Без этого симуляция на странице «Тестирование» может реально уйти на
  боевую площадку или создать документ в реальной базе 1С — это уже было
  найдено и исправлено один раз, не повтори эту ошибку.
- `app/workers/scheduler.py` — per-account задания сверяются с БД
  периодически (`reconcile_account_jobs`, каждые 5 минут). Новый активный
  кабинет из админки подхватывается сам в пределах этого интервала,
  отключённый — так же снимается; перезапуск процесса больше не нужен.
  Немедленный подхват (если ждать 5 минут не хочется) —
  `systemctl restart sync-admin-scheduler`.
- `app/workers/circuit_breaker.py` — кабинет с 5 сбоями подряд сам
  отключается (`is_active=False`). Это осознанное поведение, не баг, если
  видишь отключённый кабинет в логах.

## Тестирование на боевом сервере — только так, не иначе

Для проверки поведения на реальном товаре и реальном кабинете **используй
страницу `/testing` в самом приложении**, не создавай тестовые заказы
вручную через psql или скрипты в обход неё — только `/testing`
гарантирует простановку `is_test=True` и безопасную очистку.
`scripts/smoke_test.py` заказы НЕ симулирует: он только логинится и
проверяет, что страницы открываются (GET-запросы), — это проверка после
деплоя, а не замена странице `/testing`.

Никогда не пиши в БД прод-сервера напрямую (`psql ... UPDATE/DELETE`) в
обход приложения и alembic — это гарантированно разойдётся с тем, что
ожидает код (например, забудешь поставить `is_test`, или нарушишь
уникальные ограничения типа `uq_product_account`).

## Обновление боевой версии

**Только так:**
```bash
sudo bash deploy/safe_deploy.sh
```
Делает по порядку: бэкап кода и базы → тесты → само обновление → health-check
→ если health-check не прошёл, автоматически откатывает КОД (базу — нет,
осознанно, см. комментарий в скрипте) и сообщает, что делать дальше руками.

**Не используй `deploy/update.sh` напрямую на проде** — он не делает
бэкап и не проверяет здоровье после обновления. Он остался для случаев,
когда `safe_deploy.sh` неприменим (например, ручная отладка на стейдже),
но не для автономного запуска агентом без присмотра.

Откат вручную, если что-то пошло не так уже после успешного health-check:
```bash
sudo bash deploy/rollback.sh
```

## Границы автономности агента

Делай самостоятельно, без переспрашивания:
- Правки кода + тесты + миграции по описанной выше процедуре.
- Запуск `deploy/safe_deploy.sh` — он сам себя проверяет и откатывает при сбое.
- Чтение логов (`journalctl -u sync-admin-web`, `journalctl -u sync-admin-scheduler`).

Спрашивай подтверждение перед тем, как:
- Менять `.env` на проде (там реальные токены площадок и пароль БД).
- Деактивировать/активировать боевой кабинет площадки вручную через БД.
- Восстанавливать базу из бэкапа (`deploy/rollback.sh --with-db`) —
  это стирает любые реальные заказы, принятые после бэкапа.
- Менять что-либо в `app/workers/platform_clients/` без возможности
  проверить на реальных ключах — эти клиенты никогда не тестировались
  против живых API WB/Ozon/Kit, правки там особенно рискованны вслепую.
- Сбрасывать пароль пользователя (`sudo bash deploy/reset_password.sh`)
  без явной просьбы — это меняет доступ живого человека к системе.
