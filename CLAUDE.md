# Sync Admin — инструкции для Claude Code

**Если это первое открытие проекта после передачи — сначала прочитай
`HANDOFF.md`.** Там снимок состояния на момент передачи и конкретный
чеклист того, что нужно проверить, когда появились реальные ключи
площадок. Этот файл (`CLAUDE.md`) — общие правила работы над кодом,
актуальны всегда, не только при первом открытии.

Синхронизация остатков между 1С «Магазин одежды и обуви» и Wildberries,
Ozon, Яндекс KIT. FastAPI + фоновый планировщик (APScheduler).

Полный аудит кода и замеры на боевом масштабе — `АУДИТ_2026-09-21_полный.md`.
Там же перечислено, что осталось непроверенным и почему (клиенты площадок, где
нужен живой кабинет).

**Тесты нельзя гонять в два потока одновременно** — точнее, теперь можно:
фикстура `web_db` берёт свой файл на процесс. Раньше он был один на всех и
после каждого веб-теста делался `drop_all`, так что параллельные прогоны сносили
таблицы друг у друга — и выглядело это сотней ошибок «UNIQUE constraint failed»,
то есть как поломка кода.

**Боевой сервер — Windows И МОСКОВСКИЙ ПОЯС. Машина разработки — Linux и UTC.**
Это два разных факта, и каждый из них уже валил накат. Держи их в голове при
КАЖДОЙ правке теста: зелёный прогон здесь ничего не обещает там.

1. **Unix-only в тестах не бывает.** `time.tzset()` есть только на Unix, и тест,
   который им пользуется, на бою даёт `AttributeError` — то есть валит `pytest`
   в накате и не даёт перезапустить службы. Починить по месту нельзя: здесь он
   зелёный. 24.09 на этом встал pm122. Пояс в тесте подменяется ФУНКЦИЕЙ
   (`monkeypatch.setattr(backup, "local_date_of", …)`), а не переменной
   окружения; закрыто сканером AST в `test_audit_findings_3_to_6.py`.
2. **Местный день ≠ UTC-день, и тест не должен считать его сам.** У Москвы UTC+3,
   значит всё, что случилось после 21:00 UTC, на бою относится уже к СЛЕДУЮЩЕМУ
   местному дню. Тест, который вынимает число из строки («`name.split("-")[1]`»)
   или берёт `.date()` у UTC-времени, верен только там, где пояс совпадает с UTC
   — то есть только здесь. Считай тем же правилом, что и код: `local_date_of`.
   Тем же 24.09 на этом встал второй тест, про уборку копий.

**Поэтому перед каждым патчем набор гоняется ДВАЖДЫ:**

```bash
pytest tests/ -q                      # как здесь
TZ=Europe/Moscow pytest tests/ -q     # как на бою
```

Второй прогон и есть та проверка, которая ловит оба класса на машине
разработки, а не на боевом сервере после копии базы и девяти минут тестов.

**Остальное про боевой сервер** (проверено 17.09.2026): `C:\sync_admin`,
службы под NSSM (`sync_admin_web`, `sync_admin_worker`), база — **SQLite**
`C:/sync_admin/sync_admin.db`, git на машине НЕ установлен. Раздел «Обновление
боевой версии» ниже про Linux-вариант — на этом сервере он неприменим.
Работает с реальными деньгами и реальными остатками товаров — ошибка может
привести к оверселлу или к неверным документам в 1С. Читай этот файл перед
тем, как что-либо менять, тестировать или разворачивать.

## Прежде чем менять что угодно

1. **Всегда читай, что уже сломано/не проверено** — раздел «Что не
   проверено» в README.md и `deploy/README.md` честно перечисляют это.
   Не предполагай, что всё работает, если это не покрыто тестом.
2. **Всегда запускай тесты перед тем, как предлагать или применять
   изменение — ОБА прогона:**
   ```bash
   pytest tests/ -q                      # как здесь: Linux, UTC
   TZ=Europe/Moscow pytest tests/ -q     # как на бою: московский пояс
   ```
   Второй обязателен не для порядка: боевой сервер стоит в Москве, а эта
   машина — в UTC, и целый класс тестов зелен здесь и красен там. Накат гоняет
   `pytest` ПЕРЕД перезапуском служб, поэтому такой тест не просто падает — он
   останавливает накат на живом сервере, уже после копии базы и миграций.
   Все тесты должны быть зелёными. Если изменение ломает тест — это
   сигнал остановиться и разобраться, а не подогнать тест под новое
   поведение, пока не понятно, что поведение действительно должно было
   измениться.
3. **Любое изменение `app/models.py` требует новой миграции**:
   ```bash
   export DATABASE_URL="sqlite:///./alembic_test.db" SESSION_SECRET=x \
       SECRETS_ENCRYPTION_KEY=$(python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())")
   alembic revision --autogenerate -m "краткое описание"
   rm -f alembic_test.db
   ```
   Проверь получившийся файл в `alembic/versions/` глазами — autogenerate
   не всегда угадывает правильно (например, переименования колонок видит
   как drop+add, теряя данные при реальном апгрейде).

## Локальный запуск для тестирования

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

export DATABASE_URL="sqlite:///./dev.db"
export SESSION_SECRET="dev-secret-32-characters-long-xx"
export SECRETS_ENCRYPTION_KEY=$(python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())")

alembic upgrade head
python create_admin_user.py admin devpass
uvicorn app.main:app --reload
```

SQLite годится и для разработки, и для тестов (`tests/conftest.py` поднимает
файловую SQLite), **и на боевом сервере тоже стоит она** — установщик
`deploy/install_windows.ps1` умеет оба варианта, и эта машина поставлена по
SQLite-варианту. Отсюда WAL и `busy_timeout` в `app/database.py`: веб и
планировщик пишут в один файл, без этого они блокировали бы друг друга.

Практические следствия, о которых легко забыть:
- **Бэкап — это копия файла**, а не `pg_dump`. Копировать при остановленных
  службах либо штатным `.backup` SQLite: при живом WAL простое копирование
  `sync_admin.db` даёт неконсистентный снимок.
- Рассуждения `deploy/README.md` про необходимость PostgreSQL относятся к
  Linux-варианту развёртывания, не к тому, что работает сейчас.
- `SessionLocal` создаётся с `autoflush=False`. Это не мелочь: код, который
  добавил объекты в сессию и тут же читает их запросом, их НЕ УВИДИТ, пока не
  сделает `flush()`. На этом уже проехал дефект — расчёт порога читал строки
  ответа 1С, ещё не ушедшие в базу. Фикстуры тестов настроены так же, чтобы
  такие вещи падали в тестах, а не на бою.

## Как устроен код — коротко

- `app/models.py` — вся схема. Единица подключения к площадке —
  `PlatformAccount` («кабинет»), не сама площадка: у WB может быть
  несколько кабинетов (разных ИП/ООО) с разными токенами и складами.
- `app/workers/order_poller.py` — сердце системы: `process_new_order` и
  `process_cancellation` содержат ВСЮ логику приёма/отмены заказа. И живой
  опрос (`poll_new_orders`), и страница тестирования (`app/routers/testing.py`)
  вызывают эти же функции — не создавай отдельную копию логики для теста.
- **До включения трансляции наружу не уходит НИЧЕГО** — ни остаток, ни ноль.
  Автоматические пути (`_enqueue_dispatch_to_others` при проведении заказа,
  `enqueue_full_resend` после правки брони/факта/порога) товар с
  `broadcast_enabled=False` в очередь не ставят вовсе. Раньше ставили, рассылка
  считала по нему ноль и отправляла его: для карточки, по которой идут продажи,
  это обнуление, а не отзыв остатка — мы туда ни разу ничего не отправляли.
  Осознанный отзыв — отдельная функция `enqueue_withdrawal`, её зовёт интерфейс
  явно при снятии галочки кабинета или выключении трансляции. Различать надо не
  «включено/выключено», а «осознанно отзываем» против «никогда не отправляли».
  **Отзыв спрашивает не «включено ли», а «было ли что отзывать»** —
  `transmit.should_withdraw` / `ever_transmitted`: ноль уходит, только если мы на
  этот кабинет уже отправляли непустой остаток. Прошлые отзывы отправками не
  считаются. 18.09 на бою сначала ушли нули на Озон и Kit по товару с выключенной
  трансляцией, а потом нашёлся тот же случай при ВКЛЮЧЁННОЙ: кабинет отмечен,
  расчёт его покрыл, остаток ещё не уехал — и снятие галочки обнулило бы живую
  карточку.
- **«Актуализирован» — свойство пары товар+кабинет, а не товара.** Расчёт
  поднимает заказы только с кабинетов, отмеченных В ЕГО МОМЕНТ, и запоминает их
  в `Product.recalc_account_ids`. На кабинет вне этого списка не уходит ни
  остаток, ни ноль (ступень 2 лестницы в `app/transmit.py`) — сначала пересчёт.
  Иначе галочка на кабинете, которого расчёт не касался, через 45 секунд
  отправляла туда остаток, не сверенный с его продажами. **Включить трансляцию у
  строки, не доведённой до «актуализирован», интерфейс не даёт вовсе**
  (`broadcast_gate.blocks_broadcast_on`): у товара без расчёта `recalc_done_at` пуст,
  ступень 2 не срабатывает, и включение отправило бы полный остаток. Выключение
  не ограничено ничем и никогда. Кабинет, покрытый
  ВПЕРВЫЕ, расчёт сам ставит в очередь на доотправку (`reason="recalc_covered"`):
  ворота открыл именно он, а событие, которое поставило бы запись, случилось
  раньше и справедливо получило отказ. Без этого выходило «всё зелено, а наружу
  не ушло ничего».
- **Ноль от площадки и молчание площадки — разные вещи.** У Kit баркод строки
  заказа узнаётся отдельным запросом варианта, и 429 после всех повторов раньше
  просто выбрасывал заказ: наверх не шло ничего, расчёт считал, что продаж не
  было. Теперь `KitClient.last_unresolved` считает потерянные строки, а
  `recalc.collect_orders` превращает их в проблему и не даёт поставить отметку.
  Заодно соответствие `variant_id → баркод` берётся из своей базы
  (`platform_catalog_items`), а не тысячами запросов к площадке — именно они и
  упирались в 429.
- **Лента заказов площадки кончается не там, где кончились данные.** WB
  `/api/v3/orders?dateFrom=` отдаёт ОКНО около 29 дней от указанной даты, а не
  «всё с этой даты»: 18.09 на бою один запрос от базовой даты вернул 520 заказов
  за 07.08..05.09 и замолчал, а 253 более свежих заказа по тому же кабинету —
  включая единственную продажу 256250-015 — не увидел никто. Расчёт при этом
  рапортовал «проведено 0, проблем нет» и ставил товару «актуализирован», то есть
  открывал трансляцию полного остатка по несверенным продажам. Поэтому ленту
  берём окнами до сегодняшнего дня (`wb.ORDERS_WINDOW_DAYS`) с дедупликацией по
  id заказа, страницы листаем ПО КУРСОРУ, а не по длине страницы (короткая
  страница у WB не значит «данные кончились» — на этом же уже спотыкался
  каталог), и у Озона конец ленты спрашиваем полем `has_next`. А если выдачу
  оборвал наш защитный предел страниц, клиент поднимает `last_truncated`, и
  `collect_orders` превращает это в проблему: неполная картина не должна давать
  отметку «актуализирован». У Kit конец ленты определяет `total_count` из ответа
  — там стоял тот же стоп по короткой странице, и 19.09 на живом кабинете он
  оказался честным (100/100/88, четвёртая страница пустая, `total_count` = 288
  сошёлся с собранным), но это совпадение, а не гарантия.
- **Файл Excel не обходит гейт трансляции, а встаёт в очередь к нему.** Оператор
  настраивает каталог пачкой: в одном файле дата расчёта, факт, бронь, кабинеты и
  «Трансляция = Да». Расчёт после этого идёт минутами и заканчивается уже без него,
  поэтому включать приходилось вторым заходом — разыскав те же строки в каталоге на
  152 тысячи позиций, то есть на практике половина строк оставалась выключенной и
  молчала об этом. Теперь файл ставит ПРОСЬБУ (`Product.broadcast_requested_at`), а
  включает её тот, кто имеет право: `broadcast_gate.apply_pending_broadcast` — ровно
  тогда, когда включила бы и страница (`blocks_broadcast_on` вернул None). Условие
  общее на оба пути и живёт в `app/broadcast_gate.py` намеренно: разойдись они,
  отложенное включение открыло бы трансляцию там, где страница её не даёт. Просьба
  запоминается ТОЛЬКО из состояний, которые рассосутся сами
  (`DEFERRABLE_CALC_STATUSES`: «ждём 1С», «нужен расчёт», «нужен пересчёт: добавлен
  кабинет»); «не выбран кабинет», «расчёт не начат» и «нужен факт» без человека не
  исчезнут, и молча запомненная просьба была бы обещанием, которое никто не выполнит,
  — они остаются ошибкой импорта. Спрашивают о ней ДВОЕ, и оба обязательны: расчёт
  (`recalc.catch_up_product`) и приём ответа 1С (`offset_base.fill_waiting_products`)
  — порядок их прихода не определён, и спроси мы только в расчёте, строка, чей расчёт
  закончился раньше ответа 1С, ждала бы вечно. Включение идёт ДО постановки в
  очередь: нетранслируемый товар автоматические пути в очередь не ставят вовсе, и
  обратный порядок дал бы «всё зелено, а наружу не ушло ничего». Любое выключение —
  файлом или руками — снимает и просьбу тоже, иначе трансляция вернулась бы сама
  после ближайшего расчёта. Расчёт с проблемами отметки не ставит, значит и ворота не
  открывает. Сам расчёт файл тоже запускает (тем же `create_job`, что и кнопка) — по
  строкам, которым его и не хватает: иначе оператору надо было искать в отборе
  страницы ровно те строки, что он правил в файле.
- **Да/Нет в выгрузке — выпадающим списком, а не набором руками** (`build_xlsx_response`,
  параметр `choices`). `parse_bool_ru` читает как «Нет» всё, кроме «да/yes/true/1/истина»:
  опечатка, «+», пустая ячейка — и файл ВЫКЛЮЧАЕТ то, что оператор включал, не сказав
  об этом ни слова. Проверка на стороне Excel ловит это там, где человек ещё видит свою
  строку. Диапазон ставится по числу выгруженных строк, и правило добавляется в лист ДО
  назначения диапазона — обратный порядок молча даёт файл без проверок.
- **Отклик страниц упирался в один отсутствующий индекс.** Замер 21.09 на боевом
  каталоге (152 235 товаров, 154 232 баркода, 276 856 строк сверки) не дошёл дальше
  второй строки: поиск на «Товарах» не отвечал вовсе. Коррелированный подзапрос по
  баркодам выполнялся НА КАЖДЫЙ товар, а `barcodes.uid_1c` индекса не имел — то есть
  на каждый из 152 тысяч товаров читались все 154 тысячи баркодов. Чинится с трёх
  сторон, и все три нужны. Индексы (`alembic` 5c7ec8206dc3): `barcodes.uid_1c`,
  очередь рассылки по паре и по статусу, сверка по `checked_at` и `uid_1c`, задания
  1С по статусу — раньше НИ ОДНОГО не было, и каждое обращение читало таблицу
  целиком. Форма запроса: `IN (подзапрос)` вместо коррелированного `EXISTS` — SQLite
  считает его один раз, а не на строку; в цифрах баркода быть обязано, иначе поиск
  «куртка» читал бы таблицу баркодов ради заведомо пустого результата; `joinedload`
  баркодов убран — строке нужен один факт «есть или нет», он добирается одним
  запросом на страницу. И вес: `FILTERED_LIMIT` был 5000, а строка весит около 6 КБ —
  это 32 МБ разметки, которые не успевает ни собрать сервер, ни разложить браузер.
  Стало 500. Массовой правке потолок не мешает никак: галочка в шапке берёт ВЕСЬ
  отбор (`BULK_LIMIT`), сколько бы строк ни показали, и страница об этом пишет.
  Итог замера на копии боевого каталога: поиск — «не отвечает» → 0,4–0,5 с, «нет на
  площадке» — 2,7 → 0,8 с (там же перестали собираться объекты ORM на весь склад
  ради шести полей).
- **«Разобрать →» обязана вести К НАХОДКЕ, а не на страницу.** Находки показываются
  и на «Расхождениях», и на «Диагностике», а половина ссылок вела на `/diagnostics`
  целиком — то есть с той же страницы на ту же: «обновляется, и всё». Теперь каждая
  ведёт якорем на свою карточку (`#stuck-tasks`, `#accounts`, `#workers`,
  `#reconciliation`), а карточка подсвечивается по `:target` — без подсветки прокрутка
  посреди длинной страницы снова выглядит как «ничего не произошло». Якорь на
  несуществующий id — тот же немой отказ, поэтому он закрыт тестом.
- **Находка обязана доводить до строк, а не до страницы.** «Разобрать →» вела на
  `/products` — общий каталог, где никакого списка находки нет, хотя сама находка
  писала «…и ещё 41. Полный список — по ссылке ниже». Обещание было, страницы не
  было. Теперь у строчных находок (`FULL_LISTS` в `app/report.py`) есть своя
  страница `/report/rows/<key>` с полным списком и выгрузкой в Excel; запрос вынесен
  из проверки в `_q_<name>`, чтобы находка и список считали ОДНО И ТО ЖЕ — разойдись
  они, список показывал бы не то, что насчитала находка. Списки собираются только
  при открытии страницы, а не внутри `Finding`: отчёт идёт раз в час и на каждой
  загрузке «Диагностики», а строк бывают тысячи.
- **Причину отказа съедала обвязка, а не отсутствие причины.** В отчёте стояло

  Сверка перепроверяет только ПОСЛЕДНЮЮ отправку по товару
  (`verify_stock.rows_to_verify`), а находка брала любую строку с несовпадением.
  Разница и есть дефект: как только по товару уходит новое число, старая строка
  застывает со своим расхождением навсегда — сверка её больше не тронет, статуса
  она не сменит, и отчёт остаётся красным вечно. 22.09 это поймали в чистом виде:
  находка показывала ТРИ позиции («отправили 60, площадка держит 59»), а сверка
  тем же часом отвечала `diverged: 2`, и это были РАЗНЫЕ строки. По всем трём из
  находки уже прошла новая отправка (59, 54, 0), которую площадка и держала —
  обычная продажа: WB списал единицу, мы приняли заказ и отправили новое число.
  Разобрать такую находку нельзя ничем, она описывает прошлое.
  `report._only_latest_send` оставляет только строки, по паре которых отправка
  последняя. Пара — товар+КАБИНЕТ: свежее число, ушедшее на соседний кабинет,
  про этот не говорит ничего, и заглушить им расхождение значило бы потерять
  оверселл на кабинете, которым давно не занимались. Тот же приём, что у
  `_check_dispatch_errors`, и та же причина: вечно красный отчёт оператор
  пролистывает не читая, и тогда он бесполезен весь.
- **Страница «Есть на складе — нет на площадке»** (`/report/missing-cards`) —
  список товаров с остатком, у которых нет карточки на площадке. Такой товар не
  продаётся и молчит об этом: рассылке отправлять не по чему, заказов не будет,
  в отчёт он попадает только после того, как рассылка попробует и откажется.
  Считается ПО ПЛОЩАДКЕ, а не по кабинету: у WB три кабинета (разные ИП), а
  карточка заводится в одном — товар, заведённый у одного ИП, на витрине WB
  есть, и считать его отсутствующим у двух других значит утроить список
  впустую. Каталог берётся и от выключенных кабинетов. Остаток строго больше
  нуля: иначе список превращается в каталог всей номенклатуры.
- **Страница, к которой ведёт один элемент на другой странице, для человека
  отсутствует.** «Есть на складе — нет на площадке» (`/report/missing-cards`)
  существовала с самого начала, работала и была нужна, но в боковом меню не
  стояла НИ РАЗУ: попасть туда можно было только кнопкой в шапке «Расхождений».
  Пока пунктов было мало, это сходило с рук; 25.09, когда рядом появился пункт
  «Расхождения со складом», страницу стали искать в меню — два похожих названия
  рядом, глаз ищет третье там же, а его там нет. Теперь она в меню своим
  пунктом. Подпись короткая («Нет на площадке» — та же, что на кнопке: третье
  название одной сущности читатель перестаёт связывать с первыми двумя), а
  полное имя живёт в `title`, потому что в свёрнутом меню подписи не видно
  вовсе. Закрыто ДВУМЯ проверками, и вторая не менее важна первой
  (`test_nav_leads_somewhere.py`): пункт ведёт на живую страницу, и страница
  подсвечивает СВОЙ пункт. Второе — немой отказ потише: меню утверждает, что ты
  в другом разделе, и человек считает, что перешёл не туда. Ровно это тут и
  было — `/report/missing-cards` подсвечивала «Расхождения».
- **Страницы отчётов обновляют себя сами** (htmx, `hx-trigger="every Ns"`):
  «Расхождения» раз в две минуты, «Нет на площадке» раз в пять. Оператор держит
  их открытыми и работает по ним — руками он не перезагрузит и будет работать
  по вчерашнему списку. Отметка времени сборки живёт В ФРАГМЕНТЕ, а не в шапке:
  иначе после автообновления данные свежие, а время от первой загрузки.
- **Старые расхождения сверки закрываются кнопкой** («Диагностика»). До
  сентябрьской правки крупная разница помечалась `needs_review` и ждала ручного
  решения; теперь сверка применяет любое движение склада сама и ставит
  `resolved` тут же, так что новых неразрешённых не бывает, а старые (на бою —
  909 штук от 14–16.09) не рассосутся никогда. Кнопка закрывает только то, что
  старше суток, то есть ровно то, что отчёт уже не считает находкой: иначе она
  гасила бы сигнал вместо архива. Остатки, очередь и площадки не трогает.
- **Рассылка событийная, и поэтому нужна команда массовой переотправки.**
  Отправив число, рассылка считает его доставленным и сама к нему не
  возвращается: следующая отправка будет, только когда изменится остаток. Пока
  в кабинет писала вторая система (переход, 19.09), наши числа там перетирались
  — а у нас значилось «отправлено». Когда вторая система замолкает, на площадке
  остаётся ЕЁ картина, и сдвинуть её нечем. Кнопка «Переотправить остаток» на
  «Диагностике» (`transmit.enqueue_resend_all`) и есть недостающее событие,
  поставленное руками: кладёт в очередь текущий остаток по всем транслируемым
  товарам и всем отмеченным у них кабинетам. **Гейты те же** — каждая пара идёт
  через `enqueue_full_resend`, поэтому товар без трансляции и кабинет вне
  расчёта не поедут: по ним ушёл бы ноль и обнулил живую карточку, причём сразу
  по всему каталогу. Число команда не фиксирует: в очередь кладётся текущий
  остаток, итог считает лестница в момент отправки, поэтому повтор безопасен.
  Отсюда же `PUSH_BATCH_SIZE` в `dispatch`: очередь после такой команды длиннее
  обычной, а предел размера запроса есть у каждой площадки. Делим в рассылке, а
  не в клиентах — запрос собирает она.
- **Ноль бывает двух сортов, и различать их обязан КАЖДЫЙ путь.** Ноль от
  РАСЧЁТА (распродано, бронь съела остаток, порог кабинета выше доступного) —
  законное сообщение площадке «не продавать», и уходить он обязан даже первым
  сообщением по карточке: трансляция включена и кабинет отмечен, значит карточку
  мы сознательно взяли под управление. Ноль от ВЫКЛЮЧАТЕЛЯ (ступени 0–2) значит
  обратное — этой карточкой мы не управляем, — и если мы туда ни разу не
  отправляли непустой остаток, он не отзывает наш остаток, а обнуляет чужие
  продажи. Условие живёт в `transmit.blocked_by_switch` и спрашивается ПЕРЕД
  отправкой (`dispatch`), а не только при постановке в очередь: инцидент 18.09
  закрыли на входе, а запись, попавшая в очередь до того как оператор передумал
  (снял галочку раньше 45-секундного цикла, кабинет был на паузе или в backoff),
  доживала до отправки и обнуляла карточку уже оттуда.
- **«Отправляли ли мы туда» живёт на паре, а не в очереди.**
  `SyncSetting.last_nonzero_sent_at` пишет `dispatch` при успешной отправке
  непустого остатка, а `ever_transmitted` спрашивает СНАЧАЛА её. Очередь —
  недолговечная память: чистка удаляет терминальные записи старше тридцати
  суток, а у медленного размера остаток не меняется месяцами. Строка исчезала,
  система забывала, что писала на карточку, и снятие галочки переставало
  отзывать остаток — площадка продолжала продавать по нашему числу, а заказы по
  снятой паре живой опрос уже пропускает. Миграция несёт РАЗОВЫЙ бэкфилл по той
  же формуле: чистка стартует через девять минут после запуска воркера, то есть
  раньше любой новой отправки.
- **Миграция обязана переживать собственный обрыв.** Alembic на SQLite её НЕ
  откатывает: проверено 21.09 — упавшая посередине оставила и новую колонку, и
  временную таблицу бэкфилла, а версию в базе не сдвинула, и повторный
  `alembic upgrade head` падал на «duplicate column name». Накат при этом встаёт
  намертво: продолжить нечем, повторить нечем, службы не перезапущены. Поэтому
  каждый необратимый шаг спрашивает, не сделан ли он уже (`_has_column`,
  `get_indexes`, `DROP TABLE IF EXISTS`), а сам бэкфилл идемпотентен по условию
  `WHERE ... IS NULL`. Закрыто тестом `test_migration_backfill.py`, который
  имитирует остатки оборванного прогона и требует, чтобы повтор дошёл до конца.
- **Разовый бэкфилл идёт АГРЕГАТОМ, а не подзапросом на строку.**
  Коррелированный `SELECT MAX(...)` на каждую из 16 132 настроек SQLite выполнял
  через индекс по СТАТУСУ, а не по паре: без `ANALYZE` оптимизатор считает их
  равноценными, а статус у всех интересных строк один — то есть на каждую
  настройку читалась вся очередь целиком. Замер на боевом масштабе: **134,9 с**
  монопольной блокировки записи при `busy_timeout` 30 с у живых служб, то есть
  `database is locked` у приёма заказов, рассылки и веба, нигде не перехваченный.
  Один проход с `GROUP BY` во временную таблицу с первичным ключом пары — **0,9 с**
  и те же 16 132 отметки. Форма запроса закреплена тестом: она и есть предмет
  правки.
- **Ступень 2 спрашивает «покрыт ли кабинет», а не «был ли расчёт».** Условие
  было `recalc_done_at is not None and кабинет не покрыт`, и первая половина его
  ОТКЛЮЧАЛА: снимешь отметку — и ступень перестаёт срабатывать вовсе.
  Переподвязка баркода делает ровно это, причём в комментарии объясняет, что
  снимает отметку, чтобы остаток по новому набору баркодов не уехал
  непересчитанным, — получалось наоборот. Теперь признак — `coverage_is_tracked`:
  ведём ли мы список покрытых кабинетов. Пустая СТРОКА в `recalc_account_ids` —
  ведём, покрыт никто; NULL — расчёта не было никогда, и для таких товаров
  ступень молчит, как молчала (иначе у всех, кому трансляцию включили до
  появления расчёта, наружу уехал бы ноль).
- **Ворота трансляции спрашивают про те же кабинеты, что опрашивает расчёт** —
  только АКТИВНЫЕ (`broadcast_gate.enabled_account_ids`). Кабинет, погашенный
  предохранителем после пяти сбоёв, расчёт не опрашивает и в покрытые не кладёт,
  а ворота сравнивали покрытие с полным набором отмеченных: строка навсегда
  застревала в «нужен пересчёт: добавлен кабинет», и включить трансляцию было
  нельзя ни по этому товару, ни по любому другому, отмеченному для того же
  кабинета. Расчёт про такой кабинет теперь ГОВОРИТ (`collect_orders` кладёт
  проблему): молча ставить «актуализирован», не заглянув в часть продаж, нельзя.
- **Обрезанная выгрузка каталога не выглядит успешной.** Клиенты поднимают
  `last_truncated`, когда выдачу оборвал наш защитный предел страниц, — но при
  ЗАГРУЗКЕ каталога этот признак никто не спрашивал. Снимок выглядел свежим:
  `fetched_at` у попавших обновлён, счётчик показывает «загружено N», кнопка
  отвечает зелёным. Цена отложенная и потому незаметная: по снимку считаются
  ключи отправки — chrtId у WB (нет его, и остаток уходит баркодом, а приём
  баркода WB умеет отключить) и variant_id у Kit (нет — позиция не уедет вовсе и
  закроется терминально). Неполный каталог оборачивается не ошибкой, а тихо не
  уехавшим остатком. Теперь обрыв идёт в `stats`, в heartbeat (его показывает
  «Диагностика», а лог читают, когда уже что-то случилось) и в сообщение
  оператору на обеих кнопках загрузки.
- **Массовое действие, отправляющее ноль, спрашивает подтверждение с ЧИСЛОМ.**
  «Трансляция выкл» и «Снять кабинет» не просто гасят строки: по каждой паре,
  куда мы реально отправляли непустой остаток, уходит отзыв — ноль на живую
  карточку, и она перестаёт продавать. Число в вопросе не украшение: отбор живёт
  в браузере (sessionStorage) и переживает смену фильтра, так что отмеченные
  строки могут быть уже не видны на экране, и «выключить у отмеченных» без числа
  не говорит человеку ничего. Включение подтверждения НЕ требует: лишний вопрос
  на безопасном действии приучает жать «Да» не читая — и тогда вопрос на опасном
  тоже перестаёт работать.
- **«Сопоставление площадок» собирает картину не на каждый запрос.** Сборка
  читает весь каталог площадок и связанные баркоды 1С и строит union-find: замер
  21.09 — **3,4 с и 54 МБ** на запрос, а фильтры там живые (htmx дёргает фрагмент
  через 400 мс после набора), то есть поиск из шести букв означал несколько
  полных пересборок подряд на веб-службе, которая в это же время принимает
  заказы. С кэшем на минуту (`CLUSTERS_CACHE_TTL`) — 0,05 с и 1 МБ. Минута безопасна потому, что каталог
  меняется не сам по себе, а загрузкой, и оба её пути кэш сбрасывают; минута —
  предел для случая, когда каталог поменяли МИМО приложения.
- **Модульный кэш требует явного события сброса — и на бою, и в тестах.** За
  сессию это выстрелило дважды: кэш ленты заказов и кэш кластеров, каждый раз
  тесты падали в неожиданных местах, потому что второй тест видел данные
  первого. На бою сбрасывают явные события (`create_job` для ленты, загрузка
  каталога для кластеров), в тестах — автофикстура `_fresh_module_caches`.
  Заводишь третий кэш — добавь его в оба места сразу.
- **Сообщение о результате импорта обязано доехать — а оно пропадало.** Флеш
  едет в cookie сессии, браузер отбрасывает cookie длиннее 4096 байт ЦЕЛИКОМ и
  молча. Замер 21.09: импорт двенадцати строк с ошибками дал **7106 байт**, то
  есть оператор видел страницу вообще без сообщения — ни сколько строк
  применилось, ни сколько нет и почему. Чем хуже проходил импорт, тем вернее
  исчезало сообщение. Ловушка в счёте: JSON сессии экранирует не-ASCII, и каждая
  кириллическая буква занимает ШЕСТЬ байт, а после base64 — 8,76; предел в тысячу
  символов не помог вовсе (6674 байта). Посчитано по факту: `MAX_FLASH_CHARS` =
  440, cookie 2923 байта. Обрезаем с пометкой и с НАЧАЛА: там итоги («обновлено
  N, ошибок M»), а примеры ошибок в конце — потерять примеры неприятно, потерять
  всё сообщение значит оставить человека в уверенности, что файл применился
  целиком. Тест меряет настоящий размер cookie, а не длину строки.
- **Выгрузка конфликтов сопоставления берёт ВЕСЬ отбор, а не страницу.** Конфликт
  заводится в момент, когда по баркоду пришёл реальный заказ и разнести его не
  удалось: каждая строка — уже случившаяся непроведённая продажа, и пока баркод
  не сопоставлен, каждый следующий заказ повторит то же самое. Файл для того и
  выгружают, чтобы разобрать их пачкой, а он отдавал первые триста и молчал об
  этом. Рядом были ещё два слоя той же беды: счётчик страницы считался как
  `len(rows)`, то есть показывал «300» при любом числе конфликтов, и строка
  «Показаны первые N из M» выводилась для всех видов, КРОМЕ конфликтов. Чинить
  надо было все три — иначе оператор всё равно не узнал бы, что список обрезан.
  Тесты на сами запросы этого не ловили: дефект был в том, КАК их зовёт
  страница, — проверка идёт через HTTP.
- **Справочник баркодов коммитится ПОРЦИЯМИ.** Полный недельный прогон — 154 232
  строки, и одна транзакция на всё держала эксклюзивную блокировку записи всё
  время импорта. Замер 21.09 с параллельным писателем: одной транзакцией — 36,0 с
  и ожидание записи до **13,37 с**; порциями по тысяче (`DICT_COMMIT_EVERY`) — 26,2 с и 0,43 с. Отказа
  `database is locked` в замере не случилось только потому, что `busy_timeout`
  тридцать секунд: тринадцать — опасно близко. Атомарность тут не нужна и даже
  вредна: строки независимы, импорт идемпотентен (заводим только недостающее), и
  оборвавшийся прогон доделает следующий, а не откатит сделанное.
- **Повтор баркода в выгрузке площадки не роняет загрузку каталога.** Проверка
  «нет ли уже такого» идёт запросом, а сессия живёт с `autoflush=False`: первый
  `db.add` до базы ещё не дошёл, и второй такой же баркод в ТОЙ ЖЕ выгрузке
  уходил вторым INSERT — `UNIQUE constraint failed`, и падала вся загрузка
  каталога кабинета. Падала бы и каждый следующий раз, пока площадка отдаёт ту же
  выгрузку, а каталог тем временем молча устаревает: по нему считаются chrtId для
  WB и variant_id для Kit, то есть ключи, КОТОРЫМИ УХОДИТ ОСТАТОК. Тот же дефект
  и с той же причиной был в импорте «Мэппинга» — если видишь `db.add` после
  проверки запросом, ищи третью такую же.
- **Отказ отправки различается по одному вопросу: переживёт ли он повтор.**
  Спека `/api/v3/stocks/{warehouseId}` документирует для 409 и 406 несколько
  кодов, и до сих пор разбирался ровно один (`NotFound`). Остальные уходили
  наверх сырыми: пять попыток по нарастающей паузе в заведомо неизменный ответ,
  потом `error` по ВСЕЙ пачке, а отчёт относил это к «рассылка не доехала» — то
  есть «чините связь». `STOCK_POSITION_TERMINAL_CODES` называют виновную позицию
  поимённо в `data` и при повторе ответят тем же (склад не подходит для типа
  груза, категория недоступна для типа доставки, количество вне предела): такую
  позицию вынимаем и закрываем сразу, остальную пачку досылаем.
  `STOCK_RETRYABLE_CODES` повтор ПЕРЕЖИВУТ, и метить их терминальными нельзя —
  остаток не уехал бы уже никогда. Среди них важнейший — `StatusNotAcceptable`,
  **бан поставщика**: пока он не снят, остатки по кабинету не обновляются вовсе,
  и прятать это за «не отправлено за 5 попыток» значит искать причину не там.
  `ProductPropertyConflict` виновных НЕ называет, поэтому он тоже повторяемый:
  выкинуть всю пачку значило бы похоронить девяносто девять здоровых позиций
  из-за одной неизвестной. Незнакомый код по-прежнему отдаётся как есть —
  разбирать за площадку то, чего не понимаем, мы не беремся.
- **Лента помнит не всю историю, и слишком старая дата расчёта — это ПРОБЛЕМА.**
  Спека WB: `/api/v3/orders` отдаёт задания, созданные не более трёх месяцев
  назад (`ORDERS_HISTORY_DAYS` = 90); для старших есть отдельный метод архивных
  заказов, которого мы не используем. Запрос от более старой даты не падает и не
  жалуется — он честно отвечает ПУСТОТОЙ. Замер 18.09 это уже нащупал, только
  принял за особенность окна: `dateFrom=01.07` вернул ноль, тогда как от 07.08
  их было 244. Без проверки расчёт рапортует «проведено 0, проблем нет» и ставит
  «актуализирован», открывая трансляцию полного остатка по невиденным продажам —
  ровно исход инцидента 18.09. `collect_orders` спрашивает у клиента
  `orders_history_days` и на слишком старой дате даже не ходит в сеть: ответ
  заведомо пуст, а запрос стоит лимита. Поле есть ТОЛЬКО там, где предел
  подтверждён (WB — спекой и замером); у Ozon и Kit его нет, и выдумывать предел
  за площадку мы не станем — ложная проблема не даст включить трансляцию там,
  где всё в порядке.
- **Лента заказов кабинета берётся ОДИН раз на прогон, а не на каждый товар.**
  `collect_orders` звала `get_orders_since` на КАЖДЫЙ товар, а лента у кабинета
  одна: расчёт по тысяче позиций при пяти отмеченных кабинетах — пять тысяч
  полных выкачек, и каждая у WB идёт окнами по 29 дней с листанием по курсору,
  то есть десятки запросов. Отсюда и «расчёт идёт минутами», и упор в лимиты
  площадок — тот самый, из-за которого у Kit терялись строки заказов. Кэш живёт
  `ORDERS_CACHE_TTL` = 5 минут и НАМЕРЕННО недолго: расчёт больших пачек идёт
  десятками тиков, и вечная лента означала бы отметку «актуализирован» по
  получасовой давности картине; незамеченный заказ при этом всё равно проведёт
  живой опрос — он ходит каждые 45 секунд по тем же отмеченным кабинетам.
  Признаки неполноты (`last_unresolved`, `last_truncated`) кэшируются ВМЕСТЕ с
  лентой: иначе второй товар получил бы ленту без них и отметку по картине,
  которую первый справедливо счёл неполной. Кэш сбрасывает `create_job` (новое
  задание — новая картина) и автофикстура в тестах: модульное состояние иначе
  течёт между тестами и роняет их в неожиданных местах.
- **Смена даты расчёта снимает «актуализирован»** — но ТОЛЬКО если расчёт был.
  Расчёт поднимает заказы от заданной даты; сменили дату — его вывод к новому
  периоду не относится. Видно это было не сразу: смена даты стирает факт, а
  проверка факта в `calc_status` стоит РАНЬШЕ проверки расчёта, поэтому строка
  показывала «нужен факт», человек вводил факт — и строка объявлялась
  актуализированной по расчёту от ПРЕЖНЕЙ даты. Сдвиг даты НАЗАД опаснее всего:
  заказы за добавившийся кусок периода не проведены, остаток завышен ровно на
  них. Оговорка про «только если расчёт был» — не мелочь: у товара без расчёта
  `recalc_account_ids` пуст (NULL), и выставить там пустую СТРОКУ значит включить
  ступень 2 лестницы, которая для таких товаров обязана молчать, — на отмеченный
  кабинет ушёл бы ноль. Поймано тестом, а не глазами.
- **РАСХОЖДЕНИЕ УЧЁТА СО СКЛАДОМ — свойство ТОВАРА, а не даты**
  (`Product.stock_discrepancy`, `учёт 1С − сколько лежит на самом деле`). Это
  главное число всего механизма порога, и до 23.09 оно нигде не хранилось:
  выводилось на лету из пары «остаток на дату − факт на дату», то есть носителем
  выступала ДАТА. Отсюда весь класс бед — сменили дату, факт справедливо стёрся,
  расхождение исчезло, порог схлопнулся до брони, и наружу поехал остаток,
  завышенный ровно на расхождение. Теперь:

      порог = расхождение + бронь

  Дату можно двигать куда угодно, расхождение не шелохнётся: учёт врёт на одну и
  ту же величину, пока склад не пересчитали заново. Знак значим и обе стороны
  законны — плюс «в 1С числится больше, чем лежит», минус «на складе больше, чем
  знает 1С» (на бою таких 53 товара, до −213), поэтому `max(0, ...)` по этому
  числу где угодно — дефект. **NULL и ноль — РАЗНЫЕ вещи**: NULL «не измеряли»,
  ноль «измеряли, склад сошёлся», и ноль ставится только явно.
  Меняют расхождение ровно три события, и все три проходят через
  `offset_base.set_discrepancy`, который заодно пишет строку истории
  (`StockDiscrepancyLog`): новое измерение (`apply_fact` — факт, ОТЛИЧНЫЙ от
  учёта), прямая правка числа (поле в строке, колонка «Расхождение» в файле) и
  задание порога (`apply_offset` считает обратным счётом `порог − бронь`). Всё
  остальное — смена даты в любую сторону, снятие факта, правка брони — его не
  трогает вовсе.
  **Факт, РАВНЫЙ учёту, расхождение НЕ трогает, и это главное правило.** Он
  значит «мне нечего возразить цифре 1С», а не «я пересчитал склад и он
  сошёлся». Разница видна ровно в одном месте, и оно же самое дорогое: у строки,
  чью дату сдвинули назад, факт на новую дату пуст, а склада на прошлое число
  оператор не знает — он вписывает учётное. Прежним поведением это стирало бы
  расхождение и схлопывало порог, сразу по всему отбору. Сказать «склад сошёлся»
  по-прежнему можно — расхождением 0. Снять измерение целиком (в NULL) умеет
  только «Сбросить порог» (`clear_offset`), и он ОБЯЗАН снимать расхождение
  вместе с порогом: оставь его — ближайший пересчёт вернул бы порог по формуле, и
  кнопка выглядела бы сломанной.
  Механизм `pin_offset`/`offset_pinned` этой правкой УБРАН, и не потому, что
  надоел: он подбирал факт под сохранённый порог (`факт = учёт − порог + бронь`),
  а подобранное число оператор видит как измерение, которого не делал, и
  «поправляет» на учётное. 23.09 на бою по 27643 это сложилось в три шага, каждый
  сам по себе верный: 15:07:51 механизм удержал порог 11 и подобрал факт 32 при
  учёте 43; строка показала число, которого оператор не вводил; 15:10:44 массовая
  кнопка поставила факт = учёту, порог честно стал нулём — и на обе площадки
  уехало 22 при реальном складе около 11. Итого 62 товара и 418 лишних штук в
  продаже. Вместе с механизмом ушли счётчики `offsets_kept`/`offsets_lost`,
  строка heartbeat у `ftp_receive` и находка `offset_not_kept`: событие
  «удержать не вышло» исчезло, а находка без писателя так же бесполезна, как
  писатель без читателя. Колонка `offset_pinned` осталась мёртвой и погашена
  миграцией — `DROP COLUMN` на SQLite перестраивает таблицу в 152 тысячи строк
  при живых службах.
  **Строка на «Товарах» и колонка в файле показывают одно и то же ХРАНИМОЕ
  число.** Строка называет порог слагаемыми («расхождение 11 + бронь 2»), а не
  формулой от даты: только так видно, что изменит правка расхождения и что —
  правка брони. Арифметика «43 − (32 − бронь 0)» это тоже показывала, но читается
  как формула, а не как утверждение о складе. Колонка «Расхождение» в выгрузке
  стала ПРАВИМОЙ (была «(справочно)»): у строки, чью дату сдвинули назад, факт
  пуст, и справка «учёт минус факт» выходила пустой при живом пороге — файл
  показывал «расхождения нет» там, где оно есть. Колонок, двигающих порог, теперь
  две, и обе выгрузка заполняет, поэтому импорт спрашивает у каждой «человек
  изменил ЭТУ ячейку?», сравнивая со снимком до правок строки
  (`discrepancy_as_exported`, `offset_as_exported`): сравнивай он с текущим
  значением — нетронутая ячейка порога откатывала бы правку расхождения, молча и
  по всему файлу.
  **`broadcast_gate.calc_status` спрашивает «подтвердил ли человек цифру», а не
  «есть ли факт»**: хранимое расхождение — то же подтверждение, только снятое на
  другую дату. Спрашивай гейт один факт, каждый сдвиг даты назад возвращал бы
  строку в «нужен факт» и закрывал ворота трансляции по товару, у которого с
  порогом всё в порядке. Разница ещё и в том, ОТКУДА строка выберется сама:
  «нужен факт» в `DEFERRABLE_CALC_STATUSES` не входит (факт вводит человек), а
  «нужен расчёт» входит — то есть после сдвига даты назад отложенная просьба
  включить трансляцию из файла теперь запоминается, а не становится ошибкой
  импорта. На сами ЗАКАЗЫ факт не влияет никак и не влиял: `recalc.catch_up_product`
  спрашивает у товара только дату, и лента поднимается от неё
  (`test_orders_are_pulled_after_a_step_back_without_a_new_fact`).
  История (`StockDiscrepancyLog`) — отдельной таблицей, а не записью в общий
  журнал действий: нужна цепочка ИМЕННО по товару, а массовые пути (кнопки
  отбора, импорт Excel) в журнал построчно не пишут вовсе — по конкретной строке
  там следа нет. Храним и контекст измерения (дата, учёт, факт): без него «стало
  11» через месяц не перепроверить. Пишем только при ИЗМЕНЕНИИ значения — иначе
  повторный импорт того же файла утопил бы настоящие правки. Чистка (год) не
  трогает ПОСЛЕДНЮЮ запись по товару никогда: она и есть происхождение числа,
  которое прямо сейчас сидит в пороге, а расхождение ставят один раз и не
  трогают годами.
- **Порог, записанный мимо формулы, находит отчёт** (`_check_offset_disagrees`).
  `порог = расхождение + бронь` держится ровно тем, что `recompute_offset` зовут все,
  кто двигает любое из слагаемых, — то есть соглашением, а не механизмом. 23.09 его
  нарушение стоило 62 товаров и 418 лишних штук в продаже, и увидеть это было
  неоткуда: строка показывала согласованные числа, отчёт молчал, а наружу уже уехал
  остаток, завышенный ровно на расхождение. Находка сравнивает хранимый порог с тем,
  что даёт САМ `offset_from_base`, а «сколько уходит» считает САМА `sku_quantity`:
  повтори мы любую из двух формул запросом, находка однажды пообещала бы не то, что
  произойдёт. Запрос отбирает только кандидатов и только по колонкам, и все три его
  условия — про отсутствие следствия. Трансляция включена: у выключенной строки
  неверный порог наружу пока не уходит. Порог ЕСТЬ: строка без порога под его
  управлением и не находится — лестница отдаёт по ней «остаток минус бронь», а
  формула на ней (расхождения нет, дата есть, факта нет) даёт ровно бронь, то есть
  то же число; объяви мы это расхождением, находка горела бы у каждой настроенной,
  но ещё не измеренной строки. И есть из чего вывести порог — граница, на которой
  `offset_from_base` отдаёт None: там живёт число, введённое руками. Следствие
  называется НАПРАВЛЕНИЕМ: порог меньше формулы — наружу уходит больше, чем есть
  (оверселл, и лишние штуки считаются числом), больше — товар недопродаётся. Одно
  следствие на оба случая было бы неправдой ровно в половине строк.
  **Молчание этой находки подкрепляется числом** —
  `scripts/probe_offset_invariant.py`. Молчание проверки значит «инвариант цел»
  ТОЛЬКО если проверке было что смотреть: проверка, которая ничего не видит
  (отбор разошёлся со схемой, условие сузилось правкой), молчит ровно так же,
  как проверка, которой нечего сказать, — и по зелёному отчёту эти два случая
  неразличимы. Скрипт печатает СНАЧАЛА число кандидатов под отбор находки и
  прямо говорит, что ноль кандидатов — это не «всё хорошо». Формулу он выводит
  САМ, обычной арифметикой, вопреки правилу «у формулы один хозяин»: правило
  про боевые пути, где два счёта обязаны совпадать по построению, а здесь
  предмет проверки — сама формула, и позови скрипт `offset_from_base`, он
  согласился бы с находкой всегда, что бы в ней ни сломалось. Оба числа
  печатаются рядом, и расхождение между ними — сигнал важнее любой отдельной
  строки: отчёт считает не то, что описано в скрипте. Закрыто тестами, которые
  прогоняют сам скрипт подпроцессом, включая подмену формулы В СКРИПТЕ: сверка
  обязана закричать, а не промолчать.
- **У расхождения теперь есть своя страница** (`/discrepancies`,
  `app/discrepancies.py`). Число решает, сколько уходит на площадки
  (`порог = расхождение + бронь`), а увидеть его можно было только построчно в
  каталоге на 152 тысячи позиций либо скриптом с консоли сервера — то есть
  вопрос «где у нас расхождения и откуда они взялись» ответа не имел. Ответ при
  этом записывался: `StockDiscrepancyLog` помнит, чем и когда поставлено каждое
  число, но читателя у этой записи не было вовсе — писатель без читателя.
  Страница, а НЕ находка отчёта: ненулевое расхождение это норма, и находка,
  срабатывающая на норме, приучает пролистывать отчёт целиком. Ноль и NULL в
  список не попадают: ноль — «измеряли, склад сошёлся», то есть отсутствие
  расхождения, NULL — «не измеряли» вовсе. Сортировка ПО МОДУЛЮ, а не по знаку:
  разбирают список сверху, и плюс на 200 штук стоит разбора не меньше минуса на
  213 (закрыто тестом, где в наборе есть и то и другое — без большого минуса обе
  сортировки дают один порядок, и подмена не ловится). Два отбора, и оба про
  цену ошибки: «только отрицательные» — там наружу осознанно уходит БОЛЬШЕ
  учётного остатка, и устаревшее измерение уже оверселл; «только с включённой
  трансляцией» — по остальным неверное число пока ничем не грозит. Происхождение
  собирается ОДНИМ запросом на страницу (`_origins`, `max(id)` + `IN`), а не
  подзапросом на строку. Число, поставленное до 23.09, истории не имеет, и
  строка говорит это вслух: пустая ячейка читалась бы как «никто не ставил».
- **Артикул один на весь размерный ряд** — и `scripts/probe_offset.py` брал по
  нему `.first()`, то есть ПРОИЗВОЛЬНЫЙ размер, не печатая размера в выводе.
  Спрашиваешь «откуда расхождение −2 на 5XL», получаешь числа по S, и заметить
  это нечем: ответ выглядит ответом, а по нему решают, правильный ли порог
  уходит наружу. Теперь размер вторым аргументом, неоднозначность — ОТКАЗ со
  списком строк, а размер с цветом печатаются всегда, даже когда строка нашлась
  одна. Тест прогоняет сам скрипт подпроцессом: предмет правки — то, что увидит
  человек в консоли сервера, а не поведение функций.
- **Справочник 1С перебивает ДОГАДКУ автопривязки — и только её.**
  `catalog_sync` привязывает незнакомый баркод, если его соседи по карточке
  площадки ведут к одному товару 1С (`POOL_GUESS_SOURCE`). Догадка полезная, но
  не первичный учёт. Приём справочника не менял существующие привязки НИКОГДА,
  поэтому ошибочная догадка жила вечно: заказ списывался с ЧУЖОГО товара — у него
  остаток падал зря, у настоящего оставался завышенным и уезжал наружу, — а
  конфликт сопоставления автопривязка уже удалила, то есть увидеть это было
  неоткуда. Ручную переподвязку (`excel_repoint`) не трогаем: она сделана под
  отдельной галочкой, это решение человека.
- **Разные остатки по баркодам ОДНОГО товара — сигнал.** Несколько штрихкодов
  одного SKU держат один физический остаток, и 1С отдаёт по ним одно число.
  Разные означают ошибку привязки, а сверка берёт максимум — то есть ЧУЖОЙ
  остаток. Формулу не меняем (минимум и сумма врут так же, просто в другую
  сторону, а чинится это мэппингом), но считаем ТОВАРЫ и пишем WARNING.
- **Просьба включить трансляцию не должна повисать молча.** «Ждём 1С» рассосётся
  само — но рассосётся оно в «нужен факт», если факта нет ни у товара, ни в
  файле, а факт вводит человек. Такая просьба висела бы вечно, причём молча:
  оператор считает, что всё указал файлом. Теперь она становится ошибкой импорта
  сразу, а зависшие по другим причинам (расчёт с проблемами, погасший кабинет)
  ловит находка отчёта `stuck_broadcast_requests` со своим полным списком
  (порог — `PENDING_BROADCAST_STUCK`, сутки).
- **Предел импорта — в СТРОКАХ, потому что стоимость в строках.** Потолок в
  сорок мегабайт не защищает ни от чего: замер 21.09 — 50 000 строк весят 2,5 МБ
  и читаются 38 с, весь каталог (152 235 строк) — 7,7 МБ и **123 с**. Оба файла
  проходят мегабайтный потолок с запасом, а веб-служба, которая в это же время
  принимает заказы с площадок, занята одним запросом две минуты — и это ДО
  обработки строк, где на каждую идут запросы в базу. `MAX_IMPORT_ROWS` = 20 000,
  тот же порядок, что `BULK_LIMIT`. Отказ, а не обрезка: молча применить часть
  файла и промолчать про остальное — худшее из поведений, файл правят целиком и
  считают применённым целиком.
- **Пустая ячейка в файле импорта НИЧЕГО НЕ МЕНЯЕТ** (`_cell_intent` в
  `app/routers/products.py`). Каждая колонка понимала пустоту как самое
  разрушительное из возможных значений: «Трансляция» и «<кабинет> —
  Синхронизировать» читались как «Нет», а это не выключение, а ОТЗЫВ остатка —
  ноль на живую карточку, по всем кабинетам товара сразу; «<кабинет> — Порог»
  становился нулём; «Порог трансляции» стирался, возвращая на площадки ПОЛНЫЙ
  остаток; «Дата расчёта» снимала расчёт вместе с ФАКТОМ, полученным пересчётом
  склада руками. Выгрузка эти ячейки заполняет всегда, поэтому пустой ячейка
  становится ровно в двух случаях — её стёрли или файл собран не из нашей
  выгрузки, — и ни один не значит «примени ко всему файлу самое опасное». Снять
  значение можно, сказав вслух: «-» в ячейке (`CLEAR_CELL`). Та же дверь была на странице:
  массовое «Дата расчёта =» с пустым полем снимало расчёт и факт по всему отбору,
  хотя для чисел отказ при пустом поле стоял там всегда. Снять расчёт массово —
  кнопка «Сбросить порог».
- **Массовый путь обязан делать то же, что построчный.** Три дефекта подряд были
  ровно об этом: массовое выключение трансляции не отзывало остаток (галочка в
  строке отзывала), массовая правка брони не пересчитывала порог (одиночная
  пересчитывала), «Трансляция = Нет» в Excel не отзывала (снятие галочки
  кабинета в том же импорте — отзывало). Последствие у всех одно и то же —
  оверселл, — но массовым путём сразу по всему отбору. Правишь одиночный
  обработчик — ищи его близнеца в `bulk_edit` и в `products_import`.
- **Отбор живёт в браузере, а уезжает разметкой — и на этом стыке он терялся.**
  23.09 на бою: отбор 1739 строк, показано 500 (`FILTERED_LIMIT`), под таблицей
  написано «галочка в шапке выбирает весь текущий отбор — все 1739… остальные тоже
  будут изменены, хотя их не видно». Нажатие дало «изменено строк — 500». Причин
  две, и обе про один стык. Галочка «весь отбор» стоит В ШАПКЕ ТАБЛИЦЫ, а таблицу
  htmx подменяет целиком при каждом изменении фильтра и отдаёт всегда снятой:
  отметки строк из `sessionStorage` восстанавливались, эта галочка — нет, `all_filtered`
  на сервер не уходил, и правка шла по показанным строкам. И вторая: отмеченных
  бывает БОЛЬШЕ, чем показано (отбор переживает смену фильтра), а форма отправляет
  только те чекбоксы, что есть в разметке, — счётчик говорил 849, уезжало 500.
  Теперь флаг хранится рядом с самим отбором (`pr-all-filtered`) и восстанавливается
  на каждую подмену, а недостающие отметки дописываются скрытыми полями перед
  отправкой. Счётчик обязан называть ЧИСЛО («весь отбор — 1739 шт»), а не одно
  слово: флаг переживает смену фильтра, и число — единственное, по чему видно, что
  под галочкой стало другое множество. Снятая галочка строки при включённом «весь
  отбор» — противоречие, которого сервер выразить не умеет («всё, кроме этой»): она
  переводит правку на отметки, и счётчик тут же меняет число — сужение видно в
  момент, когда происходит. Цена дефекта не в неудобстве: «изменено 500» выглядит
  как успех, оператор считает отбор настроенным, а про оставшиеся 1239 строк не
  узнаёт никогда — они просто молчат. Предел и порции по `IN (...)` теперь на ОБОИХ
  путях: он стоял только у правки по отбору, а список отметок уходил в базу любой
  длины (`UIDS_CHUNK` — про 999 параметров у SQLite до 3.32, чего на машине
  разработки не увидеть).
- **Отбор, переживший смену фильтра, обязан спрашивать про строки вне экрана.**
  Это обратная сторона правки, которая научила форму дописывать невидимые
  отметки скрытыми полями. Само свойство верное — без него уезжало 500 строк из
  1739, и оператор об этом не узнавал, — но 24.09, в первый же день после
  наката, оно выстрелило с другой стороны: в отборе накопилось 846 строк от
  прежних фильтров, оператор нашёл поиском ОДИН товар, отметил его строку и
  нажал «Расчёт» — задание ушло по всем 846. С экрана это выглядело как работа с
  одной строкой: искал один товар, видел один товар, отметил один товар.
  Счётчик «846 шт» рядом с кнопками не спас и не мог — он маленький, серый и не
  объясняет, что 845 из этих строк сейчас не видно. Теперь любая кнопка массовой
  правки (`button[name="action"]`, а не только те, у кого свой `data-confirm`)
  спрашивает подтверждение с ТРЕМЯ числами: сколько отмечено, сколько из них на
  экране и сколько уедет невидимыми. Условие строгое — `offscreen > 0`: отмечено
  ровно то, что видно, значит вопроса нет, иначе лишний вопрос на безопасном
  действии приучит жать «Да» не читая, и вопрос на опасном тоже перестанет
  работать. «Весь отбор» тоже молчит намеренно: там галочка стоит в шапке ТОЙ ЖЕ
  таблицы, счётчик называет число текущего отбора и меняет его при смене
  фильтра, а строка под таблицей говорит это словами.
- **«Записать остаток ЦС на дату» не затирает порог, поставленный человеком.**
  23.09 на бою по 27643, по журналу с точностью до минуты: 15:07:14 дата сдвинута
  назад (07.08 → 06.07); 15:07:51 механизм удержания СРАБОТАЛ — порог 11 сохранён,
  под него подобран факт 32, наружу ушло 11 из 22; 15:10:44 массовая кнопка
  поставила факт = учёту (43), расхождение стало 0, порог 0, и на обе площадки
  уехало 22 при реальном складе около 11. Дальше то же по 500 и дважды по 849
  строкам. То есть механизм удержания отработал, а через три минуты его результат
  стёрла кнопка — молча, сразу по всему отбору и в сторону ЗАВЫШЕНИЯ остатка.
  Соседняя ветка того же цикла (`fact_from_stock`) это правило соблюдала и прямо о
  нём говорила: «затирать введённые руками цифры массовой кнопкой нельзя». Две
  соседние ветки утверждали противоположное, и выиграла та, у которой не было
  теста. Условие теперь ОДНО на двух хозяев — `offset_base.offset_is_established`:
  сдвиг даты назад спрашивает по нему, что удерживать, кнопка — чего не затирать;
  разойдись они, один механизм сохранял бы порог, а второй тут же схлопывал.
  Порог, равный броне, работой человека НЕ считается (формула даёт его сама),
  иначе кнопка перестала бы работать почти везде. Пропуск не молчит: сообщение
  называет число и говорит, как всё-таки схлопнуть («Сбросить порог», затем
  кнопка) — молчаливый пропуск был бы тем же дефектом с другой стороны.
  Восстановить затёртое из текущей базы нечем — прежний факт перезаписан, склад в
  прошлом не пересчитать; выручает только суточная копия, и для этого есть
  `scripts/restore_offsets_from_backup.py`: сверяет ПОРОГ (не факт — между копией
  и сегодня дату могли сдвинуть, и факт «на дату» относился бы к другой дате) и
  собирает .xlsx для штатного импорта. Отбор вынесен в `plan_restore` и закрыт
  тестами: цена ошибки тут вся в нём — лишняя строка вернёт порог там, где человек
  изменил его намеренно, недостающая оставит оверселл, и обе ошибки молчаливые.
  `--broadcasting` сужает до товаров с ВКЛЮЧЁННОЙ трансляцией: только их остаток
  уходит наружу прямо сейчас, то есть только по ним неверный порог и есть оверселл;
  трансляция читается из БОЕВОЙ базы, а не из копии (её могли включить после).
  `--exact` берёт все расхождения, а не только упавшие. Две корзины в файл не идут
  и перечисляются ПОИМЁННО: «в копии порога не было» (снять порог у строки с датой
  файлом нельзя — это кнопка «Сбросить порог») и «вернуть нельзя» (подобранный факт
  вышел бы отрицательным). Молчание о них означало бы «восстановлено всё», когда
  часть работы осталась человеку. Писатель .xlsx ОДИН на приложение и скрипты
  (`excel_utils.build_xlsx_bytes`): второй разошёлся бы заголовками, и файл из
  скрипта перестал бы читаться импортом.
- **Постоянное состояние установки не ездит тем же флешем, что ответ на действие.**
  «Пока нет ни одного активного кабинета» ставилось на КАЖДОЙ загрузке `/products` и
  затирало сообщение, приехавшее с редиректа: отказ массовой правки, итог импорта,
  «изменено строк — N». Видно это только на свежей установке, где кабинета ещё нет, —
  то есть ровно тогда, когда идёт настройка и сообщения нужнее всего.
- **`is_test` закрывает одну сторону границы, боевой номер заказа — другую.**
  Флаг не даёт симуляции создать боевую побочную запись, но боевую запись можно
  было ПЕРЕДАТЬ в симуляцию: «Симулировать отмену/подтверждение» искали заказ
  только по номеру и кабинету, а номер приходит формой. Отмена боевого заказа
  возвращала остаток у НАС по-настоящему, а задание в 1С помечала тестовым —
  обратного документа там не будет никогда: товар вернулся в продажу у нас и
  остался отгруженным в 1С. Вдобавок заказ помечался `cancelled`, и настоящую
  отмену живой опрос потом пропустил бы как уже обработанную. Подтверждение тем
  же способом съедало перемещение «Ожидает → Склад». Теперь обе кнопки требуют
  номер с префиксом `TEST-` (`_refuse_live_order`).
- **Отправка со страницы «Тестирование» настоящая — значит и след настоящий.**
  «Шаг 1» шлёт непустой остаток на боевую площадку, но `last_nonzero_sent_at` не
  писал: система не запоминала, что писала на карточку, и снятие галочки потом
  не отзывало остаток — ровно тот дефект, ради которого колонка и заведена.
  Пауза кабинета там же: непустой остаток в остановленный кабинет не уходил и
  раньше (пауза — ступень 3 лестницы, она даёт 0), но пара, куда мы КОГДА-ТО
  писали, проходила проверку «ноль не отправляем» — и кнопка обнуляла карточку в
  кабинете, который оператор намеренно остановил, показывая зелёное «успешно
  отправлен». Теперь отказ идёт раньше и называет причину.
- **Страница «Тестирование» ставит записи в очередь ТОЛЬКО через
  `enqueue_full_resend`.** «Очистить» и «Сброс истории бэкфилла» делали это
  прямым `db.add`, мимо обоих гейтов, — а страница для того и нужна, чтобы
  прогнать товар ДО включения трансляции, то есть кнопку нажимают ровно в том
  состоянии, где лестница даёт ноль. Кнопка «Шаг 1: отправить остаток» шлёт на
  боевую площадку по-настоящему, поэтому она тоже спрашивает `ever_transmitted`
  и на ноль по нетронутой карточке отвечает отказом, а не зелёным «успешно
  отправлен».
- **Лента площадки кончается там, где сказала площадка, — и это про ВСЕ методы,
  а не только про заказы.** У Ozon приём заказов читал одну страницу на сто
  отправлений (больше сотни в `awaiting_approve` — и заказы со сто первого не
  видел никто), а отмены — одну страницу из тысячи САМЫХ СТАРЫХ. Каталог WB
  просил `limit=1000` при `maximum: 100` по спеке, то есть двести страниц
  покрывали двадцать тысяч карточек вместо двухсот. Каталог Kit останавливался
  по короткой странице — тем самым стопом, который в этом же файле объявлен
  ненадёжным. Упёрлись в свой предел — поднимаем `last_truncated`; неполный
  список скрытых карточек Kit возвращается как `None`, а не как полный.
  Там же и вторая половина правила: **упереться в предел мало — надо сказать**.
  У каталога Ozon ветки `else: last_truncated = True` не было вовсе (`range(50)`
  без неё), то есть огрызок отдавался как полный каталог, и вся видимость
  обрыва — `stats["truncated"]`, предупреждение в логе, текст на странице —
  молчала. Цена у Ozon выше, чем у соседей: остаток туда адресуется АРТИКУЛОМ из
  каталога, и позиция, не попавшая в огрызок, ключа отправки не получает —
  рассылка закроет её как «нет карточки», а отчёт отнесёт к `unknown_sku`
  («продавать нечего, оверселла не будет»), что для живой продающейся карточки
  неправда. Обязанность общая на все три клиента и закрыта тестом на каждый.
- **Не публиковать и молчать — разные вещи.** `_publish_restocked` спрашивает у
  Kit список скрытых карточек, и `None` значит «спросить не удалось», а пустое
  множество — «скрытых нет». Код проглатывал оба одним `if not hidden: return 0`,
  хотя комментарий рядом объявлял различие важным. Следствие у первого своё:
  остаток на карточку ушёл, площадка его приняла, у нас всё зелено — а карточка
  осталась скрытой, товар покупателям не виден и сам не вернётся. Второй попытки
  не будет: публикация идёт по ключам, отправленным В ЭТОМ цикле, а у медленного
  размера следующая отправка случится, когда изменится остаток, то есть через
  месяцы. Теперь это WARNING в логе, счётчик `unchecked` в статистике цикла и
  запись журнала действий — она переживёт ротацию логов.
- **Повтор зависшего создания по ОТМЕНЁННОМУ заказу создаёт документ, который
  нечем отменить.** Последовательность вся штатная: `CREATE_MOVEMENT` ушёл, 1С
  уронила файл целиком и молчит → через 15 минут `timeout`; площадка приносит
  отмену, `process_cancellation` возвращает остаток, заводит `CANCEL_MOVEMENT` и
  ставит заказу `cancelled`, а зависшее создание НЕ ТРОГАЕТ; отмена уезжает
  минутным файлом, `ОтменитьПеремещенияЗаказа` документа не находит (его и не
  было) и отвечает `OK|нет документов для отмены` — задание закрывается; через
  полчаса `repost_stuck_movements` возвращает создание в `pending`, и 1С СОЗДАЁТ
  перемещение по заказу, которого больше нет. Второй отмены не будет никогда:
  `existing_cancel_task` видит закрытое CANCEL_MOVEMENT в любом статусе, а заказ
  со статусом `cancelled` из опроса отмен выпал. Единица навсегда числится
  отгруженной, физически лёжа на ЦС, и часовая сверка это закрепляет.
  Идемпотентность 1С, на которой держится весь механизм повтора, здесь работает
  ПРОТИВ нас: она обещана по СУЩЕСТВУЮЩЕМУ документу, а тут документа нет вовсе.
  Отбор на повтор теперь спрашивает `ProcessedOrder` (`_orders_already_cancelled`,
  пара заказ+КАБИНЕТ — номера у разных площадок совпадают), и такое задание
  уходит в ручной разбор: есть документ в 1С или нет, знает только человек.
- **Зависшее задание, которого не возьмёт автоповтор, обязано попасть в разбор.**
  Правило общее, и раньше его не было: `tasks_needing_review` требовал
  исчерпанных повторов ИЛИ выключенного автоповтора. А `repost_stuck_movements`
  берёт ТОЛЬКО `CREATE_MOVEMENT` — значит у `CANCEL_MOVEMENT` и
  `CONFIRM_MOVEMENT` счётчик повторов не растёт и не может, и при включённом на
  бою автоповторе зависшая отмена не попадала в разбор ВООБЩЕ. Цена обратная
  обычной: открытая отмена вычитается из «в пути», то есть остаток ЗАВЫШЕН и
  наружу уходит больше, чем есть, — прямой оверселл, самоподдерживающийся.
  Карточка «Диагностики» этот случай уже умела показывать (направление ошибки у
  отмены там объяснено отдельно), ей просто никогда не доставалось таких строк.
- **Пустая ячейка не должна давать ОШИБКУ импорта.** В колонках «Факт на дату» и
  «Порог трансляции» число разбиралось ДО проверки намерения: `_cell_intent`
  отдаёт пустую ячейку как `("skip", "")`, а `float("")` бросает `ValueError` —
  и пустая ячейка давала «некорректный факт на дату». Значение при этом не
  менялось, поэтому тесты на поля дефект не ловили. Цена не в строчке, а в том,
  что она вытесняет: выгрузка пишет сюда пустоту у каждой ненастроенной строки,
  то есть штатный круг «выгрузка → правка → импорт» давал до ДВУХ ложных ошибок
  на строку, а показываются первые пять и всё режется по `MAX_FLASH_CHARS` —
  настоящие ошибки в сообщение не попадали никогда. Оператор видел жёлтую плашку
  на успешном импорте и переставал её читать.
- **Мёртвый отказ воскресает, когда чистка удалит перекрывшую его отправку.**
  Отсев мёртвых отказов построен на «последней записи пары»
  (`latest_queue_ids`), а чистка удаляет `sent` через тридцать суток и не
  удаляет `error` никогда — оба правила по отдельности верные. Вместе они дают
  вот что: перекрывающая отправка исчезает, последней СНОВА становится старый
  отказ, и он воскресает КРИТИЧНОЙ находкой «площадка продаёт то, чего нет» про
  число, доехавшее месяц назад. Разобрать нельзя ничем: статуса запись не
  сменит, удалена не будет, отчёт красный навсегда. На бою заготовлены сотни
  таких записей от дефекта Kit 14–20.09 — прикрытие начнёт исчезать через
  тридцать суток после той отправки. `report._not_overtaken_by_a_later_send`
  спрашивает `SyncSetting.last_nonzero_sent_at`: она живёт на ПАРЕ и чистку
  переживает — для того и заведена. Сравнение строго ПОЗЖЕ создания отказа:
  отправка раньше него про него ничего не говорит. Тем же путём шла и находка
  `unknown_sku`, поэтому фильтр стоит в обеих.
- **Привязка нового баркода снимает «актуализирован» — во ВСЕХ путях.**
  Переподвязка и справочник 1С это делали, а автопривязка по пулу
  (`catalog_sync`, `POOL_GUESS_SOURCE`) и заведение нового баркода импортом
  «Мэппинга» — нет. Разница для остатка ровно та же: расчёт собирает заказы
  строго по баркодам товара, значит продажи по только что привязанному баркоду
  он заведомо не видел. Догнать их нечем — товар числится актуализированным,
  `catch_up_product` по нему не зовут, живой опрос старый заказ не принесёт, —
  и наружу уходит остаток, завышенный ровно на эти продажи. Автопривязка вдобавок
  сама удаляет ЕДИНСТВЕННЫЙ след, конфликт сопоставления с его счётчиком попыток.
  Общий помощник — `broadcast_gate.drop_recalc_mark`, и в нём же обе
  предосторожности: пустая СТРОКА, а не NULL (иначе ступень 2 перестала бы
  срабатывать вовсе), и НИЧЕГО не трогаем у товара, где расчёта не было никогда
  (иначе ступень 2 включилась бы там, где обязана молчать, и на отмеченный
  кабинет уехал бы ноль).
- **Повтор ID_1С в файле импорта роняет импорт ЦЕЛИКОМ.** Третий случай одного и
  того же: `db.add` после проверки запросом при `autoflush=False`. Второй строке
  файла с тем же ID_1С запрос не покажет первый `db.add`, и на пару
  товар+кабинет добавлялся второй `SyncSetting` под `uq_product_account`. Коммит
  на весь импорт один, обработчика исключений нет — оператор получал 500 и откат
  ВСЕХ строк: ни даты расчёта, ни факта, ни брони, ни отметок кабинетов. А
  повтор ID_1С — обычное дело: склеили две выгрузки, скопировали строку ради
  опечатки. Лечится словарём заведённых в этом файле настроек, как `in_file` в
  «Мэппинге» и `guessed_here` в загрузке каталога.
- **Каждый шаг миграции переживает собственный обрыв — включая batch.**
  `batch_alter_table` на SQLite перестраивает таблицу через
  `_alembic_tmp_<имя>`, и это самый долгий шаг: на `ftp_tasks` он переливает
  десятки тысяч строк при живых службах. Обрыв оставлял временную таблицу, и
  повторный `alembic upgrade head` падал на «table … already exists» НАВСЕГДА:
  продолжить нечем, повторить нечем, службы не перезапущены. `DROP TABLE IF
  EXISTS _alembic_tmp_<имя>` перед batch-блоком, и остаток закреплён тестом
  вместе с тремя другими остатками оборванного прогона.
- **Тест про календарный день обязан переживать полночь.** `TODAY` вычислялся
  при импорте модуля, а сбор тестов идёт раньше их выполнения: прогон,

  накат под местную полночь упёрся бы в красные тесты и отказался перезапускать
  бой. Дата берётся в момент теста.
- **Выгрузка не должна убивать просьбу включить трансляцию.** Колонка
  «Трансляция» писала `broadcast_enabled`, и у строки, ждущей расчёта, там
  стояло «Нет» — правда про сегодняшнее состояние и неправда про решение
  оператора: он попросил «Да», гейт согласился и отложил. Круг «выгрузил →
  поправил другую колонку → залил обратно» возвращал это «Нет», импорт читал его
  как осознанное выключение и снимал просьбу — ту самую, про которую минуту
  назад пообещал «ждут расчёта и включатся сами: N». Ни в сообщении, ни в
  ошибках об этом не было ни слова: трансляция не включалась никогда, товар
  молча не продавался, а человек считал, что настроил всё файлом. Чинится на
  стороне ВЫГРУЗКИ (`_broadcast_cell`: «Да» и у запрошенной тоже), а не импорта:
  правило «любое выключение файлом снимает и просьбу» верное, и ослаблять его
  нельзя — просто «Нет» в ячейке теперь означает правку человека, а не наше
  собственное эхо. Текущее состояние из файла не теряется: сколько уходит прямо
  сейчас, показывает соседняя «Уходит на площадки».
- **Ошибка импорта обязана отличать «человек изменил» от «человек не трогал».**
  Проверка колонки «Порог трансляции» сравнивала значение из файла с
  ПЕРЕСЧИТАННЫМ по только что применённым дате, брони и факту. А правка факта —
  единственный разрешённый способ сдвинуть порог, и подсказка на странице велит
  делать именно так: то есть ошибку получала КАЖДАЯ строка, где оператор сделал
  ровно то, что ему сказали, и ошибка советовала ему сделать то, что он и
  сделал. Сравнивать надо с тем, что стояло В ВЫГРУЗКЕ (`offset_as_exported`,
  снимается до правок строки). Тот же класс отказа сигнала, что и ложные ошибки
  на пустых ячейках: место в сообщении ограничено пятью строками и 440
  символами, и мусор вытесняет настоящие ошибки.
- **Включение кабинета сбрасывает счётчик предохранителя.** Кабинет гасится на
  пятом сбое подряд; счётчик оставался на пяти, и первая же ошибка давала
  шестой — `record_failure` гасил кабинет снова. Пяти попыток, ради которых
  предохранитель и сделан, у включённого кабинета не было вовсе. А включают его
  ровно тогда, когда первая попытка чаще всего и не проходит: оператор поправил
  ключи и даёт новый шанс. Кнопка «Диагностики» счётчик сбрасывала, кнопка
  «API-ключей» — нет, хотя человек обеими делает одно и то же.
- **Расчёт порога на «Тестировании» ставит новое число в очередь.** Рассылка
  СОБЫТИЙНАЯ и сама к порогу не вернётся: следующая отправка будет, только когда
  изменится остаток, а у медленного размера это месяцы. Близнец на странице
  «Товары» (`_repropagate`) это делал, здесь не делал — оператор видел новый
  порог в строке и считал карточку обновлённой, при том что на площадке лежало
  прежнее число. Через `enqueue_full_resend`, а не прямым `db.add`: страницу
  открывают ровно в том состоянии, где лестница даёт ноль.
- **Отказ площадки по КОНКРЕТНОЙ позиции обязан приходить с `sku` и `terminal`.**
  У WB и Kit так и было, у Ozon словарь уходил наверх сырым — и рассылка не
  могла отличить «этой карточки нет» от обрыва связи: пять попыток по
  нарастающей паузе в заведомо неизменный ответ, а потом отчёт относил запись к
  «рассылка не доехала» («чините связь») вместо «неизвестный sku» («чините
  мэппинг»). И обратное: позиция, которую площадка ОТКЛОНИЛА, не может
  одновременно считаться отправленной — WB возвращал такие баркоды и в `ok`, и в
  `errors`, а рассылка проверяла `ok` раньше. Теперь `terminal` проверяется
  первым.
- **Ответ 1С архивируется ПОСЛЕ разбора, и несёт имя команды.** Архивирование
  первым действием означало, что сбой записи в базу (`database is locked`)
  уносит ответы безвозвратно — из архива их никто не перечитывает. А без имени
  команды разбор брал самое старое незакрытое задание по номеру заказа: ответ по
  ОТМЕНЕ закрывал СОЗДАНИЕ, отмена уходила в `timeout` и навсегда считалась «в
  пути» со знаком минус. Формат ответа: `order_id|OK|номер|ИМЯ_КОМАНДЫ`, и это
  закрыто тестом, который читает сам модуль обработки.
- **`1c/src/` обязан совпадать с `1c/ОбменССайтом_МодульОбъекта.txt`** — тест
  `test_1c_sources_match.py`. Они разошлись на 274 строки, и сборка `.epf` по
  инструкции из `1c/README.md` откатила бы 1С на состояние до 19.09: вернулись бы
  потеря ответов, дубли документов, двойная отмена — и, главное, исчезла бы
  проверка `НайтиПроведённоеПеремещение` при включённом `MOVEMENT_REPOST_ENABLED`,
  то есть каждый повтор зависшего задания списывал бы остаток ВТОРОЙ раз.
- **Исключение на одной строке не должно уносить цикл.** Приём заказов,
  подтверждения, отмены, рассылка по кабинетам — каждый цикл ловит исключение по
  ОДНОЙ единице работы, делает `db.rollback()` (без него сессия остаётся
  сломанной после неудачного commit) и идёт дальше, складывая причины в
  `problems`. Без этого одна сбойная строка обрывала весь проход, и сбой при
  этом был НЕВИДИМ: счётчик предохранителя не рос, heartbeat не писался.
- **`_heartbeat` откатывает сломанную сессию сам** (`if not db.is_active`). Он
  почти всегда зовётся из `except`, а самый важный класс сбоя — упавший commit
  внутри задания: после него `_heartbeat` падал САМ, и в базе оставались время и
  `last_success=True` от ПРОШЛОГО прогона. `/health` зелёный, «Диагностика»
  пустая, текст ошибки потерян. Откат ИМЕННО условный: часть заданий коммитит
  свою работу тем же коммитом, что и отметку.
- **Копия базы снимается ОДНИМ шагом** (`src.backup(dst)`, без `pages`).
  `Connection.backup()` при чужой записи между шагами начинает копирование
  ЗАНОВО: порциями по тысяче страниц на базе в 150 МБ при десяти коммитах в
  секунду это 33,5 с и 1448 перезапусков, при двадцати и ста — не завершается за
  минуту вовсе. Задание при этом не падает, а крутится на 100% CPU и не обновляет
  heartbeat. Порции ничего не покупали: в WAL читатель писателя не блокирует.
  Сорвавшаяся попытка откладывается в `.bad` — под именем копии она проходила за
  полноценную у `last_backup` и у задания, и мониторинг был зелёным при
  отсутствующей копии. Хранение — по копии на КАЛЕНДАРНЫЙ ДЕНЬ, а не «последние
  четырнадцать файлов»: при копиях чаще раза в сутки четырнадцать «ежедневных»
  превращались в четырнадцать последних часов.
- **Копию моложе суток уборка не удаляет — сколько бы их за день ни сняли**
  (`KEEP_ALL_WITHIN_HOURS`). Правило «одна на календарный день» писалось под копии
  ПО РАСПИСАНИЮ и для них верно. Но копию снимает ещё и накат — первым делом, перед
  миграцией, — а накатов за день бывает несколько, и тогда правило работает против
  своей же цели: оно оставляет САМУЮ СВЕЖУЮ копию дня, то есть снятую уже ПОСЛЕ
  того, что человек собрался отменить. 23.09 это стоило ровно того, ради чего бэкап
  и заводился: массовая кнопка схлопнула пороги у 62 товаров в 15:10, единственная
  копия до этого была 14:31 — и её удалил накат в 15:32. Обе площадки потеряли файл
  одновременно, и это не сбой, а следствие: правило уборки у папки и у облака ОДНО,
  намеренно. Восстанавливать пришлось по вчерашней копии, то есть принимая на веру,
  что за сутки до порчи ничего важного не правили. Сутки — ровно тот срок, пока
  живёт вопрос «отменить то, что только что сделали»; дальше день схлопывается в
  одну копию, как и раньше. Свежая копия при этом НЕ занимает недельный слот: 23.09
  копия 15:32 уцелела не как «сегодняшняя» (то место заняла 16:10), а как
  недельная — то есть вытеснила бы копию месячной давности, ради которой второй
  слой и заведён.
- **Копии лежат на том же диске, что и база, — и это лечится зеркалом.**
  Отказ диска унёс бы разом и базу, и все копии, то есть ровно то, от чего бэкап
  и заводился. `BACKUP_MIRROR_DIR` (папка облака, сетевая шара, второй диск) —
  вторая площадка. Три правила, и каждое от конкретной беды. Копируем ПОСЛЕ
  проверки: непроверенная копия на второй площадке — это две надежды вместо
  одной. Копируем через временное имя `.part` с переименованием: клиент
  облачной синхронизации смотрит за папкой и заливает всё, что меняется, — под
  финальным именем файл обязан появиться уже целым, иначе в облако уедет
  недописанная база. И `BACKUP_DIR` прямо в облако указывать НЕЛЬЗЯ:
  `Connection.backup()` пишет сразу в целевой файл, рядом мелькают `-wal`/`-shm`,
  а клиент держит файлы открытыми и мешает уборке. Сбой зеркала бэкап НЕ роняет
  (локальная копия снята и прочитана — тревожить из-за недоступной сетевой папки
  не о чем), но и не глотается: текст уходит в `last_error` УСПЕШНОЙ отметки, и
  читатель у него есть — `report._check_backup_mirror`. Зеркало — вторая
  ПЛОЩАДКА, а не глубина хранения: чистится своим сроком, просто более щедрым.
- **Чистка удаляет только `sent`.** Запись в `error` выглядит терминальной, но
  описывает НЕЗАКОНЧЕННОЕ дело: остаток списан, число не уехало, площадка продаёт
  то, чего нет. Через тридцать суток критичная находка просто исчезала из отчёта.
  Мёртвые отказы отсеивает сам отчёт — это его работа, а не чистки.
- **Совпадение в сверке — не расхождение.** `resolved` ставится и при `delta == 0`.
  Раньше только при `delta != 0`, поэтому каждая сходящаяся строка — около сорока
  тысяч в сутки — оставалась «неразрешённой» навсегда, и кнопка «Закрыть старые
  расхождения» поднимала их все разом одной транзакцией: на 250 тысячах это 10,9 с
  эксклюзивной блокировки записи и 857 МБ памяти, а к девяностому дню хранения их
  было бы около трёх с половиной миллионов. Сама кнопка теперь работает порциями.
- **Предохранитель, сработавший молча, — половина предохранителя.** «Снимок 1С
  покрыл меньше половины прежних ненулевых» отключает обнуление распроданного —
  правильно (обрезанный файл не должен стереть каталог), но состояние
  самоподдерживающееся: час за часом наружу уходит остаток по тому, чего на
  складе нет. Теперь это WARNING в журнале, текст в heartbeat и отдельная
  КРИТИЧНАЯ находка отчёта.
- **Файл из 1С архивируется ПОСЛЕ того, как его разбор дошёл до базы.** Это про
  все четыре канала: ответы по заданиям, дельту остатка ЦС, остатки на дату,
  справочник. Архивирование первым действием означало, что сбой на любом
  следующем шаге (`database is locked` на коммите, ошибка в расчёте порога)
  уносит файл безвозвратно — из архива его никто не перечитывает, а повторно 1С
  его не пришлёт. Разбор идемпотентен по построению, поэтому повторное чтение
  того же файла безопасно, а потеря — нет. У дельты вместе с файлом откладывается
  и пометка «документ применён»: помеченный документ при нетронутом остатке
  означает, что правка 1С пропала насовсем.
- **Дельта остатка ЦС применяется со временем ФАЙЛА, а не приёма.** Она
  описывает склад на ту минуту, когда 1С её записала. Со временем приёма
  задания, закрытые в промежутке, переставали считаться «в пути», хотя в файле
  их ещё нет, — и уже отгруженные единицы возвращались на склад и уезжали на
  площадки. Берём время САМОГО СТАРОГО файла пачки: ошибка в эту сторону
  занижает остаток, а не завышает.
- **Уборка заявок «остатки на дату» не трогает незавершённые.** Шла по номеру,
  без фильтра по статусу: закажи оператор больше десяти срезов подряд — и самые
  старые исчезали вместе с теми, на которые 1С ещё не ответила. Товары с этой
  базовой датой оставались в «ждём выгрузку 1С» навсегда, потому что ждать стало
  нечего, а находка отчёта про такие заявки ослепла.
- **`build_task_batch` коммитит «отправлено» ДО публикации файла — намеренно.**
  Обратный порядок выглядит надёжнее и платит хуже: при сбое коммита файл уже у
  1С, задания остались `pending`, следующий цикл отправит их второй раз.
  `CREATE_MOVEMENT` это переживёт (идемпотентность по заказу), `CANCEL_MOVEMENT`
  нет — второй обратный документ и вдвое больший возврат на ЦС. Потеря при
  нынешнем порядке хотя бы видна: задание уходит в `timeout` и в ручной разбор.
- **Выгрузка Excel пишется ПОТОКОМ** (`Workbook(write_only=True)`). Обычный режим
  держит объект на каждую ячейку: 50 000 строк — 36,5 с и 344 МБ, 152 235 — 112 с
  и 829 МБ, и это на веб-службе, которая в это же время принимает заказы. Потоком
  те же объёмы — 4,3 с / 50 МБ и 13,1 с / 103 МБ. Ширину колонок считаем по первым
  пятистам строкам: второй проход по выгрузке означал бы держать её в памяти
  целиком ради числа, ограниченного шестьюдесятью символами.
- **Отчёт о расхождениях (`app/report.py`, страница `/report`) — про то, что
  система разошлась с реальностью, а НЕ про то, жива ли она.** Живость — дело
  `/health` и «Диагностики». Каждый серьёзный дефект сентября был виден в данных
  за часы до того, как его нашли: каталог Kit лежал пятидневной давности, 12
  заданий 1С висели в `timeout`, аномалии копились сотнями. Не хватало не данных,
  а того, кто посмотрит. Поэтому `job_discrepancy_report` собирает отчёт раз в час
  и пишет ОДНУ строку в лог — при критичной находке уровнем WARNING, иначе INFO,
  но пишет ВСЕГДА: отсутствие строки обязано означать «отчёт не собрался», а не
  «расхождений нет». Правил при добавлении проверки два. Первое: находка называет
  не факт, а **следствие** («остаток занижен, наружу уходит меньше, чем есть»), —
  не формулируется следствие, значит это не расхождение, а просто число. Второе:
  отчёт ТОЛЬКО ЧИТАЕТ, ничего не чинит и не шлёт наружу, иначе его начнут бояться
  запускать. Молчание на исправной системе — обязательное свойство, закреплённое
  тестом: свежий кабинет без каталога и не стартовавшая сверка находками НЕ
  считаются (ругать установку за то, что она свежая, — верный способ приучить
  оператора пролистывать отчёт). Упавшая проверка превращается в собственную
  находку и не уносит остальные. **Аномалии `order_on_disabled` в отчёт не
  попадают вовсе, и это не упущение**: пока идёт переход, часть каталога
  транслирует ещё старая система, продажи по неподключенным у нас карточкам идут
  мимо нас в порядке вещей (остаток по ним мы не рассылали и не списывали), и с
  полным переходом эти строки исчезнут сами. Считать их расхождением значит
  держать отчёт вечно непустым. В отчёте только `missing_barcode` — там заказ
  есть, а разнести его не на что, и переходом это не лечится.
- **Отметка «задание отработало» ставилась по факту «функция вернулась».**
  Счётчики непроведённой работы (`failed`, `errors`, `skipped`, `truncated`)
  наверх не влияли ни у одного задания. Правило теперь общее: **задание,
  вернувшее ненулевой счётчик непроведённой работы, пишет текст в `last_error`
  УСПЕШНОГО heartbeat, и у этого текста обязан быть читатель** — образец
  `reconciliation_applied` → `report._check_suspicious_snapshot`. Успех, а не
  ошибка, намеренно: `/health` про живость, расхождение разбирает отчёт; разовый
  сбой стирается следующим циклом и находки не даёт, а устойчивый доживает до
  часового прогона. Закрыто у трёх: опрос заказов (`_check_orders_not_processed`
  — откат по заказу уносит и `SyncAnomaly`, и `ProcessedOrder`, следа не
  оставалось НИГДЕ), сверка остатков (`_check_verify_stock_broken`), выгрузка
  каталога (`_check_truncated_catalog` — признак вычислялся, а комментарий
  «Диагностика показывает именно его» был прямой неправдой: страница рисовала по
  кабинету только `poll_orders_account_*`). «Диагностика» теперь показывает такой
  heartbeat как «с оговоркой» с текстом, а не зелёным «ок».
- **Молчание площадки и «читать не умеем» — разные вещи, и признак нужен
  ДАННЫМИ.** `get_stocks` отдаёт `None` в обоих случаях: у Ozon и Kit метод не
  написан (вслепую такое не пишется), а у WB `None` значит, что площадка не
  ответила — 403 по снятой области, 404 по переименованной ручке, хронический
  429 дают именно `None`, потому что `with_retry` 4xx кроме 429 не повторяет.
  Оба ложились в один `skipped`, и сверка — единственная проверка, которая ловит
  перезапись наших остатков второй системой, — могла молчать неограниченно долго
  при зелёном мониторинге. Различает `PlatformClient.reads_stocks`.
- **«Карточки нет» несёт колонка `DispatchQueueItem.card_missing`, а не русский
  текст.** Отчёт искал две подстроки (`площадка не знает этот sku`, `нет карточки
  в каталоге кабинета`) и совпадал ровно с одним WB-шным текстом. У Kit слова
  другие («площадка не знает такой ТОВАР (variant_id …)», «карточка товара в
  архиве»), у Ozon в `detail` уезжает сообщение площадки ПО-АНГЛИЙСКИ. Всё
  остальное становилось КРИТИЧНОЙ находкой «остаток списан, площадка продаёт то,
  чего нет» — при том, что продавать там нечего, — и НАВСЕГДА: запись
  терминальная, успешной отправки по паре не будет, снять её нечем ни
  `latest_queue_ids`, ни `_not_overtaken_by_a_later_send`, ни `_only_live_pairs`.
  Отчёт по кабинетам Kit и Ozon был бы красным вечно. Признак ставит клиент
  (`card_missing` в ответе по позиции), кладёт рассылка, читает отчёт; подстроки
  оставлены ТОЛЬКО ради записей, лежащих в базе с прежних времён (их добирает
  бэкфилл миграции `3af1c62b7d05`; ozon-овские не поднять — текст произвольный).
  Заводишь новый терминальный код у площадки — реши, `card_missing` он или нет.
- **Конфликт сопоставления заводят ДВОЕ, и следствия у них разные.**
  `resolve_barcode` (приём заказа) — это уже случившаяся непроведённая продажа, и
  `attempts` считает, сколько раз она повторилась. `catalog_sync` (суточная
  выгрузка) — это карточка площадки, которой нет в 1С: заказов ноль, товара в 1С
  нет, завышать нечего. Находка брала ВСЕ строки, печатала их число как «заказов
  по ним N» и обещала «остаток завышен ровно на эти продажи», становясь через
  трое суток КРИТИЧНОЙ и не гаснув: чистит их только появление баркода в 1С, а
  выгрузка заводит новые. Каталожные теперь заводятся с `attempts=0` и живут в
  своей находке (`catalog_cards_without_1c`).
- **Зависшую отмену нельзя описывать словами создания.** В разбор попадает любая
  команда, кроме `CREATE_MOVEMENT` (автоповтор берёт только его), так что отмен
  там не «иногда», а по построению. У открытого `CANCEL_MOVEMENT` знак ОБРАТНЫЙ:
  остаток ЗАВЫШЕН, наружу уходит больше, чем есть. Отчёт давал одно следствие на
  всех, а флеш после «документа нет» обещал «N шт. вернутся в остаток» — тогда
  как по отмене остаток УМЕНЬШИТСЯ. Правильная формулировка всё это время лежала
  рядом, в `_stuck_rows`; три текста про одну сущность расходились между собой, и
  человек, читающий их буквально, перестаёт верить всем трём.
- **Кнопка «Сбросить счётчик сбоев» погашенному кабинету ОТКАЗЫВАЕТ.** Она
  писала `consecutive_failures = 0`, не трогая `is_active`, а
  `_check_breaker_disabled` требует ОБОИХ признаков — значит после нажатия
  критичная находка исчезала навсегда: у выключенного кабинета per-account
  задание снято, счётчик больше никто не увеличит, `/health` выключенные
  кабинеты пропускает намеренно. Убрать из находки второе условие нельзя: туда
  попал бы и кабинет, выключенный человеком осознанно. Включают на «API-ключах»,
  где `activate_account` сбрасывает счётчик заодно.
- **Восстановление из копии молча не восстанавливало НИЧЕГО.** Процедура в

  страницами ПРЕЖНЕЙ базы, и SQLite при первом открытии накатывает их поверх
  подложенной копии. Отказ немой — `integrity_check` = ok, размер правдоподобный,
  человек уверен, что откатился. А это единственная процедура восстановления в
  проекте и единственный выход после оборванной миграции, которую alembic на
  SQLite не откатывает. Теперь `scripts/restore_db.py`: проверяет, что службы
  стоят, снимает текущую базу ШТАТНЫМ механизмом (не `Copy-Item` при живом WAL),
  уносит её ВМЕСТЕ со спутниками под `.before-restore`, кладёт копию, сводит
  журнал и проверяет чтением товаров.
- **Накат кончался зелёным и когда файлы не приезжали вовсе.** 23.09: блок

  `update_windows.ps1` честно отработал на СТАРОМ коде. Копия базы снята,

  того, что новой версии на сервере нет, было ОТСУТСТВИЕ строки `Running upgrade`
  в логе миграций — признак, которого никто не ищет, а `alembic current` при этом
  показывает `(head)`, потому что head он считает по тому, что видит НА ДИСКЕ.
  Человек уверен, что поставил версию; на деле её нет, и узнает он об этом в день,
  когда полезет за новым поведением. Два шага наката были независимы, и второй
  ничего не знал о первом. Теперь apply-скрипт пишет `deploy/INSTALLED_TAG` —

- **Уведомления наружу — единственный путь, которым система зовёт человека**
  (`app/alerts.py`, задание `alerts` раз в пять минут). До 22.09 их не было
  вовсе, и это была главная слабость системы — не в коде: внутри она видела про
  себя всё, а узнать об этом мог только тот, кто пришёл и открыл страницу. Тот
  же дефект «находка без читателя», который чинили внутри весь день, только на
  уровне системы целиком. Правила. **Будят ДВЕ вещи**: `/health` не зелёный
  (задание встало — остатки перестают синхронизироваться молча) и КРИТИЧНАЯ
  находка отчёта. **WARNING не будит никогда** — жёлтых находок в исправной
  системе бывает несколько штук постоянно, и, разбудив на жёлтом раз, мы научим
  не читать и красное; канал перестанет работать весь, а не наполовину. То же
  правило, что с подтверждением на массовых действиях. **Тихих часов нет**:
  оверселл — проданный дважды товар, до утра он не подождёт; если окажется
  слишком, сужать надо то, что считается критичным, а не вводить окно молчания —
  молчащему по расписанию каналу перестают верить. **Ничего не чинит**, как и
  отчёт: только читает и рассказывает. Состояние `/health` спрашивается ОДНОЙ
  функцией с самой страницей (`health.snapshot`) — повтори алерты эту логику у
  себя, они однажды разошлись бы с ней, и уведомление замолчало бы на настоящей
  поломке или будило на ровном месте. Дедупликация живёт в `AlertState`: пока
  отпечаток картины тот же — молчим, иначе пять одинаковых сообщений в час
  добьются того, что канал отключат. В отпечаток идут только ключи и имена, без
  чисел, которые скачут сами (возраст, счётчики), — иначе та же поломка
  выглядела бы новой каждый цикл. Состояние двигается ТОЛЬКО на удачной
  отправке: не доехало — повторим, иначе тревога, потерянная из-за недоступной
  сети, была бы потеряна навсегда. Отбой шлётся ровно один раз и только если до
  него была тревога. **Проверять канал обязательно** кнопкой «Отправить пробное
  уведомление» на «Диагностике»: опечатка в токене выглядит так же, как исправная
  тишина, и обнаружилась бы в худший из возможных часов — ровно то, что уже
  проходили с бэкапом, который снимался, но не проверялся чтением. Кнопка шлёт
  мимо дедупликации намеренно: запиши она проверку связи как «последнюю
  сообщённую картину», настоящая тревога следом сочлась бы повтором и не ушла.
  Ненастроенные каналы и недоставленное сообщение — РАЗНЫЕ вещи, и обе видны в
  `last_error` успешного heartbeat: первое штатно на свежей установке, второе
  значит, что тревога прямо сейчас не дошла и узнать об этом больше неоткуда.
  Само задание в `REQUIRED_WORKERS`: замолчав, оно молчит ровно так же, как
  исправная система. **И главное ограничение всего механизма: он живёт ВНУТРИ
  воркера.** Умер воркер — умерли и уведомления, то есть самый важный случай
  («ночью легли обе службы») ими не покрывается в принципе: процесс, которого
  нет, не сообщит, что его нет. Закрывает это только обратная полярность —
  `alerts.ping_alive` дёргает `ALERT_HEARTBEAT_URL` на КАЖДОМ прогоне, а о
  молчании пишет внешний сервис («сторож мёртвого человека», healthchecks.io и
  подобные; конкретный сервис в код не зашит, только адрес). Пинг идёт
  независимо от того, всё ли в порядке внутри: сторож отвечает на ОДИН вопрос —
  «жив ли воркер». Смешай мы туда второй смысл, его сигнал стал бы неотличим от
  падения службы, а о беде внутри живой системы и так скажут каналы.
- **Сторож воркера не видит смерти ВЕБ-СЛУЖБЫ** — для неё заведён второй чек
  (`alerts.ping_web_alive`, `WEB_HEARTBEAT_URL`). Разбор по случаям: легли обе
  службы — воркер молчит, первый сторож будит; умер воркер при живом вебе — то
  же самое, и это самый дорогой случай; а «умер веб, воркер жив» не видно
  НИЧЕМ. Третий случай выглядит изнутри полностью исправным: воркер пингует,
  `job_alerts` спрашивает состояние функцией `snapshot(db)` — то есть читает
  БАЗУ, а не ходит по HTTP, — и видит все задания свежими. Остатки при этом
  синхронизируются дальше (входящих ручек у веба нет, весь обмен с площадками
  исходящий, из воркера), денег никто не теряет; слепнет ЧЕЛОВЕК: ни отчёта, ни
  «Диагностики», ни включения трансляции, ни разбора зависшего задания 1С. И
  скверный частный случай: настоящая критичная тревога в это время уйдёт в
  Telegram со словами «разберите на Диагностике», а Диагностика не откроется.
  На боевом сервере порт наружу НЕ ОТКРЫТ, внешним монитором веб не достать —
  поэтому за него говорит воркер: он жив, значит может подтвердить. Спрашиваем
  `http://127.0.0.1:8000/health` у себя на машине, и **не ответил веб — сторожа
  НЕ ДЁРГАЕМ вовсе**: пинг означает «подтверждаю, что беды нет», а подтверждать
  нечего; пингуй мы всё равно, второй чек был бы украшением. Чек именно ВТОРОЙ,
  а не строка в первом: у сигнала обязан быть ОДИН смысл, иначе молчание
  первого сторожа стало бы значить «что-то не так», неотличимо от падения
  воркера. Раздельно таблица однозначна: молчат ОБА — умер воркер или машина;
  молчит только веб-сторож — умерла веб-служба; молчит только первый —
  невозможно по построению (веб-пинг идёт ИЗНУТРИ воркера), и если такое
  увидели, сломан сам механизм. Оба пинга дёргает `job_watchdog` — полярность у
  них одна, задание только носитель, — и обе оговорки складываются в ОДНУ
  отметку через `; `: две беды сразу не должны вытеснять друг друга. Критичной
  находкой мёртвый веб НЕ становится намеренно: критичное — это «деньги
  теряются прямо сейчас», а тут не теряются; разбавь мы критичное таким, канал
  обесценился бы весь. Да и показывает находку страница, которую мёртвый веб
  как раз и не отдаст.
- **Настройка, от которой зависит работа, заводится СТРАНИЦЕЙ, а не файлом.**
  Каналы уведомлений жили только в `.env`, и это плохо по трём причинам сразу.
  `.env` читается ОДИН РАЗ, на импорте (`app/__init__.py`), — правка без
  `nssm restart sync_admin_worker` не действует, а про перезапуск забывают;
  забыл — и человек уверен, что канал настроен, пока система молчит. Токен бота
  лежал открытым текстом в одном файле с `SECRETS_ENCRYPTION_KEY`, то есть ключ
  рядом с тем, что им защищено. И правку файла потом не установить: кто сменил
  адресата тревог — вопрос, который однажды зададут. Страница «Уведомления»
  (`app/routers/notifications.py`) закрывает все три, храня значения в
  `AppSetting` — секреты шифрованно, остальное открыто, и колонку выбирает
  ОПИСАНИЕ поля в `app/settings_store.py`, а не вызывающий код: разойдись они,
  токен однажды уехал бы в открытую колонку молча и навсегда. Развилка одна на
  всех (`settings_store.get`): **строка в базе есть — её значение; строки нет —
  смотрим окружение**. Пустая строка в базе — ЭТО ЗНАЧЕНИЕ. Считай мы её за
  «не задано», человек стёр бы поле, а значение из `.env` вернулось бы, и тревоги
  продолжили бы уходить туда, откуда адресата только что убрали, при пустом поле
  на странице. Обратный порядок (окружение важнее базы) отвергнут по зеркальной
  причине: забытая строка в файле молча отменяла бы правку, и человек чинил бы
  то, что не ломалось. Поэтому же страница ГОВОРИТ, что значение пришло из
  `.env`: оттуда она его перекроет, но удалить не может. Заводишь такую
  настройку — добавь поле в `settings_store`, а не читай `os.environ` на месте.
  Туда же переехало зеркало копий (`BACKUP_MIRROR_DIR` и его сроки), и там
  всплыли две особенности. Первая: **сессию надо ДОНЕСТИ**. `mirror_backup`
  получал `db`, а дальше звал `mirror_dir()` без него — и это худший из
  возможных исходов, потому что при пустом окружении функция возвращает «всё
  хорошо»: бэкап зелёный, `mirror_error` пуст, находка отчёта молчит, второй
  площадки нет. Поймано тестом, который проверяет не настройку, а её следствие —
  файл в папке зеркала. Вторая: **`scripts/backup_db.py` обязан работать на
  сломанной базе**. Его запускают ИМЕННО когда что-то пошло не так, а саму базу
  он копирует файлом через `sqlite3`, минуя SQLAlchemy, — то есть снимет копию и
  с той, которую приложение открыть не может (нет `SECRETS_ENCRYPTION_KEY`, побит
  пул). Поэтому `backup._setting` заводит свою сессию, а любую неудачу на этом
  пути ГЛОТАЕТ и читает окружение: хуже недоступной настройки только копия,
  которая из-за неё не снялась. И `BACKUP_DIR` полем НЕ выставлен намеренно —
  указать туда папку облака нельзя (`Connection.backup()` пишет в целевой файл на
  месте, рядом мелькают `-wal`/`-shm`, клиент синхронизации держит их открытыми),
  а текстовое поле ровно к этому и приглашает; страница показывает путь только
  для чтения.
- **Копия в облаке проверяется ЧТЕНИЕМ на той стороне** (`backup.upload_to_remote`).
  На боевом сервере (Hetzner, Windows Server 2016, рабочая группа) папку-зеркало
  взять негде: второго диска нет, соседней машины нет, а клиент Яндекс.Диска на
  серверную Windows не ставится вовсе — он проверяет редакцию и отказывается.
  Отсюда rclone, и взят он **ровно за одно свойство**: у облака можно спросить,
  доехала ли копия. У папки синхронизации этого нет принципиально — там видно
  только, что файл положен в папку, а отсутствие второй площадки выглядит точно
  так же, как её наличие (и выглядело бы: клиенту нужна живая сессия
  пользователя, а службы работают без неё, так что выход из RDP молча выключал
  бы выгрузку). Поэтому после `copyto` читается `lsjson` и сверяется РАЗМЕР, а
  «выгрузили, но проверить не смогли» — это отказ, а не успех: сказать «копия в
  облаке», не увидев её там, значит вернуться ровно к тому, от чего уходили. То
  же правило, по которому локальная копия проверяется `integrity_check` и
  чтением товаров. Ошибка складывается в `mirror_error` ВМЕСТЕ с ошибкой папки:
  у этого поля уже есть читатель (`report._check_backup_mirror` и строка «с
  оговоркой» на «Диагностике»), а завести второе значило бы завести находку без
  читателя. Уборка в облаке идёт ОДНИМ правилом с локальной
  (`backup.names_to_drop`, вынесено из `prune` именно ради этого): разойдись они,
  в облаке лежало бы не то, что обещано, и узналось бы это в день
  восстановления. Токена у нас нет и не будет — его выдаёт `rclone config` в
  диалоге с человеком и сам обновляет; в базе только путь и два имени файлов.
  `--config` задаётся ЯВНО: `rclone config` пишет конфиг в профиль того, кто его
  запустил, а служба работает под своей учётной записью и этого файла не увидит —
  проверили руками, сошлось, а суточная выгрузка молчит. И общее правило, из-за
  которого поля «команда» на странице нет и не будет: страница открыта любому
  пользователю админки, и свободная строка с командой — это выполнение
  произвольного кода на сервере, а не настройка.
- **Загрузка каталога поднимает пары, закрытые из-за ЕГО ЖЕ отсутствия**
  (`catalog_sync.revive_after_catalog`). 22.09 на живом кабинете КИТ:
  последовательность вся штатная — завели карточку, включили трансляцию, расчёт
  поставил пару в очередь, — а каталог кабинета выгружается раз в сутки и про
  новую карточку ещё не знал. `variant_id` нет, рассылка закрыла позицию
  ТЕРМИНАЛЬНО (иначе Kit бракует весь запрос целиком), через четыре минуты
  пришёл каталог, ключ появился — и не случилось НИЧЕГО: запись терминальна,
  повтора нет, следующая отправка будет, только когда изменится остаток. У
  зимней куртки это месяцы; остаток не уедет никогда при полностью выполненных
  условиях, и увидеть это можно только придя смотреть глазами. Тот же случай,
  что `recalc_covered` у расчёта: ворота открыло это событие — ему и поднимать.
  **Поднимаем НЕ всё подряд, и это главное.** `card_missing` метит два разных
  отказа: НАШ (рассылка не нашла ключа, позиция в запрос не пошла вовсе —
  `sent_sku` пуст, потому что он пишется только уехавшим) и отказ ПЛОЩАДКИ
  (запрос ушёл, она ответила «такого sku на складе нет», у WB это `409
  NotFound` — `sent_sku` заполнен). Каталогом лечится только первый; подними мы
  второй — сожгли бы запрос, закрыли пару снова и заставили находку «Площадка
  не знает наш sku» мигать на ровном месте, а таких на живом кабинете под сотню.
  Различаем ДАННЫМИ (`sent_sku IS NULL`), не текстом: тексты у трёх площадок
  разные, на этом уже обожглись. Плюс поднимаем только те пары, у которых ключ
  ТЕПЕРЬ действительно есть, иначе каждая суточная выгрузка гоняла бы по кругу
  мёртвые. Правило выбора ключа — ОДНО на рассылку и на каталог
  (`dispatch.push_identifier`): разойдись они, каталог поднимал бы пары, по
  которым отправлять по-прежнему нечем. Ставим через `enqueue_full_resend`, то
  есть со всеми гейтами: обойти их здесь значило бы отправить ноль на живую
  карточку.
- **`1c/ОбменССайтом_8.2_МодульОбъекта.txt` отстал на 379 строк** (345 против

- **Возвраты — про физическую вещь, а не про SKU** (`app/returns.py`, страница
  `/returns`). Кладовщик забирает возвраты из ПВЗ одной площадки коробкой, не зная,
  FBS это или FBO, и сканирует баркод. Баркод опознаёт SKU, а не вещь: три
  одинаковых свитшота дают три записи с одним баркодом, а статусы у них личные —
  одна уехала в химчистку, вторая в утиль. Поэтому запись всегда на ОДНУ вещь
  (`quantity` = 1), а различает их в руках наклейка `RET-<id>`, которая печатается
  сразу на приёмке; без наклейки статус через неделю стоял бы не на той вещи, и
  страница уверенно показывала бы неправду. Площадка выбирается СЕССИЕЙ приёмки, а
  не на каждый скан: она нужна только для склада-источника перемещения
  (`PENDING_WAREHOUSE_NAME` по ПЛОЩАДКЕ, ИП к документу отношения не имеет), а
  коробка приезжает из одного ПВЗ. Неопознанный баркод приёмке НЕ мешает: вещь
  существует независимо от нашего мэппинга, и отказать в скане значит заставить
  человека отложить её в сторону и забыть.
- **Пока вещь в разборе, её нет НИГДЕ — и всё остальное следствие этого.** Ни в
  нашем `stock_on_hand`, ни в снимке 1С: мы её не приходовали, 1С о ней не знает,
  числа сходятся, и подстраивать сверке нечего. Отсюда: утилизация в 1С не идёт
  вовсе (вещи там уже нет, списывать нечего); статус «возвращён в продажу» ставит
  ТОЛЬКО ответ 1С, а не кнопка — заявить, что остаток вырос, пока 1С этого не
  сказала, и есть тот класс дефекта, ради которого проект переписывался; и
  **команда своя, `RETURN_TO_STOCK`**. Соблазн оформить возврат как
  `CREATE_MOVEMENT` с перевёрнутыми складами есть — в 1С тогда менять нечего, — но
  `reconciliation._in_flight_adjustment` знает ровно две команды (создание плюс,
  отмена минус), и возврат в той цепочке ЗАНИЗИЛ бы остаток вдвое против правды.
  Ноль там — ЗНАЧЕНИЕ, а не пропуск, и выглядит он как пропуск, поэтому закреплён
  тестом (`test_a_return_task_is_not_counted_as_in_flight`), который вдобавок
  проверяет, что видит настоящее движение: слепая проверка молчала бы так же.
  Автоповтора у возвратов нет по той же причине, по которой его нет у отмен —
  `repost_stuck_movements` берёт только `CREATE_MOVEMENT`, — значит
  идемпотентность на стороне 1С для них не требуется, а зависшее задание уходит в
  ручной разбор по общему правилу.
- **У ручного разбора три следствия, а не два.** Тексты про зависшее задание живут
  в ОДНОМ месте (`ftp_channel.review_effect`) и читаются четырьмя: карточкой
  «Диагностики», подтверждением у кнопки «документа нет», сообщением после неё и
  находкой отчёта. До возвратов их было четыре разных, собранных по СОЗДАНИЮ, и
  они уже расходились. Возврат не похож ни на создание, ни на отмену: в «в пути»
  он не участвует вовсе, то есть остаток не занижен и не завышен — он просто ещё
  не вырос, и сам не вырастет НИКОГДА. Слова создания («остаток занижен, наружу
  уходит меньше») пообещали бы, что это рассосётся сверкой. Там же вторая
  половина: `resolve_stuck_task` двигает и сам возврат — не сдвинь мы его, вещь
  осталась бы в «ждём 1С» навсегда, молча и при закрытом задании.
- **Складская учётная запись видит ТОЛЬКО возвраты, и запрет ПО УМОЛЧАНИЮ**
  (`app/access.py`, роль `warehouse`). Это не опрятность интерфейса: на остальных
  страницах кнопки, двигающие боевые остатки по всему каталогу одним нажатием.
  Разрешение перечисляется, запрет — нет: перечисли запрещённое, и КАЖДАЯ новая
  страница окажется открытой складу, потому что автор новой страницы про список не
  вспомнит. Про него не вспомнят и так, но цена ошибки обратная — страница будет
  закрыта, человек скажет «не открывается», и её откроют осознанно; молчаливое
  открытие доступа не замечает никто. Проверка стоит в `get_current_user`, а не в
  обработчиках: единственный способ её «обойти» — убрать зависимость, а тогда
  страница не откроется вовсе, потому что не знает, кто пришёл. Меню фильтруется
  ТОЙ ЖЕ функцией (`templating.can_see`) — прятать пункт не защита, а вежливость,
  но предлагать то, что не откроется, прямой обман. Главный тест перебирает ВСЕ
  адреса приложения: он и стережёт будущее. Им же нашлись три дыры, открытые не
  складу, а вообще всем: `/docs`, `/redoc` и `/openapi.json` отдавали карту
  приложения без входа (выключены целиком — публичного API у нас нет), а старые
  адреса `/sync-products` и `/stock-control` вели куда угодно без единой проверки.
- **Страница отказа — обычная страница приложения, и у неё та же шапка.** Значит

  Jinja до браузера не доезжает вовсе — состояние остаётся навсегда. У приёмки
  возвратов это была печать наклейки: она открывалась на КАЖДУЮ загрузку
  страницы, а страница у кладовщика открыта весь день, то есть одна наклейка
  превращалась в пачку и на вещах оказывались чужие номера — ровно то, ради чего
  наклейка и заводилась. Обратная сторона того же: вопрос «это вторая вещь или
  повтор?» перезагрузку ПЕРЕЖИВАЕТ намеренно и снимается только ответом.
  Снимай его отрисовка, и F5 по привычке молча стёр бы решение по настоящей
  второй вещи. И «пропустить» обязана быть действием, а не ссылкой на ту же
  страницу: ссылка вопрос не снимала, и кнопка выглядела нажатой впустую.
- **Терминальные статусы возврата выводятся ДОПОЛНЕНИЕМ к `IN_WORK`, а не из
  таблицы переходов.** Пустая строка в `RETURN_TRANSITIONS` значит «руками не
  выйти», а не «выхода нет», и у `awaiting_1c` она пуста именно поэтому — его
  двигает ответ 1С. Выведи терминальные из таблицы (соблазн прямой: одна
  строчка), и чистка удаляла бы вещи, ПРЯМО СЕЙЧАС ждущие 1С: ответ пришёл бы
  на запись, которой уже нет, а вещь так и осталась бы лежать на складе. Два
  списка дополняют друг друга по построению, и это закреплено тестом — иначе
  новый статус не попал бы ни в один и не чистился бы никогда, молча.
- **Историю вещи чистка удаляет СВОИМ запросом и ПЕРЕД самой вещью.** `_purge`
  делает массовый `DELETE`, а он не поднимает ни каскад ORM, ни
  `ON DELETE CASCADE` — на SQLite внешние ключи по умолчанию вообще не
  проверяются. Оставь мы это каскаду, строки истории осиротели бы навсегда и
  росли бы без предела, причём молча: удалённых вещей в интерфейсе нет, и
  заметить их было бы неоткуда. Заводишь таблицу-ребёнка — чисти её отдельно.
- **Подпись статуса не говорит человеку ни что это значит, ни что делать.**
  «Отложен» он видит через неделю после того, как сам его поставил, и уже не
  помнит почему. Поэтому у каждого статуса возврата два текста
  (`returns.RETURN_HINTS`): что это значит и что делать дальше — вопросы разные,
  и один ответ на оба не отвечает ни на один. Живут они РЯДОМ С ТАБЛИЦЕЙ
  ПЕРЕХОДОВ, а не в шаблоне: подсказка обязана называть те же кнопки, которые
  страница действительно даст, — посоветуй она кнопку, которой нет, человек
  ищет её, не находит и решает, что страница сломана. Оттуда же легенда в
  списке: два текста про один статус разошлись бы, и читающий их буквально
  перестал бы верить обоим. Закрыто тестами: пояснение есть у КАЖДОГО статуса,
  у терминального «что делать» отвечает «ничего», а у «ждём 1С» прямо сказано,
  что руками он не меняется. И сама инструкция «что делать на этой странице»
  стоит НА СТРАНИЦЕ, а не в бумажке рядом с монитором: бумажку теряют, а новый
  человек садится за эту работу без неё.
- **Тренировочный режим возвратов — ОДИН НА УСТАНОВКУ, а не на сессию.** Склад
  работает под общей учётной записью, и режим, живущий в браузерной сессии,
  означал бы, что один человек тренируется, а второй в соседнем окне принимает
  настоящие возвраты, считая, что тоже тренируется. Про режим должна знать
  установка (`RETURNS_TEST_MODE` в `settings_store`), а полоса обязана висеть на
  КАЖДОЙ странице раздела: увидь человек её один раз на входе, через час он про
  неё не вспомнит, а неверное представление о том, в каком ты режиме, и есть вся
  опасность затеи. Полоса говорит не «тест», а что из этого следует — «в 1С
  задания не поедут, остаток не изменится».
- **`is_test` живёт НА ВЕЩИ, а не на моменте.** `send_to_1c` спрашивает флаг у
  возврата, а не текущий режим: считай он режим на момент отправки, настоящий
  возврат, отправленный при включённой тренировке, молча стал бы тренировочным —
  в 1С он не поехал бы никогда, а при выходе из режима его бы ещё и стёрли.
  Проверяется СЛЕДСТВИЕМ: тренировочного задания нет в файле, который собирает
  `build_task_batch`, а боевое в нём есть — без второй половины проверка молчала
  бы и на сломанной выборке.
- **Выход из режима и уборка — одно действие, и вопрос называет ЧИСЛО.** Разними
  их, и установка осталась бы с тренировочными вещами в боевом списке, причём
  одна из них висела бы в «ждём 1С» вечно: настоящего ответа по ней не будет
  никогда. А число в вопросе не украшение — в тренировочном режиме мог быть
  принят НАСТОЯЩИЙ возврат (человек ошибся режимом), и это единственный шанс
  заметить до того, как запись исчезнет. Вход подтверждения НЕ требует: лишний
  вопрос на безопасном действии приучает жать «да» не читая, и тогда вопрос на
  выходе тоже перестанет работать.
- **Ответ 1С понарошку упирается в ДВА рубежа, и проверять их надо порознь.**
  `simulate_1c` спрашивает и вещь (`item.is_test`), и её задание
  (`task.is_test`). У боевой вещи задание тоже боевое, поэтому тест «отказать на
  настоящем возврате» проходит по ВТОРОМУ рубежу и молчит, если убрать первый, —
  верный ответ по неверной причине. Поэтому каждый рубеж закрыт своим тестом,
  собирающим состояние, невозможное по построению (боевая вещь с тренировочным
  заданием и наоборот): раз оно возникло, значит мы уже где-то ошиблись, и
  единственный верный ответ — отказ. Правило «терминальный статус ставит только
  ответ 1С» при этом цело: статус по-прежнему ставит `apply_1c_result`, просто
  ответ ему приносит кнопка.
- **Раздел, рисующий шапку общим `base.html`, обязан класть флеш В КОНТЕКСТ.**
  `base.html` берёт его оттуда, а не из сессии сам, и забытая строка означает,
  что КАЖДЫЙ отказ раздела уходит в никуда: человек нажимает «Вернуть в
  продажу», экран не меняется, и он решает, что кнопка сломана. Весь раздел
  возвратов проехал на этом до первого теста, и поймался тот не сразу: проверка
  искала слово «мэппинг», которое есть и в статическом тексте шаблона, — то есть
  молчала бы, даже пропади сообщение целиком. Проверять надо текстом ОТКАЗА
  слово в слово и по ОТВЕТУ на нажатие: `TestClient` идёт по редиректу сам, и
  отдельный `GET` после него видит уже пустую страницу.

## Тестирование на боевом сервере — только так, не иначе

Для проверки поведения на реальном товаре и реальном кабинете **используй
страницу `/testing` в самом приложении**, не создавай тестовые заказы
вручную через psql или скрипты в обход неё — только `/testing`
гарантирует простановку `is_test=True` и безопасную очистку.
`scripts/smoke_test.py` заказы НЕ симулирует: он только логинится и
проверяет, что страницы открываются (GET-запросы), — это проверка после
деплоя, а не замена странице `/testing`.

Никогда не пиши в БД прод-сервера напрямую (`psql ... UPDATE/DELETE`) в
обход приложения и alembic — это гарантированно разойдётся с тем, что
ожидает код (например, забудешь поставить `is_test`, или нарушишь
уникальные ограничения типа `uq_product_account`).

## Обновление боевой версии

**На реальном сервере (Windows) — блоком наката.** git там не установлен, файлы
приносятся копированием или скриптом, который сверяет sha256 КАЖДОГО файла до
первой записи и не трогает ничего, если хоть один разошёлся.

**Патч на этом сервере запускают ФАЙЛОМ, а не вставкой блоков в консоль.**
Отдавая патч, всегда выводи рядом обе команды целиком — сам патч и накат с
`-Tag`:

```powershell
powershell -ExecutionPolicy Bypass -File C:\sync_admin\pmNNN_deploy.ps1
powershell -ExecutionPolicy Bypass -File C:\sync_admin\deploy\update_windows.ps1 -Tag pmNNN
```

Отсюда же обязательность BOM у файла патча (`utf-8-sig` в генераторе): при
запуске файлом PowerShell 5.1 без BOM читает его как cp1251, длинное тире
закрывает строковый литерал раньше времени, и парсер падает, не дойдя до
блоков. Вставка в консоль это не ловила — там кодировка уже верная. Дальше по порядку:
`alembic upgrade head` → `pytest -q` → `nssm restart sync_admin_worker` и
`sync_admin_web` → `/health`. Подробности и особенности — `deploy/README_WINDOWS.md`.

**Ниже — Linux-вариант развёртывания.** На боевом сервере он неприменим: там нет
ни systemd, ни PostgreSQL, ни sudo.

```bash
sudo bash deploy/safe_deploy.sh
```
Делает по порядку: бэкап кода и базы → тесты → само обновление → health-check
→ если health-check не прошёл, автоматически откатывает КОД (базу — нет,
осознанно, см. комментарий в скрипте) и сообщает, что делать дальше руками.

**Не используй `deploy/update.sh` напрямую на проде** — он не делает
бэкап и не проверяет здоровье после обновления. Он остался для случаев,
когда `safe_deploy.sh` неприменим (например, ручная отладка на стейдже),
но не для автономного запуска агентом без присмотра.

Откат вручную, если что-то пошло не так уже после успешного health-check:
```bash
sudo bash deploy/rollback.sh
```

## Границы автономности агента

Делай самостоятельно, без переспрашивания:
- Правки кода + тесты + миграции по описанной выше процедуре.
- Запуск `deploy/safe_deploy.sh` — он сам себя проверяет и откатывает при сбое
  (только Linux-вариант).
- Чтение логов. На боевом Windows: `C:\sync_admin\logs\worker.err.log` и
  `web.err.log`, **обязательно с `-Encoding UTF8`** — лог пишется в UTF-8, без
  указания кодировки кириллица превратится в мусор и не найдётся поиском.
  В Linux-варианте — `journalctl -u sync-admin-web`, `-u sync-admin-scheduler`.

Спрашивай подтверждение перед тем, как:
- Менять `.env` на проде (там реальные токены площадок и пароль БД).
- Деактивировать/активировать боевой кабинет площадки вручную через БД.
- Восстанавливать базу из бэкапа (`deploy/rollback.sh --with-db`) —
  это стирает любые реальные заказы, принятые после бэкапа.
- Менять что-либо в `app/workers/platform_clients/` без возможности
  проверить на реальных ключах — эти клиенты никогда не тестировались
  против живых API WB/Ozon/Kit, правки там особенно рискованны вслепую.
- Сбрасывать пароль пользователя (`sudo bash deploy/reset_password.sh`)
  без явной просьбы — это меняет доступ живого человека к системе.
