# Синхронизация площадок — админка

Каркас веб-интерфейса: вход, API-ключи, мэппинг с фильтрами, синхронизируемые
товары с чекбоксами и фильтрами. FastAPI + Jinja2 + HTMX (без сборки фронтенда,
живая фильтрация без перезагрузки страницы). База — SQLite на боевом
Windows-сервере, PostgreSQL в Linux-варианте развёртывания (см. ниже).

## Что уже реализовано

- Страница входа с логином/паролем (bcrypt, сессии на cookie).
- Страница API-ключей — по одному блоку на площадку (WB / Ozon / Kit),
  значения хранятся зашифрованными (Fernet), в интерфейсе показываются
  маскированными.
- Страница мэппинга — таблица «Баркод → номенклатура» с поиском и фильтром
  по площадке-источнику, переключение на список конфликтов сопоставления.
- Страница синхронизируемых товаров — чекбоксы WB/Ozon/Kit по каждому
  товару, живое переключение без перезагрузки, значок ⚡ для товаров с
  необработанным предложением (карточка найдена на площадке), фильтр
  «только с предложениями», предупреждение «нет баркода».

## Статус готовности к проду

Три вещи, которые раньше числились как «доделать», уже закрыты — ниже их
текущее состояние. Осталось одно настоящее «непроверено» (клиенты площадок
на живых ключах):

1. **Фоновые процессы** (опрос площадок, выгрузка из 1С, очередь рассылки,
   сверка) — реализованы, см. раздел «Фоновые воркеры (app/workers/)» ниже.
   Наполнение `products`/`barcodes`/`sync_settings` идёт из них и из канала
   обмена с 1С (локальная папка `C:\sync`).
2. **`enqueue_full_resend()`** — реализована и живёт в `app/transmit.py`
   (страницы «Синхронизируемые товары» и «Управление остатками» слиты в одну,
   `app/routers/products.py`): кладёт запись в очередь рассылки
   (`DispatchQueueItem`, `reason="manual_enable"`), которую разбирает воркер
   `app/workers/dispatch.py`. Снятие галочки кабинета кладёт туда же ноль
   (`enqueue_withdrawal`) — остаток отзывается с площадки.
3. **Alembic-миграции** — первая миграция сгенерирована
   (`alembic/versions/`), `alembic upgrade head` поднимает полную схему.
   `Base.metadata.create_all()` в `main.py` оставлен только для быстрого
   старта в разработке.

Единственный реальный непроверенный пробел — HTTP-клиенты площадок против
живых ключей WB/Ozon/Kit (подробности ниже в разделе «Что всё ещё не
проверено» и в `HANDOFF.md`).

## Фоновые воркеры (app/workers/)

Это уже не каркас, а рабочая реализация разделов 4-10 спецификации:
`order_poller.py` (приём заказов + отмены + частичные возвраты Kit),
`dispatch.py` (рассылка с дедупликацией по товару за цикл),
`ftp_channel.py` (Python-сторона канала с 1С через локальную папку `C:\sync` —
класс `LocalExchange`, сборка заданий, разбор результатов, детект просроченных),
`reconciliation.py` (сверка с классификацией дельты и авто-коррекцией),
`catalog_poller.py` (индикатор-предложение ⚡),
`platform_clients/{wb,ozon,kit}.py` (HTTP-клиенты по документации,
**не проверены против реальных ключей** — см. предупреждение в
`platform_clients/base.py`).

Покрыты тестами (`tests/`, 1047 тестов, без сети и без реальных ключей —
API площадок подменяются фейковыми клиентами):

```bash
pytest tests/ -v
```

Запуск воркеров в проде — отдельный процесс, не тот же, что веб-сервер:

```bash
python -m app.workers.scheduler
```

Требует переменные окружения `WAREHOUSE_ID_WB/OZON/KIT` и `SYNC_DIR_TASKS/RESULTS/ARCHIVE`
(см. `.env.example`) плюс заполненные API-ключи в самой админке (раздел
«API-ключи») — без них соответствующий воркер будет тихо пропускать цикл
и писать об этом в `/health` (`last_success: false`).

## Склады в 1С — создать и назвать ДО запуска

Система привязывается к складам старой базы 1С **по точному имени** (код ищет
их по названию, не по коду/ID). Заведите их заранее — или переименуйте
существующие ровно так:

Реальные имена в базе «Магазин одежды и обуви» (сверено по конфигурации):

| Роль | WB | Ozon | Kit (магазин «Сайт AWER») |
|---|---|---|---|
| Источник (физический остаток) | `ЦС Склад` | `ЦС Склад` | `ЦС Склад` |
| «В пути» (резерв под заказ) | `Wildberries_Впути` | `OZON_Впути` | `AWER в пути` |
| Склад площадки (продано/отгружено) | `Wildberries_Склад_FBO` | `OZON_Склад` | `Сайт AWER` |

Склад-источник `ЦС Склад` — один на все площадки. Склады «в пути» и «склад
площадки» — по одному на площадку (реюз действующих складов заказчика). Магазин
документа перемещения заполняется автоматически из реквизита `Склад.Магазин`.

Жизненный цикл заказа в 1С (перемещения):

| Событие | Перемещение (на примере WB) |
|---|---|
| Заказ принят | `ЦС Склад` → `Wildberries_Впути` (резерв) |
| Заказ **подтверждён** | `Wildberries_Впути` → `Wildberries_Склад_FBO` |
| Заказ **не подтверждён** (отменён до подтверждения) | `Wildberries_Впути` → `ЦС Склад` (возврат) |

Поток заканчивается на одном из двух: товар либо ушёл на склад площадки
(подтверждён), либо вернулся на `ЦС` (не подтверждён). **Продажу и возврат
ПОСЛЕ подтверждения система не обрабатывает** — подтверждённый заказ терминален
(отмена уже подтверждённого заказа игнорируется).

> Оговорка: перемещение **на подтверждении** реализовано на стороне приложения
> (движение, статус заказа, команда `CONFIRM_MOVEMENT`, покрыто тестами), но
> **сам детект статуса «подтверждён» по каждой площадке ещё не реализован** —
> для него нужны реальные статусы живого API (WB `supplierStatus`, Ozon posting
> status, Kit статус). Пока этот детект не заполнен, движение на подтверждении в
> проде не создаётся (см. `get_confirmed_orders` в `platform_clients/base.py`).

Важные правила именования:

- **Точное совпадение**, включая регистр и пробелы: `Wildberries_Впути`, не
  `wildberries_впути` и не `Wildberries Впути`.
- Склад «в пути» — **один на площадку, а не на кабинет**: три кабинета WB
  (разных ИП) резервируют в один и тот же `Wildberries_Впути`. Если нужен раздельный
  учёт резерва по ИП — это отдельная доработка на стороне 1С (доп. склады).
- Склад «в пути» площадки нужен только там, где есть **активный кабинет**.
  Актуальный список для вашей конфигурации всегда показан на странице
  **«API-ключи»** (блок «Склады, которые нужны в 1С») — он обновляется сам при
  добавлении/отключении кабинетов.

`ID склада на площадке` в админке (у каждого кабинета) — это **другое**: там ID
склада продавца на самом маркетплейсе (куда пишутся остатки), не имя склада 1С.

## Мониторинг живости

```
GET /health
```

Без авторизации (для внешних систем мониторинга). Возвращает 200, если все
воркеры отчитались вовремя, 503 — если хотя бы один "протух" (не запускался
дольше ожидаемого интервала x3) или упал с ошибкой. Отдельно 503 отдаётся,
если не отчитался вообще ни один воркер (планировщик не запущен или упал до
первого цикла) — иначе мёртвый планировщик выглядел бы «здоровым». Подходит
для Zabbix, Uptime Kuma, или простого curl из cron/NSSM.

Отдельная строка `reconciliation_applied` — не воркер, а отметка ФАКТА: когда
сверка в последний раз реально применила выгрузку остатков из 1С. Само задание
`reconciliation` отчитывается об успехе и тогда, когда применять было нечего
(1С не отдала свежий файл — ошибки нет, задание отработало честно). Для системы
про остатки это разные вещи: пока выгрузки нет, остаток в приложении не сверяется
со складом, расходится с ним и в этом виде уезжает на площадки. Три пропущенных
часовых цикла подряд — 503.

## Миграции (Alembic)

Первая миграция уже сгенерирована (`alembic/versions/`). Дальнейшие изменения
моделей — через `alembic revision --autogenerate -m "..."`, затем

## Что всё ещё не проверено (честно)

- Ни один из трёх HTTP-клиентов площадок не тестировался против настоящих
  API-ключей — их пока нет в системе.
- Kit в заказе отдаёт `product_variant_id`, а не физический баркод — код
  обходит это (раздел `_representative_barcode` в `order_poller.py`), но
  это стоит пересмотреть, когда будет ясно, отдаёт ли Kit баркод где-либо ещё.
- Список статусов, разрешающих `POST /v1/orders/{id}/cancel` у Kit, не
  раскрыт в документации — код полагается на прямую проверку статуса заказа,
  а не на список "разрешено/нет".

## Инструменты стабильности и тестирования (app/workers/http_retry.py, circuit_breaker.py, /diagnostics)

Отдельный слой, добавленный поверх воркеров именно для эксплуатации:

- **Проверка подключения** — кнопка на страницах «API-ключи» и «Диагностика»
  дёргает лёгкий read-only запрос (`/ping` у WB, список товаров с лимитом 1
  у Ozon, список складов у Kit) и сразу показывает, валиден ли токен —
  не нужно ждать первого цикла планировщика, чтобы узнать, что ключ не тот.
- **Retry с бэкоффом** (`http_retry.py`) — все HTTP-вызовы к площадкам
  автоматически повторяются при 429/5xx, с уважением к специфичному для
  WB заголовку `X-Ratelimit-Retry` (раздел 12.1 спецификации) и обычному
  `Retry-After` у остальных. 4xx, кроме 429, не ретраятся — это ошибка
  запроса, а не лимита.
- **Автоматический выключатель** (`circuit_breaker.py`) — если у кабинета
  подряд накопилось 5 сбоев опроса заказов, он сам отключается
  (`is_active = False`), чтобы не долбить сломанные ключи бесконечно и не
  засорять очередь. Видно на странице «Диагностика», сбрасывается вручную
  одной кнопкой после того, как ключи поправили.
- **Страница «Диагностика»** (`/diagnostics`) — сводка по каждому кабинету:
  живость последнего опроса заказов, глубина очереди рассылки и очереди
  заданий в 1С, счётчик сбоев. Кнопки «Опросить заказы сейчас» и «Обновить
  каталог сейчас» запускают воркер вне расписания и сразу показывают
  результат — не нужно ждать интервал планировщика или лезть в логи сервера.

## Страница «Тестирование» (/testing) — прогон одного товара перед запуском

Ровно то, чего не хватало для уверенного запуска в бой: выбираете один
товар и один кабинет, дальше:

1. **Отправка остатка** — реальный вызов `push_stock` с текущим фактическим
   количеством. Безопасно (не меняет ничего, чего там уже не должно быть),
   подтверждает, что ключи и склад настроены верно.
2. **Симуляция заказа** — без необходимости реальной покупки: синтетический
   заказ (`TEST-...`) прогоняется через **ту же функцию**
   `process_new_order`, что использует живой опрос — сопоставление баркода,
   списание остатка, рассылка на остальные кабинеты, задание в 1С. Видно
   сразу, что именно произошло на каждом шаге.
3. **Симуляция отмены** — реверс тестового заказа, тот же код, что и
   реальная отмена.
4. **Очистка** — восстанавливает физический остаток, ставит корректирующую
   запись в очередь рассылки (не удаляет чужие записи из очереди вслепую —
   это было бы небезопасно, см. комментарий в `testing.py`) и убирает
   тестовые `ProcessedOrder`/`FtpTask`/`SyncAnomaly` по точному совпадению
   `order_id` с префиксом `TEST-`.

Ключевая идея: страница не содержит отдельной «тестовой» реализации логики —
она вызывает ровно тот же код (`process_new_order`, `process_cancellation`),
что работает в проде. Значит успешный прогон здесь — это реальная гарантия,
а не проверка отдельной параллельной ветки, которая могла разойтись с боевой.

## Развёртывание — целевая среда

> ⚠️ **Актуальный целевой сервер — Windows Server** (WIN-Q0QVP2SM59L,
> `136.243.92.95`), на котором уже работают 1С (клиент-сервер, база `modus_new`)
> и будет крутиться это приложение. Обмен с 1С — через локальную папку `C:\sync`
> (не FTP). Инструкции ниже (`deploy/install.sh`, systemd, Nginx, Certbot, reg.ru
> VPS) описывают **Linux-развёртывание** и оставлены как альтернатива — под
> текущий Windows-таргет они не подходят. Windows-развёртывание (uvicorn + служба
> через NSSM/Task Scheduler, планировщик как отдельная служба, папка `C:\sync`)
> **развёрнуто и работает** с 09.2026: `deploy/install_windows.ps1`,
> `deploy/README_WINDOWS.md`. База там — SQLite (`C:/sync_admin/sync_admin.db`),
> а не PostgreSQL: установщик умеет оба варианта, выбран SQLite. Отсюда WAL и
> `busy_timeout` в `app/database.py` — веб и планировщик пишут в один файл.

## Установка одной командой (Linux/VPS — альтернатива)

```bash
sudo bash deploy/install.sh your-domain.ru
```

Делает всё из `deploy/README.md` за один проход: системные пакеты,
пользователь приложения, PostgreSQL с сгенерированным паролем, `.env` с
автоматически сгенерированными секретами (`SESSION_SECRET`,
`SECRETS_ENCRYPTION_KEY` через Fernet), миграции, первый пользователь
админки со случайным паролем (выводится в конце), systemd-службы, Nginx,
бесплатный SSL через Certbot. Повторный запуск безопасен — существующий
`.env` не перезаписывается, пароль администратора не создаётся повторно.

Если DNS домена ещё не настроен на этот сервер — выпуск SSL пропустить:
`SKIP_SSL=1 sudo bash deploy/install.sh your-domain.ru`, выпустить позже
вручную командой `certbot --nginx -d your-domain.ru`.

Обновление уже установленного приложения новой версией кода — без
пересоздания базы, секретов и пользователей:

```bash
sudo bash deploy/update.sh
```

Оба скрипта проверены `shellcheck` без единого замечания.

## Развёртывание на reg.ru — читать перед покупкой хостинга

**Обычный «Хостинг с поддержкой Python» на reg.ru не подходит** — он
работает через Passenger WSGI (несовместимо с ASGI/FastAPI), даёт только
MySQL вместо PostgreSQL и не позволяет держать постоянно работающий процесс
(наш `scheduler.py` должен крутиться круглосуточно). Нужен **VPS/VDS или
облачный сервер** (`reg.cloud`) — там это всё есть из коробки. Подробная
инструкция с systemd-юнитами и конфигом Nginx — в `deploy/README.md`.

## Где в системе действительно стоило бы поставить ИИ-агента

Честная оценка, не «давайте добавим ИИ везде». Прошлась по всем задачам
программы — большинству ИИ не место: это система про деньги и остатки,
там нужна детерминированность, а не правдоподобное угадывание.

**Единственный по-настоящему хороший кандидат — подсказки при разборе
конфликтов сопоставления** (страница «Мэппинг», вкладка «Конфликты»).
Сейчас оператор видит баркод и — если загружена спецификация площадки —
название товара оттуда, и вручную ищет, какому `ID_1С` это соответствует.
При росте каталога это станет узким местом. ИИ-агент мог бы предлагать
наиболее вероятное совпадение (по схожести названия/артикула с уже
существующими товарами), но **не решать сам** — просто подставлять
предложенное значение в колонку `ID_1С` экспортированного Excel, которое
оператор всё равно проверяет и подтверждает тем же импортом, что уже есть.
Риск при ошибке ИИ — ноль, потому что человек и так финальная инстанция.

**Не критично прямо сейчас** — система ещё ни разу не работала с реальными
данными (нет ни одного настоящего кабинета с ключами), неоткуда взяться
объёму конфликтов, который оправдывал бы доработку. Плюс это требует
нового внешнего API-ключа (Anthropic) с отдельным управлением, аналогично
ключам площадок — не бесплатная доработка «заодно», а отдельная система
хранения секретов, которой сейчас в проекте нет.

**Где ИИ точно не место:** приём заказов/списание/рассылка/задания в 1С
(must stay deterministic), диагностика ошибок API площадок (нужна точная
документация конкретной площадки, не генерация текста), аномалии (причины
уже фиксированный список из двух понятных формулировок).

## Работа с прод-версией через Claude Code

В корне проекта — `CLAUDE.md`, который Claude Code читает автоматически.
Там прописаны: как гонять тесты перед любым изменением, где граница
автономности агента (что можно делать без подтверждения, что — только
после явного «да» от человека), и единственный правильный путь
обновления прода:

```bash
sudo bash deploy/safe_deploy.sh
```

В отличие от `deploy/update.sh` (остался для ручной отладки), этот скрипт:
бэкапит код и базу (`deploy/backup.sh`) → гоняет весь тестовый набор **до
того**, как тронуть прод → деплоит → проверяет здоровье (что службы живы,
что `/login` отвечает 200) → если что-то не так, **автоматически
откатывает код**. Базу при автооткате сознательно не трогает — восстановить
дамп проще, чем объяснить клиенту, откуда делись реальные заказы, принятые
за то время, пока деплой был неудачным.

Ручной откат — `deploy/rollback.sh` (с флагом `--with-db`, если нужно
откатить и базу, спрашивает явное подтверждение).

Проверка после деплоя без браузера — `scripts/smoke_test.py`: логинится,
открывает все основные страницы, ничего не создаёт и не меняет. Реально
протестирован на поднятом сервере (успешный и неуспешный вход).

## Защита от подбора пароля

10 неверных попыток подряд — аккаунт блокируется на 30 минут
(`app/login_security.py`). Попытки входа во время самой блокировки не
продлевают её и не увеличивают счётчик — иначе можно было бы держать
чужой аккаунт заблокированным бесконечно, просто продолжая стучаться.
Успешный вход сбрасывает счётчик. Блокировка пишется в общий аудит-лог
(`actor='system'`). Неизвестный логин не выдаёт, существует ли
пользователь — тот же обобщённый текст ошибки, без счётчика попыток.

## Как авторизоваться после развёртывания в облаке

1. `deploy/install.sh` в конце вывода печатает логин и пароль первого
   пользователя (пароль — один раз, дальше он хранится только как хэш и
   нигде не восстановим в открытом виде). Открываете
   `https://ваш-домен.ru/login`, вводите эти логин/пароль.
2. **Если пароль потерян** (или аккаунт заблокирован после 10 неверных
   попыток — см. ниже):
   ```bash
   sudo bash deploy/reset_password.sh admin
   ```
   Без второго аргумента сам сгенерирует пароль и один раз его покажет.
   Можно и явно: `sudo bash deploy/reset_password.sh admin мой-пароль`.
   Заодно снимает блокировку по неудачным попыткам, если она была, и
   пишет запись в аудит-лог (`actor='cli'`).

## Тесты

Два уровня: юнит-тесты воркеров (изолированная in-memory БД, фейковые
клиенты площадок — без сети) и веб-тесты (реальный FastAPI + файловая
SQLite, проверяют весь HTTP-слой: вход, фильтры, Excel-экспорт/импорт,
чекбоксы, health-чек). 678 тестов, ни один не требует реальных ключей площадок.

```bash
pytest tests/ -v
```

## Запуск локально

Поддерживается Python 3.11–3.14. Все зависимости ставятся готовыми
колёсами (`psycopg2-binary==2.9.13` даёт колёса вплоть до 3.14 —
компилятор и `pg_config` для установки не нужны).

```bash
python -m venv venv
source venv/bin/activate   # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env
# Заполнить .env реальными значениями:
#   SESSION_SECRET — любая случайная строка от 32 символов
#   SECRETS_ENCRYPTION_KEY — вывод команды:
#     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

# Поднять PostgreSQL (пример через Docker):
docker run -d --name sync-db -e POSTGRES_USER=sync_user \
    -e POSTGRES_PASSWORD=sync_password -e POSTGRES_DB=sync_admin \
    -p 5432:5432 postgres:16

set -a; source .env; set +a
python create_admin_user.py admin ваш_пароль

uvicorn app.main:app --reload --port 8000
```

Открыть `http://localhost:8000` — редирект на страницу входа.

## Структура проекта

```
app/
  main.py            — точка входа, роуты, сессии, обработчик 401
  database.py        — подключение SQLAlchemy
  models.py          — таблицы (соответствуют объектам спецификации)
  security.py        — хэширование паролей
  crypto.py          — шифрование API-ключей
  dependencies.py    — get_current_user, редирект неавторизованных
  transmit.py        — сколько уходит на площадку и почему (единый расчёт)
  routers/
    auth.py          — вход/выход
    api_keys.py      — страница API-ключей
    mapping.py       — страница мэппинга
    platform_matching.py — сопоставление площадок между собой
    products.py      — «Товары и остатки» (заменила «Синхронизируемые товары»
                       и «Управление остатками»)
    anomalies.py     — аномалии
    diagnostics.py   — диагностика
    testing.py       — страница тестирования и бэкфилла
    stock_on_date.py — «Остатки на дату»: запрос в 1С остатков ЦС на заданное
                       число и просмотр ответа (справка, на площадки не влияет)
    health.py        — /health для мониторинга
  templates/         — Jinja2-шаблоны (base + страницы + HTMX-фрагменты)
  static/style.css   — стили, без сторонних UI-фреймворков
create_admin_user.py — разовый скрипт создания первого пользователя
```
