# HANDOFF — передача в Claude Code для тестирования с реальными ключами

Читать в первую очередь при открытии проекта. `CLAUDE.md` — правила
работы над кодом (тесты, миграции, границы автономности). Этот файл —
снимок состояния на момент передачи и конкретный чеклист того, что
осталось проверить теперь, когда появился доступ к терминалу и, видимо,
к реальным ключам площадок.

## Статус на момент передачи

- 187 автотестов, все зелёные (`pytest tests/ -q`).
- Вся бизнес-логика (приём заказов, отмены, частичный возврат Kit,
  рассылка, минимальный порог, реконсиляция, кабинеты, блокировка входа)
  написана и покрыта тестами через фейковые/подменные клиенты площадок.
- Административный веб-интерфейс — 7 страниц, все с тестами уровня HTTP.
- Скрипты развёртывания на VPS (`deploy/`) — синтаксически и логически
  проверены (`shellcheck`, `bash -n`, юнит-прогоны отдельных кусков), но
  **ни разу не запускались на настоящем systemd/PostgreSQL/Nginx** — этой
  песочнице некуда столько дать.
- **Ни один из трёх клиентов площадок (`app/workers/platform_clients/`) ни
  разу не вызывал реальный API.** Всё написано строго по документации,
  собранной на этапе проектирования, и проверено только на примерах
  ответов, воспроизведённых вручную по документации — не на живых данных.

Это последний big-picture пробел во всём проекте. Всё остальное можно
было проверить без реальных ключей; это — нельзя было в принципе.

## Порядок первого реального теста — не наугад, по шагам

1. **Одна площадка, один кабинет.** Не пытаться подключить все три сразу.
   Начать с той, где ключи получить проще всего (обычно Ozon — там
   Client-Id/Api-Key выдаются сразу в личном кабинете без модерации).
2. `/api-keys` → добавить кабинет → вписать реальные ключи → вписать
   реальный ID склада (`warehouse_id`) с площадки.
3. `/diagnostics` → кнопка «Проверить подключение» — это самый дешёвый
   и безопасный первый шаг, единственный `test_connection()` в каждом
   клиенте, который делает один лёгкий read-only запрос. Если он падает —
   почти наверняка неверный формат ключа/токена, чинить в первую очередь
   здесь, ещё до заказов и остатков.
4. `/mapping` → вкладка «Конфликты» → кнопка «Загрузить спецификацию»
   для этого кабинета — проверяет `get_catalog_items()`, самый насыщенный
   по данным метод (баркод + артикул + название). Если тут всё ок —
   парсинг ответа API реально работает на живых данных.
5. Сопоставить один реальный товар с этим кабинетом (через «Мэппинг»),
   включить синхронизацию на `/products`.
6. `/testing` → выбрать этот товар и кабинет → «Отправить текущий
   остаток» — первый реальный `push_stock()` на живую площадку.
   Безопасно (отправляет то значение, что и так должно там стоять).
7. Только после этого — `/diagnostics` → «Опросить заказы сейчас» на
   этом кабинете, если там реально есть тестовый/технический заказ для
   проверки `get_orders_awaiting_confirmation()`. Если тестового заказа
   нет и негде его создать — можно ограничиться следующим шагом.
8. `/testing` → «Симулировать поступление заказа» — прогоняет ровно ту
   же логику приёма заказа, что и боевой опрос, но на синтетических
   данных. Не заменяет пункт 7 (реальный формат ответа API всё равно
   нужно увидеть), но проверяет, что наша сторона (сопоставление,
   списание, рассылка, задание в 1С) отработает правильно, когда пункт 7
   даст реальные данные.

Повторить шаги 2–8 для Kit, затем для WB (WB — самая содержательная
площадка по функциональности: 3 кабинета, `X-Ratelimit-Retry`, `/ping` —
имеет смысл разбирать последней, когда уже есть опыт на двух других).

## Чеклист по площадкам — конкретные места, где я честно писала «предположение»

### Wildberries (`app/workers/platform_clients/wb.py`)

- [ ] Поле с названием карточки (строка ~135): использовано
  `card.get("title") or card.get("subjectName")` — ни то, ни другое не
  подтверждено вживую, только предположение по фрагментам документации.
  Первый реальный ответ `/content/v1/cards/cursor/list` покажет, как на
  самом деле называется поле.
- [ ] `/ping` (в `test_connection()`) — правильный ли это путь для
  категории Marketplace, и правда ли не требует отдельных прав.
- [ ] `X-Ratelimit-Retry` — реальный ли это заголовок при 429, или WB
  использует что-то другое (тогда `http_retry.py` упадёт в общий
  `Retry-After`, что тоже не катастрофа, но стоит перепроверить).
- [ ] Реальная схема ответа `/api/v3/orders/new` — поле `skus` как список
  баркодов, `id` как строка/число — сверить типы.

### Ozon (`app/workers/platform_clients/ozon.py`)

- [ ] `/v3/product/info/list` действительно отдаёт `barcode` — это
  единственное, что подтверждено официальной документацией (не просто
  предположением) среди всех трёх площадок, поэтому Ozon, вероятно,
  заведётся ровнее остальных.
- [ ] Пагинация `/v2/product/list` через `last_id` — логика написана по
  документации, не проверена на каталоге больше одной страницы (100+
  товаров).

### Яндекс KIT (`app/workers/platform_clients/kit.py`)

Сверено с OpenAPI-спекой Kit (skill `yandex-kit-cabinet`, офлайн) + живыми
вызовами — вопросы ниже **закрыты**:

- [x] Заголовок авторизации `Authorization: Bearer <token>` — подтверждён на
  живом API (200 на `/v1/orders`, `/v1/warehouses`, `/v1/variants`).
- [x] Статусы заказа — по спеке (`schema Order`): приём =
  `WAIT_FOR_CONFIRMATION`; отмены = `CANCELLED`/`DELIVERY_CANCELLED`/`FULL_REFUND`;
  частичный возврат = `PARTIAL_REFUND` (поле позиции `refused_count`);
  подтверждение = переход в доставку (`SETUP_DELIVERY`/`WAIT_FOR_DELIVERY`/…) —
  реализован детект `get_confirmed_orders`.
- [x] `product_variant_id` в позиции заказа (`OrderItem`) → баркод через
  `GET /v1/variants/{id}` — подтверждено спекой.
- [x] Обновление остатков — `POST /v1/variants/stocks/bulk_update`, элемент
  `variant_id`(uuid)+`warehouse_id`(uuid)+`quantity`(абсолютное) — совпадает.
- [ ] Кэш `_resolve_variant_barcode` только в рамках одного вызова — при
  большом потоке заказов можно кэшировать между вызовами (оптимизация, не баг).
- [ ] `GET /v1/orders` без фильтров — заказы вычитываются постранично и
  фильтруются локально по статусу (так устроен API Kit, подтверждено спекой).

### Канал 1С (не в этом репозитории — отдельный артефакт из более ранней сессии)

- [ ] Версия платформы 1С 8.2 на конкретной сборке клиента — не
  подтверждена, влияет на доступность `ЧтениеJSON`/`ЗаписьJSON`.
- [ ] Наличие объекта `FTPСоединение` в этой сборке 8.2.
- [ ] Реальное имя регистра `ШтрихКодыНоменклатуры` в конфигурации
  клиента — использовано по аналогии с типовой «Розницей», не
  подтверждено на редакции 1.0 «Магазин одежды и обуви».
- [ ] `.epf`-обработка ни разу не запускалась на реальной базе.

## Что стоит сделать сразу после первого реального прогона

Как только пункты чеклиста выше подтвердятся или найдутся расхождения —
поправить соответствующий клиент и обязательно обновить тесты
(`tests/test_connection_check.py`, `tests/test_catalog_sync.py` и
парсинг-тесты в них построены на предположениях о формате ответа; когда
появятся настоящие ответы API — заменить примеры в тестах на реальные,
а не просто починить код и оставить тесты проверять старое предположение).
