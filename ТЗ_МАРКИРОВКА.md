## 1. Назначение и границы

Одна программа вместо трёх несвязанных инструментов, которыми сейчас
делается поставка на Lamoda:
- **kiz-tool** — браузерная страница: заказ кодов, ввод в оборот, этикетки;
- **upd-constructor** — УПД 5.03 из файла Lamoda;
- **lamoda_stickers** — стикеры коробов в Excel.

Их проверенная логика и найденные тупики **переносятся**, а не
изобретаются заново. Для kiz-tool это `docs/API_NOTES.md` и
`docs/HISTORY.md`.

Что сейчас плохо и что меняется:
- Коды живут во вкладке браузера и в xlsx. Закрыли вкладку между заказом и
  сохранением — оплаченные коды потеряны. В программе **каждый код
  пишется в базу в момент получения** и сразу уходит в резервную копию.
- Истории нет: какие коды в какой поставке, что введено, какой УПД ушёл. В
  программе всё это в базе с журналом.
- Справочник «артикул → GTIN» лежит в `localStorage` одного браузера. В
  программе он в базе.
- Файлы переносятся между инструментами руками. В программе поставка —
  одна запись, из неё строится всё остальное.

**Путь товара (основной случай):**

```
Файл поставки: размерный артикул + количество
  → EAN и цена — из справочника «Одежда полный»                     (6.1)
  → Проверка остатка в 1С → перемещение «ЦС Склад» → «Lamaoda_Склад»  (6.2, 9)
  → Заказ кодов в СУЗ по GTIN → коды в базу                          (7.1)
  → Ввод в оборот (ждём «Нанесён» → документ → «В обороте»)          (7.2)
  → Этикетки 58×40 (по желанию)                                      (7.3)
  → Файл поставки С кодами (полный код) → человек грузит в Lamoda     (6.3)
  → Lamoda отдаёт «Поставки FBO» (коды короткие) → УПД 5.03 ДОП      (6.4, 6.5)
  → Стикеры коробов (Excel)                                          (6.6)
  → Отчёт о приёмке Lamoda → сверка                                  (6.7)
```

**Основной путь кодов — заказ в СУЗ и ввод в оборот.** Импорт готового
файла кодов — редкий случай (7.5), он не определяет этапность.

**Входит:** товарная группа «Лёгкая промышленность» (`lp`); поставки Lamoda
FBO одного ИП; заказ, получение, ввод в оборот и проверка статусов кодов;
этикетки; УПД; стикеры коробов; разбор отчёта о приёмке; заказ кодов от
других ИП вне поставки Lamoda.

**Не входит (первая версия):**
- отправка УПД через ЭДО (Диадок — вручную) и загрузка файлов в Lamoda
  Seller (вручную);
- УКД и исправленный УПД;
- отмена поставки и изменение её состава после перемещения (6.2);
- отчёт о нанесении — для `lp` ручная отправка запрещена (ошибка 7710) ✅;
- агрегация в короба (SSCC), возвраты, перемаркировка, выбытие;
- другие товарные группы (поле группы закладываем).

## 2. Архитектура: отдельная программа

«Маркировка и поставки» — **отдельная программа**, не модуль синхронизации
остатков (sync_admin). Связь с sync_admin одна — **обмен с 1С**: общая
обработка `ОбменССайтом` и общая папка заданий. Ни общей базы, ни общего
кода, ни вызовов друг друга.

| | sync_admin (есть) | Маркировка (новая) |
|---|---|---|
| Машина | `136.243.92.95`, Windows Server 2016 | **рабочий компьютер с КриптоПро** (не сервер); с 1С — по SFTP до сервера |
| Каталог | `C:\sync_admin` | `C:\marking` на рабочем компьютере |
| Службы | NSSM: `sync_admin_web`, `sync_admin_worker` | нет: запуск ярлыком «Маркировка», фоновая работа в том же процессе, пока программа открыта |
| Веб | `127.0.0.1:8000` на сервере | `127.0.0.1:8001` на рабочем компьютере |
| База | `sync_admin.db` | своя `marking.db` (SQLite, WAL) |
| Ключ шифрования, пользователи, настройки | свои | свои |
| Резервная копия | своя, rclone → Яндекс.Диск | своя, свой rclone, своя папка облака (11) |
| Задания в 1С | `C:\sync\tasks\task_<время>.txt` | `C:\sync\tasks\task_mark_<время>.txt` |
| Ответы 1С | `C:\sync\results\result_*.txt` | `C:\sync\results\marking\result_mark_*.txt` |
| Тесты, накат | свои | свои, накат везёт только `marking/` |

**Почему программа на рабочем компьютере, а не на сервере** (решение 29.09).
Всё, что делает этап 4, требует этой машины: подпись КриптоПро, сертификаты
всех ИП, и сам Честный знак — СУЗ с сервера (Германия) ответил 451, а через
прокси на этой машине авторизация проходит (проверено заказчиком). На
сервере программа жила бы на цепочке «SSH-туннель + прокси + плагин в
браузере», и любое звено рвало бы работу. С сервером её связывает только 1С,
а к 1С обращаются редко и по факту работы с поставкой — это файлы, которым
всё равно, откуда их положили (9.1).

Раздельность даёт одно главное свойство: сбой, накат или откат одной
программы не трогает другую. Красный тест маркировки не останавливает накат
синхронизации, и наоборот.

**Код** — каталог `marking/` в этом репозитории, без импортов из `app/`, со
своими тестами, миграциями и накатом. Нужное из sync_admin (резервная копия,
выгрузка Excel потоком, шифрование секретов, запись заданий через `.part`,
вход и роли) **копируется**, а не импортируется: общий импорт снова связал
бы накаты. Независимость закреплена тестом: ни один файл `marking/` не
импортирует `app`, и наоборот. Правила `CLAUDE.md` sync_admin (два прогона
тестов — UTC и Москва, BOM у `.ps1`, cp1251 в консоли, `is_test`,
миграции, переживающие обрыв) переносятся в собственный `marking/CLAUDE.md`.

**Где программы встречаются — все три места, каждое решено явно (детали в
разд. 9):**
1. **Общая папка ответов.** sync_admin забирает из `C:\sync\results` все
   `result_*.txt`. Ответ на чужое задание он отправил бы в архив как
   «несопоставленный», и маркировка его не увидела бы. Поэтому ответы на
   `task_mark_*` обработка пишет в подкаталог `results\marking\`, куда
   sync_admin не заглядывает (`glob` без захода в подкаталоги). **Код
   sync_admin не меняется.**
2. **Остаток ЦС, который транслирует sync_admin.** Документ поставки
   должен дойти до sync_admin минутной дельтой, иначе снятые под поставку
   штуки до часа продаются на WB/Ozon/Kit. Для этого у документа два
   условия: комментарий **не на `sync`** и дата — **текущая** (9.3).
3. **Обработка одна на двоих.** Её обновление под маркировку проверяется на
   копии базы с обеих сторон (9.6).

**Остатков из базы sync_admin программа не читает.** Истина об остатке —
1С, спрашивается она командой `SUPPLY_CHECK` (9.2).

## 3. Принципы безопасности

1. **Всё, что меняет внешний мир, — только кнопкой человека.** Заказ кодов,
   ввод в оборот, перемещение в 1С. Фоном программа только читает: статусы
   кодов, карточки НК, ответы 1С. Исключение — ввод в оборот «при
   готовности» (7.2): человек нажимает один раз, и дальше документ уходит
   по мере готовности кодов.
2. **Код — уникальный ресурс.** Хранится один раз (уникальный индекс по
   короткому КИ), имеет один статус и максимум одну поставку. В файл
   поставки и в УПД не попадает код не «в обороте» по проверке ГИС МТ (не
   по нашей отметке).
3. **Истина — статус кода в ГИС МТ**, а не «документ принят» ✅ (урок
   kiz-tool).
4. **Двойной заказ.** Перед заказом показывается, сколько неиспользованных
   кодов по этому GTIN уже есть; заказ сверх — с подтверждением. Повторное
   нажатие второй заказ не создаёт.
5. **Журнал.** Все действия с внешним эффектом пишутся в журнал. Выгрузка
   полных кодов доступна только авторизованным и тоже пишется в журнал:
   по полному коду печатается «легальная» этикетка.
6. **Контур ЧЗ** (`sandbox`/`production`) — поле организации, переключение
   с подтверждением. **[?]** Доступа к песочнице может не быть; тогда
   проверки идут на боевом контуре партиями по 1–2 кода.
7. **`is_test`.** Тренировочная поставка не кладёт файлы в `C:\sync\tasks`
   и не обращается к ЧЗ с изменяющими запросами.

## 4. Поставка: жизненный цикл

Решение заказчика: **поставки не отменяются, прецедента нет.** Поэтому
жизненный цикл линейный. Правка возможна только до перемещения в 1С, после
него поставка фиксируется. Ошибку в уже проведённом перемещении исправляют
вручную в 1С. Ручной документ не несёт комментария `sync`, поэтому его
дельту sync_admin применит сам.

| Статус | Как попадает | Что можно | Что нельзя |
|---|---|---|---|
| **Черновик** | загружен файл | править строки, дату, номер; удалить поставку; проверить остаток в 1С | — |
| **Проверено в 1С** | `SUPPLY_CHECK` вернул OK | то же; «Переместить» | — |
| **Перемещено** | `SUPPLY_MOVEMENT` вернул OK | заказывать и закреплять коды, вводить в оборот, печатать этикетки | менять состав, количество, удалять поставку |
| **Коды готовы** | все коды поставки «в обороте» | выдать файл поставки | — |
| **Файл выдан** | файл поставки скачан | повторно скачать тот же файл; загрузить «Поставки FBO» | менять коды поставки |
| **УПД выпущен** | УПД сформирован и прошёл проверку | повторно скачать; проверить в ЧЗ; стикеры | менять номер документа |
| **Принята** / **с расхождениями** | загружен отчёт о приёмке | — | — |

- Удалить можно только черновик и «Проверено в 1С». В 1С к этому моменту
  ничего не создано.
- **Коды закрепляются за поставкой в момент заказа или подбора** (7.1, 7.5)
  и больше никуда не уходят. Файл поставки берёт ровно закреплённые коды.
  Так один код не может оказаться в двух поставках (принцип 3.2).
- Статусы кодов (7.2) живут отдельно от статуса поставки. «Коды готовы»
  наступает сам, как только все закреплённые коды «в обороте».

## 5. Справочники

### 5.1 Организации (ИП)
- **С Lamoda работает один ИП — сейчас ИП Яворская Т.Н.** Это одна
  настройка программы («ИП для Lamoda»), а не выбор в каждой поставке.
  Замена — сменой настройки, например если договор с Lamoda переходит на
  другой ИП.
- Поставка при создании запоминает ИП, и смена настройки на созданные
  поставки не влияет. Черновик можно перевести на новый ИП. После
  перемещения — нельзя: коды одного ИП не должны попасть в УПД другого.
- **Других ИП может быть сколько угодно** — для заказа кодов вне поставки
  Lamoda. В таком заказе ИП по умолчанию тот же, человек может выбрать
  другой.
- **Нумерация поставок общая** на всю программу: шаг 10, текущая 12550.
  Номер не повторяется, даже у удалённого черновика.

Поля организации:
- реквизиты для УПД (для Яворской — из `upd_constructor/config.py`);
- договор с покупателем с редакциями по датам (5.4, разд. 8);
- ЧЗ: ИНН, контур, `omsId`, `connectionId` СУЗ, API-ключ Нацкаталога
  (зашифрованно), отпечаток сертификата;
- идентификатор участника ЭДО; ставка НДС (5%).

**Что привязано к организации и не смешивается:**
- **Коды** принадлежат ИП, который их заказал: в поставку закрепляются
  только коды её ИП.
- **GTIN.** Заказ разрешён только на GTIN, карточка которого в НК
  принадлежит этому ИП или к которой ему открыт доступ. Нынешние префиксы
  `0462018040…` и `0463068831…` — оба Яворской. Заказ на чужой GTIN
  блокируется с объяснением, а не уходит в СУЗ за отказом.
- **Токены ЧЗ** — у каждой организации свои (10.4).

### 5.2 Справочник «Одежда полный» (каталог Lamoda Seller)
Источник штрихкода и цены для поставки. Образец —
`marking/tests/fixtures/lamoda_catalog_full_2026-09-28.xlsx`: лист «Upload
Template», 801 строка, 91 колонка. Строка 1 служебная, строка 2 —
описания, **строка 3 — заголовки** вида `Название #код`, данные с 4-й.
Колонки находим **по коду после `#`**, а не по позиции и не по названию.

| Код | Что | Зачем |
|---|---|---|
| `supplier_sku` | размерный артикул поставщика | **ключ** поставки |
| `product_identifier` | штрихкод (EAN, `2000…`) | файл Lamoda, связь с 1С |
| `price` | цена | цена в поставке и УПД |
| `sku` | Lamoda SKU | сверка с отчётом о приёмке |
| `supplier_parent_sku`, `size_value`, `color_family`, `title` | модель, размер, цвет, название | показ, подписи этикеток |
| `tn_ved` | ТН ВЭД | сверка с карточкой НК |
| `tax_class` | ставка НДС | сверка со ставкой УПД |

`special_price` (цена со скидкой) не используется: на поставке 12550 все 80
строк несут `price` (12000 при `special_price` 6500). Проверено: все 80
артикулов 12550 найдены, штрихкод и цена совпали у 80 из 80.

Правила загрузки:
- повторная загрузка обновляет по `supplier_sku` и показывает, что
  изменилось;
- отсутствующие в новой выгрузке артикулы не удаляются (выгрузка могла быть
  частичной), а помечаются датой последнего появления;
- дубль `supplier_sku` в файле — отказ этих строк с перечнем;
- артикул сравнивается после обрезки краёв, пробелы внутри значимы (в
  каталоге встречаются двойные). Совпадение без учёта двойных пробелов —
  подсказка, а не подстановка;
- смена штрихкода или цены у артикула из черновика — отказ проверки и
  перемещения до «Перечитать из «Одежды полной»»: иначе в 1С уехал бы старый
  штрихкод, выгрузка «Поставки FBO» не сошлась бы, а перемещение не отменить.
  У поставки после перемещения цена и EAN уже зафиксированы.

### 5.3 GTIN и Национальный каталог
**GTIN ≠ EAN** ✅. EAN — внутренние `2000…` из 1С. GTIN — 14 знаков с
ведущим нулём, из Национального каталога.

**Справочник «размерный артикул ↔ GTIN»** пополняется из трёх источников:
1. **Файлы `product_gtin`**, которые заказчик загружает в Lamoda Seller.
   История получена (`marking/tests/fixtures/product_gtin/`, 10 файлов,
   11.06–21.09.2026): 1012 пар, строго один к одному. Вместе со
   справочником kiz-tool — 1031 пара без конфликтов.
2. **Выгрузка «Поставки FBO»** (6.4): GTIN берётся из КИЗ каждой строки. По
   12550 это дало 80 пар, из них 54 новых.
3. **Ручное сопоставление** для нового артикула: программа предлагает
   кандидатов из карточек НК по модели, цвету и размеру, человек
   подтверждает.

Во всех трёх случаях конфликт (тот же артикул с другим GTIN или наоборот)
не перезаписывается молча, а показывается.

**Выгрузка `product_gtin` для Lamoda** — по новым парам, которые Lamoda ещё
не получала:
- GTIN ровно 14 цифр и начинается с `046`;
- не больше 1000 строк в файле, больше — несколько файлов;
- лист инструкций сохраняется;
- правило шаблона «Supplier SKU ≤ 20 символов» Lamoda не применяет (974 из
  1012 загруженных длиннее), поэтому его не проверяем.

Доступ Lamoda (ООО «Купишуз») открыт на все карточки НК, включая новые,
поэтому программа его не проверяет.

**Карточка НК — первоисточник** для ТН ВЭД, разрешительного документа (тип,
номер, даты), цвета и размера, признаков `goodMarkFlag`/`goodTurnFlag`.
- Читается **с токеном True API** (вход сертификатом, 10.4), дальше фоном,
  из воркера. Одного API-ключа мало: `GET /nk/product?apikey=` отвечает 401
  «Токен не действителен» ✅ (30.09.2026). Токен ~10 ч; без него очередь
  карточек стоит с пометкой «нужен вход».
  Методы: `GET /nk/product?gtin=` / `gtins=` и
  `POST /api/v4/true-api/product/info`, базовый адрес True API. Методы НК
  принимают либо `apikey` в URL, либо токен True API, не оба сразу (иначе
  400).
- **Лимит жёсткий: 10 запросов за 5 минут, до 25 GTIN в запросе.**
  Карточки кэшируются в базе, в сеть идут только новые GTIN, пачкой. Для
  поставки 12550 (80 артикулов) это 4 запроса. Этикетки и проверки читают
  кэш, а не сеть.
- Имена атрибутов одежды (цвет, размер, модель, разрешительный документ)
  документация показывает только на примере сметаны. **Разбор пишется по

## 6. Поставка: функции

### 6.1 Входящий файл
**Нужны только размерный артикул и количество.** Штрихкод и цена берутся
из «Одежды полной» (5.2).
- Типовой вход — `marking/tests/fixtures/lamoda_shipment_input_typical.xlsx`:
  шаблон `fulfilment_shipment` без кодов, 80 строк / 338 шт.
- Заголовок — строка 4, шапка — A1:A3 / B1:B3; лист «Инструкции» не
  трогаем.
- **Где загружается:** «Поставки» → «Новая поставка» → поле «Файл поставки».
  Файл сохраняется при поставке и скачивается с её страницы («Исходный
  файл»): к нему возвращаются, когда строка вызывает вопрос.
- **B1 Дата поставки** — обязательна: из поля формы, иначе из B1. B1 читается
  и как дата Excel, и как число Excel без формата (инструмент КИЗ пишет 46297 =
  02.10.2026), и как текст ДД.ММ.ГГГГ.
- **B2 Номер поставки** — из поля формы, иначе из B2, иначе «последний + 10»
  (12560); повтор запрещён. Знак «_» в номере поставки запрещён, хотя Lamoda
  его допускает: номер — ключ поиска документа перемещения в 1С через ПОДОБНО,
  где «_» означает любой символ, и поставка «A_1» нашла бы документ «AB1».
- **B3 Номер документа** — равен номеру поставки (правило Lamoda: номер
  поставки = номер УПД). Отдельно не вводится и не правится: программа
  проверяет равенство при создании и правке шапки; после выпуска УПД номер
  поставки не меняется (6.3).
- Цена или EAN в файле, если есть, сверяются со справочником. Расхождение —
  предупреждение по строке; в поставку идёт значение справочника.
- Дубль артикула — предупреждение: строки разворачиваются каждая сама, коды
  берутся из общего запаса GTIN.
- Количество — целое больше 0. Лимиты Lamoda — 5000 артикулов и 10 000
  единиц; больше — предложить разбить на несколько поставок.
- Дополнительные колонки (образец с «ТНВЭД» —
  `lamoda_shipment_input_with_tnved.xlsx`, 89 строк / 366 шт) сохраняются
  и копируются при развёртке.
- Нет артикула в «Одежде полной» — строка красная: без EAN и цены поставку
  не переместить.
- Нет GTIN у артикула — строка жёлтая: переместить можно, заказать коды —
  нет, пока GTIN не указан (5.3).
- Формат входа — только шаблон `fulfilment_shipment` (лист «Лист1»,
  заголовки в 4-й строке, первая колонка «Seller SKU»). Прежняя строка ТЗ о
  разборе листа «Поставка» из выгрузки Lamoda и файла с колонками из 1С
  реализацией не подтверждена: такой файл получает отказ «строка 4 — не
  заголовки шаблона», а не молчаливый разбор. Нужен другой формат — это
  отдельная доработка с образцом файла.
- После отправки перемещения в 1С состав, номер и дата поставки заморожены
  ДО ответа 1С (не только после статуса «перемещено»): документ в 1С уже
  создаётся, правка разошлась бы с ним, а новый номер сменил бы ключ
  идемпотентности, и повтор создал бы второй документ. Отказ 1С снимает
  заморозку.

### 6.2 Проверка остатка и перемещение в 1С
**Сопоставление — по штрихкоду, основа та же, что у sync_admin.** Каждому
цветоразмерному SKU 1С (номенклатура + характеристика) принадлежит пул
штрихкодов, и каждый штрихкод пула принадлежит ТОЛЬКО этому SKU. Артикул
Lamoda сопоставлен, если его штрихкод совпал с ЛЮБЫМ штрихкодом пула — не
обязательно с первым. На образце так и есть: из 558 артикулов каталога,
найденных в остатках 1С, 12 совпадают не по первому штрихкоду своего пула.
Остаток у всего пула один.
- Поиск в 1С — по всему регистру штрихкодов, только среди
  владельцев-номенклатуры (как `ВыгрузитьСправочникБаркодов`). Штрихкод,
  записанный на двух SKU, нарушает правило «пул принадлежит только своему
  SKU» — отказ проверки со статусом «штрихкод у нескольких товаров», а не первый
  попавшийся: перемещение не отменяется, и наугад выбранный размер уехал бы на
  Lamoda навсегда.
- Один штрихкод у разных артикулов поставки — отказ до отправки в 1С: 1С
  различает позиции только по штрихкоду и увезла бы оба артикула одним товаром.
- Сопоставление один к одному: SKU 1С соответствует ровно один артикул
  Lamoda. В этом отличие от sync_admin: там несколько SKU 1С законно ведут на
  одну карточку площадки (одна вещь под двумя артикулами 1С, остатки
  складываются). У Lamoda таких случаев нет, а артикул с одним штрихкодом на два
  SKU 1С лечь не может — это был бы штрихкод в двух пулах, отказ выше. Если штрихкоды двух артикулов лежат в пуле одного SKU 1С (видно по
  ответу проверки), поставка не становится «проверенной» и перемещение закрыто:
  1С переместила бы сумму верно, но коды пошли бы по двум GTIN на одну вещь.
  Перепроверка при этом доступна — штрихкод могли поправить в 1С.
- Догадку по соседям карточки (автопривязка sync_admin) не переносим: у Lamoda
  на артикул один штрихкод, соседей нет, а угадывать товар для документа,
  который нельзя отменить, нельзя.
Наименования не сравниваем: `3030 KAHVE 4XL АВЕР Рубашка Д/р сатин` против
`3030-3032 АВЕР Рубашка Д/р одн Коричневый` — норма, `2XL` = `XXL` — тоже.
На образце 12550: 80 из 80 строк найдены по EAN, остатка хватает (нужно
338, на ЦС 1880).

1. **Проверить в 1С** (`SUPPLY_CHECK`, 9.2). 1С отвечает по каждому
   баркоду: товар (ID, артикул, наименование, размер, цвет), остаток ЦС,
   хватает или нет. Отрицательный остаток бывает — это «не хватает».
   Предварительно можно загрузить файл «Остатки на дату» из sync_admin
   (образец `stock_1c_2026-09-28.xlsx`): это только подсказка до ответа 1С,
   решение по нему не принимается.
2. **Переместить на склад Lamoda** (`SUPPLY_MOVEMENT`, 9.2) — кнопка,
   доступная после свежего `SUPPLY_CHECK` без ошибок. Автоматически при
   загрузке — нет: ошибочный файл увёл бы товар со склада.
   - **Один документ** «ЦС Склад» → «**Lamaoda_Склад**» на всю поставку,
     атомарно: либо проведён целиком, либо не создан вовсе.
   - Склады задаются **кодами справочника «Склады»**, не наименованиями:
     ЦБ0000012 «ЦС Склад», ЦБ0000017 «Lamaoda_Склад» (так, с опечаткой, склад
     заведён в боевой базе; снимок 02.10.2026). Код от правки наименования не
     зависит. Обработка ищет по коду (`НайтиСкладПоКоду`, два склада с одним
     кодом — отказ) и называет наименования в ответе на проверку: «позиций N;
     ЦС Склад -> Lamaoda_Склад». Настройка — `MARKING_WAREHOUSE_FROM_CODE` /
     `MARKING_WAREHOUSE_TO_CODE`.
   - Не `Lamoda_Впути`: это временное хранилище, а перемещение в этой
     конфигурации проводится между основными складами магазинов.
   - Остаток перед записью 1С проверяет сама, ещё раз.

**Почему перемещение, а не резерв.** Штуки физически ещё на ЦС и
транслируются на WB/Ozon/Kit. Перемещение снимает их с ЦС в 1С. sync_admin
видит это минутной дельтой и перестаёт их продавать. Программа маркировки в
базу sync_admin не пишет.

**Принятый риск.** 1С не знает о заказах WB/Ozon/Kit, которые sync_admin
уже принял, но ещё не провёл своим перемещением. Обычно это 4–7 минут, при
сбое — до ручного разбора. `SUPPLY_CHECK` может счесть свободной уже
проданную штуку. Закрыть это полностью, не читая базу sync_admin, нельзя.
Смягчение: проверка повторяется непосредственно перед перемещением и внутри
него. Если недостача всё же случилась, она всплывёт при сборке коробов и
исправляется вручную в 1С.

### 6.2а Страница «Мэппинг» — сопоставление каталога с 1С заранее
Проверка поставки (6.2) сопоставляет только её строки и только в момент
отправки. Страница «Мэппинг» сопоставляет **весь каталог «Одежда полный»** со
справочником баркодов 1С заранее, по тем же правилам (`marking/markapp/mapping.py`):
ключ — штрихкод; пул штрихкодов SKU принадлежит только ему; совпадение с любым
штрихкодом пула; строго один к одному; без догадок. Статусы: «сопоставлен»,
«нет в 1С», «штрихкод у нескольких SKU 1С», «один SKU у двух артикулов», «нет
штрихкода в каталоге» — у каждого пояснение, что значит и что делать. Рядом —
GTIN и цвет/размер из Нацкаталога: вся цепочка артикул → EAN → SKU 1С → GTIN в
одной строке. Отбор по статусу и поиску; в Excel уходит весь отбор, не экран.
Справочник 1С — снимок: командой `BARCODE_DICT` (9.2) или файлом `barcodes_*.txt`
вручную; загрузка заменяет снимок целиком, пустой файл — отказ. Исправляют
сопоставление в карточке Lamoda или в 1С, не на странице: привязка руками
значила бы, что программа знает о товаре то, чего не знает 1С.

### 6.3 Файл поставки для Lamoda
Формируется **из официального шаблона**
`marking/tests/fixtures/lamoda_fulfilment_shipment_template.xlsx`:
программа открывает шаблон и заполняет, а не рисует свой. Лист инструкций
сохраняется.

| Ячейка / колонка | Поле | Правило Lamoda |
|---|---|---|
| B1 | Дата поставки | `DD.MM.YYYY`, обязательно |
| B2 | Номер поставки | ≤ 20 символов: латиница, цифры, `_`, `-` |
| B3 | Номер документа отгрузки | тот же алфавит; **уникален среди всех подтверждённых поставок** |
| A | Seller SKU | размерный артикул; ≤ 5000 уникальных |
| B | Количество | > 0; ≤ 10 000 на поставку |
| C | Стоимость | > 0; «стоимость, которую указываете в УПД» |
| D | EAN | если у одной строки есть — нужен у всех |
| E | Вес ЮИ | только ювелирка, у нас пусто |
| F | Data Matrix | полный код или КИ 31/38 символов; для маркированного обязателен |

**Развёртка: 1 строка = 1 артикул = 1 КИЗ.**
- «Количество» входящей строки — это число её повторов в исходящем файле.
- Повторы идут подряд, в порядке входящего файла.
- В каждой копии все колонки как во входящей строке, кроме двух: Количество
  = 1 и свой КИЗ в Data Matrix.
- Проверки перед выдачей: число строк = сумме количеств; каждый КИЗ ровно
  один раз; КИЗ строки — только с GTIN этого артикула; все правила таблицы.

**Data Matrix — ПОЛНЫЙ код с криптохвостом** (`91`/`92`, 85 символов), так
его вводит заказчик. GS (0x1D) в xlsx пишется заменой **`_x001D_`**:
openpyxl отказывается писать сам символ (`IllegalCharacterError`).

**Эталон записи — файл kiz-tool по поставке 12550**, принятый Lamoda
(`reference_kiz_tool_supply_12550.xlsx`). Разбор его `sharedStrings.xml`
дал правила:
- GS → `_x001D_`, заглавными, по два на код;
- `<` `>` `&` → `&lt;` `&gt;` `&amp;`;
- `"` и `'` — без сущностей;
- `_` в серийном номере — как есть (ни один не образует `_xHHHH_`).

Тест сверяет сырой XML записи программы с эталоном по всем 44 кодам
побайтно.

**Номер документа** — один на весь комплект: ячейка B3, номер УПД
(`СвСчФакт/@НомерДок`), имена файлов `<номер>.xlsx` и `<номер>.xml`
(Диадок принимает ✅).
- **Всегда равен номеру поставки** — правило Lamoda, не умолчание.
- Уникален по всем поставкам программы.
- После выпуска УПД не меняется.

**Коды поставки в txt** (требование заказчика 29.09.2026). Рядом с файлом
поставки — кнопка «Коды поставки (.txt)». В файл идут **только коды этой
поставки**, в том же порядке, что в файле Lamoda. Формат — **как выдаёт СУЗ**
(образец `marking/tests/fixtures/codes_12550.txt`):
- полный код на строку, с GS (0x1D) внутри, а не `_x001D_`;
- каждая строка, включая последнюю, заканчивается CRLF; без BOM.

Условия выдачи те же, что у файла поставки: все коды «в обороте» и
закреплены за поставкой. Имя файла — `<номер документа>_коды.txt`. Выдача
пишется в журнал: полный код — то, по чему печатается легальная этикетка
(принцип 3.5). Функция записи — `marking/markapp/codes_txt.py`; тест
проверяет, что файл по 12550 совпадает с образцом побайтно. Кнопка
появляется с этапа 4, когда коды закрепляются за поставкой.

**Стоимость = цена в УПД:** шаблон это прямо говорит, `price_mode=gross`.
Одна цена на строку живёт в поставке и попадает и в файл, и в УПД.

### 6.5 УПД
**Строится из выгрузки «Поставки FBO»**, как сейчас в upd-constructor:
принятый Lamoda документ собирается ровно так, и сумма сходится (6.4). Цены
и КИЗ в выгрузке уже сверены с поставкой, поэтому расхождение между файлом,
выгрузкой и УПД исключено проверкой, а не надеждой. Порядок строк — как в
выгрузке.

- Ядро `upd_constructor` переносится в `marking/upd/` вместе с тестами и
  эталонами: формат 5.03, функция ДОП, НДС 5%, `price_mode=gross`,
  windows-1251 + CRLF, Decimal half-up построчно, разные адреса
  `ГрузПолуч`/`СвПокуп`, ElementTree, не выдумывать теги.
- `КИЗ` — короткий, 31 символ, без криптохвоста: так в обоих принятых УПД,
  833 кода из 833 (7.4).
- Итоги в шапке — режим `rows`. Режим `reference` остаётся только для
  байтового теста против эталона №12100.
- Номер и имя файла — номер документа (6.3); номер и дата ТТН — номер и
  дата поставки.
- Схема договора — по **дате УПД** (разд. 8).
- **Перевыпуск** — новый документ под тем же номером: если прежний уже ушёл
  в Lamoda по ЭДО, это корректировка. Поэтому для перевыпуска нужны причина
  (пишется в журнал) и ИдФайл действующего УПД со страницы. Повторная
  отправка формы или вчерашняя вкладка документ не заменяют.
- Встроенная проверка перед выдачей и история выпущенных УПД. Страница
  «Проверить УПД» принимает любой XML.
- **Проверка в ЧЗ** — `POST /doc/validator/create`: XML в windows-1251,
  base64, `documentType: UPD`. ЧЗ проверяет статусы кодов, полномочия
  продавца на коды, разрешительные документы, карточки НК. Нужен токен True
  API (10.4). УПД с ошибками не выдаётся для Диадока без явного «всё равно»,
  с записью в журнал. Формат ответа `/doc/validator/status` вживую не видели 📄.

**Эталоны:** №12100 и второй комиссионный (upd-constructor). **УПД 12550
уже принят Lamoda** — если приложить его XML, он станет третьим (**[?]**).
Первый принятый **агентский** УПД станет четвёртым.

**Проверки против каталога ошибок Lamoda** (лист «Пояснения к ошибкам», 22
причины):

| Ошибка Lamoda | Проверка программы |
|---|---|
| только статус 2 (ДОП) | функция `ДОП` |
| склад грузополучателя не найден | `ГрузПолуч` = склад из справочника покупателя |
| не определена номенклатура | `КодТов` (EAN) каждой строки есть в поставке |
| связка «артикул + код» ≠ поставке | пара EAN + КИЗ = пара в выгрузке |
| не переданы коды маркировки | у каждой строки есть КИЗ |
| количество ≠ поставке | Σ `КолТов` = Σ количеств выгрузки |
| сумма ≠ поставке | Σ `СтТовУчНал` = «Итого стоимость» |
| ИНН владельца кода ≠ отправителю | проверка УПД в ЧЗ или `/cises/info` |
| статус кода ≠ «В обороте» | то же |
| запрещённый символ в коде | КИЗ строго по шаблону 31 символа |
| `СпОбстФДОП` ≠ 00005 | `СпОбстФДОП=00005` |
| `ВидОборотаМАРК`, `Идентиф = СвВыбытияМАРК` | таких тегов у нас нет — проверка запрещает |
| версия 5.01/5.02 | `ВерсФорм=5.03` |
| ЭДО не настроен / склад ≠ брони | не проверяется — вопрос к менеджеру Lamoda |

## 7. Коды маркировки

### 7.1 Заказ и получение (СУЗ) ✅
- По кнопке — заказ **недостающего** количества по каждому GTIN поставки
  или отдельный заказ вне поставки (любой организации, 5.1).
- Тело заказа как в kiz-tool: `POST /order?omsId`, `productGroup: lp`,
  `serialNumberType: OPERATOR`, `templateId: 10`, `cisType: UNIT`,
  `releaseMethodType: PRODUCTION`. Весь товар произведён в РФ.
- Заказ пишется в базу **до** отправки, номер заказа СУЗ — сразу после
  ответа, коды — порциями по мере получения. Сбой на середине не теряет ни
  заказ, ни полученные коды; повтор продолжает с места остановки.
- Полученные коды **сразу закрепляются за поставкой**, под которую
  заказаны, и запускают внеочередную резервную копию (11).
- **Каждый запрос СУЗ, включая статус заказа и получение кодов, требует
  откреплённой подписи в `X-Signature`** ✅. Поэтому получение кодов идёт,
  пока открыта страница на машине с КриптоПро (10.3). Без неё это станет
  возможно только с сервисом подписи (10.6).
- **[?]** Можно ли повторно получить уже выданный блок кодов (срок и
  условия) — уточнить по руководству СУЗ. От этого зависит, насколько
  критична внеочередная копия.

### 7.2 Ввод в оборот (True API) ✅
- Документ JSON `LP_INTRODUCE_GOODS`, `document_format: MANUAL`, `?pg=lp`,
  `uit_code` — **короткий** КИ, `production_type: OWN_PRODUCTION`.
  Подпись **прикреплённая**. XML — тупик ✅.
- Проверено 28.09.2026 kiz-tool'ом: коды, полученные заранее, введены,
  `/cises/info` показал «в обороте».
- **Свежезаказанные коды** сразу дают ошибку `14 «Недопустимый статус кода
  идентификации»`. Для `lp` отчёт о нанесении ЧЗ формирует сам, и время до
  «Нанесён» **нестабильно** (опыт заказчика). Поэтому никакого «ждать N
  минут» нет — только опрос до факта.

**Опрос статусов** (`/cises/info`, до 1000 кодов в запросе) идёт **в
воркере, фоном**. Ему нужен только токен True API, подпись на каждый запрос
не нужна.
- **Пределы:** по документации — 50 запросов/с на участника (превышение —
  блокировка), у части методов 10/с, у выгрузок 15/мин. Рабочий предел —
  70%: **35/с, 7/с, 10/мин**. Числа — настройка, не константа.
- **Один ограничитель на участника (ИНН)** для всех обращений к ЧЗ: опрос,
  заказ, ввод, НК. Он живёт **в базе**: так он переживает перезапуск программы
  (и годится для варианта «на сервере», где веб и воркер — два процесса). Опросу отдаётся не больше половины предела, чтобы кнопки
  человека не ждали очереди.
- Цикл — все коды, ждущие «Нанесён», пачками по 1000; следующий цикл — как
  только позволит ограничитель. Для 338 кодов это один запрос за цикл.
- **429** — пауза (по `Retry-After`, иначе 60 с), затем предел опроса
  вдвое ниже до конца часа, с записью в журнал.
- Время до «Нанесён» пишется по каждому коду только для диагностики. Код
  без «Нанесён» дольше суток — находка отчёта.
- Истёк токен (~10 ч) — опрос встаёт с отметкой «нужен вход», а не молча.

**Ввод «при готовности».**
- Человек один раз нажимает «Ввести в оборот при готовности».
- Коды, получившие «Нанесён», копятся не дольше 10 с и уходят одним
  документом: 338 кодов не превращаются в 338 документов.
- Документ подписывает страница на машине с КриптоПро. Закрыта — поставка
  показывает «готово N, нужна подпись», и документ уйдёт, как только её
  откроют.
- Результат проверяется **по статусам кодов** (`INTRODUCED`), а не по
  «документ принят».
- Ошибка по части кодов остальные не блокирует. Уже введённые повторно не
  отправляются.

**Перед отправкой по карточке НК** (5.3) проверяются:
- `goodMarkFlag` и `goodTurnFlag` = true;
- ТН ВЭД;
- срок разрешительного документа.

Отправитель должен быть собственником кодов. Разрешительный документ
передаётся либо массивом `certificate_document_data`, либо тремя полями,
не одновременно.

Сырые ответы `/cises/info` и `/doc/list` при первом живом прогоне
сохраняются в фикстуры, с маскировкой.

### 7.4 Формат КИЗ — где какой
| Куда | Формат | Подтверждение |
|---|---|---|
| Этикетка | **полный**, 85 символов, два GS, части `91`/`92` | 3 этикетки прочитаны приложением ЧЗ |
| Файл поставки в Lamoda | **полный**; GS в xlsx — `_x001D_` | файл kiz-tool по 12550 принят |
| Выгрузка «Поставки FBO» | короткий, 31 | выгрузки 12100 и 12550 |
| УПД, `КИЗ` | **короткий**, 31, без хвоста | оба принятых УПД: 833 из 833 |
| Ввод в оборот (`uit_code`), `/cises/info` | короткий, 31 | успешный документ kiz-tool |

- **Одна функция проверки короткого КИ на все места:**
  - длина 31;
  - `01` + 14 цифр + `21` + 13 символов;
  - контрольная цифра GTIN верна;
  - серийный номер только из набора GS1 «82»;
  - нет GS, табуляций, пробелов, `_x00…`;
  - в Excel — текст, не число.

  Прогон: «Поставки FBO» 12550 — 338 из 338 без замечаний; оба УПД — 833 из
  833.
- **Короткий из полного** — не «первые 31 символ», а разбор по шаблону и
  часть до первого GS. Не прошёл разбор — отказ с номером строки.
- **На входе GS бывает в любой записи**: настоящий 0x1D, `_x001D_` /
  `_x001d_` (xlsx), `\u001d` (документация). До разбора всё приводится к
  одной форме.
- В XML УПД символы кода экранирует ElementTree.

### 7.5 Импорт кодов из файла (редкий случай)
Для кодов, заказанных вне программы. Образец —
`marking/tests/fixtures/codes_12550.txt`: 338 полных кодов, CRLF, без BOM,
сгруппированы по GTIN в другом порядке, чем строки поставки.
1. **Строки делятся только по `\r\n` / `\n`.** `str.splitlines()` считает
   GS концом строки и режет каждый код на три (1014 «строк» вместо 338).
   Тест обязателен.
2. Каждый код проверяется по шаблону. Дубли в файле и коды, уже лежащие в
   базе, — отказ с перечнем.
3. Коды раскладываются по строкам поставки **по GTIN**, не по позиции.
   Число кодов на GTIN должно совпасть с количеством по артикулу.
4. GTIN без пары в справочнике — коды заносятся «без артикула», а поставка
   предлагает сопоставить вручную. Сопоставление запоминается.
5. Коды закрепляются за поставкой в момент подбора. Статус «в обороте»
   проверяется по ГИС МТ, до того файл поставки с ними не выдаётся.
6. Коды из файла тоже запускают внеочередную копию (11).

## 8. Схема договора: комиссия → агентский (с 01.10.2026)

Источник — статья Lamoda «Переход на агентскую модель…» (обновлена
16.09.2026). Агент продаёт от имени партнёра; договор не перезаключается,
нумерация сохраняется. Поставка, маркировка и статус УПД (ДОП) не меняются.

**В УПД меняются ровно два атрибута:**

| Атрибут | По 30.09 (эталоны) | С 01.10 |
|---|---|---|
| `СвПер/@ВидОпер` | `ПродажаКомиссия` | `Реализация по агентскому договору` |
| `ОснПер/@РеквНаимДок` | `Договор комиссии` | `Агентский договор` |

Остальное без изменений: `РеквНомерДок=б/н`, `РеквДатаДок`,
`СпОбстФДОП=00005`, функция, коды, суммы, НДС, реквизиты, адреса, `ИдФайл`.
- `ВидОпер` по XSD Диадока — свободная строка до 255 символов.
- Lamoda ищет «комис» в `НаимОсн`, `НомОсн`, `ИныеСвИзмСтоим`, `Значен`.
  Мы проверяем строже — во всём XML.
- Блоки из примеров Lamoda, сделанных в 1С/СБИС (`ТекстИнф` с
  «ПередачаТовараКомитентом» и т. п.), не добавляем: в наших принятых
  эталонах их нет.

**Правило выбора — по дате УПД** (решение заказчика):
- «Авто» (по умолчанию): дата УПД ≤ 30.09.2026 — комиссия, с 01.10.2026 —
  агентский.
- Ручной выбор на поставке: Авто / Комиссия / Агентский. Если выбор
  расходится с датой — предупреждение и запись в журнал с обязательной
  причиной.
- Схема **одна на поставку** и управляет и УПД, и стикерами (6.6). У
  поставки есть **плановая дата УПД**, по умолчанию — дата поставки. Стикеры
  печатаются по ней, УПД выпускается по фактической. Разошлись схемы —
  предупреждение.
- Дата перехода — **настройка договора** (редакции по датам), не
  константа.
- Исправления по старой поставке — по схеме исходного документа.

Уже сделано вне программы (28.09.2026):
- `upd-constructor` — `--scheme auto|commission|agency`, `--vid-oper`,
  имя файла `<номер>.xml`, проверка «комис», 24 теста; веб-версия
  пропатчена;
- `lamoda_stickers` — «АГЕНТ» с 01.10.2026, `--scheme`, 4 теста.

Переносится в программу вместе с этими тестами.

## 9. Обмен с 1С

### 9.1 Канал
Выбран канал, работающий на бою с 19.09: файлы через `C:\sync` сервера и
обработка `ОбменССайтом` из «Дополнительных обработок» по расписанию.
COM, OData, HTTP-сервис и «загрузчик» `.epf` не делаем: COM работает только
на самом сервере и держит лицензию 1С, HTTP-сервис и OData требуют публикации
базы и правки конфигурации.
- **Доставка файлов — SFTP до сервера** (программа на рабочем компьютере,
  разд. 2). На сервер ставится OpenSSH Server (Microsoft) на TCP 443 — этот
  порт от провайдера этой машины проходит; до этого на сервере для
  программы не стоит ничего. Обычный FTP отвергнут: порт 21 и диапазон портов данных, пароль
  открытым текстом, а WireGuard этот провайдер уже резал. Учётная запись
  `marking_sftp` заперта в `C:\sync` (`ChrootDirectory`) и умеет только SFTP
  (`ForceCommand internal-sftp`); вход только по ключу; ключ сервера
  сверяется один раз вручную, незнакомый ключ — отказ обмена. Инструкция —
  `marking/deploy/SFTP_1C.md`. Хост не задан — те же папки локально
  (вариант «на сервере»).
- **Обращения — по факту работы с поставкой.** Постоянного опроса нет:
  сервер трогается, только пока есть задание, ждущее отправки или ответа
  (`onec.has_work`); зависшее ждём ещё сутки. Соединение — на один проход.
- **Задание:** `C:\sync\tasks\task_mark_ГГГГММДДЧЧММССмкс.txt`. Пишется
  через `<имя>.part` с переименованием, чтобы 1С не увидела недописанный
  файл. Одна строка — одно задание, поля через `|`. Не больше одной проверки
  поставки на файл: подробности проверки 1С пишет одним файлом на задание.
- **Ответ:** `C:\sync\results\marking\result_mark_<метка>.txt`. Обработка
  называет ответ по имени задания (`result_` + метка).
- Разобранное уезжает в `C:\sync\archive\marking\` на сервере, копия — в
  `C:\marking\onec_archive` у программы.
- Пути — настройка программы.
- Задержка — период расписания обработки (обычно минута-две).

### 9.2 Команды
Программа посылает **только свои команды**: `PING`, `SUPPLY_CHECK`,
`SUPPLY_MOVEMENT`, `BARCODE_DICT` (с версии `mark-2`). Это закреплено тестом, и вот почему. Старая обработка
на незнакомую команду молчит: ветки нет, строки ответа нет, файл ответа не
публикуется, задание архивируется (модуль 1С, стр. 81–170). А на знакомую
(`CREATE_MOVEMENT`, `CANCEL_MOVEMENT` …) ответила бы в общую папку, и ответ
достался бы sync_admin.

```
PING|<id>
SUPPLY_CHECK|lamoda-<номер>-c<id>|ЦБ0000012|ЦБ0000017|<баркод>:<кол>;<баркод>:<кол>;…|поставка <номер> от <дата>
SUPPLY_MOVEMENT|lamoda-<номер>|ЦБ0000012|ЦБ0000017|<баркод>:<кол>;<баркод>:<кол>;…|поставка <номер> от <дата>
BARCODE_DICT|dict-<id>
```
`BARCODE_DICT` — справочник баркодов 1С для страницы «Мэппинг» (6.2а): тот же
текст, что `EXPORT_BARCODES` sync_admin (`uid|артикул|наименование|баркод|размер|цвет`),
но файлом `barcodes_<метка>.txt` в `results\marking` и раньше ответа.
`EXPORT_BARCODES` не годится: он кладёт файл в общий `results`, и его забрал бы
sync_admin.

- **`PING`** — ответ `<id>|OK|<версия модуля>|PING` в `results\marking\`.
  Пока ответа нет, кнопки, отправляющие задания в 1С, выключены с
  объяснением «обработка 1С не обновлена». Старая обработка на `PING`
  молчит, поэтому проверка безопасна и до обновления.
- **`SUPPLY_CHECK`** — документ не создаётся.
  - В `result` строка `…|OK|позиций N; <склад откуда> -> <склад куда>|SUPPLY_CHECK`
    (наименования складов по их кодам — видно, куда уедет поставка) или
    `…|ERROR|<кратко>|SUPPLY_CHECK`.
  - Подробности — **отдельным файлом** `supplycheck_<метка>.txt` рядом:
    строка на баркод, поля `баркод|ID товара|артикул|наименование|размер|цвет|остаток ЦС|нужно|статус`,
    значения очищены от разделителей (`ОчиститьПоле`, как в выгрузках).
  - В одно поле `result` 80 позиций с наименованиями надёжно не
    помещаются.
- **`SUPPLY_MOVEMENT`** — один документ `ПеремещениеТоваров` на поставку.
  - Все баркоды ищутся и остаток ЦС проверяется **до** создания документа.
    Не хватает или не найден хоть один — документа нет, ответ `ERROR` со
    списком.
  - Одинаковые номенклатура и характеристика складываются.
  - Строки заполняются как в `ВыполнитьПеремещение` (`ЕдиницаИзмерения`
    хранения, `Коэффициент` = 1).
  - Склады — по коду (`НайтиСкладПоКоду`); общая `НайтиСклад` (по
    наименованию) остаётся заданиям sync_admin.
  - Идемпотентность — своя `ПроведённаяПоставка(ИдЗаказа, СкладКуда)`
    (комментарий `mark order_id=<id> …`, проведён, тот же склад-получатель):
    повтор задания возвращает номер уже проведённого документа.
  - Ответ `lamoda-<номер>|OK|<номер документа 1С>|SUPPLY_MOVEMENT`.
- Проверка числа полей — **до** `Попытка`, как у остальных команд. Иначе
  строка роняет разбор файла, файл не архивируется и разбирается снова.
- Отмены поставки нет (разд. 4), команды `SUPPLY_CANCEL` не делаем.

### 9.3 Два условия, без которых sync_admin не увидит перемещение
Дельта остатка ЦС (`ВыгрузитьИзменениеОстатковЦС`) выбирает движения:
- **по дате документа**: `Дв.Период > &МоментС И Дв.Период <= &МоментПо`,
  модуль 1С стр. 704–720;
- **и отбрасывает документы с комментарием на `sync`** — sync_admin
  считает их своими, уже учтёнными.

Отсюда:
1. **Комментарий** — `mark order_id=lamoda-<номер> lamoda <дата поставки>`,
   не на `sync`. Поиск `НайтиПроведённоеПеремещение` идёт по
   `%order_id=…%` и от префикса не зависит.
2. **Дата документа — всегда текущая**: поля даты в строке задания нет вовсе
   (шестое поле — только примечание для комментария).
   Дата в будущем (например, дата поставки) оставит движение вне дельты и
   вне остатка «на сейчас»: sync_admin продавал бы эти штуки до наступления
   даты. Дата в прошлом — до часа до часовой выгрузки. Дата поставки идёт
   только в комментарий.

Нарушение любого из двух — не ошибка, а тихий оверселл на WB/Ozon/Kit. Оба
условия закрываются тестом и проверкой на копии базы (9.6).

### 9.4 Задание без ответа
Жизненный цикл задания в программе: `pending` → `sent` → `done` / `failed`.
Через 15 минут без ответа — `timeout` с находкой на «Диагностике».
Автоповтора нет. Повтор `SUPPLY_MOVEMENT` безопасен (идемпотентность), но
решение принимает человек кнопкой, посмотрев в 1С.

### 9.5 Обновление обработки 1С
Обработка хранится **внутри базы** («Дополнительные обработки»), поэтому
замена файла на диске ничего не даёт. Порядок обновления:
1. в карточке «Выгрузить в файл» — это рабочая `.epf` и заодно резервная
   копия;
2. Конфигуратор → Модуль объекта → Ctrl+A → вставить новый текст →
   **Ctrl+F7** → сохранить;
3. проверка на копии базы (9.6);
4. в карточке «Загрузить обработку из файла» → записать.

Откат — шаг 1. Платформа **8.3.9.2233**. XML в `1c/src/` — формат 2.17
(8.3.27), на 8.3.9 скорее всего не загрузится, поэтому основной путь —
вставка модуля.

Поставляется **одним комплектом**:
- полный текст модуля с номером версии в первой строке;
- инструкция;
- тестовые `task_mark_*.txt` и ожидаемые ответы.

Правятся `1c/ОбменССайтом_МодульОбъекта.txt` и
`1c/src/…/ObjectModule.bsl` (они обязаны совпадать — тест sync_admin), а
также `1c/README.md`. Доработок держим как можно меньше: каждая — ручной
заход в Конфигуратор.

### 9.6 Проверка обновления на копии базы — с обеих сторон
1. `PING` отвечает в `results\marking\`.
2. `SUPPLY_CHECK` и `SUPPLY_MOVEMENT` на поставке 12550: документ один, 80
   строк, дата текущая, комментарий на `mark`.
3. Повтор `SUPPLY_MOVEMENT` возвращает тот же номер документа.
4. Нехватка по одному баркоду — документа нет вовсе.
5. `delta_*.txt` после проведения содержит движение с источником
   «ПеремещениеТоваров», а не `sync`.
6. **Ответы на команды sync_admin не изменились**: `CREATE_MOVEMENT`,
   `CONFIRM_MOVEMENT`, `CANCEL_MOVEMENT`, `RETURN_TO_STOCK`, `SCRAP_RETURN`,

Подпись, сертификаты и запросы в ЧЗ — на одной машине: страница

настраивался и не нужен. **На сервер для программы ставится ровно одно —
OpenSSH Server** с настройкой скриптом `deploy/server_sftp_setup.ps1`; плюс
обновление обработки 1С в Конфигураторе.

**[?]** Доверяет ли плагин КриптоПро адресу `http://127.0.0.1:8001` —
проверить страницей `marking/tools/plugin_check.html` (открыть её из

### 10.3 Подпись в браузере (КриптоПро ЭЦП Browser plug-in, CAdES-BES)

### 10.4 Вход в ЧЗ — у каждой организации свой
- Выбор организации → сертификаты этой машины с ИНН и сроком. Первым
  предлагается сертификат, чей отпечаток записан у организации.
- **ИНН сертификата обязан совпасть с ИНН организации.** Сертификаты всех
  ИП лежат на одной машине рядом, и так ловится самая дорогая ошибка — заказ
  не от того ИП.
- «Войти» получает два токена: True API (Bearer) и `clientToken` СУЗ по
  `connectionId` организации; время жизни ~10 ч. Токены хранятся
  зашифрованно **раздельно по организациям**: вход под вторым ИП не
  выбивает первого. Статус виден — «вошли до 22:40» / «нужен вход».
- **Операция берёт токен организации своей записи** (заказа, поставки,
  кода), а не «текущий вход». Нет токена — операция не идёт и называет, под
  каким ИП войти.
- Токен истёк (ошибка 1160 ✅) — нужен повторный вход.

### 10.5 Путь до ЧЗ
- Программа на рабочем компьютере — True API и СУЗ **напрямую** ✅. С этой
  машины СУЗ доступен (проверено заказчиком 29.09.2026; с неё же заказывали

- **CORS-прокси kiz-tool (`cors_proxy.py`) не нужен.** Он решал задачу
  браузера, а не сети: kiz-tool — страница, и браузер не пускает страницу в
  чужой домен без CORS-заголовков, которых у ЧЗ нет. У нас запросы в ЧЗ шлёт
  программа (Python), на CORS ей всё равно; браузер только подписывает то,
  что ему дала программа, и отдаёт подпись обратно (10.3).
- Необязательный HTTP-прокси остаётся настройкой (`MARKING_CHZ_PROXY`) на
  случай другой сети; кода он не меняет.
- Входное условие этапа 4 выполнено (разд. 13).

### 10.6 Фоновая подпись (этап 6)
Отдельный сервис подписи не нужен: программа работает на той же машине, что
и КриптоПро. Фоновые операции (получение кодов из СУЗ, ввод в оборот по

через CSP этой машины со списком разрешённых отпечатков и журналом каждой
подписи. Детали — на этапе 6.

## 11. Резервное копирование

У программы своя база и **своя** копия. Копия sync_admin её не покрывает.
Механизм копируется у sync_admin, где он проверен на бою:
- копия снимается штатным `Connection.backup()` на живой базе одним шагом;
- журнал сводится в сам файл;
- копия проверяется `integrity_check` и чтением;
- хранятся копия на календарный день и недельные; копии моложе суток не
  удаляются.

**Облако — свой rclone и свой конфиг**: `C:\marking\tools\rclone.exe`,
`C:\marking\rclone.conf`, папка `yandex:marking_backups`, суточная копия
**в другое время, чем у sync_admin**. Общий с sync_admin `rclone.conf` не
годится по двум причинам:
- переустановка sync_admin сломала бы копии маркировки;
- rclone переписывает конфиг при обновлении токена, и два одновременных
  запуска могут испортить файл, остановив копии обеих программ.

**Рабочий компьютер выключают на ночь**, поэтому копия не «по расписанию»,
а первая — через 10 минут после запуска программы и дальше не чаще раза в
сутки: у выключаемого компьютера суточное расписание не наступало бы вовсе.
База живёт только на этом компьютере — облачная копия для неё не
дополнение, а единственная вторая площадка.

После выгрузки программа читает список папки в облаке и сверяет размер.
«Выгружено, но не проверено» — отказ. Сбой облака копию неудачной не
делает, но виден на «Диагностике».

Требования данных маркировки:
1. **Внеочередная копия после получения или импорта кодов.** Коды оплачены
   и уникальны, и до ночи они не должны жить в одном экземпляре. Предел «не
   чаще раза в N минут» её не глушит. Пока копия не в облаке, у заказа видна
   пометка «коды не в копии».
2. **Ключ шифрования — отдельно от копий** (там же, где пароли, не на
   Яндекс.Диске). Без ключа копия даёт только короткие КИ, этикетку по ним
   не напечатать. Копия вместе с ключом — это утечка всех кодов. После
   восстановления программа расшифровывает один код и сверяет его короткую
   часть.
3. **Выпущенные документы хранятся в базе** (XML УПД, файл поставки, ответы
   ЧЗ) и попадают в копию. Этикетки и стикеры не храним: собираются заново.

## 14. Критерии приёмки

- **Связь с sync_admin:**
  - ответ на задание маркировки лежит только в `results\marking\`, у
    sync_admin нет «несопоставленных»;
  - документ поставки датирован текущим моментом, комментарий на `mark`;
  - дельта применяется sync_admin в течение цикла обработки, остаток на
    WB/Ozon/Kit по этим штукам уменьшается;
  - ответы обработки на команды sync_admin не изменились (9.6).
- **Независимость:** код sync_admin не изменён; тест «нет импортов между
  `app/` и `marking/`» зелёный; накат маркировки не трогает `C:\sync_admin`.
- **Поставка:** правка невозможна после перемещения; удалить можно только
  до него; перемещение атомарно (нехватка по одной строке — документа нет).
- **Коды:** один код не попадает в две поставки; в файл и УПД не попадает
  код не «в обороте»; полученные из СУЗ коды не теряются при закрытии
  страницы или сбое; после получения кодов копия в облаке появляется без
  ожидания ночи.
- **Этикетки** декодируются как GS1 DataMatrix побайтно (автотест).
- **Файл поставки** совпадает с эталоном kiz-tool 12550 по сырому XML
  кодов.
- **УПД:** оба комиссионных эталона — байт в байт; первый агентский УПД
  принят Lamoda без ошибок сопоставления.
- **Ввод в оборот:** заказ 1–2 кодов → программа сама дождалась «Нанесён»
  → ввод → `INTRODUCED` в ГИС МТ; время записано в журнал.
- **Несколько ИП:** вход под сертификатом с чужим ИНН отказан; операция
  другого ИП без его токена не идёт.
- **Сеть:** на сервере для программы открыт только SSH на 443; учётная
  запись `marking_sftp` получает SFTP в `C:\sync` и ничего больше — ни
  командной строки, ни проброса портов, ни RDP; программа видна только на
  `127.0.0.1` рабочего компьютера.
- **Тесты** программы зелёные в обоих прогонах (UTC и `TZ=Europe/Moscow`).
