## 0. Что уже есть (входные материалы)

Три готовых инструмента. Модуль **переносит их проверенную логику и знания
на сервер**, а не изобретает заново:

1. **`kiz-tool`** — браузерная страница (один HTML, ~1700 строк JS): подпись
   КриптоПро в браузере → заказ КИЗ в СУЗ → ввод в оборот → проверка статусов
   кодов → файл поставки Lamoda с кодами → этикетки 58×40 GS1 DataMatrix.
   На живом ЧЗ проверены: авторизация (оба токена) ✅, заказ и получение кодов ✅,
   приём документа ввода в оборот сервером ✅. **Не доведено: успешный ввод в
   оборот свежезаказанных кодов** (п. 5.3). Его `docs/API_NOTES.md` и
   `docs/HISTORY.md` (тупики) — обязательная база для серверного клиента ЧЗ.
2. **`upd-constructor`** (Python, 14 тестов против 2 УПД, принятых Купишуз):
   УПД 5.03, функция **ДОП**, из файла поставки Lamoda. Продавец — ИП Яворская
   Т.Н. (НДС 5%), покупатель — ООО «Купишуз». Эталоны — главный критерий
   правильности; правила из его `CLAUDE.md` (цена в xlsx = с НДС, Decimal
   half-up построчно, windows-1251 + CRLF, разные адреса ГрузПолуч/СвПокуп,
   ElementTree, не выдумывать теги) переходят без изменений. Веб-версия
   (React) не переносится.
3. **`lamoda_stickers`** — Excel со стикерами коробов (A4, 2×4, по шаблону).
   Переносится как есть вместе с шаблоном и `verify.py`.

**Что не так в текущем процессе и что даёт модуль:**
- Коды живут в памяти вкладки браузера и в xlsx-файлах. Закрыли вкладку между
  заказом и сохранением файла — оплаченные коды потеряны (в ЧЗ они есть, у нас
  нет). Модуль: **реестр кодов в БД**, каждый код записывается в момент
  получения из СУЗ.
- Нет истории: какие коды в какой поставке, что введено в оборот, какой УПД
  отправлен. Модуль: всё это в БД с журналом.
- Справочник артикул→GTIN — в `localStorage` одного браузера. Модуль: в БД.
- Нужен CORS-прокси, запущенный в отдельном окне. Модуль: запросы к ЧЗ делает
  сервер, прокси не нужен.
- Три инструмента не связаны: файл руками переносится из одного в другой.

## 1. Цель и путь товара

```
Файл поставки Lamoda БЕЗ кодов (из ЛК Lamoda: Seller SKU, кол-во, цена, EAN)
  → GTIN по справочнику (артикул → GTIN; GTIN ≠ EAN)
  → Заказ КИЗ в СУЗ по каждому GTIN → коды в реестр
  → Печать этикеток 58×40 (полный код, GS1 DataMatrix)
  → Ввод в оборот (True API, LP_INTRODUCE_GOODS) → проверка статусов кодов
  → Перемещение в 1С «ЦС Склад» → «Lamoda_Склад» (сразу, одной кнопкой)
  → Файл поставки С кодами (короткий КИ, 31 символ) → загрузка в ЛК Lamoda
  → УПД 5.03 ДОП (XML для Диадока) + стикеры коробов
  → Отчёт о приёмке Lamoda (из того же xlsx) → сверка → коды «отгружен»
```

## 2. Границы

Входит: товарная группа **«Лёгкая промышленность» (`lp`)**; заказ,
получение, печать, ввод в оборот, проверка статусов; поставки Lamoda FBO;
УПД; стикеры коробов; разбор отчёта о приёмке Lamoda.

НЕ входит (первая версия):
- Отправка УПД через ЭДО — файл загружается в Диадок вручную (API Диадока — позже).
- УКД, исправленный УПД — позже, по образцам принятых документов.
- Отчёт о нанесении: для `lp` ручная отправка **запрещена** (ошибка 7710) ✅.
- Агрегация в короба (SSCC), возвраты, перемаркировка, выбытие.
- Обувь и другие товарные группы — **[?]** (закладываем поле группы).

## 3. Принципы безопасности

1. **Ничего не уходит в ЧЗ без действия оператора.** Заказ кодов и ввод в
   оборот — только кнопкой; фоном — только чтение (статусы, получение уже
   заказанных кодов).
2. **Код — уникальный ресурс.** Код хранится один раз (уникальный индекс по
   короткому КИ), один статус, максимум одна поставка. В файл поставки и в УПД
   не попадает код не «в обороте» (по проверке ГИС МТ, не по нашей отметке).
3. **Истина — статус кода в ГИС МТ**, а не «документ принят» ✅ (урок kiz-tool).
4. **Двойной заказ.** Перед заказом показывается, сколько неиспользованных
   кодов по этому GTIN уже есть в реестре; заказ сверх — с подтверждением.
   Идемпотентность: повторное нажатие не создаёт второй заказ.
5. Все действия с внешним эффектом — в `AuditLog`. Выгрузка полных кодов (по
   ним печатаются «легальные» этикетки) — только авторизованным, с записью.
6. Песочница ЧЗ: у организации поле «контур» (`sandbox`/`production`);
   переключение — с подтверждением. **[?]** Есть ли у вас доступ к песочнице;
   если нет — тесты идут на боевом контуре минимальными партиями (1–2 кода).
7. Правило `is_test` из `CLAUDE.md` действует и здесь.

### 4.2 Товар маркировки: GTIN, ТН ВЭД, разрешительный документ
- **GTIN ≠ EAN** ✅. EAN в файлах Lamoda — внутренние `2000…` из 1С. GTIN —
  14 знаков с ведущим нулём, из Национального каталога.
- Справочник «Supplier SKU → GTIN». **Источник — файлы `product_gtin`, которые
  заказчик загружает в Lamoda Seller** (шаблон Lamoda: лист «Лист1» —
  `Supplier SKU`, `Gtin`; лист «Инструкции по заполнению»). История загрузок
  получена — `tests/fixtures/marking/product_gtin/` (10 файлов, 11.06–21.09.2026):
  **1012 пар артикул ↔ GTIN**, строго один к одному, без противоречий; со
  старым справочником kiz-tool (475) пересекаются на 456 без конфликтов —
  вместе **1031 пара**. Артикул — **размерный** (с размером в названии).
- Модуль делает с этим файлом две вещи:
  1. **Импорт** любого количества файлов `product_gtin` (и старого
     `product_gtin.xlsx` kiz-tool) в справочник; конфликт (тот же артикул с
     другим GTIN или наоборот) — не перезаписывается молча, а показывается.
  2. **Выгрузка** `product_gtin` для Lamoda по новым парам (которых Lamoda
     ещё не получала — модуль помнит, какие пары уже выгружены), по правилам
     шаблона: GTIN — ровно 14 цифр, начинается с `046`; **≤ 1000 строк в
     файле** (больше — несколько файлов); лист инструкций сохраняется.
     Правило шаблона «Supplier SKU ≤ 20 символов» Lamoda на деле не
     применяет (974 из 1012 загруженных артикулов длиннее) — не блокируем.
  3. **Условие из шаблона Lamoda** (доступ по субаккаунту для ООО «Купишуз»,
     ИНН 7705935687, к каждому GTIN в Нацкаталоге) — **выполнено навсегда**:
     доступ Lamoda открыт на все карточки, включая новые (ответ заказчика).
     Модуль это не проверяет и не напоминает — лишнее предупреждение на
     каждой выгрузке приучило бы его не читать. `/nk/linked-accounts` нужен
     только для разбора, если Lamoda однажды откажет по доступу.
- Покрытие поставки 12550 этим справочником: **26 из 80 артикулов** (у всех
  26 число кодов в `codes_12550.txt` совпало с количеством) — остальные 54
  артикула в Lamoda ещё не загружались, и 54 GTIN из файла кодов без пары.
  Именно этот случай модуль закрывает ручным сопоставлением (п. 5.2а) с
  последующей выгрузкой `product_gtin` для Lamoda.
- **Первоисточник — карточка Национального каталога** (ответ заказчика):
  оттуда же берутся для каждого GTIN **ТН ВЭД**, **тип, номер и дата
  разрешительного документа** (декларация/сертификат). То есть одна
  карточка НК на размерный артикул даёт всё, что нужно для заказа кодов,
  ввода в оборот и `product_gtin` для Lamoda.
  Как это забирать в модуль:
  1. **Через API НК — основной путь.** API-ключ **есть**, один и для
     контура заказа кодов, и для Национального каталога (ответ заказчика).
     По документации True API (`reference/chz/`, строка ~41443) методы НК
     принимают ЛИБО `apikey` в URL, ЛИБО токен True API в заголовке — не оба
     сразу (иначе 400). Ключ важен тем, что **не требует подписи**: карточки
     НК модуль может читать фоном, без открытой страницы с КриптоПро.
     Нужные методы: `GET /nk/product?gtin=` (карточка: `good_name`,
     `good_attrs` — пары «имя атрибута → значение», категории с ТН ВЭД,
     статус карточки), `POST /api/v4/true-api/product/info` (пачкой по
     GTIN). Имена атрибутов одежды
     (артикул, размер, цвет, ТН ВЭД, разрешительный документ,
     `goodMarkFlag`/`goodTurnFlag`) в документации только на примере
     сметаны — **первый живой ответ по нашему GTIN сохраняется в фикстуры**,
     разбор пишется по нему, а не по догадке. ТН ВЭД короче 10 знаков —
     предупреждение. Ключ хранится зашифрованно (`app/crypto.py`), вводится
     на странице настроек, в чат и в репозиторий не попадает.
  2. **Через выгрузку из ЛК НК** (Excel) — запасной путь, если ключа нет.
     **[?]** Нужен образец такой выгрузки.
  Связь карточки с артикулом Lamoda: **[?]** по какому полю карточки её
  узнать — в карточке есть наименование, размер, цвет, артикул
  производителя; с каким из них совпадает (или из которого собирается)
  Seller SKU `3030 KAHVE 4XL АВЕР Рубашка Д/р сатин`? Пока ответа нет —
  сопоставление подтверждает оператор (модуль предлагает кандидатов по
  совпадению модели, цвета и размера), дальше оно запоминается.
  Разрешительный документ: проверка срока действия (дата окончания) перед
  вводом в оборот; дата публикации хранится как есть.
- Порядок определения GTIN — как в kiz-tool: из кода в файле → по артикулу →
  по EAN в справочнике. **Отличие:** «EAN как GTIN на удачу» в модуле
  **запрещён для заказа** (заказ кодов на чужой/несуществующий GTIN — деньги
  и мусор в ЧЗ); оператор должен указать GTIN явно.
- ТН ВЭД (ровно 10 цифр ✅), вид/номер/даты разрешительного документа
  (декларация `CONFORMITY_DECLARATION` / сертификат `CONFORMITY_CERTIFICATE`) —
  на артикул. Источники: файл «Поставка с КИЗ» из 1С (колонки ТНВЭД / Номер
  разрешительного документа / Дата начала / Дата окончания — уже так делается),
  ручной ввод, позже — API Нацкаталога (нужен ключ **[?]**).
- Проверка срока разрешительного документа перед вводом в оборот.

## 5. Функции

### 5.0 Справочник «Одежда полный» (каталог Lamoda Seller)
Источник штрихкода и цены для поставки (решение заказчика). Образец —
`tests/fixtures/marking/lamoda_catalog_full_2026-09-28.xlsx`: выгрузка
каталога из Lamoda Seller, лист **«Upload Template»**, 801 строка, 91
колонка; строка 1 — служебная (`5637156360`, `full_update`), строка 2 —
описания колонок, **строка 3 — заголовки** вида `Название #код`, данные с
4-й. Колонки находим по **коду после `#`**, а не по позиции и не по
русскому названию (их Lamoda меняет, коды стабильнее).

Что берём (код колонки → назначение):

| Код | Что | Зачем |
|---|---|---|
| `supplier_sku` | размерный артикул поставщика | **ключ** — по нему поставка находит товар |
| `product_identifier` | штрихкод (EAN, `2000…`) | в файл поставки Lamoda; связь с 1С |
| `price` | цена | цена в поставке и в УПД |
| `sku` | Lamoda SKU (`MP002XM0…`) | для сверки с отчётом о приёмке |
| `supplier_parent_sku`, `size_value`, `color_family`, `title` | модель, размер, цвет, название | показ оператору, подписи этикеток |
| `tn_ved` | ТН ВЭД (10 цифр у всех 801) | сверка с карточкой НК перед вводом в оборот |
| `tax_class` | ставка НДС (`5%` у всех) | сверка со ставкой УПД |

`special_price` (цена со скидкой) **не используется**: проверено на поставке
12550 — все 80 строк несут `price` (12000 при `special_price` 6500).

Проверено на образце: все 80 артикулов поставки 12550 найдены, штрихкод
совпал у 80 из 80, цена — у 80 из 80. Размерный артикул в каталоге уникален.
GTIN есть у 556 из 801 артикулов (по файлам `product_gtin`).

Правила загрузки:
- повторная загрузка **обновляет** по `supplier_sku`; модуль показывает, что
  изменилось (новые артикулы, сменившиеся штрихкод/цена);
- артикулы, которых нет в новой выгрузке, **не удаляются** (выгрузка могла
  быть частичной) — помечаются датой последнего появления;
- дубль `supplier_sku` в файле — отказ этих строк с перечнем;
- сравнение артикула — после обрезки краёв, **пробелы внутри значимы**
  (в каталоге встречаются двойные: `C26-2818C Авер Куртка  56 чёрный`);
  если точного совпадения нет, а без учёта двойных пробелов есть —
  подсказка, а не молчаливая подстановка;
- смена штрихкода или цены у артикула из неотгруженной поставки —
  предупреждение на поставке; уже выпущенный УПД не меняется (правка — через
  исправление УПД);
- расхождение ТН ВЭД каталога Lamoda и карточки НК — предупреждение перед
  вводом в оборот (для ЧЗ истина — НК).

### 5.1 Поставка: входящий файл
**Минимально нужны только размерный артикул и количество** (решение
заказчика): штрихкод и цена берутся из справочника «Одежда полный» (п. 5.0)
по размерному артикулу. **Типовой входящий документ** (от заказчика) —
`tests/fixtures/marking/lamoda_shipment_input_typical.xlsx`: тот же шаблон
`fulfilment_shipment` (п. 5.5), заполненный без кодов. Что в нём на самом деле:

| Что | Как во входящем файле | Что делает модуль |
|---|---|---|
| B1 Дата поставки | **пусто** | вводит оператор (обязательно) |
| B2 Номер поставки | **пусто** | модуль предлагает следующий: **последний + 10** (текущий — 12550, следующий 12560); оператор может исправить. Начальное значение и шаг — настройка. Номер не должен повторяться |
| B3 Номер документа отгрузки | **пусто** | «Номер документа», генерирует модуль (п. 5.5) |
| Строки | **одна строка на артикул**, Количество > 1 (80 артикулов, 338 единиц; кол-во 2–5) | разворачивает: **одна строка на единицу**, Количество = 1, свой код в каждой (как в принятой поставке 12100 и в kiz-tool) |
| Seller SKU | размерный артикул с наименованием (`3030 KAHVE 4XL АВЕР Рубашка Д/р сатин`), уникален в файле | ключ справочника GTIN (п. 4.2) |
| Стоимость | в типовом файле есть, но **источник — справочник «Одежда полный»** (п. 5.0, колонка `price`); если в файле цена есть и отличается — предупреждение по строке | в файл Lamoda — как в образцах (текст без копеек); в УПД — число через `Decimal` |
| EAN | в типовом файле есть, но **источник — справочник** (`product_identifier`); расхождение с файлом — предупреждение | связь с 1С (`Barcode`) |
| Вес ЮИ, Data Matrix | пусто | Data Matrix заполняет модуль |

Разбор и проверки при загрузке:
- заголовок — строка 4, шапка — A1:A3 / B1:B3; лист «Инструкции по
  заполнению» не трогаем;
- дубли артикула в файле → предупреждение (строки объединяются по артикулу
  для заказа кодов, но в выходном файле порядок исходных строк сохраняется);
- EAN у всех или ни у кого; цена > 0 (текст парсится как число); кол-во —
  целое > 0; лимиты 5 000 артикулов / 10 000 единиц;
- для каждого артикула — GTIN по справочнику; нет GTIN → строка красная,
  заказ кодов по ней невозможен до указания GTIN;
- если в файле уже есть коды (файл после kiz-tool или частично собранный) —
  коды сверяются с реестром и заносятся в него.

Другие форматы, которые уже встречались ✅ и тоже разбираются: лист
«Поставка» (выгрузка Lamoda после приёмки, заголовок в 3-й строке, колонка

### 5.1а Сверка поставки с остатками 1С (по штрихкоду)
Образец от заказчика — `tests/fixtures/marking/stock_1c_2026-09-28.xlsx`.
Это **выгрузка этой же админки** (страница «Остатки на дату», колонки
`ID_1С, Артикул, Наименование, Размер, Цвет, Баркоды, Остаток` —
`app/routers/stock_on_date.py`). Поэтому модулю файл не нужен: те же данные
уже в БД (`Product.stock_on_hand` + таблица `Barcode`, срез на дату —
`StockDateRow`). Загрузка такого файла остаётся запасным путём.

Правило сопоставления (от заказчика): **строка поставки ↔ товар 1С — по
штрихкоду**: EAN строки файла Lamoda = один из баркодов товара 1С.
- В колонке «Баркоды» бывает несколько через запятую (56 из 1786 строк) —
  совпадение с любым; один баркод у двух товаров — ошибка данных, показать.

  сатин`, в 1С `3030-3032 АВЕР Рубашка Д/р одн Коричневый` — это норма.

Проверка на образце — поставка 12550: **80 из 80 строк найдены по EAN**,
остатка хватает по каждой (нужно 338, на ЦС 1880).

Что показывает модуль по каждой строке поставки: товар 1С (ID, артикул,
наименование, размер, цвет), остаток ЦС, «хватает / не хватает N»,
«EAN не найден в 1С». Отрицательные остатки в 1С бывают (42 строки в
образце) — такая строка считается «не хватает».

заказчика). Штуки поставки физически ещё на ЦС и продолжают транслироваться

**проводит перемещение в 1С «ЦС Склад» → «Lamoda_Склад»**:
- Склад-получатель — **`Lamoda_Склад`** (магазин «Lamoda», код ЦБ0000017, тип

  конфигурации перемещение проводится только между основными складами

  товар со склада.

### 5.2а Импорт кодов из файла (типовой формат)
Коды приходят не только из заказа модулем, но и готовым файлом. Типовой
образец от заказчика — `tests/fixtures/marking/codes_12550.txt` (коды к
поставке 12550, **338 кодов = 338 единиц** типового входящего файла, п. 5.1).

Формат (проверено по файлу побайтно):
- текст ASCII, без BOM, **один полный код на строку, строки через CRLF**;
- код — 85 символов: `01` + GTIN(14) + `21` + серийный(13) + **GS** + `91` +
  ключ(4) + **GS** + `92` + подпись(44); GS = байт `0x1D`, по два на код;
- 80 разных GTIN, коды **сгруппированы по GTIN**, но порядок групп **не
  совпадает** с порядком строк поставки; размеры групп совпадают с
  количествами строк как набор (3, 2, 5, 5 …).

Правила разбора — каждое уже стоило или могло стоить ошибки:
1. **Делить строки только по `\r\n` / `\n`.** Стандартный
   `str.splitlines()` в Python считает GS (`0x1D`) концом строки и режет
   каждый код на три куска (проверено на этом файле: 1014 «строк» вместо 338).
   Тест на это — обязательный.
2. Каждая строка проверяется по шаблону полного кода; короткий КИ (31) —
   первые 31 символ. Дубли внутри файла и коды, уже лежащие в реестре
   (в т.ч. в другой поставке), — отказ с перечнем.
3. **Сопоставление с поставкой — только по GTIN**, не по позиции в файле:
   GTIN кода → артикул по справочнику (п. 4.2) → строка поставки. Число
   кодов на GTIN должно совпасть с количеством по артикулу; иначе —
   расхождение по строке (не хватает / лишние коды).
4. Если справочник не знает GTIN — коды всё равно заносятся в реестр
   («без артикула»), а поставка показывает, каким артикулам не хватает
   GTIN. Сопоставить вручную: оператор выбирает GTIN для артикула из списка
   «коды без артикула» (с количеством — подсказка).
5. Модуль **запоминает** связь артикул ↔ GTIN из каждой успешно собранной
   поставки — справочник пополняется сам.

Что показал образец (риски, которые модуль должен ловить):
- **Справочник kiz-tool устарел:** в `product_gtin.xlsx` нет ни одного из 80
  артикулов поставки 12550. Выход kiz-tool по этой поставке покрывает 12
  артикулов / 44 кода (все 44 совпали с файлом кодов). Для остальных 68
  артикулов связь «артикул → GTIN» взять неоткуда — **[?]** откуда вы её
  берёте для новых артикулов (карточки Нацкаталога, выгрузка «Товары» Lamoda
  Seller, 1С)? От ответа зависит, какой импорт справочника делать.
- **Два префикса GS1 в одной поставке:** GTIN `0462018040…` и
  `0463068831…` — **оба принадлежат ИП Яворской** (подтверждено заказчиком).
  Префикс сам по себе не признак чужого кода. Проверка владельца всё равно
  остаётся: перед выпуском УПД модуль сверяет ИНН владельца каждого кода
  (`/cises/info`) с ИНН продавца — Lamoda принимает в УПД только такие коды.
- kiz-tool писал полный код в xlsx как текст с `_x001d_` вместо GS (длина 97
  вместо 85) — поэтому в файл Lamoda пишем только короткий КИ (п. 5.5).

### 5.5 Файл поставки для Lamoda (шаблон `fulfilment_shipment`)
Официальный шаблон Lamoda Seller получен от заказчика —
`tests/fixtures/marking/lamoda_fulfilment_shipment_template.xlsx`. Модуль
**формирует файл строго по нему** (открывает шаблон и заполняет, а не рисует
свой), лист «Инструкции по заполнению» сохраняется как есть.

Структура листа «Лист1»:

| Ячейка | Поле | Правило Lamoda (из листа инструкций) |
|---|---|---|
| A1 / B1 | Дата поставки | `DD.MM.YYYY`, обязательно; ожидаемая дата, склад может сдвинуть |
| A2 / B2 | Номер поставки | обязательно; ≤ 20 символов: латиница, цифры, `_`, `-` |
| A3 / B3 | Номер документа отгрузки | необязательно; ≤ 20 символов, тот же алфавит; **уникален в рамках всех подтверждённых поставок** |
| строка 4 | заголовки таблицы | `Seller SKU`, `Количество`, `Стоимость`, `EAN`, `Вес ЮИ`, `Data Matrix` |
| A | Seller SKU | обязательно; **размерный** артикул из Lamoda Seller; ≤ 5 000 уникальных в поставке |
| B | Количество | обязательно; > 0; **≤ 10 000 единиц на всю поставку** |
| C | Стоимость | обязательно; > 0, два знака после запятой; «стоимость, которую указываете в УПД» |
| D | EAN | необязательно; ≤ 13 цифр; **если указан хоть у одной строки — нужен у всех** |
| E | Вес ЮИ | только ювелирка — у нас пусто |
| F | Data Matrix | полный код **или** КИ длиной **31 или 38** символов; для маркированного товара обязателен |

Что из этого следует для модуля:
- **Одна строка = один код** (Количество = 1), как в образцах kiz-tool и
  в принятой поставке 12100: код маркировки индивидуален, строк с
  количеством > 1 для маркированного товара быть не может.
- Проверки перед выгрузкой — все правила таблицы выше: формат номера
  поставки и номера документа отгрузки, лимиты 5 000 SKU / 10 000 единиц
  (больше — предложить разбить на несколько поставок), цена > 0, EAN у всех
  или ни у кого, код у каждой строки.
- Data Matrix пишем **коротким КИ (31 символ)** — так в принятой поставке
  12100 ✅; шаблон допускает и полный код, но полный содержит невидимый GS,
  который теряется в Excel (урок kiz-tool). 38 символов — КИ с доп.
  идентификатором `240` + 4 знака ТН ВЭД (так в примере шаблона); у наших кодов
  его нет — **[?]** появится, если коды будут заказываться с этим полем.
- **Стоимость = цена в УПД.** Шаблон прямо говорит «стоимость, которую
  указываете в УПД» — это подтверждает трактовку upd-constructor
  (`price_mode=gross`: в файле цена с НДС = `СтТовУчНал` за единицу), хотя в
  выгрузке принятой поставки колонка подписана «Стоимость (без НДС)».
  Значит **одна цена на строку живёт в поставке, и из неё строятся и файл
  Lamoda, и УПД** — расхождение цены между ними исключено конструктивно.
- **Номер документа** — решение заказчика: у поставки есть поле «Номер
  документа», модуль его генерирует, оператор может исправить. Это **один
  номер для всего комплекта**:
  - ячейка B3 «Номер документа отгрузки» в файле Lamoda;
  - номер УПД (`СвСчФакт/@НомерДок`);
  - имя файла поставки: `<номер документа>.xlsx`;
  - имя файла УПД: `<номер документа>.xml`.
  Генерация: по умолчанию = номер поставки (как сейчас: УПД №12100 к
  поставке 12100), если он проходит правила Lamoda (≤ 20 символов,
  латиница/цифры/`_`/`-`); иначе — следующий свободный номер по истории.
  Проверки: формат по правилам шаблона; **уникальность по всем поставкам и
  УПД в модуле** (Lamoda требует уникальности среди подтверждённых поставок);
  после выпуска УПД номер не меняется (правка — только через исправление УПД).
  Имя файла УПД `<номер документа>.xml` — ✅ Диадок принимает (подтверждено
  заказчиком). Внутри XML `ИдФайл` остаётся по образцу эталонов.
- Коды — только «в обороте» (по ГИС МТ) и не занятые другой поставкой;
  закрепляются за поставкой в момент выгрузки файла.

### 5.7 Смена схемы: комиссия → агентский договор (с 01.10.2026)

Источник: статья Lamoda «Переход на агентскую модель: что меняется для
партнеров FBO с 1 октября 2026» (обновлена 16.09.2026), сохранённая страница
с картинками 7–12 получена от заказчика.

**Суть:** агент продаёт от имени партнёра (продавец для покупателя — ИП
Яворская), товар до продажи — наш. Договор не перезаключается, нумерация
сохраняется, меняются название («агентский договор») и терминология.
Поставка, возвраты, маркировка, статус УПД (статус 2, ДОП) — без изменений.
Товар, переданный по комиссии, не переоформляется. Коды из оборота
выводит Lamoda.

**Правило переключения — по дате документа:** УПД с датой **по 30.09.2026
включительно** — старые правила, **с 01.10.2026** — новые.

**Что проверяет Lamoda (картинка 12):** в УПД/УКД на наличие «комис» (без
учёта регистра, шаблон `комис%`) проверяются поля:

| Тег у Lamoda | Что это в XML 5.03 | У нас сейчас |
|---|---|---|
| `НаимОсн` — наименование документа-основания | `СвПер/ОснПер/@РеквНаимДок` | `Договор комиссии` ❌ |
| `НомОсн` — номер документа-основания | `СвПер/ОснПер/@РеквНомерДок` | `б/н` ✔ |
| `ИныеСвИзмСтоим` — для УКД | — | УКД не делаем |
| `Значен` — дополнительные сведения | `ТекстИнф/@Значен` | в наших УПД `ТекстИнф` нет ✔ |

Плюс по FAQ: **`ВидОпер="ПродажаКомиссия"` и `ВидОпер="Комиссия"` недопустимы**
(у нас сейчас `ПродажаКомиссия` ❌). `СпОбстФДОП=00005` — без изменений.

**Итого, в нашем УПД меняются ровно два атрибута:**

| Атрибут | По 30.09 (эталоны) | С 01.10 |
|---|---|---|
| `СвПер/@ВидОпер` | `ПродажаКомиссия` | **[?]** значение без «комис» — см. ниже |
| `ОснПер/@РеквНаимДок` | `Договор комиссии` | `Агентский договор` |

Всё остальное (`РеквНомерДок=б/н`, `РеквДатаДок`, `СпОбстФДОП=00005`,
функция, коды, суммы, НДС, реквизиты, адреса, `ИдФайл`) — без изменений.

**Что из примеров Lamoda к нам не относится:**
- Картинки 8–10 — УПД других продавцов, сделанные в 1С/СБИС: там «комиссия»
  сидит ещё в номере основания (`РеквНомерДок="Договор комиссии б/н"`), в
  «Иных сведениях» и в `ИнфПолФХЖ3/ТекстИнф` (`Идентиф="ПередачаТовараКомитентом"`).
  Наш генератор этих блоков не пишет — добавлять их не нужно (правило
  upd-constructor: не выдумывать теги; в наших принятых эталонах их нет).
  Строка «ПередачаТовараПринципалом: Истина…» из текста статьи — это как раз
  такой блок 1С, нам не нужен.
- В тексте статьи пример «Станет» содержит «…№Договор комиссии б/н от
  12.02.2026» — это противоречит их же проверке (`НомОсн` не должен содержать
  «комис»); считаем опечаткой статьи и не повторяем.
- `РеквДатаДок`: в примере Lamoda — дата договора; у нас в обоих принятых
  эталонах — дата УПД. Lamoda это поле не проверяет — оставляем как было.

**`ВидОпер` — решено:** `Реализация по агентскому договору` (значение без
«комис», из списка, рекомендованного Lamoda). По документации Диадока (XSD
УПД 5.03 в официальном SDK `diadoc/diadocsdk-csharp`, `Utd970/V050301`)
`ВидОпер` — свободная строка до 255 символов, необязательная, справочника
значений у Диадока нет; «НаимОсн»/«НомОсн» в таблице Lamoda — это
`РеквНаимДок`/`РеквНомерДок` в `ОснПер`. Значение настраиваемое
(`--vid-oper`), подтверждается первым принятым УПД.

**Стикеры коробов — решено:** с поставок от 01.10.2026 «АГЕНТ» вместо
«КОМИССИЯ» и `Получатель: ООО "КУПИШУЗ" Агент` (по дате поставки). Сделано в
`lamoda_stickers` 28.09.2026, вёрстка не менялась (сверено с файлом 12350
ячейка в ячейку), 4 теста.

**Переключение схемы (требование заказчика).** Схема не зашита намертво:
- **По умолчанию — «Авто по дате»:** УПД `≤ 30.09.2026` — комиссия (оба
  эталона байт-в-байт), `≥ 01.10.2026` — агентский договор.
- **Ручной выбор на поставке:** поле «Схема договора» — Авто / Комиссия /
  Агентский договор. Выбранное значение хранится в поставке и в выпущенном
  УПД; одно поле управляет и УПД, и стикерами коробов, и словом «комиссия»
  в любых других документах поставки.
- Если ручной выбор расходится с датой — предупреждение на странице и в
  проверке УПД (не ошибка: переключатель должен работать), запись в журнал
  (кто, когда, какая схема, почему — поле «причина» обязательно).
- Проверка УПД сверяется с **выбранной** схемой: для агентской — нет «комис»
  нигде в документе; для комиссии — `ВидОпер`/основание комиссии.
- **Дата перехода — настройка** (справочник договора), а не константа: если
  Lamoda сдвинет переход или вернёт комиссию, меняется одна дата, а не код.
  Можно завести и обратный переход (агент → комиссия с даты X) — редакции
  договора идут последовательно по датам.
- Исправления (УПД(и)) и возвраты по старой поставке — по схеме исходного
  документа, а не по дате исправления.

Уже сделано вне модуля (28.09.2026): `upd-constructor` — `--scheme
auto|commission|agency`, в веб-версии поле «Схема договора» с
предупреждением; `lamoda_stickers` — `--scheme`.

**Требования к модулю:**
1. Профиль УПД — по схеме поставки (см. «Переключение схемы» выше).
2. Справочник договора с редакциями (наименование основания, `ВидОпер`).
3. Проверка перед выпуском документа агентского периода: ни в одном атрибуте
   и тексте XML нет «комис» (строже Lamoda — по всем полям, не только по четырём).
4. Первый УПД, принятый Lamoda без ошибок сопоставления, — третий эталон с тестом.

**Сделано вне модуля (28.09.2026):** в `upd-constructor` — выбор схемы по
дате УПД, два атрибута, проверка «комис» в `check`, флаги `--scheme` /
`--vid-oper`, 6 новых тестов (всего 20, зелёные); веб-версия пропатчена тем
же правилом и проверена в headless Chromium. При переносе в модуль —
переносится вместе с этими тестами.

## 6. Подпись КЭП

Опыт kiz-tool ✅: подпись работает **в браузере оператора** через КриптоПро
ЭЦП Browser plug-in (CAdES-BES). Детали, стоившие часов отладки:
авторизация — прикреплённая подпись, base64 без переносов, подписывается
base64(UTF-8(data)); запросы СУЗ — откреплённая подпись в `X-Signature`
(POST — тело, GET — путь с query от `/api/v3`); токены: True API — `Bearer`,
СУЗ — `clientToken` через `simpleSignIn/{connectionId}` (10 ч).

КриптоПро с токеном — на отдельной машине, токен постоянно. Отсюда два режима:

1. **Подпись в браузере (основной, первым этапом).** Админка открывается на
   машине с КриптоПро; страница подписывает данные плагином, а запросы к ЧЗ
   отправляет сервер (CORS-прокси не нужен). Каждая операция: сервер готовит
   данные → браузер подписывает → сервер отправляет. Ограничение: всё, что
   требует подписи (включая опрос СУЗ), идёт, **пока страница открыта**.
   **[?]** Плагин должен доверять адресу админки (https-домен в списке
   доверенных сайтов КриптоПро) — проверить на этой машине.
2. **Сервис подписи на машине с КриптоПро (вторым этапом, для работы без
   оператора).** Windows-служба, доступ только через VPN/туннель, HMAC,
   журнал подписей, подписывает только auth-строку ЧЗ, запросы СУЗ и документы
   ввода в оборот; PIN — на той машине. Если недоступен — режим 1.

## 10. Критерии приёмки

- УПД: оба эталона комиссии байт-в-байт; агентский профиль принят Lamoda без
  ошибок сопоставления.
- Один код нельзя поставить в две поставки; в файл/УПД не попадает код не
  «в обороте»; полученные из СУЗ коды не теряются при закрытии страницы или
  сбое на середине.
- Этикетки декодируются как GS1 DataMatrix байт-в-байт (автотест).
- Заказ 1–2 кодов → модуль сам дождался «Нанесён» → ввод в оборот → `INTRODUCED`
  в ГИС МТ; время ожидания зафиксировано в журнале.
- Все тесты зелёные (1923 + новые).
