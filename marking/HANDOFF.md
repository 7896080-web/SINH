## 2. Что программа умеет сейчас (этапы 2–3 ТЗ)

- **Поставки Lamoda:** входящий файл (шаблон `fulfilment_shipment`) →
  штрихкод и цена из «Одежды полной» → проверка остатка в 1С
  (`SUPPLY_CHECK`) → перемещение «ЦС Склад → Lamoda_Склад» одним документом
  (`SUPPLY_MOVEMENT`). Отмены поставки нет; правка — только до перемещения.
- **«Поставки FBO» → УПД** (ядро `upd_constructor/` без изменений), схема
  «комиссия/агентский» по дате УПД, стикеры коробов (`lamoda_stickers/`).
- **«Мэппинг»** — весь каталог Lamoda против справочника баркодов 1С по
  правилам sync_admin (ТЗ 6.2а): статусы, пул штрихкодов, GTIN и НК в одной
  строке, выгрузка отбора в Excel. Справочник — командой `BARCODE_DICT`
  (обработка `mark-2`) или файлом `barcodes_*.txt`.
- **Справочник GTIN** (product_gtin, из «Поставок FBO», вручную) и кэш
  карточек **Нацкаталога** по API-ключу (лимит 7 запросов/5 мин).
- **Этикетки 58×40** DataMatrix из готового файла кодов; `codes_txt.build` —
  коды поставки в txt в формате СУЗ (в интерфейс не выведено — этап 4).
- Организации (ИП), нумерация поставок, копия базы с выгрузкой в облако,
  «Диагностика», `/health`.

**Чего нет — этап 4:** вход в ЧЗ по сертификату (True API и СУЗ), владелец
GTIN по `/product/info`, заказ кодов, опрос статусов, ввод в оборот, файл
поставки с кодами, проверка УПД в ЧЗ. Поля OMS ID и connectionId на странице
организации — заготовка под вход, сейчас не используются.

## 3а. Состояние сервера после правок безопасности 01.10.2026

Сервер `136.243.92.95` разбирали вместе с заказчиком: наружу были открыты общие
папки (445) и удалённое управление Windows (5985) — сеть была помечена
«Частной», и правила Windows по умолчанию пускали к ним всех. Следов чужого
входа в доступной части журналов не найдено. Что сделано (вручную, PowerShell
на сервере — в репозитории этого нет):
- запрещающие правила `BLOCK SMB inbound` (139, 445), `BLOCK NetBIOS inbound`
  (UDP 137–138), `BLOCK WinRM inbound` (5985–5986); тип сети — `Public`;
- удалено правило `FinanceBot settings` (порт 8765 был открыт всем; бот
  заказчика на Python, настройки — только `localhost:8765` на сервере);
- выключено правило IIS «Службы Интернета (входящий трафик HTTPS)» — оно
  держало 443 для всех;
- **443 (`SFTP marking 443`) — только с адреса офиса `178.34.159.213`.**
  Сменится адрес офиса — обмен с 1С встанет («недоступен» на «Диагностике»);
  лечится той же командой с новым адресом (`SFTP_1C.md`, «Что если»);
- **SSH слушает 22 и 443; `AllowUsers marking_sftp Sergey`.** Sergey —
  администратор заказчика, входит по ключу на 22 (автоматически, каждые ~3
  минуты, с `79.117.246.237`). Первая версия `server_sftp_setup.ps1` отрезала
  ему доступ 30.09 (заменила порт и завела AllowUsers) — вернули 01.10, скрипт
  исправлен. Правила OpenSSH на 22 включены, открыты всем (вход только по ключу);
- RDP — порт **50303** (не 3389), NLA включена.

**Не закрыто на 01.10:** блокировка после неверных паролей не включена

## 5. Как работать в Claude Code на этом компьютере

**Два каталога, и путать их нельзя:**
- `C:\marking` — **установленная программа с настоящей базой**. Здесь не
  разрабатывают: не правят файлы, не запускают тесты на её базе, не пишут в
  `marking.db` в обход программы.
- `C:\dev\sinh` — **клон репозитория** для разработки:
  ```powershell
  git clone -b claude/magical-keller-i9x52y https://github.com/7896080-web/sinh C:\dev\sinh
  ```
  Клон целиком, не только `marking/`: тесты модуля 1С читают `../1c/`.

**Разработка** — в `C:\dev\sinh\marking`, свой venv, своя `dev.db`, порт
**8011** (`README.md`, раздел «Разработка»). Без `MARKING_ONEC_SFTP_HOST`
обмен идёт в локальные папки — к серверу 1С разработка не обращается. Для
проверок ЧЗ на этапе 4 — только тестовый контур ЧЗ (`chz_contour`) или
методы, ничего не меняющие (вход, статусы, проверка УПД); заказ кодов и ввод
в оборот на бою — только по согласованию с человеком, это деньги и
необратимые документы.

**Тесты — дважды:**
```powershell
cd C:\dev\sinh\marking
python -m pytest -q                       # на этой машине это пояс Москвы
$env:TZ="UTC0"; python -m pytest -q; Remove-Item Env:TZ   # попытка UTC-прогона
```
Проверь, что UTC-прогон действительно в UTC:
`$env:TZ="UTC0"; python -c "import datetime; print(datetime.datetime.now().astimezone().tzinfo)"`.
Если Windows переменную не понимает — UTC-прогон делается в облачной сессии
(Linux) или в CI; так и скажи в отчёте, а не считай его пройденным.
Правка общего модуля 1С (`1c/…МодульОбъекта.txt` + `1c/src/…/ObjectModule.bsl`)
— гонять и тесты sync_admin: `cd C:\dev\sinh; python -m pytest tests -q`
(ставится по корневому `requirements.txt`, в своём venv).

**Поставить свою правку в `C:\marking`:**
```powershell
robocopy C:\dev\sinh\marking C:\marking /E /XD .venv ssh backups logs tools onec_archive __pycache__ .pytest_cache /XF .env marking.db marking.db-wal marking.db-shm rclone.conf dev.db
powershell -ExecutionPolicy Bypass -File C:\marking\deploy\update_workstation.ps1
```
Никогда `/MIR`: он удалил бы `.env`, базу и ключи. Скрипт обновления сам
останавливает программу, снимает копию базы, ставит зависимости, гоняет
миграции и тесты и запускает программу.

**Коммиты** — в ветку `claude/magical-keller-i9x52y`, пуш туда же; PR не
создавать без просьбы. Без идентификаторов модели в сообщениях.

**Нельзя никогда** (подробнее — `deploy/РАБОЧИЙ_КОМПЬЮТЕР_CLAUDE.md`):
выводить или пересылать закрытые ключи (`ssh\id_ed25519`, ключи

## 6. Дальше — этап 4, и почему его удобно делать здесь

Здесь то, чего нет в облачной сессии: плагин КриптоПро, сертификаты и сеть,
из которой ЧЗ отвечает. Порядок (ТЗ, разд. 7 и 10, этапы — разд. 13):

0. **Проверка плагина** со страницы программы (`/diagnostics/plugin-check`):
   видны ли сертификаты с ИНН, проходит ли пробная подпись. Не проходит с
   `127.0.0.1` — сначала решить это (ТЗ 10.2), потом писать вход.
1. **Вход в ЧЗ по ИП** (ТЗ 10.3–10.4): выбор организации → сертификаты этой
   машины с ИНН и сроком; ИНН сертификата обязан совпасть с ИНН организации;
   `auth/key` → страница подписывает (прикреплённая CAdES-BES, base64 без
   переносов, подписывается base64(UTF-8(data))) → токен True API; `clientToken`
   СУЗ по `connectionId`. Токены — зашифрованно, **раздельно по
   организациям**, со сроком (~10 ч); операция берёт токен организации своей
   записи. В ЧЗ запросы шлёт ПРОГРАММА (Python), браузер только подписывает —
   CORS-прокси kiz-tool не нужен.
2. **Владелец GTIN и готовность карточки** — `/product/info` (ИНН,
   `permittedInns`, `goodMarkFlag`/`goodTurnFlag`).
3. **Заказ и получение кодов в СУЗ** (ТЗ 7.1): тело как в kiz-tool; каждый
   запрос СУЗ — с откреплённой подписью в `X-Signature`; заказ пишется в базу
   до отправки, коды — порциями, сразу за поставкой, внеочередная копия.
   Коды — зашифрованно (полный код), короткий КИ — открыто.
4. **Опрос статусов и ввод в оборот при готовности** (ТЗ 7.2):
   `LP_INTRODUCE_GOODS`, короткий КИ, прикреплённая подпись; ошибка 14 у
   свежих кодов — норма, только опрос до «Нанесён»; ограничитель на ИНН в базе.
5. **Файл поставки с кодами** для Lamoda (ТЗ 6.3; эталон записи —
   `tests/fixtures/reference_kiz_tool_supply_12550.xlsx`) и кнопка «Коды
   поставки (.txt)» (`codes_txt.build`, эталон `tests/fixtures/codes_12550.txt`).
6. **Проверка УПД в ЧЗ** — `/doc/validator/create`.

**Материалы:**
- `../reference/chz/true_api_v734_2026-09-28.txt.gz` — офлайн-копия
  документации True API (номера строк нужных разделов — в её README).
- `../reference/kiz-tool/cors_proxy.py` — только прокси; **самой страницы
  kiz-tool (рабочий код подписи и заказа) в репозитории нет** — попроси её у
  человека: она лежит у него, и по ней заказывали коды с этой машины.
- Фикстуры `tests/fixtures/` — реальные данные поставки 12550.
- Сырые ответы ЧЗ при первом живом прогоне — в фикстуры, с маскировкой.
