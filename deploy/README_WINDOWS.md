# Развёртывание на Windows Server (локальный вариант)

Целевой сервер — Windows Server `136.243.92.95` (WIN-Q0QVP2SM59L), где уже
работает 1С. Приложение и планировщик крутятся здесь же, обмен с 1С — через
локальную папку `C:\sync` (без FTP).

## Предпосылки (поставить заранее)

| Компонент | Зачем | Обязателен |
|---|---|---|
| **Python 3.11–3.14** | сам runtime (при установке — галочка «Add to PATH») | да |
| **PostgreSQL для Windows** | боевая БД (веб + планировщик — два процесса) | рекомендуется |
| **NSSM** (`nssm.exe` в PATH) | запуск веба и планировщика как служб Windows | для автозапуска |

Без PostgreSQL скрипт откатится на SQLite-файл — для небольшого объёма приемлемо,
но при активной одновременной записи двух процессов PostgreSQL надёжнее.
Без NSSM всё установится, но службы придётся поднять вручную (скрипт покажет как).

## Запуск

PowerShell **от имени администратора**:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\install_windows.ps1
```

Параметры (необязательно): `-SyncRoot C:\sync` (папка обмена), `-WebPort 8000`.

## Что делает скрипт

1. Проверяет Python 3.11+.
2. Создаёт `.venv` и ставит зависимости.
3. Создаёт `C:\sync\{tasks,results,archive}`.
4. Генерирует `.env` (если его ещё нет): `SESSION_SECRET`, `SECRETS_ENCRYPTION_KEY`
   (Fernet), `DATABASE_URL`, `SYNC_DIR_*`. Секреты в консоль не выводятся.
5. Создаёт роль/БД PostgreSQL (если доступен `psql` и введён пароль postgres).
6. Прогоняет миграции `alembic upgrade head`.
7. Создаёт пользователя `admin` со случайным паролем (**показывается один раз**),
   если пользователей ещё нет.
8. Регистрирует и запускает службы `sync_admin_web` (uvicorn) и
   `sync_admin_worker` (планировщик) через NSSM.

Скрипт идемпотентен: существующий `.env` и пользователь-админ не пересоздаются.

## После установки

- Веб-админка: `http://127.0.0.1:8000/login` (логин/пароль из вывода скрипта).
- Здоровье воркеров: `http://127.0.0.1:8000/health`.
- Логи служб: `logs\<имя службы>.log` (stdout) и `logs\<имя службы>.err.log` (stderr).
  Имена задаются при установке, и на сервере, развёрнутом не этим скриптом, они
  другие — на боевом это `logs\web.err.log` и `logs\worker.err.log`. Точный путь
  всегда можно спросить у самой службы: `nssm get sync_admin_worker AppStderr`.
  Всё содержательное (Python logging) идёт в **err**-файл; `.log` обычно пустой.
- Время в логе — **местное**, со смещением в конце (`16:00:20,561+0300`), а в базе
  и на страницах админки — UTC. Не сопоставляйте их напрямую: три часа разницы
  один раз уже дали ложный вывод «1С обработала задание дважды».
- Лог пишется в **UTF-8** (воркер задаёт кодировку сам, независимо от локали
  системы). Под Windows PowerShell читать его нужно с явным указанием кодировки,
  иначе кириллица превратится в мусор и не найдётся поиском:
  `Select-String -Path ... -Encoding UTF8`, `Get-Content ... -Encoding UTF8`.
  **Строки, записанные до 18.09.2026, лежат в cp1251** — Python до этой правки
  кодировал stderr по локали. В одном файле поэтому могут соседствовать обе
  кодировки: старый хвост читается без `-Encoding` (или с `-Encoding Default`),
  новый — только с `-Encoding UTF8`. Проще всего не смешивать: после обновления
  увести старый файл в архив (`Rename-Item logs\worker.err.log worker.err.cp1251.log`)
  — NSSM заведёт новый.

Дальнейшие шаги в самой админке:
1. Ввести API-ключи площадок (страница «API-ключи»).
2. Заполнить `WAREHOUSE_ID_WB/OZON/KIT` в `.env` (ID склада продавца на площадке),
   перезапустить службу `sync_admin_worker`.
3. Убедиться, что 1С-обработка `ОбменССайтом.epf` смотрит в те же
   `C:\sync\{tasks,results,archive}` и стоит на расписании.

## Управление службами

```powershell
nssm restart sync_admin_worker      # перечитать .env после правок
nssm stop sync_admin_web
nssm status sync_admin_worker
Get-Content (nssm get sync_admin_worker AppStderr) -Tail 50
```

Размер и время файла в `Get-ChildItem` у работающей службы **отстают**: пока NSSM
держит файл открытым, Windows обновляет эти поля лениво. Судить о том, пишется ли
лог, по ним нельзя — читайте хвост самого файла.

### Ротация лога

NSSM по умолчанию пишет в один файл без ограничения размера — за месяцы это
десятки мегабайт, и открыть их в редакторе уже нечем. Включается так (раз и
навсегда, служба переживает обновления):

```powershell
nssm set sync_admin_worker AppRotateFiles 1
nssm set sync_admin_worker AppRotateOnline 1
nssm set sync_admin_worker AppRotateBytes 10485760   # 10 МБ
nssm set sync_admin_web    AppRotateFiles 1
nssm set sync_admin_web    AppRotateOnline 1
nssm set sync_admin_web    AppRotateBytes 10485760
nssm restart sync_admin_worker
nssm restart sync_admin_web
```

## Уведомления: чтобы система позвала сама

**Пока это не настроено, система не позовёт никого.** `/health`, «Диагностика» и
часовой отчёт умеют рассказать про себя всё — но только тому, кто пришёл и
открыл страницу. Упади обе службы ночью, узнать об этом можно будет утром от
оператора.

**Настраивается на странице «Уведомления»** в самом приложении — там же
подсказки по каждому полю. Достаточно одного канала, можно оба: тогда сообщение
уйдёт по обоим.

Правка со страницы действует СРАЗУ, без перезапуска службы, и токен ложится в
базу зашифрованным. Значения в `.env` (ниже) по-прежнему работают как запасной
вариант: их читают, пока соответствующее поле на странице не заполнено, — но
правка файла подействует только после `nssm restart sync_admin_worker`, потому
что `.env` читается один раз, на старте процесса.

**Telegram** (проще и доходит быстрее):

```
TELEGRAM_BOT_TOKEN=123456:AA...
TELEGRAM_CHAT_ID=-1001234567890
```

Токен даёт `@BotFather` (`/newbot`). `chat_id` — это адресат: напишите боту
что-нибудь и откройте `https://api.telegram.org/bot<ТОКЕН>/getUpdates`, нужное
число лежит в `message.chat.id`. Для группы сначала добавьте бота в неё; id
группы отрицательный.

**Почта:**

```
ALERT_SMTP_HOST=smtp.yandex.ru
ALERT_SMTP_PORT=465
ALERT_SMTP_USER=robot@example.ru
ALERT_SMTP_PASSWORD=пароль-приложения
ALERT_EMAIL_TO=ruslan@example.ru
```

Порт 465 — SSL, 587 — STARTTLS; другое значение тоже работает, шифрование можно
снять `ALERT_SMTP_TLS=0`. Пароль нужен **отдельный для приложения**, а не от
почтового ящика — обычный почти везде отклоняется.

Необязательное:

```
ALERT_REPEAT_HOURS=6          # как часто напоминать о той же поломке
ALERT_BASE_URL=http://127.0.0.1:8000   # адрес для ссылки в сообщении
```

После настройки **обязательно нажмите «Отправить пробное уведомление»** на
«Диагностике» (если правили `.env`, а не страницу, — сначала
`nssm restart sync_admin_worker`). Канал, который не
проверили, — это надежда, а не канал: опечатка в токене выглядит ровно так же,
как исправная тишина, и обнаружилась бы в худший из возможных часов. Ровно то
же уже проходили с бэкапом, который снимался, но никогда не проверялся чтением.

### Сторож: кто позовёт, если ляжет сам воркер

Всё описанное выше живёт **внутри воркера**. Умер воркер — умерли и
уведомления, и самый важный случай («ночью обе службы легли») остаётся
непокрытым. Изнутри это не решается никак: процесс, которого нет, не может
сообщить, что его нет.

Поэтому полярность обратная — воркер раз в пять минут говорит наружу «я жив», а
о молчании пишет человеку внешний сервис. Поле «Пинг внешнего сторожа» на
странице «Уведомления», оно же переменной окружения:

```
ALERT_HEARTBEAT_URL=https://hc-ping.com/ваш-уникальный-ключ
```

Подойдёт любой, кто умеет ждать пинг по адресу: **healthchecks.io** (бесплатно,
достаточно завести проверку и скопировать её адрес), Better Stack, push-монитор
Uptime Kuma. Конкретный сервис в коде не зашит — только адрес.

Поставьте у проверки период 5 минут и запас (grace) 15: два пропущенных пинга
подряд означают, что воркер встал, один — что не доехал запрос.

Это **не замена** уведомлениям и не дублирует их: сторож отвечает ровно на один
вопрос, «жив ли воркер», и дёргается на каждом прогоне независимо от того, всё
ли в порядке внутри. О беде внутри живой системы пишут каналы выше.

**О чём напишет.** Только о двух вещах, и обе означают «деньги идут не туда
прямо сейчас»: задание не работает (`/health` не зелёный) и критичная находка
отчёта. Жёлтые находки — отрицательные остатки, расхождения со складом,
несопоставленные карточки — **не будят никогда**: их в исправной системе бывает
несколько штук постоянно, и, разбудив на жёлтом один раз, мы научим не читать и
красное.

Тихих часов нет намеренно. Оверселл — это реальный товар, проданный дважды; до
утра он не подождёт. Одно и то же сообщение не повторяется, пока картина не
изменилась, и ещё раз приходит по таймеру, чтобы висящая поломка не забылась.
Когда всё пройдёт — придёт отбой, ровно один раз.

## Доступ снаружи (если нужен)

По умолчанию веб слушает `127.0.0.1` — только локально. Чтобы открыть админку
из сети, поставьте перед приложением обратный прокси с HTTPS (IIS ARR или Nginx),
проксируйте на `127.0.0.1:8000` и выставьте в `.env` `SESSION_COOKIE_SECURE=1`.
Публиковать голый HTTP-порт наружу не нужно.

## Обновление кода

**На боевом сервере git не установлен** (проверено 17.09.2026: `git` не
распознаётся как команда). Значит `git pull` там неприменим — файлы приносятся
копированием или блоком наката, который сверяет sha256 каждого файла до записи.

Файлы на диске заменены — дальше **одна команда**:

```powershell
powershell -ExecutionPolicy Bypass -File C:\sync_admin\deploy\update_windows.ps1
```

Она делает по порядку: зависимости → **копия базы** → миграции → `pytest -q` →
перезапуск обеих служб → ожидание `/health` до устойчивого 200 (до 150 секунд).
Любой шаг не прошёл — останавливается и говорит, в каком состоянии остался бой.

Раньше здесь стояла ручная последовательность из пяти команд, и она вела мимо
скрипта: ни копии перед миграцией, ни тестов, ни проверки `/health`. Миграция на
живых службах без свежей копии — это как раз тот случай, когда восстановление
из бэкапа становится единственным выходом, а alembic на SQLite оборванную
миграцию не откатывает.

Ручная последовательность оставлена **как аварийная**, на случай, когда скрипт
неприменим. Копию снять ОБЯЗАТЕЛЬНО первой строкой:

```powershell
.\.venv\Scripts\python.exe .\scripts\backup_db.py     # без неё не начинать
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m pytest -q                 # красные тесты — не перезапускать
nssm restart sync_admin_web
nssm restart sync_admin_worker
# и потом две минуты смотреть http://127.0.0.1:8000/health
```

## Копии базы: где лежат и что нужно для восстановления

Копия снимается сама, раз в сутки, заданием `backup`, и лежит в
`C:\sync_admin\backups` — **на том же диске, что и сама база**. Путь меняется
переменной `BACKUP_DIR` в `.env`, и если есть сетевая папка или второй диск,
указать их стоит: отказ единственного диска сегодня уносит и базу, и все копии
разом.

Снять копию руками (например, перед рискованной операцией):

```powershell
.\.venv\Scripts\python.exe .\scripts\backup_db.py
```

`update_windows.ps1` делает это сам перед миграциями.

**В копию НЕ входит ключ шифрования.** Токены площадок лежат в базе
зашифрованными, а ключ — в `SECRETS_ENCRYPTION_KEY` в файле `.env`. Копия базы
без этого ключа восстановит всё, кроме доступов к площадкам: их придётся
вводить заново. Поэтому `.env` нужно хранить отдельно от копий базы и
отдельно от этой машины — в том месте, где у вас хранятся пароли.

Хранение: по одной копии на каждый из последних 14 дней плюс по одной на
неделю за два месяца. Файл с непонятным именем в этом каталоге не удаляется
никогда — если вы положили туда копию руками, она останется. Файл с
расширением `.db.bad` — это НЕ копия: так помечается сорвавшаяся попытка,
чтобы её не приняли за целую.

### Вторая площадка: копии на Яндекс.Диске

Копии лежат на том же диске, что и база. Отказ этого диска унесёт разом и её, и
все копии — ровно то, от чего бэкап должен был защитить. Лечится одним полем:
**«Папка зеркала»** на странице «Уведомления», раздел «Зеркало резервных копий».
Правка действует сразу, перезапускать службу не надо.

Папку синхронизации облака задавайте **вне профиля пользователя** (например
`C:\YandexDisk\sync_admin_backups`): файл туда пишет служба, а она работает под
своей учётной записью и путь вида `C:\Users\<кто-то>\...` может не увидеть.

Та же настройка переменной окружения (запасной вариант; действует только после
`nssm restart sync_admin_worker`):

```
BACKUP_MIRROR_DIR=C:\YandexDisk\sync_admin_backups
```

`BACKUP_DIR` менять под облако НЕЛЬЗЯ — копия снимается туда первой, SQLite
пишет в целевой файл на месте, рядом появляются `-wal` и `-shm`, а клиент
синхронизации держит их открытыми и мешает уборке. В облако уезжает только
готовая и уже проверенная копия, отдельным шагом.

Проверить сразу, не дожидаясь ночи:

```powershell
.\.venv\Scripts\python.exe .\scripts\backup_db.py
```

В конце он напишет либо `зеркало: <путь>`, либо `ВНИМАНИЕ: копия не доехала` с
причиной. Если папку видно в приложении Яндекс.Диска — файл начнёт заливаться
через несколько секунд.

**Проверять надо в облаке, а не в папке.** Клиенту синхронизации нужна живая
сессия пользователя, а службы работают без неё: выйдете из RDP через «Завершить
сеанс» — клиент остановится, файлы будут копиться в папке и никуда не поедут.
Наша сторона при этом отрапортует успехом честно: мы кладём файл в папку, а
доехал ли он в облако, отсюда не видно. Выходите закрытием окна RDP (сеанс
остаётся) и загляните на `disk.yandex.ru` через сутки.

**Почему именно отдельная папка, а не `BACKUP_DIR` прямо в облако.** Копия
снимается штатным механизмом SQLite **сразу в целевой файл**: клиент
синхронизации увидел бы его растущим и залил недописанную базу, а рядом успели
бы мелькнуть `-wal`/`-shm`. Плюс клиент держит файлы открытыми и мешает уборке
старых копий. Поэтому порядок такой: снять локально → **проверить чтением** →
положить в зеркало целиком, через временное имя `.part` с переименованием.
Под финальным именем файл появляется уже полным.

**Сбой зеркала не делает бэкап неудачным** — локальная копия снята и прочитана,
и поднимать тревогу из-за недоступной сетевой папки незачем. Но и молчать
нельзя: об этом скажет строка «с оговоркой» у задания `backup` на «Диагностике»
и находка отчёта «Копия базы не уходит на вторую площадку».

**Сколько места.** Копия около 136 МБ, в зеркале держим 30 ежедневных и 12
недельных — порядка 5–6 ГБ и растёт вместе с базой. Глубина меняется полями
«Хранить ежедневных» и «Хранить недельных» на той же странице (или переменными
`BACKUP_MIRROR_KEEP_DAILY` и `BACKUP_MIRROR_KEEP_WEEKLY`).

### Если папку-зеркало взять негде: rclone

Так и вышло на боевом сервере (Hetzner, Windows Server 2016, рабочая группа):
второго диска нет, соседней машины в сети нет, а клиент Яндекс.Диска на
серверную Windows **не ставится в принципе** — он проверяет редакцию и
отказывается, сколько ни обновляй систему.

rclone закрывает этот случай: один исполняемый файл, устанавливать нечего,
живая сессия пользователя не нужна. И главное — **после выгрузки у облака можно
спросить, доехала ли копия**. У папки синхронизации этого нет принципиально: там
видно только, что файл положен в папку, а отсутствие второй площадки выглядит
ровно так же, как её наличие.

**1. Положить rclone на сервер.** Скачать zip с `rclone.org/downloads`
(windows-amd64), распаковать `rclone.exe` в `C:\sync_admin\tools\`.

**2. Настроить доступ к облаку — один раз, в консоли:**

```powershell
C:\sync_admin\tools\rclone.exe --config C:\sync_admin\rclone.conf config
```

Дальше диалогом: `n` (новый) → имя `yandex` → из списка выбрать **Yandex Disk** →
`client_id` и `client_secret` оставить пустыми → `y` на автоматическую
авторизацию → откроется браузер, подтвердить доступ.

`--config` здесь **обязателен, и это не формальность**: без него rclone пишет
конфиг в профиль того, кто его запустил (обычно администратора), а служба
работает под своей учётной записью и этого файла не увидит. Человек настроил,
проверил руками, всё сошлось — а суточная выгрузка молчит. Тот же класс отказа,
что и «клиенту нужна живая сессия».

**3. Проверить, что облако отвечает:**

```powershell
C:\sync_admin\tools\rclone.exe --config C:\sync_admin\rclone.conf mkdir yandex:sync_admin_backups
C:\sync_admin\tools\rclone.exe --config C:\sync_admin\rclone.conf lsd yandex:
```

**4. Вписать на странице «Уведомления»**, раздел «Копии в облако (rclone)»:

| Поле | Значение |
|------|----------|
| Путь в облаке | `yandex:sync_admin_backups` |
| Файл rclone.exe | `C:\sync_admin\tools\rclone.exe` |
| Файл конфигурации rclone | `C:\sync_admin\rclone.conf` |

Перезапускать службу не надо.

**5. Проверить целиком:**

```powershell
.\.venv\Scripts\python.exe .\scripts\backup_db.py
```

Копия уедет в облако, и приложение **само прочитает список удалённой папки и
сверит размер**. Не сошлось — скажет прямо, а не зелёным «готово». Заодно
загляните на `disk.yandex.ru`.

**Токен у нас не хранится.** Его выдаёт `rclone config` в диалоге с человеком,
rclone же его и обновляет; в базе лежат только путь и два имени файлов. Зато
`rclone.conf` теперь сам по себе доступ к вашему облаку — **в облако его класть
нельзя**, как и `.env`.

**Уборка в облаке** идёт тем же правилом, что и локальная (30 ежедневных + 12
недельных), и файл с неразборчивым именем не трогает никогда: в облаке, как и в
каталоге, может лежать копия, положенная руками.

Сбой облака бэкап неудачным **не делает** — локальная копия снята и прочитана, —
но и молчанием не покрывается: текст попадёт в строку «с оговоркой» у задания
`backup` на «Диагностике» и в находку отчёта.

**Ключ шифрования туда класть НЕЛЬЗЯ.** Токены площадок лежат в базе
зашифрованными, а ключ — в `SECRETS_ENCRYPTION_KEY` в `.env`. Пока `.env` не в
том же облаке, утечка копии не даёт доступа к кабинетам; положите рядом — и
одна утечка даст всё. Храните `.env` там, где у вас пароли.

**Зеркало — вторая площадка, а не глубина хранения.** Оно защищает от отказа
диска и шифровальщика, но не от «удалили месяц назад и не заметили»: уборка в
зеркале идёт по своему сроку, и старые копии оттуда тоже уходят.

### Восстановление

```powershell
nssm stop sync_admin_web
nssm stop sync_admin_worker
.\.venv\Scripts\python.exe .\scripts\restore_db.py C:\sync_admin\backups\sync_admin-ГГГГММДД-ЧЧММСС.db
nssm start sync_admin_worker
nssm start sync_admin_web
```

**Не заменяйте файл базы копированием.** Здесь раньше стояло ровно это —
`Copy-Item` копии поверх `sync_admin.db`, — и оно НЕ ВОССТАНАВЛИВАЕТ НИЧЕГО,
причём молча. База живёт в режиме WAL, и NSSM при жёсткой остановке оставляет
рядом `sync_admin.db-wal` и `-shm` со страницами ПРЕЖНЕЙ базы. SQLite при первом
открытии считает их своим журналом и накатывает поверх подложенной копии.
Отказа при этом нет: `integrity_check` отвечает `ok`, размер правдоподобный,
приложение поднимается — а данные остались старые, и человек уверен, что
откатился.

`restore_db.py` делает то, чего не хватало: проверяет, что службы действительно
остановлены; снимает текущую базу штатным механизмом SQLite (файловая копия при
живом WAL даёт неконсистентный снимок); уносит текущую базу **вместе со
спутниками** под `.before-restore`; кладёт копию, сводит её к одному файлу и
проверяет чтением товаров, а не только структуры. Скрипт ничего не запускает и
не останавливает сам — службы поднимаете вы.

Текущая база отложена, а не удалена: в ней заказы, принятые после копии, и их
придётся сверять с площадками руками.
