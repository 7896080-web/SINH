# MAX Bot API

Сверено 18.10.2026 по https://dev.max.ru/docs-api, OpenAPI-схеме https://github.com/max-messenger/api-schema
и официальному SDK https://github.com/max-messenger/max-bot-api-client-ts. API молодой и меняется: перед правкой
клиента открой https://dev.max.ru/docs-api/changelog-api и проверь, не было ли изменений после этой даты.

## Обязательные факты

| Что | Как правильно | Ошибка, которую уже делали |
|---|---|---|
| Адрес | `https://platform-api2.max.ru` (с 19.07.2026) | `platform-api.max.ru` — устарел (в SDK помечен `@deprecated`) |
| TLS | сертификат цепочки Минцифры (Russian Trusted Root CA) должен быть в доверенных: `httpx.Client(verify=ssl_ctx)`, где в `ssl_ctx` загружен корневой сертификат | `httpx` по умолчанию берёт только `certifi` → `ConnectError` |
| Токен | заголовок `Authorization: <token>`, без `Bearer` | `?access_token=` — **больше не поддерживается** |
| Отправка | `POST /messages?user_id=<id>` (личный диалог) или `?chat_id=<id>`; тело `{"text": ≤4000 символов, "format": "markdown" \| "html", "notify": true, "attachments": [...]}`; ответ `{"message": {...}}` | — |
| Кнопки | `attachments: [{"type": "inline_keyboard", "payload": {"buttons": [[{...}]]}}]` | — |
| События (опрос) | `GET /updates?marker=&timeout=0..90&limit=1..1000&types=a,b` → `{"updates": [...], "marker": N}` | HTTP-таймаут клиента должен быть больше `timeout` опроса |
| Типы событий | `bot_started`, `bot_stopped`, `message_created`, `message_callback` и др. | без `bot_stopped` бот не знает, что продавец его остановил |
| Ошибки | коды 400/401/403/404/405/429/500/503, тело `{"code": "...", "message": "..."}`; 403 `chat.denied` — пользователь остановил бота | все ошибки одинаковы для кода — нельзя отличить «нет доступа» от сбоя |
| Лимиты | ≤ 2 сообщений в секунду в один диалог, ≤ 30 запросов в секунду на бота | — |

### Поля событий

```text
bot_started:     {update_type, timestamp, chat_id, user: {user_id, first_name, ...}, payload, user_locale}
                 payload — то, что после ?start= в ссылке https://max.ru/<бот>?start=<payload> (до 128 символов)
message_created: {update_type, timestamp, message: {sender: {user_id, is_bot, ...} | null,
                  recipient: {chat_id, chat_type, user_id}, body: {mid, seq, text, attachments, markup}}}
```
Отвечать только на `recipient.chat_type == "dialog"`, пропускать `sender.is_bot`, учитывать `sender: null`.

## Опрос или вебхук

Документация прямо говорит: long polling «не подходит для production», для боевой работы — только вебхук.
Одновременно они не работают: при активной подписке `/updates` молчит.

Вебхук (`POST /subscriptions`): только HTTPS на порту 443, сертификат доверенного центра или Минцифры, секрет в
заголовке `X-Max-Bot-Api-Secret` (5–256 символов `A-Za-z0-9_-`), ответ 200 за 30 секунд; недоставленные события
повторяются до 8 часов, потом бота отписывают.

Для awer-sales-bot это решение владельца, а не правка «на месте»:
* бот стоит на Windows-компьютере в магазине, публичного HTTPS-адреса у него нет;
* входящие нужны только для привязки по коду и команд `/plan`, `/svodka`; рассылка — исходящая, ей вебхук не нужен;
* варианты: оставить опрос (риск: ограничения по скорости и сроку хранения событий), поднять вебхук через
  публичный адрес/туннель, или привязку делать без бота (user_id вводит админ).

Перед стартом опроса проверь `GET /subscriptions`: если там есть подписка — опрос ничего не получит.

## Правила площадки (до первой рассылки)

* Бота создаёт только резидент РФ — юрлицо, ИП или самозанятый — на https://business.max.ru после верификации
  (Госуслуги, T-Business ID или Alfa ID); модерация до 48 рабочих часов, токен — после неё; имя бота `id<ИНН>_bot`.
* https://dev.max.ru/docs/legal/requirements п. 1.5 запрещает через API «Сервисные сообщения» и массовые
  рассылки без договора с MAX. Ежедневные сообщения сотрудникам, которые сами запустили бота, скорее всего не
  массовая рассылка, но **вопрос к владельцу**: прочитать https://dev.max.ru/docs/legal/rules до запуска.

## Два бота проекта

«План» (`MAX_BOT_TOKEN`, `bot.handle`) и «Обучение» (`MAX_TRAINING_BOT_TOKEN`, `bot.handle_training`) — один процесс, два опроса событий (`max_marker`, `max_marker_training`). Какие виды сообщений идут во второй бот — `jobs.Sender.TRAINING_KINDS`. Пользователь второго бота — `sellers.training_user_id` (не считаем, что user_id в двух ботах совпадает). Кнопка «Подключить обучение» — `type: link` на `max_training.bot_link?start=<код>`.

## Как работать с кодом проекта

* Клиент — `src/awer_sales_bot/max_api.py`, разбор событий — `bot.py::_extract`, отправка с журналом —
  `jobs.Sender` (таблица `message_log`, повтор за тот же день блокируется).
* Не повторяй `POST /messages` при 5xx вслепую — запрос не идемпотентный, продавец получит дубль. Повторять
  можно сетевые ошибки до отправки и 429.
* 401 — токен отозван: не крутить вечный цикл, а сообщить владельцу и остановиться.
* 403 `chat.denied` — пометить продавца «бот остановлен», не считать это сбоем. Другой 403 — сбой (`MaxError`).
* Проверки без отправки: `awer-bot daily --dry-run --force` (печатает тексты). Живые сообщения реальным
  продавцам не слать для теста — только на свой user_id из `max.owners`.
* Токен только в `.env` (`MAX_BOT_TOKEN`), в логи и `message_log` не писать.

## Первый живой запуск — чеклист

1. Токен в `.env`, адрес `platform-api2.max.ru`, сертификат Минцифры подключён.
2. `GET /me` отвечает данными бота (`awer-bot check-max`; в службе — строка `MAX bot: {...}` в журнале). Второй
   экземпляр (`awer-bot bot` при работающей службе) не стартует: замок `*.db.bot.lock`.
3. `GET /subscriptions` пуст (если остаётся опрос).
4. Свой user_id: написать боту, взять `user_id` из события; записать в `max.owners`.
5. Отправить себе тестовое сообщение с `**жирным**` — проверить, что markdown отрисован.
6. Привязать одного продавца по коду, проверить `bot_started` с `payload`.
7. Только потом — рассылка всем.
